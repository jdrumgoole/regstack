## 🟠 WARNING (Address within 1 week)

### W-1 — Admin delete does not cascade `oauth_identities` (orphan rows + OAuth lockout)

**File:** `src/regstack/routers/admin.py` — `delete_user` endpoint  
**Section:** §3 Authentication & Authorization Audit

The `DELETE /admin/users/{user_id}` endpoint deletes the user record, their pending
registration row, and their lockout failures, but it **never calls
`rs.oauth_identities.delete_by_user_id(user.id)`**.

By contrast, the user-initiated `DELETE /account` path in `account.py` correctly
cascades the identity rows before deleting the user.

**Impact of the orphan row:** When `_resolve_user` in `oauth.py` receives a sign-in
for the same Google identity later, it finds the orphan `oauth_identities` row,
attempts `get_by_id(identity.user_id)`, gets `None` (deleted user), and raises
`_LinkConflictError("user_inactive")`. The redirect becomes
`/login?error=user_inactive`. This **permanently blocks** the Google identity from
being linked to any new regstack account — the orphan is never reaped.

**Fix:** Add `await rs.oauth_identities.delete_by_user_id(user.id)` before
`rs.users.delete(user.id)` in `delete_user`, mirroring the pattern in
`delete_account`.

### W-2 — JWT decode error reason leaked in 401 response

**File:** `src/regstack/auth/dependencies.py:120`  
**Section:** §7 Session & Token Security, §9 Data Exposure

```python
detail=f"Invalid token: {exc}",          # leaks the specific PyJWT error
```

An attacker can distinguish "Signature verification failed" from "Token is expired"
from "Invalid header padding" by reading the `detail` field of the 401 JSON body.
This can aid in crafting JWT attacks or in profiling token-handling behaviour.

The security review requirement is explicit: "JWT decode errors → 401 generic, never
the specific reason."

**Fix:** Replace with a static string:

```python
detail="Authentication required.",
```

The original `exc` should still be logged at `DEBUG` level for operator visibility,
but must not appear in the HTTP response body.

### W-3 — `phone.py` endpoints skip `_require_password_set()` for OAuth-only users

**File:** `src/regstack/routers/phone.py:65, 149`  
**Section:** §3 Authentication & Authorization Audit, §14e OAuth-only user side effects

Both `POST /phone/start` and `DELETE /phone` call:

```python
if not rs.password_hasher.verify(payload.current_password, user.hashed_password):
```

without a prior `_require_password_set(user)` guard. For an OAuth-only user
(`hashed_password=None`), passing `None` to `pwdlib.PasswordHash.verify()` is
undefined and likely raises an unhandled `TypeError`, resulting in a 500 response.

`_require_password_set()` already exists in `account.py` and returns a clear 400
directing the user to the password-reset flow. The same check is missing here.

The `POST /change-password`, `POST /change-email`, and `DELETE /account` routes all
call `_require_password_set(user)` correctly — this is an inconsistency.

**Fix:** Call `_require_password_set(user)` (or inline the equivalent check) at the
start of both `start` and `disable` handlers, before any `password_hasher.verify`
call.

### W-4 — GitHub Actions: actions pinned by mutable tag/branch refs

**Files:** `.github/workflows/publish.yml`, `.github/workflows/test.yml`  
**Section:** §12a Third-party action pinning

Every `uses:` directive references a version tag or branch, not a commit SHA:

| Workflow | Action | Ref type |
|---|---|---|
| both | `actions/checkout@v4` | tag |
| both | `astral-sh/setup-uv@v3` | tag |
| both | `actions/upload-artifact@v4` | tag |
| publish | `actions/download-artifact@v4` | tag |
| publish | `pypa/gh-action-pypi-publish@release/v1` | **branch** |

Tag and branch references can be silently rewritten by the action author. The
`pypa/gh-action-pypi-publish@release/v1` branch reference is the highest-risk
entry: it runs with `id-token: write` access and can publish a wheel to PyPI on
behalf of the project. A compromised or repointed branch could inject malicious
code into every published release.

**Fix:** Pin every `uses:` to its full commit SHA, e.g.:

```yaml
uses: pypa/gh-action-pypi-publish@9b5ee3fc0e33f55e1c5e0c79b8a0bea5be1d8a77  # release/v1 as of YYYY-MM-DD
```

Use Dependabot or `pin-github-actions` to maintain SHA pins automatically.

### I-2 — `pywebview` bundled in base `dependencies` (GUI library on server nodes)

**File:** `pyproject.toml:37`  
**Section:** §13c Dependency pinning in shipped metadata

`pywebview>=5.0` (pinned to 6.2.1) is in the main `dependencies` list, not an
optional extra. The OAuth setup wizard (`regstack oauth setup`) and theme designer
(`regstack theme design`) use it, but these are developer-machine tools, not
server-runtime requirements.

Consequence: every host that runs `pip install regstack` in a production
environment pulls in a native GUI framework (WebKit/GTK on Linux,
WKWebView on macOS, Edge on Windows) with a large OS-level surface. On a headless
server this dependency cannot be exercised and simply adds an unnecessary attack
surface.

**Recommendation:** Move `pywebview`, `tomlkit`, and the `uvicorn[standard]`
duplicate (already in `dev`) into a `[wizard]` optional-extra, and make
`regstack oauth setup` / `regstack theme design` emit a clear installation hint
when the extra is missing.

### I-3 — GitHub Actions: missing `permissions:` on test jobs and publish build job

**Files:** `.github/workflows/test.yml`, `.github/workflows/publish.yml` (`build` job)  
**Section:** §12c Workflow permissions

Only the `publish` job in `publish.yml` declares:
```yaml
permissions:
  id-token: write
```

All jobs in `test.yml` and the `build` job in `publish.yml` have no `permissions:`
block and rely on the repository default, which includes `contents: write` in
some GitHub/org configurations.

**Fix:** Add `permissions: contents: read` (or stricter) to every job that does not
need write access, and add a workflow-level default:

```yaml
permissions:
  contents: read
```

This applies the principle of least-privilege at the job level; the `publish` job's
`id-token: write` override would still take effect.

### I-4 — MongoDB CVE-2025-14847 ("MongoBleed") — server-level advisory for operators

**Section:** §1 Dependency Vulnerability Check

CVE-2025-14847 is a high-severity (CVSS 8.7) memory-disclosure vulnerability in
the MongoDB *server* — not in the pymongo driver (pinned: 4.17.0, which is
unaffected). When zlib network-compression is enabled, an unauthenticated remote
attacker can leak arbitrary server memory. The vulnerability is under active
exploitation.

**Regstack's pymongo 4.17.0 driver is not vulnerable.** However, hosts deploying
regstack against MongoDB should ensure their server is patched:

| Series | Minimum patched version |
|---|---|
| 8.x | 8.2.3 or 8.0.17 |
| 7.x | 7.0.28 |
| 6.x | 6.0.27 |
| 5.x | 5.0.32 |
| 4.4 | 4.4.30 |

This advisory is included because regstack ships a MongoDB backend and its
documentation should surface this class of operational risk to hosts.

### I-6 — `/oauth/exchange` always returns `was_new_account=False`

**File:** `src/regstack/routers/oauth.py:150-155`  
**Section:** §14 OAuth Subsystem Audit

The `ExchangeResponse` model has a `was_new_account: bool` field, but the `exchange`
endpoint hardcodes it to `False`:

```python
return ExchangeResponse(
    ...
    was_new_account=False,  # always False regardless of _resolve_user result
    ...
)
```

The actual `was_new` value is computed in `oauth_callback` by `_resolve_user` but
is never written to the `OAuthState` row, so it cannot be retrieved at exchange
time. Clients (and the `regstack.js` frontend) cannot distinguish new signups from
returning sign-ins. This prevents personalised first-run experiences and correct
analytics.

This is a correctness defect, not a security vulnerability.

**Fix:** Add a `was_new: bool` column to `OAuthState` and the SQL/Mongo storage
layer; write it from `oauth_callback` via a new `set_result_metadata` method (or
extend `set_result_token`); read it back in `exchange`.
