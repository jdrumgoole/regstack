## 🟠 WARNING (Address within 1 week)

### W-1 — PyJWKClient missing timeout (carry-forward from 2026-05-22)

**Status:** Still open. No code change since the 2026-05-22 review.

**Location:** `src/regstack/oauth/providers/google.py:83`

```python
self._jwks_client = PyJWKClient(jwks_url, cache_keys=True)
```

No `timeout` argument is passed to `PyJWKClient`. The underlying urllib call that fetches Google's JWKS keys has no deadline (`timeout=None` → indefinite). PR #80 correctly offloaded the call to `asyncio.to_thread`, preventing event-loop blocking, but did not add a timeout:

```python
# In verify_id_token — correct async offload, but still no timeout upstream:
signing_key_obj = await asyncio.to_thread(
    self._jwks_client.get_signing_key_from_jwt, id_token
)
```

**Risk:** Under sustained JWKS cache-miss conditions (Google JWKS outage, network partition, or adversarial key-ID rotation), concurrent OAuth sign-in requests each occupy a thread-pool worker indefinitely. Python's asyncio thread pool is bounded (`min(32, cpu_count + 4)` workers). Exhausting it stalls all `to_thread` calls across the entire application, not just OAuth.

A direct attacker cannot force JWKS cache misses (the JWT `kid` must belong to a real Google key to pass signature verification), so this is primarily an operational risk during a Google infrastructure event. With the default JWKS cache TTL, refreshes happen periodically and any outage longer than a few minutes will start queuing threads.

**Fix:** Add `timeout=5` (or similar) to the constructor:

```python
self._jwks_client = PyJWKClient(jwks_url, cache_keys=True, timeout=5)
```

`PyJWKClient` accepts `timeout` from PyJWT ≥ 2.4; the project floor is already 2.12.1.

### I-1 — `was_new_account` always `False` in `/oauth/exchange` response (carry-forward from 2026-05-22)

**Status:** Still open. No code change since the 2026-05-22 review.

**Location:** `src/regstack/routers/oauth.py:176`

```python
return ExchangeResponse(
    access_token=state.result_token,
    redirect_to=state.redirect_to,
    was_new_account=False,   # ← always False; the real value is never persisted
    expires_in=rs.config.jwt_ttl_seconds,
)
```

The `was_new` boolean is correctly computed inside `_resolve_user` during the callback, but is not stored on the `oauth_states` row, so the exchange endpoint cannot surface it. This is not a security issue — a SPA seeing `False` when an account is genuinely new does not create an exploitable condition — but it is an API accuracy gap that may cause host implementors to silently fail on "Welcome! Account created." UX flows.

**Fix:** Add `result_was_new: bool = False` to `OAuthState` and the `oauth_states` schema; populate it inside `_resolve_user`; return it from `exchange`.

### I-3 — OAuth token-exchange exception includes full Google response body in server logs (carry-forward from 2026-05-22)

**Status:** Still present. No code change since the 2026-05-22 review.

**Location:** `src/regstack/oauth/providers/google.py:143–145`

```python
raise OAuthTokenExchangeError(
    f"google token exchange failed: {response.status_code} {response.text}"
)
```

This exception message is logged at `WARNING` by the router:

```python
log.warning("oauth token exchange failed: %s", exc)
```

The full HTTP response body from Google's token endpoint is written to the server log. Google's error responses are standard JSON (`{"error":"invalid_grant","error_description":"..."}`) and do not include the client secret or the authorization code. The risk in practice is low, and no information leaks to the client (they receive only `?error=token_exchange_failed`).

**Suggested improvement:** Separate the status code (WARNING) from the body (DEBUG) to reduce production log noise and to avoid any future surprise if the response body ever contains more:

```python
log.warning("google token exchange failed: HTTP %s", response.status_code)
log.debug("google token exchange response body: %s", response.text)
```

### §3 — Authentication & Authorization Audit

- **Router mounting:** `build_router` always mounts `register`, `verify`, `login`, `logout`, and `account`. Optional sub-routers (`password`, `phone`, `admin`, `oauth`) mount only when their config flag is enabled.
- **Endpoint authentication:** Every endpoint that mutates user state or returns user data requires either `current_user()` or `current_admin()`. No unauthenticated mutation endpoints found.
- **Response projection:** All endpoints return `UserPublic.from_user(user)` or a scoped model — never a raw `BaseUser`. `hashed_password` is not a field on `UserPublic`.
- **Bulk-revoke discipline:**
  - Password reset: `users.update_password` sets `tokens_invalidated_after`; `lockout.clear` called ✓
  - Change-password: `users.update_password` sets `tokens_invalidated_after` ✓
  - Confirm email-change: `users.update_email` sets `tokens_invalidated_after` ✓
  - Admin disable: router explicitly calls `users.set_tokens_invalidated_after` when `is_active=False` ✓
  - Account deletion: `oauth_identities.delete_by_user_id` cascades before `users.delete` ✓
- **OAuth-only users:** `POST /login` returns generic 401 (no password hash → same 401 as wrong password). `change-password`, `change-email`, `delete-account` return 400 via `require_password_set()`.
- **Constant-time comparison:** `pwdlib.PasswordHash.verify()` uses Argon2id's constant-time comparison.
- **Per-purpose JWT keys:** `derive_secret(jwt_secret, purpose)` via HMAC-SHA256 is called for every token kind. CLEAN.
- **`tokens_invalidated_after` in `UserPublic`:** Intentionally included as a documented design trade-off (see `docs/security.md` §"Data-exposure trade-off"). Hosts requiring stricter data minimization can strip the field in their own API wrapper.

### §6 — Rate Limiting & DoS Prevention

- Login lockout: `rs.lockout.check(email)` runs at the very start of `POST /login`, before any user lookup or password verification. A locked-out attacker receives 429 + `Retry-After` header without triggering a DB lookup.
- `record_failure` fires after verifying the credentials are wrong (user not found, wrong password, inactive, unverified). This is correct: it prevents the lockout counter from incrementing for requests that never reached the credential-check stage (because they were already blocked by `check`).
- `login_attempts` Mongo TTL index sized to `login_lockout_window_seconds`; SQL relies on read-side filtering via `count_recent` plus the optional `purge_expired()` reaper.
- Admin `/admin/users` listing: `limit` capped at 200 (`Query(ge=1, le=200)`) ✓
- OAuth state TTL: 5-minute default for the flow, shortened to 30 seconds (`completion_ttl_seconds`) after the callback populates the result token. SQL `purge_expired()` and Mongo `purge_expired()` both work correctly.
- No file-upload endpoints present.

### §7 — Session & Token Security

- JWT signing algorithm: HS256 (default); HS384/HS512 also supported. Secret minimum length enforced at `RegStack.__init__`.
- Every JWT includes `jti` (random `token_urlsafe(16)`). Per-token revocation via `BlacklistRepo.is_revoked(jti)` works correctly.
- `iat` emitted as a float (`now.timestamp()`) — preserves microsecond precision for accurate bulk-revoke comparisons.
- `JwtCodec` disables pyjwt's `exp`/`iat` checks and validates both against the injected `Clock`. `FrozenClock`-driven tests remain deterministic.
- `_authenticate` checks in order: decode → blacklist (`jti`) → user active → bulk revoke (`iat ≤ tokens_invalidated_after`). All four gates present.
- No token values appear in any `log.info`/`log.warning`/`log.error` call. `jwt_secret`, `client_secret`, `smtp_password`, `ses_secret_access_key`, `twilio_auth_token` are all `SecretStr`; `.get_secret_value()` is called only at the point of use.
