## 🟠 WARNING

### W-1 (carry-over, day 26 — SLA MISSED 2026-08-18)

**Section:** §1 — Dependency Vulnerability Check
**CVE:** CVE-2026-69247 — `cryptography` Bleichenbacher oracle (`pkcs7_decrypt`)
**Affected range:** `cryptography` ≥ 44.0.0, < 50.0.0
**Resolved in:** `cryptography==50.0.0` (released 2026-07-31 — 36 days ago)
**Current resolved version in `uv.lock`:** 49.0.0 (within affected range)
**Current floor in `pyproject.toml`:** `cryptography>=48.0.1` (does not exclude affected versions)
**Fix required:** Bump floor to `cryptography>=50.0.0` in both the `oauth` and `dev` extras in
`pyproject.toml`; run `uv lock`.
**Tracking:** GitHub issue #181 (`[security] Raise cryptography floor to >=50.0.0`), open since
2026-08-19 — no fix PR, no assignee, no comment — **18 days unacknowledged.**

**Technical impact:** `pkcs7_decrypt_der`, `pkcs7_decrypt_pem`, and `pkcs7_decrypt_smime` expose
distinguishable error paths and timing differences during RSA `RecipientInfo.encryptedKey` decryption,
constituting a Bleichenbacher-style oracle. regstack does not call these functions directly, but
`pip install regstack[oauth]` resolves to 49.0.0 by default, shipping a version with an open advisory
to all downstream consumers. The fix (cryptography 50.0.0+) substitutes a random key on RSA
decryption failure per RFC 3218.

**Urgency:** The fix version has been on PyPI for 36 days. The 7-day SLA lapsed 2026-08-18. This
finding will appear daily until resolved.

### W-2 (carry-over, day 5 — NEW 2026-09-01) — `POST /confirm-email-change` email-change JWT not revoked after use

**Section:** §3 — Authentication & Authorization Audit
**File:** `src/regstack/routers/account.py`, `confirm_email_change` handler
**Status:** Unresolved. No change to `account.py` since first flagged.

The `confirm_email_change` endpoint successfully updates the user's email address but does not
call `await rs.blacklist.revoke(token_payload.jti, token_payload.exp)` after doing so. The
password-reset path (`password.py`) correctly performs this revocation after every successful
reset. Within the email-change token's TTL, the same confirmation URL can be submitted repeatedly.
Each subsequent submission attempts `update_email`, which succeeds as a no-op when the address is
already the user's own, and the endpoint returns HTTP 200 — confirming the link is still usable.

The `_decode_email_change_token` helper currently returns only `(user_id, new_email)` and discards
the `jti` and `exp` claims. Any fix must also thread these through to the caller.

**Fix:** Expand `_decode_email_change_token` to return `(user_id, new_email, jti, exp)` and add
`await rs.blacklist.revoke(jti, exp)` immediately after the successful `update_email` call.

### W-3 (carry-over, day 5 — NEW 2026-09-01) — `POST /confirm-email-change` bulk-revoke not applied to email-change tokens

**Section:** §3 — Authentication & Authorization Audit
**File:** `src/regstack/routers/account.py`, `confirm_email_change` handler
**Status:** Unresolved. No change to `account.py` since first flagged.

`AuthDependencies._authenticate` calls `is_payload_bulk_revoked(payload, user.tokens_invalidated_after)`
for session tokens. The `confirm_email_change` endpoint decodes the email-change JWT and calls
`get_by_id` + `update_email` with no equivalent temporal cutoff check. Because the purpose-derived
key correctly prevents session tokens from satisfying this endpoint, the purpose isolation is sound —
but a stale email-change token minted before a password-change event can still be used after
`tokens_invalidated_after` has been bumped.

**Attack scenario:**
1. User initiates email-change → token minted at `iat=T1`, link emailed.
2. User detects compromise of email account, changes password → `tokens_invalidated_after` bumped to `T2 > T1`.
3. Attacker (who has inbox access) clicks the email-change link minted at `T1` → `confirm_email_change`
   succeeds because `T1 < T2` is never evaluated.
4. Attacker now controls the user's email address.

**Fix:** After decoding the email-change JWT in `confirm_email_change`, fetch the user record and check
`if rs.auth.is_payload_bulk_revoked(token_payload, user.tokens_invalidated_after): raise HTTPException(400, ...)`.
The pattern mirrors the `_authenticate` dependency. Both W-2 and W-3 can be fixed in a single pass
through `confirm_email_change`.

### W-4 (carry-over, day 5 — NEW 2026-09-01) — OAuth `_resolve_user` unhandled `UserAlreadyExistsError` → HTTP 500

**Section:** §3 / §14 — Authentication & Authorization / OAuth Subsystem
**File:** `src/regstack/routers/oauth.py`, `_resolve_user` (brand-new account path, line ~716),
`oauth_callback` (line ~325)
**Status:** Unresolved. No change to `oauth.py` since first flagged.

A race between a concurrent email registration and the OAuth sign-in flow creates an unhandled
exception path that returns HTTP 500 to the user's browser. `oauth_callback` catches only
`_LinkConflictError`; `UserAlreadyExistsError` from `rs.users.create()` propagates unhandled.

**Scenario:**
1. User clicks "Sign in with Google" with `email@example.com`.
2. `_resolve_user` calls `get_by_email("email@example.com")` → returns `None`.
3. Concurrently, another request completes `POST /register` with the same email.
4. `_resolve_user` calls `rs.users.create(new_user)` → raises `UserAlreadyExistsError`.
5. `oauth_callback` catches only `_LinkConflictError`; `UserAlreadyExistsError` propagates as HTTP 500.

**Fix:** In `_resolve_user`, wrap `rs.users.create(new_user)` in a `try/except UserAlreadyExistsError`
and re-raise as `_LinkConflictError("email_in_use")`. This is consistent with how the auto-link
policy already handles the known-email case.

## 🟢 CLEAN

The following areas were re-checked today and remain secure:

- **§2 Hardcoded secrets:** No API keys, JWTs, private keys, or real credentials in `src/`, `tests/`,
  `examples/`. Example `regstack.toml` files contain only `localhost` URLs and `console` email
  backend — no real secrets. `.gitignore` correctly covers `.env`, `regstack.secrets.env`, `*.pem`,
  `*.key`, `*.p12`, `htmlcov/`, `.coverage`. `git ls-files` surfaces only
  `src/regstack/config/secrets.py` (the key-derivation module, not a credential file).

- **§3 Auth/authz (excluding W-2/W-3/W-4):** All authenticated routes inject `current_user` or
  `current_admin`. All admin endpoints require `current_admin()`. Per-token blacklist and bulk-revoke
  checks both present in `_authenticate` (lines 167, 174, 180). JWT `iat` emitted as float (confirmed
  in `src/regstack/auth/jwt.py` line 69). pyjwt `exp`/`iat` checks disabled; `Clock`-injection seam
  intact. Constant-time password comparison via `pwdlib` (not `==`). JWT keys derived per-purpose
  via `derive_secret`. OAuth-only user (`hashed_password=None`) handled in login with same generic
  401. Account deletion cascades `oauth_identities` before deleting the user.

- **§4 Storage-layer injection:** No `$where`/`$expr`/`$function`/`$accumulator` operators in Mongo
  repos. `ObjectId.is_valid()` guard present on all `get_by_id` paths in `user_repo.py`. SQL repos
  use SQLAlchemy Core parameterised binds; no f-string interpolation into raw SQL. The two
  `text(...)` usages (`SELECT 1` health check and migration count query) are non-user-controlled.
  `UtcDateTime` TypeDecorator correctly re-attaches UTC tzinfo on both write and read.

- **§5 Input validation:** All API inputs go through Pydantic models. `EmailStr` validated on
  email-bearing fields. E.164 validation confirmed in `phone.py` line 61. Jinja2 autoescape on in
  email templates; no `| safe` or `{% autoescape false %}` in SSR templates. `redirect_to` validated
  same-origin via `_validate_redirect` (backslash and `//` prefix checks included).

- **§6 Rate limiting / DoS:** Login lockout wired via `LockoutService` (`check()` before
  `record_failure()`, correct ordering). Admin listing endpoint caps `limit` at 200 (`ge=1, le=200`).
  No user-facing file upload endpoints.

- **§7 Session/token security:** All tokens include `jti`. `iat` is float. Bulk-revoke uses `<=`
  cutoff. `UserPublic` excludes `hashed_password` and internal fields in all response models.

- **§8 CSP / SSR layer:** No `<style>` blocks, `style="..."` attributes, or inline `<script>` tags
  found in `src/regstack/ui/templates/`. `oauth_complete.html` follows the same discipline.
  SSR pages are stateless — no `{{ user.email }}` or auth state rendered into HTML.

- **§9 Data exposure:** All API responses use `UserPublic`. No `f"...{exc}"` patterns in HTTP error
  responses. No token values (JWT, access_token, id_token) logged in routers — log.warning calls
  use only generic exception objects. JWT secret, OAuth client_secret, SMTP password not logged.

- **§10 Git history:** No accidentally committed secrets (only `src/regstack/config/secrets.py`
  matches `*secret*` glob — it is the key-derivation code, not credentials). No security-relevant
  code changes in the last 30 commits beyond the daily security reports.

- **§11 Third-party integrations:** SMTP password in `SecretStr` (`EmailConfig.smtp_password`). SES
  backend uses config-sourced profile/region. Google OAuth `client_secret` stored as `SecretStr`.
  ID-token verification goes through `PyJWKClient` with timeout.

- **§12 GitHub Actions:** All `uses:` SHA-pinned. No `${{ github.event.* }}` untrusted interpolation

  `id-token: write`. No `pull_request_target` trigger. No `self-hosted` runners. No `PYPI_API_TOKEN`

- **§13 PyPI Package Integrity:** OIDC trusted publishing only. `id-token: write` on publish job
