## 🟡 INFO (Best practice recommendations)

### I-1 · `UserPublic` exposes `tokens_invalidated_after` — review checklist expectation vs. intentional design

**Section:** §9 — Data Exposure  
**File:** `src/regstack/models/user.py`, line 105

The review checklist at §9 states: "`UserPublic` excludes `hashed_password`, `tokens_invalidated_after`, internal IDs." The actual `UserPublic` model does **include** `tokens_invalidated_after` — and does so intentionally:

```python
tokens_invalidated_after: datetime | None = None
"""Bulk-revoke cutoff. SPAs comparing this to their session JWT's
`iat` can tell when the token they hold has been invalidated by a
password change / email change without making another request."""
```

The previous eight daily reviews incorrectly asserted this field was excluded. The design decision is sound and documented — the field enables SPA auto-logout when a user changes their password — but it constitutes deliberate leakage of a user's password-change timestamp:

- `GET /me` (authenticated): a user can see their own `tokens_invalidated_after` — their own data, low concern.
- `GET /admin/users` and `GET /admin/users/{id}` (superuser only): admins can observe when any user last bulk-revoked their sessions. This is admin-level privilege and is acceptable in most deployments.

**Security impact:** Limited. The timestamp reveals *when* the user last changed their password or email (or was locked out), not the password itself. An attacker who holds a valid session token gains no additional access by knowing this value; they would discover the token was invalidated the first time they use it.

**Recommendation:** Update the §9 bullet in `scripts/security-review-prompt.md` to reflect the actual design: "`UserPublic` excludes `hashed_password`; `tokens_invalidated_after` is intentionally exposed for SPA bulk-revoke awareness." Operators sensitive to this timestamp leakage can strip the field from `UserPublic` in a host-level response projection without touching regstack internals.

### I-2 · CVE-2026-24486 (python-multipart path traversal) not documented in `pyproject.toml`

**Section:** §1 — Dependency Vulnerability Check

**CVE-2026-24486** (path traversal, HIGH, CVSS ~7.5) affects `python-multipart < 0.0.22`. When `UPLOAD_DIR` + `UPLOAD_KEEP_FILENAME=True` are both set and an upload exceeds `MAX_MEMORY_FILE_SIZE`, a crafted filename starting with `/` can write files to arbitrary filesystem paths (potential RCE via webshell). The advisory was published after the last review's CVE sweep.

regstack's current floor is `python-multipart >= 0.0.32` — well above the affected range — so **no action is needed**. However, the five CVEs that motivated the floor are documented in `pyproject.toml`'s inline comment block (CVE-2026-40347/42561/53537/53538/53539/53540), and CVE-2026-24486 is not. Keeping the comment block current makes future dependency-floor bump decisions traceable.

**Recommendation:** Add CVE-2026-24486 to the `python-multipart` comment in `pyproject.toml` alongside the existing six-CVE note.

### §3 — Authentication & Authorization Audit

**Mounted routers:** `build_router(rs)` wires the composite router. Always-on: `register`, `verify`, `login`, `logout`, `account`. Conditionally: `password` (`enable_password_reset`), `phone` + MFA (`enable_sms_2fa`), `admin` (`enable_admin_router`), `oauth` (`enable_oauth` AND at least one registered provider). Every conditional mount is gated on the correct flag. ✅

**Auth dependency injection:** Every endpoint that reads or mutates user-owned data injects `rs.deps.current_user()` or `rs.deps.current_admin()` via `Depends(...)`. Confirmed for: `GET /me`, `PATCH /me`, `POST /change-password`, `POST /change-email`, `DELETE /account`, all `/admin/*` routes, `GET /oauth/providers`, `POST /oauth/{provider}/link/start`, `DELETE /oauth/{provider}/link`. ✅

**Bulk-revoke discipline:**
- Password reset (`POST /reset-password`): `users.update_password()` bumps `tokens_invalidated_after`; `lockout.clear()` called. ✅
- Password change (`POST /change-password`): same path via `users.update_password()`. ✅
- Email-change confirm (`POST /confirm-email-change`): `users.update_email()` bumps `tokens_invalidated_after`. ✅
- Admin disable (`PATCH /admin/users/{id}` with `is_active=False`): explicit `users.set_tokens_invalidated_after(user.id, rs.clock.now())` called in `admin.py:112`. ✅
- Account deletion: cascades `oauth_identities.delete_by_user_id(user.id)` before `users.delete()` — no orphan identity rows. Same pattern in admin `DELETE /admin/users/{id}`. ✅

**Password reset token re-use prevention:** `reset-password` blacklists the token's `jti` on first success; a second use returns the same "invalid or expired" 400 as a truly expired link. ✅

**OAuth-only user (`hashed_password=None`) handling:**
- `POST /login` (`login.py:99`): `if user.hashed_password is None or not rs.password_hasher.verify(...)` — same generic 401 as wrong-password. No enumeration. ✅
- `POST /change-password`, `POST /change-email`, `DELETE /account`: guarded by `require_password_set()` → 400. ✅
- `DELETE /oauth/{provider}/link`: refuses if last sign-in method. ✅

**Constant-time comparison:** `pwdlib.PasswordHasher.verify()` (Argon2). No `==` comparison of password material. ✅

**Per-purpose JWT keys:** `JwtCodec._key(purpose)` calls `derive_secret(master, purpose)` (HMAC-SHA256). Compromise of one purpose key does not compromise others. ✅

### §7 — Session & Token Security

`options={"require": ["sub", "exp", "iat", "jti", "purpose"]}` — every token carries `jti` for per-token revocation. ✅

`_authenticate` chain (`src/regstack/auth/dependencies.py`):
1. Decode → static `"Invalid or expired token."` 401 on `TokenError` (pyjwt reason never echoed). ✅
2. `blacklist.is_revoked(payload.jti)` → 401. ✅
3. `users.get_by_id(payload.sub)` + `is_active` check → 401. ✅
4. `is_payload_bulk_revoked(payload, user.tokens_invalidated_after)` → 401. ✅
