### W-2 — confirm_email_change: email-change JWT not blacklisted after use (day 19, SLA overdue 12 days)

**Tracking:** Issue #197  
**File:** `src/regstack/routers/account.py` — `confirm_email_change`

`_decode_email_change_token` returns a payload but discards the `jti`. After `users.update_email(...)` succeeds the token is never inserted into `BlacklistRepo`. A replay attack within the token's TTL window can re-run `update_email` a second time, repeatedly cycling the victim's email address and bumping `tokens_invalidated_after` to force session expiry. Confirmed still present in HEAD.

**Remediation:** Extract `jti` from the payload and call `blacklist.revoke(jti, exp)` after `update_email` succeeds, mirroring the logout pattern.

### W-3 — confirm_email_change: bulk-revoke cutoff not applied to the token itself (day 19, SLA overdue 12 days)

**Tracking:** Issue #198  
**File:** `src/regstack/routers/account.py` — `confirm_email_change`

`_decode_email_change_token` does not call `is_payload_bulk_revoked` before acting. If a user's `tokens_invalidated_after` has been bumped (e.g., by a concurrent `change-password`), a pre-bump email-change token can still be consumed. The window is narrow but the invariant is violated. Confirmed still present in HEAD.

**Remediation:** After decoding the email-change token, fetch the user and call `is_payload_bulk_revoked(payload, user.tokens_invalidated_after)`. If revoked, return 401.

### W-4 — OAuth _resolve_user: UserAlreadyExistsError not caught on concurrent new-user branch (day 19, SLA overdue 12 days)

**Tracking:** Issue #199  
**File:** `src/regstack/routers/oauth.py` — `_resolve_user`

In the new-user branch, `users.create()` can raise `UserAlreadyExistsError` if two OAuth callbacks arrive simultaneously for the same email address. This exception propagates unhandled → HTTP 500 instead of a safe recovery path. Confirmed still present in HEAD.

**Remediation:** Wrap `users.create()` in a `try/except UserAlreadyExistsError` block; on conflict, fall through to `users.get_by_email()` and continue with the link step.

### W-6 — SQL oauth_states.consume() SELECT+DELETE not atomic (day 11, SLA overdue 4 days)

**Tracking:** Issue #208  
**File:** `src/regstack/backends/sql/repositories/oauth_state_repo.py`

The SQL backend's `consume()` wraps a `SELECT` and `DELETE` in a `BEGIN` transaction. On PostgreSQL at `READ COMMITTED` isolation, two concurrent `POST /oauth/exchange` calls can both read the row before either commits the delete, yielding two "successful" consumes of the same state row. This breaks the one-shot PKCE guarantee.

**Remediation:** Use `DELETE ... RETURNING *` (Postgres/SQLite 3.35+) or `SELECT ... FOR UPDATE` inside the transaction so only one concurrent caller can consume the row.

### W-8 — Timing oracle: OAuth-only account type disclosed via response latency (day 1, SLA expires 2026-09-25)

**Tracking:** Issue #217  
**File:** `src/regstack/routers/login.py` line 99

```python
if user.hashed_password is None or not rs.password_hasher.verify(
    payload.password, user.hashed_password
):
```

Python short-circuit `or` evaluation means that when `user.hashed_password is None` (OAuth-only account), `rs.password_hasher.verify()` is never called. Argon2id verification takes ~100 ms by design; skipping it causes OAuth-only accounts to respond in ~1 ms. An attacker with a list of email addresses can distinguish OAuth-only accounts from password accounts (and non-existent accounts) purely by measuring response latency — despite the code comment explicitly stating that account type must not be disclosed. Confirmed still present in HEAD.

**Remediation:** Always run a dummy Argon2 verify before returning the 401, even when `hashed_password is None`. Store `is_oauth_only = user.hashed_password is None` before verification; then call `rs.password_hasher.verify(payload.password, user.hashed_password or DUMMY_HASH)`, discard the result if `is_oauth_only`, and return the same generic 401.

### W-9 — SNS SMS backend: no config fields for explicit AWS credentials (day 1, SLA expires 2026-09-25)

**Tracking:** Issue #218  
**File:** `src/regstack/sms/sns.py` line 29; `src/regstack/config/schema.py` `SmsConfig`

The SES email backend exposes `ses_access_key_id`, `ses_secret_access_key`, and `ses_profile` in `EmailConfig` so credentials can be supplied explicitly when no ambient IAM role is available. The SNS SMS backend calls `aioboto3.Session()` with no credential arguments and has no equivalent fields in `SmsConfig`. In environments without ambient IAM (a bare EC2 instance, a non-AWS VPC host, or any non-AWS cloud) the SNS backend will silently fail with an `AuthorizationError` from aioboto3 rather than a configuration validation error at startup. Confirmed still present in HEAD (`aioboto3.Session()` takes no credential arguments).

**Remediation:** Add `sns_access_key_id: SecretStr | None`, `sns_secret_access_key: SecretStr | None`, and `sns_profile: str | None` to `SmsConfig` (matching the SES pattern). Pass them to `aioboto3.Session(...)` in `sns.py` when set, with the same mutual-exclusivity validator.

### W-10 — GoogleProvider stores client_secret as plain str (day 1, SLA expires 2026-09-25)

**Tracking:** Issue #219  
**File:** `src/regstack/oauth/providers/google.py` lines 79, 90

`GoogleProvider.__init__` accepts `client_secret: str` (a plain Python `str`) and stores it as `self._client_secret`. All other credential fields in the codebase use Pydantic `SecretStr`, which overrides `__repr__` to emit `'**********'` in place of the value. A plain `str` attribute will appear verbatim in exception tracebacks captured by APM tools (Sentry, Datadog), heap dumps, and any introspection tool that enumerates the instance's `__dict__`.

**Remediation:** Change `GoogleProvider.__init__` to accept `client_secret: SecretStr` (not `str`); update the call site in `app.py` to pass the `SecretStr` directly rather than unwrapping it; call `.get_secret_value()` only at the use site inside `exchange_code`. Add `__repr__` returning `<GoogleProvider client_id=...>` (no secret).

## 🟡 INFO

### I-1 — SQL purge_expired() not automatically scheduled

**Files:** All SQL repos with `expires_at` columns; `src/regstack/backends/protocols.py`

MongoDB TTL indexes expire documents automatically. On SQL backends, expired rows accumulate indefinitely unless the host application calls `purge_expired()` on each repo. The protocol interface documents this requirement, but there is no built-in background task, startup hook, or documentation in the user-facing README or `regstack init` output to inform hosts. The accumulation is a storage leak, not a security bypass (expiry checks are done in-query), but a host that never calls `purge_expired()` will have unbounded table growth for `login_attempts`, `pending_registrations`, `mfa_codes`, `token_blacklist`, and `oauth_states`.

**Recommendation:** Add a note to the `docs/` user guide and/or the `regstack init` output instructing SQL-backend users to schedule `purge_expired()` calls. Optionally provide a `RegStack.purge_expired_all()` convenience method.

### I-2 — pyproject.toml CVE comment misattributes CVE-2026-2978/2979

**File:** `pyproject.toml` (comment near `fastapi>=0.120.0`)

The comment attributes CVE-2026-2978 and CVE-2026-2979 to `fastapi`. Those CVEs affect the unrelated third-party package "FastApiAdmin", not the `fastapi` package itself. The floor version for `fastapi` is correct but the comment creates confusion about the actual threat. No security impact; update the comment for accuracy.

### I-3 — tokens_invalidated_after included in UserPublic

**File:** `src/regstack/models/user.py` line 105

`tokens_invalidated_after` is exposed in `UserPublic`. This is documented as intentional (allows SPAs to detect token invalidation without a round-trip). No attack vector identified; authenticated users can only read their own value; admins can read all users'. Noted for awareness.
