## 🟠 WARNING (Address within 1 week)

### W-1 — SQL `oauth_states.consume()` TOCTOU race under concurrent `/oauth/exchange` requests

**File:** `src/regstack/backends/sql/repositories/oauth_state_repo.py:63–71`

```python
async def consume(self, state_id: str) -> OAuthState | None:
    async with self._engine.begin() as conn:
        row = (await conn.execute(select(self._t).where(self._t.c.id == state_id))).first()
        if row is None:
            return None
        await conn.execute(delete(self._t).where(self._t.c.id == state_id))
    return _row_to_state(row)
```

Under PostgreSQL's default **READ COMMITTED** isolation, two simultaneous
`POST /oauth/exchange` requests sharing the same `state_id` can interleave
like this:

1. T1 `SELECT` → row found, value captured  
2. T2 `SELECT` (before T1 commits) → row found, same value captured  
3. T1 `DELETE` + commit  
4. T2 `DELETE` → 0 rows affected, but T2 already has the row → commits and returns it  

Both callers receive the embedded `result_token` (session JWT), breaking the
"each OAuth state may be exchanged exactly once" invariant. In practice the
window is 30 seconds (`completion_ttl_seconds`) and the `state_id` is 256-bit
random (unguessable), so exploitation requires an attacker who already holds
the `state_id` AND races a legitimate exchange. Nevertheless the backend parity
is broken: the MongoDB backend correctly uses `find_one_and_delete` (atomic
read-and-delete) and has no such race.

**Fix:** add `FOR UPDATE` to the SELECT so PostgreSQL serialises concurrent
consumers at the row lock:

```python
async def consume(self, state_id: str) -> OAuthState | None:
    async with self._engine.begin() as conn:
        row = (
            await conn.execute(
                select(self._t)
                .where(self._t.c.id == state_id)
                .with_for_update()          # serialise concurrent consumers
            )
        ).first()
        if row is None:
            return None
        await conn.execute(delete(self._t).where(self._t.c.id == state_id))
    return _row_to_state(row)
```

SQLite ignores `FOR UPDATE` (it file-locks on write anyway, so concurrent
writes are already serialised there). The change is safe for the full matrix.

## 🟡 INFO (Best practice recommendations)

### I-1 — `tokens_invalidated_after` and `phone_number` in `UserPublic` (carry-forward)

Unchanged from the 2026-06-20 review (I-3) and the chain of reviews before it.
`UserPublic.tokens_invalidated_after` is intentional — SPAs use it to detect
when a held JWT has been bulk-revoked without an extra round-trip
(`src/regstack/models/user.py:105–108`). `phone_number` is the authenticated
user's own data. Both deviate from the security-review-prompt's stated
"`UserPublic` excludes `hashed_password`, `tokens_invalidated_after`" rule but
are documented design trade-offs in `docs/security.md`. Hosts who want them
hidden wrap the response model. No code change required; carrying forward for
awareness.

### I-2 — Per-IP rate limits all default `None` — distributed throttling is opt-in only

`RegStackConfig` exposes 15 per-route rate-limit fields (`login_rate_limit`,
`register_rate_limit`, `forgot_password_rate_limit`, etc.) all defaulting to
`None` (`src/regstack/config/schema.py:224–241`). Per-account lockout
(`LockoutService`) is always enforced. IP-level throttling requires the
`rate_limit` extra (`slowapi>=0.1.9`) AND explicit configuration of each field.

A fresh deployment with no extra gets no protection against distributed
credential stuffing from many source IPs (each IP is within the per-account
attempt budget). The `forgot-password` and `resend-verification` endpoints
are additionally vulnerable to email-flood abuse without per-IP limits.

**Recommendation:** the `regstack init` wizard and the example `regstack.toml`
files should recommend a sensible default such as `login_rate_limit = "10/minute"`
with a comment. The `rate_limit` extra is not required for the global lockout
mechanism — consider making the wizard emit these fields even when slowapi is not
installed, so operators see the slots and fill them when they add the extra.

### I-3 — `code_verifier` and `result_token` stored plaintext in `oauth_states`

`oauth_states` rows contain:
- `code_verifier` — the 64-byte random PKCE verifier (valid for
  `state_ttl_seconds`, default 5 min). A DB read during an open flow yields
  a verifier that could be used to replay a stolen authorisation code.
- `result_token` — the session JWT written after the provider callback
  (valid for `completion_ttl_seconds`, default 30 s). A DB read during
  that 30-second window yields an active session token.

Storing hashes here would require the OAuth callback to also hash before storing,
adding complexity. Given the short TTLs this is an accepted design trade-off.
Worth noting for operators who run DB hot-standby replication or take periodic
snapshots that might include live state rows.

### §3 — Authentication & Authorization

- Every endpoint in `routers/` that reads or mutates user state injects
  `rs.deps.current_user()` or `rs.deps.current_admin()`.
- `UserPublic.from_user()` is used at every response site; `hashed_password`
  is excluded. `BaseUser` is never returned directly from a route handler.
- **Bulk-revoke discipline complete:**
  - `reset-password` → `users.update_password` (bumps `tokens_invalidated_after`)
    + `lockout.clear` + blacklists the reset token's `jti` (prevents replay).
  - `change-password` → `users.update_password` + `lockout.clear`.
  - `confirm-email-change` → `users.update_email` (bumps
    `tokens_invalidated_after`) + `lockout.clear(previous_email)`.
  - `PATCH /admin/users/{id} {is_active: false}` → `users.set_active` +
    `users.set_tokens_invalidated_after`.
  - `DELETE /account` and `DELETE /admin/users/{id}` → cascade
    `oauth_identities.delete_by_user_id` before `users.delete`.
- OAuth-only users (`hashed_password=None`) get the same generic 401 on
  password login as a wrong-password attempt; `require_password_set` guards
  `change-password`, `change-email`, `delete-account`, and phone
  setup/disable.
- Constant-time password comparison via `pwdlib` Argon2 (no `==`).
- JWT keys derived per-purpose via HMAC-SHA256 (`config/secrets.py:8–17`).

### §14 — OAuth Subsystem

- **PKCE:** `code_verifier` is generated server-side (`_secrets.token_urlsafe(64)`)
  and stored only on the `oauth_states` row. Only `code_challenge` (SHA-256)
  goes to the provider. The browser never sees the verifier.
- **State lifecycle:** find-then-verify-expiry-then-consume pattern is correct.
  Expiry check uses `rs.clock.now()` (not `datetime.now(UTC)`). `consume()`
  is atomic in MongoDB (`find_one_and_delete`). See W-1 for the SQL race.
- **ID-token verification:** signature against JWKS, `iss` == configured
  issuer, `aud` == `client_id`, `exp > now` (pyjwt default checks re-enabled
  here, unlike session-token decodes), `nonce` cross-checked. Failures raise
  `OAuthIdTokenError` with a generic outer message; specifics logged only at
  WARNING level.
- **Linking policy:** `auto_link_verified_emails` defaults to `False`.
  Identity-in-use → `?error=identity_in_use`. Already-linked to same user →
  `?error=already_linked`. Email claimed by existing password-user →
  `?error=email_in_use`. All checked before any DB write.
- **OAuth-only user side effects:** generic 401 on password login; 400 +
  forgot-password pointer on `change-password`/`change-email`/`delete-account`.
  `DELETE /oauth/{provider}/link` returns 400 when it would remove the last
  sign-in method.
- **Identity-row uniqueness:** `(provider, subject_id)` and `(user_id, provider)`
  unique in both Mongo (named indexes in `mongo/indexes.py:73–86`) and SQL
  (`UniqueConstraint` in `schema.py:143–145`).
- **Hooks:** `oauth_signin_started`, `oauth_signin_completed`,
  `oauth_account_linked`, `oauth_account_unlinked` all in `KNOWN_EVENTS`
  (`hooks/events.py:29–35`) and fired at the correct call sites in
  `routers/oauth.py`.
