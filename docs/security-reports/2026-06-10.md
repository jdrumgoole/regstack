## 🟠 WARNING (Address within 1 week)

### W-1 — JWT secret minimum length not enforced (`src/regstack/auth/jwt.py:117–123`)

**Finding:**

`JwtCodec.__init__` checks only that the secret is non-empty:

```python
if not config.jwt_secret.get_secret_value():
    raise ValueError(
        "RegStackConfig.jwt_secret is empty. Run `regstack init` to generate one, "
        "or set REGSTACK_JWT_SECRET."
    )
```

There is no minimum-length check. The `RegStackConfig.jwt_secret` field also has no lower-bound validator:

```python
jwt_secret: SecretStr = Field(default_factory=lambda: SecretStr(""))
```

A host that sets `REGSTACK_JWT_SECRET=abc` gets a silently weak HS256 signing key. NIST SP 800-107 recommends HMAC-SHA256 keys of at least 32 bytes (256 bits) to match the hash output width; shorter keys make offline brute-force feasible for an attacker who observes any signed token.

The 2026-05-22 review's §7 "CLEAN" section asserted "secret ≥32 chars enforced at `JwtCodec` construction" — this was incorrect. The `regstack init` wizard does generate a 64-byte key, so well-configured deployments are unaffected, but a manually configured short secret is accepted without warning.

**Impact:** An attacker who can observe a signed session JWT (e.g., from a compromised log pipeline) and knows the secret is short could brute-force it offline, then forge or decode tokens for any user.

**Fix:** Add a length guard in `JwtCodec.__init__` immediately after the non-empty check:

```python
secret_value = config.jwt_secret.get_secret_value()
if not secret_value:
    raise ValueError(
        "RegStackConfig.jwt_secret is empty. Run `regstack init` to generate one, "
        "or set REGSTACK_JWT_SECRET."
    )
if len(secret_value.encode("utf-8")) < 32:
    raise ValueError(
        f"RegStackConfig.jwt_secret must be at least 32 bytes "
        f"(got {len(secret_value.encode('utf-8'))}). "
        "Run `regstack init` to generate a secure one, or set "
        "REGSTACK_JWT_SECRET to at least 32 random characters."
    )
```

Alternatively, add `min_length=32` to the `RegStackConfig` field so Pydantic surfaces it at config-load time instead of at JwtCodec construction. Either location is acceptable; construction-time is preferable because it fires even when hosts build `JwtCodec` directly.

## 🟡 INFO (Best practice recommendations)

### I-1 — `tokens_invalidated_after` exposed in `UserPublic` (documented design decision)

`UserPublic` includes `tokens_invalidated_after`:

```python
tokens_invalidated_after: datetime | None = None
"""Bulk-revoke cutoff. SPAs comparing this to their session JWT's
`iat` can tell when the token they hold has been invalidated by a
password change / email change without making another request."""
```

The security-review prompt specifies that `UserPublic` should exclude `tokens_invalidated_after`. This was surfaced as I-2 in the 2026-05-17 review and intentionally kept as an accepted trade-off (closed in PR #63 with documentation in `docs/security.md`).

Exposing the timestamp leaks when the user last performed a bulk-revoking operation (password change, email change, admin disable). The documentation in `docs/security.md` covers this trade-off. Noting here for completeness and to ensure each review cycle re-evaluates the decision.

**Recommendation (not required):** If the SPA self-diagnosis feature becomes less important, consider replacing `tokens_invalidated_after` exposure with a dedicated lightweight `GET /me/session-status` endpoint that returns only a boolean `{ "valid": true/false }` without exposing the raw timestamp.

### I-2 — FastAPI CVE-2026-2979 / CVE-2026-2978 (carried forward from 2026-05-22 review)

### §3 — Authentication & Authorization Audit

- Every authenticated endpoint injects `rs.deps.current_user()` or `rs.deps.current_admin()` via FastAPI `Depends`.
- All user-state-mutating endpoints require authentication; all read endpoints that return user data go through `UserPublic.from_user()`.
- Bulk-revoke discipline verified across all flows:
  - `update_password` bumps `tokens_invalidated_after` on both backends ✓
  - `update_email` bumps `tokens_invalidated_after` ✓
  - Admin disable (`set_active(..., is_active=False)`) calls `set_tokens_invalidated_after` ✓
  - Account deletion cascades `oauth_identities.delete_by_user_id` before `users.delete` ✓
- OAuth-only users (`hashed_password=None`): `POST /login` returns the same generic 401 as a wrong-password attempt; `change-password`, `change-email`, `delete-account` reject via `require_password_set()` with a 400 pointing at forgot-password.
- Password verification uses `rs.password_hasher.verify()` (pwdlib Argon2id, constant-time).
- JWT signing uses per-purpose HMAC-SHA256 key derivation (`derive_secret(jwt_secret, purpose)`). Compromise of one purpose key does not expose the master or other keys.
- Admin `/users` listing uses `Query(ge=1, le=200)` cap on `limit`.

### §4 — Storage-layer Injection Safety

**MongoDB:** No `$where`, `$expr`, `$function`, or `$accumulator` operators in any repository. All user-supplied values are bound as filter values, never interpolated into key positions. `ObjectId.is_valid(user_id)` guards every `get_by_id` before `ObjectId(user_id)` conversion — returns `None` instead of raising on invalid input. ### §6 — Rate Limiting & DoS Prevention

- `LockoutService.check()` fires at the top of the login handler before any user lookup. A locked account always gets 429 with `Retry-After`; password guesses never occur.
- `record_failure` is called for all failure branches: user not found, wrong password, disabled account, unverified account — preventing enumeration via differential lockout rates.
- `login_attempts` Mongo TTL index expires rows after `login_lockout_window_seconds`.
- OAuth `state` rows: Mongo TTL index on `expires_at` (`oauth_state_ttl`); SQL backends have `purge_expired()`. Default `state_ttl_seconds=300` bounds the pre-callback accumulation window.
- Admin user listing: `Query(ge=1, le=200)` cap on `limit`.
- No file-upload endpoints exist.
- `rate_limit_disabled=True` (test mode) short-circuits both `record_failure` and `check` — no docs written.

### §7 — Session & Token Security

*(See W-1 above for the minimum-length gap.)*

- HS256 algorithm by default; configurable to HS384/HS512.
- Every JWT includes `jti` generated with `secrets.token_urlsafe(16)`.
- `iat` emitted as `float` (RFC 7519 NumericDate) — microsecond precision enables correct `iat <= cutoff` comparisons when a login completes in the same wall-clock second as a password change.
- pyjwt's built-in `exp`/`iat`/`nbf` checks are disabled; both are validated against the injected `Clock`. `FrozenClock` tests and production correctness rely on this seam.

- No token values appear in log messages. Token decode errors return a single static "Invalid or expired token." 401, never the pyjwt exception text.

### §14 — OAuth Subsystem

- **PKCE:** `code_verifier = secrets.token_urlsafe(64)` generated server-side; stored on `oauth_states` row. Only `code_challenge = base64url(sha256(verifier))` sent to the provider as a query parameter. Verifier never appears in any URL the browser sees. ✓
- **State row lifecycle:** Expiry checked against `rs.clock.now()` (not bare `datetime.now(UTC)`). Mongo uses `find_one_and_delete` (atomic consume). SQL uses `SELECT + DELETE` inside a single `engine.begin()` transaction (atomic). A second exchange with the same state-id returns 404. Completion TTL shortened to `oauth.completion_ttl_seconds` (default 30s) after the callback sets `result_token`, bounding the stolen-state-id window. ✓
- **ID-token verification:** Signature verified via `PyJWKClient` (RS256). `iss` matches `GOOGLE_ISSUER`. `aud` matches `client_id`. `exp > now` validated by pyjwt (no `verify_exp: False` in this path). `nonce` validated against state row. Failure raises `OAuthIdTokenError` with generic outer message; detail logged, not echoed to redirect. ✓
- **Linking policy:** Existing-email sign-in → `email_in_use` (no auto-link unless `auto_link_verified_emails=True` AND `email_verified=True`). Already-linked identity to different user → `identity_in_use`. Same identity same user → `already_linked`. Unlink last method with no password → 400. ✓
- **OAuth-only users:** `POST /login` → generic 401 (same as wrong-password). `change-password`, `change-email`, `delete-account` → `require_password_set()` 400. ✓
- **Identity uniqueness:** `(provider, subject_id)` UNIQUE and `(user_id, provider)` UNIQUE enforced at DB level on both backends. ✓
- **Hooks:** `oauth_signin_started`, `oauth_signin_completed`, `oauth_account_linked`, `oauth_account_unlinked` present in `KNOWN_EVENTS` and fired at the correct points. ✓
