## 🟠 WARNING (Address within 1 week)

### W-1 · `cryptography` floor misses CVE-2026-69247 (Bleichenbacher oracle in PKCS7 decrypt)

**Section:** §1 — Dependency Vulnerability Check  
**File:** `pyproject.toml` line 108 (oauth extra)  
**New finding**

`cryptography` 50.0.0 was released 2026-07-31 and contains a security fix for
CVE-2026-69247: `pkcs7_decrypt_der` and its PEM/S/MIME variants previously
exposed distinguishable errors or timing on `RecipientInfo.encryptedKey`
unwrapping, acting as a Bleichenbacher oracle for callers that decrypt untrusted
messages.

regstack itself does not call PKCS7 decrypt — it uses `cryptography` only for
JWKS-backed JWT signature verification via `pyjwt[crypto]`. However, the
published `oauth` extra declares `cryptography>=48.0.1` (unchanged since the
2026-06-20 CVE cluster was closed), so:

1. `pip install regstack[oauth]` resolves to 49.0.0 in the current lockfile —
   missing the 50.0.0 fix.
2. Any host that uses `cryptography` for PKCS7 operations in the same
   environment inherits the exposure.
3. A consumer who audits their transitive dependency set will find a version
   with an open advisory in their `pip show cryptography` output.

**Recommended fix:** raise the floor in the `oauth` extra (and the
`dev` extras) from `>=48.0.1` to `>=50.0.0` and run `uv lock`.

## 🟡 INFO (Best practice recommendations)

### I-1 · `UserPublic` exposes `tokens_invalidated_after` — acknowledged intentional design

**Section:** §9 — Data Exposure  
**File:** `src/regstack/models/user.py`  
**Carry-over from:** 2026-08-10 (and prior reviews)

`UserPublic.tokens_invalidated_after` is included in API responses. The code
carries an inline docstring explaining this is intentional: SPAs can compare this
field to their session JWT's `iat` to detect server-side revocation without an
extra round-trip. The field reveals when a password or email change occurred,
which is low-sensitivity metadata. No action recommended unless future privacy
requirements tighten.

### I-2 · CLI `cmd:` log-source variant passes operator input to shell

**Section:** §5 — Input Validation & Injection  
**File:** `src/regstack/cli/validate/logtail.py`  
**Carry-over from:** 2026-08-10

The `regstack validate --log-source cmd:<command>` path passes the
user-supplied value via `["sh", "-c", target]`. This is an operator-facing tool
explicitly documented as accepting arbitrary shell commands, running only on
operator workstations under the operator's own credentials. No HTTP endpoint can
reach this code path. Noting for awareness; the design is intentional. If ever
exposed to untrusted input, the `cmd:` variant must be removed or sandboxed.

### I-3 · PyJWT floor sits exactly at minimum CVE-fixed version

**Section:** §1 — Dependency Vulnerability Check  
**File:** `pyproject.toml` line 55  
**Carry-over from:** 2026-08-10

The floor `pyjwt >= 2.13.0` is the exact version that fixes the June-2026 PyJWT
cluster (CVE-2026-48522 through CVE-2026-48526). PyJWT 2.13.0 (released
2026-05-21) remains the latest upstream release as of this review — no 2.14.x
exists yet. This is a low-headroom carryover: the moment a new PyJWT advisory
is published, the current floor will be under it. Continue monitoring; raise
as soon as upstream releases a higher version.

### §7 — Session & Token Security

- **HS256 by default**, secret read from `config.jwt_secret`, minimum 32 chars
  enforced at `JwtCodec` construction.
- **`iat` emitted as `float`** (`self.iat.timestamp()` at `jwt.py:69`), not
  `int`. The bulk-revoke comparison `iat <= cutoff` is safe.
- **pyjwt's `exp`/`iat` checks disabled** (`"verify_exp": False,
  "verify_iat": False`); both are re-validated against the injected `Clock`
  at decode time.
- **Every JWT includes `jti`** — required claim enforced via
  `"require": ["sub", "exp", "iat", "jti", "purpose"]`.
- **`_authenticate` flow** (verified at `auth/dependencies.py:146`):
  1. Validates Bearer scheme → 401
  2. `jwt.decode()` → generic `"Invalid or expired token."` 401 on any
     `TokenError` (internal reason never echoed)
  3. `blacklist.is_revoked(jti)` → 401 if revoked
  4. `users.get_by_id(sub)` + `is_active` check → 401
  5. `is_payload_bulk_revoked(payload, user.tokens_invalidated_after)` → 401
- **Per-purpose key derivation:** `derive_secret(jwt_secret, purpose)` uses
  HMAC-SHA256 (`hmac.new(master, purpose.encode(), sha256).digest()`).
  Compromise of one derived key cannot compromise the master or other purposes.
- **No token logging:** `log.warning` calls on OAuth token-exchange errors log
  only the exception string from `OAuthTokenExchangeError` (the provider's
  error body, not the token). No `access_token` or `id_token` values appear
  in any log call.
