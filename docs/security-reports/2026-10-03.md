## Section 3 — Authentication and Authorization

### 🟠 W-2 · Email-change token not jti-blacklisted · day 33 (SLA expired +26 d)

**File:** `src/regstack/routers/account.py`

`POST /change-email` mints a JWT (purpose `email_change`) and sends it to the new address. On `POST /confirm-email-change`, the token is verified and the email is updated — but the consumed token is never inserted into `BlacklistRepo`. A copy of the link remains clickable until the token's TTL expires. The `tokens_invalidated_after` bump on `update_email` does not help here: that revokes session tokens, not the purpose-derived email-change token.

**Fix:** call `blacklist.add(jti, exp)` after successfully consuming the token in `confirm-email-change`.

---

### 🟠 W-3 · Email-change confirm skips bulk-revoke check · day 33 (SLA expired +26 d)

**File:** `src/regstack/routers/account.py`

`POST /confirm-email-change` decodes the `email_change` JWT and uses `is_payload_bulk_revoked` only for session tokens in `_authenticate`. If an admin disables the user between `POST /change-email` and the confirm click, the confirm endpoint does not reject the request: it has no call to `users.get_by_id` + `is_active` check before committing the email update.

**Fix:** fetch the user from the DB at the start of `confirm-email-change` and reject if `not user.is_active`.

---

### 🟠 W-4 · OAuth new-user concurrent registration race → unhandled 500 · day 33 (SLA expired +26 d)

**File:** `src/regstack/routers/oauth.py` — `_resolve_user`

When two OAuth callbacks for the same new identity arrive within milliseconds of each other (edge case but possible under retry storms), both pass the "identity not found" check and both attempt `users.create`. The second `users.create` raises `UserAlreadyExistsError` which propagates as an unhandled 500.

**Fix:** wrap the `users.create` call in a try/except for `UserAlreadyExistsError`; on conflict, re-fetch the user that won the race and return them.

---

### 🟠 W-8 · Timing oracle on login for OAuth-only accounts · day 15 (SLA expired +8 d)

**File:** `src/regstack/routers/login.py`

When `user.hashed_password is None` (OAuth-only account), `rs.password_hasher.verify` is short-circuited entirely (lines 99–103). A probing attacker can distinguish OAuth-only accounts from non-existent accounts by the response latency: non-existent hits the `user is None` branch (fast), while OAuth-only reaches the hash branch but bypasses Argon2 (faster than a full Argon2 verify on a real hash). Attacker learns which email addresses are registered and whether they use OAuth.

**Fix:** run a dummy `rs.password_hasher.verify(payload.password, dummy_hash)` even when `hashed_password is None`, so all failure paths take Argon2 time.

## Section 9 — Data Exposure

### 🟡 I-1 · `tokens_invalidated_after` in `UserPublic` · day 54

**File:** `src/regstack/models/user.py`

`UserPublic.from_user` serialises `tokens_invalidated_after` (a timestamp). Returning this timestamp to an API consumer reveals the exact moment of the last password-change / admin-disable event. This is an internal field that has no UI purpose.

**Recommendation:** exclude `tokens_invalidated_after` from `UserPublic` in a future minor version. No code-change urgency since the field is not a secret on its own; combined with other information it narrows timing windows.

### 🟡 I-3 · `last_login` internal field in `UserPublic` · day 54

**File:** `src/regstack/models/user.py`

`UserPublic` exposes `last_login`. For non-admin callers (`GET /me`) this is the user's own field, which is acceptable. When returned by admin endpoints it reveals login timing to administrators — generally fine, but worth an explicit product decision.

**Recommendation:** document the intended visibility policy in the `UserPublic` docstring.

### 🟠 W-9 · SNS credentials not `SecretStr` in `SmsConfig` · day 15 (SLA expired +8 d)

### 🟠 W-10 · `GoogleOAuthProvider` holds `client_secret` as plain `str` · day 15 (SLA expired +8 d)

**File:** `src/regstack/oauth/providers/google.py` lines 79, 89

`GoogleProvider.__init__` accepts `client_secret: str` and stores it as `self._client_secret: str`. The `RegStack.__init__` unwraps from `SecretStr` via `.get_secret_value()` before passing it in (`app.py`), so the `SecretStr` protection is lost at the provider boundary. The value is visible in `repr(provider)` and any serialisation of the object.

**Fix:** accept `SecretStr | str`, store as `SecretStr`, call `.get_secret_value()` only in `exchange_code`.

## Section 14 — OAuth Subsystem

### 🟢 CLEAN (flow integrity)

PKCE enforced (S256): `code_verifier` stored server-side in the state row only; `code_challenge` sent to provider. `oauth_states.consume` uses `find_one_and_delete` (atomic) on MongoDB. Nonce verified before and after decode in `google.py`. JWKS fetch offloaded to `asyncio.to_thread` with 5 s timeout to avoid thread-pool exhaustion. ID token checks: RS256, `aud=client_id`, `iss=GOOGLE_ISSUER`, required claims `[sub, iss, aud, exp, iat, nonce]`. Redirect validated by `_validate_redirect` before any DB write. Errors redirect to `?error=<short_code>` — no raw provider error surfaced.

### 🟠 W-6 · SQL `OAuthStateRepo.consume` non-atomic under READ COMMITTED · day 25 (SLA expired +18 d)

**File:** `src/regstack/backends/sql/repositories/oauth_state_repo.py`

The SQL implementation of `consume()` executes SELECT followed by DELETE in a single `engine.begin()` transaction. Under READ COMMITTED isolation (the default for PostgreSQL and SQLite WAL mode), a second concurrent request carrying the same `state` token can read the row before the first transaction's DELETE commits. Both requests pass the state-exists check and both proceed — defeating the one-shot guarantee. MongoDB's `find_one_and_delete` is inherently atomic; the SQL path is not.

**Fix:** use `DELETE … RETURNING *` (PostgreSQL) or `SELECT … FOR UPDATE` followed by `DELETE` under SERIALIZABLE isolation to achieve the same atomicity.
