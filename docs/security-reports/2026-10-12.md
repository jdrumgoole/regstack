## Section 3 — Authentication and Authorization

### 🟠 W-2 · Email-change token not jti-blacklisted · day 42 (SLA expired +35 d)

Unchanged. `POST /confirm-email-change` (`src/regstack/routers/account.py:177`) decodes the email-change JWT, extracts `jti` from claims, but never calls `blacklist.is_revoked(jti)` before processing nor `blacklist.revoke(jti, exp)` after success. A valid email-change link can be replayed until its TTL expires (default 1 h). Confirmed: no `is_revoked` or `blacklist.revoke` calls visible in the account router for the email-change confirmation path.

**Fix:** return `jti` and `exp` from `_decode_email_change_token`, check `await rs.blacklist.is_revoked(jti)` before proceeding, call `await rs.blacklist.revoke(jti, exp)` on success.

### 🟠 W-4 · OAuth new-user concurrent registration race → unhandled 500 · day 42 (SLA expired +35 d)

Unchanged. Concurrent OAuth sign-ins for a new email address can both pass the `find_by_subject` check, both attempt `users.create`, and one raises an unhandled `UserAlreadyExistsError`. The callback redirects to `?error=oauth_error` (generic 500 path) instead of the expected `?error=email_in_use` or a clean session token for the winner. Catching `UserAlreadyExistsError` in `_resolve_user` and re-trying with `find_by_subject` would close the window.

### 🟠 W-8 · Timing oracle on login for OAuth-only accounts · day 24 (SLA expired +17 d)

Unchanged. `hashed_password is None` short-circuits `pwdlib`'s `verify()` call with a direct `return False` via `or`-short-circuit evaluation (`src/regstack/routers/login.py:99`). An attacker can statistically distinguish OAuth-only from password-having accounts by measuring login response time (no Argon2 work = faster 401). Confirmed present in code check today.

**Fix:** perform a dummy `pwdlib.verify()` call against a pre-hashed sentinel value before returning the 401 when `hashed_password is None`.

### 🟠 W-10 · `GoogleProvider` client_secret in plain string at construction · day 24 (SLA expired +17 d)

## Section 14 — OAuth Subsystem Audit

### 🟠 W-6 · SQL `OAuthStateRepo.consume` non-atomic under READ COMMITTED · day 34 (SLA expired +27 d)

Unchanged. `src/regstack/backends/sql/repositories/oauth_state_repo.py:63` wraps SELECT + DELETE in `engine.begin()` (one transaction), but PostgreSQL's default READ COMMITTED isolation means a concurrent request can read the same row between the SELECT and DELETE, allowing two `/oauth/exchange` calls with the same state ID to both return a session token. Mongo is safe (`find_one_and_delete` is atomic). SQL fix requires `SELECT … FOR UPDATE` on the SELECT or a `DELETE … RETURNING` for true atomicity.

### 🟡 I-8 · `mfa_confirm` does not re-check `is_verified` · day 9

Carry-forward. `POST /login/mfa-confirm` and `POST /phone/confirm` do not re-check `user.is_verified`. Not currently exploitable (a user can't receive an SMS code without a valid phone number attached, and phone setup requires an authenticated session), but defence-in-depth recommendation.

### 🟢 CLEAN (flow integrity)

PKCE: `code_verifier` stored on `oauth_states` row only; only `code_challenge` (SHA-256 of verifier) sent to provider. State row lifecycle: missing row → `?error=bad_state`; expired row → `?error=state_expired` using `rs.clock.now()` (not `datetime.now(UTC)`). Mongo consume: `find_one_and_delete` (atomic). ID-token verification: signature via `PyJWKClient` against Google JWKS, `iss`/`aud`/`exp`/`nonce` all checked; outer error is generic redirect. Linking policy: email-in-use / identity-in-use / already-linked enforced. OAuth-only user side-effects: same generic 401 on password login, 400 on change-password/change-email/delete-account. Identity uniqueness at DB level (`(provider, subject_id)` and `(user_id, provider)`). Hooks firing correctly. No changes.
