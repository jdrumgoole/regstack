### W-1 (carry-over, day 22 — SLA MISSED 2026-08-18)

**Section:** §1 — Dependency Vulnerability Check
**CVE:** CVE-2026-69247 — `cryptography` Bleichenbacher oracle (`pkcs7_decrypt`)
**Affected range:** `cryptography` ≥ 44.0.0, < 50.0.0
**Resolved in:** `cryptography==50.0.0` (released 2026-07-31 — 32 days ago)
**Current resolved version in `uv.lock`:** 49.0.0 (within affected range)
**Current floor in `pyproject.toml`:** `cryptography>=48.0.1` (does not exclude affected versions)
**Fix required:** Bump floor to `cryptography>=50.0.0` in both the `oauth` and `dev` extras in `pyproject.toml`; run `uv lock`.
**Tracking:** GitHub issue #181 (`[security] Raise cryptography floor to >=50.0.0`), open since 2026-08-19 — no fix PR, no assignee, no comment — 14 days unacknowledged.

**Technical impact:** `pkcs7_decrypt_der`, `pkcs7_decrypt_pem`, and `pkcs7_decrypt_smime` expose distinguishable error paths and timing differences during RSA `RecipientInfo.encryptedKey` decryption, constituting a Bleichenbacher-style oracle. regstack does not call these functions directly, but `pip install regstack[oauth]` resolves to 49.0.0 by default, shipping a version with an open advisory to all downstream consumers. The fix (cryptography 50.0.0+) substitutes a random key on RSA decryption failure per RFC 3218.

**Urgency:** The fix version has been on PyPI for 32 days. The 7-day SLA lapsed 2026-08-18. This finding will appear daily until resolved.

### W-2 (NEW) — `POST /confirm-email-change` email-change JWT not revoked after use

**Section:** §3 — Authentication & Authorization Audit
**File:** `src/regstack/routers/account.py`, `confirm_email_change` handler
**Severity rationale:** The password-reset path (`password.py` line 123) explicitly calls `await rs.blacklist.revoke(token_payload.jti, token_payload.exp)` after a successful reset. The email-change confirm path performs no equivalent revocation. Within the token's TTL (default short, but configurable), the same confirmation URL can be submitted more than once.

**Scenario:** User A initiates an email-change to `new@example.com`. An attacker who has access to A's inbox (or intercepts the link) bookmarks the confirmation URL. A completes the change on first click. Attacker clicks again within TTL — the second submission reaches `update_email`, which will raise a DB-level conflict (duplicate email) only if another user has taken the address in the interim. In the normal case where the address is now A's own, the update is a no-op at the DB level but the endpoint returns HTTP 200, confirming the link still works.

**Fix:** Add `await rs.blacklist.revoke(token_payload.jti, token_payload.exp)` immediately after the successful `update_email` call, matching the pattern in `password.py`.

### W-3 (NEW) — `POST /confirm-email-change` bulk-revoke not applied to email-change tokens

**Section:** §3 — Authentication & Authorization Audit
**File:** `src/regstack/routers/account.py`, `confirm_email_change` handler
**Severity rationale:** `AuthDependencies._authenticate` calls `is_payload_bulk_revoked(payload, user.tokens_invalidated_after)` for session tokens. The `confirm_email_change` endpoint decodes the email-change JWT and calls `get_by_id` + `update_email` with no equivalent temporal cutoff check. The purpose-derived key correctly prevents session tokens from satisfying this endpoint, but a stale email-change token minted before a password-change event can still be used after `tokens_invalidated_after` has been bumped.

**Attack scenario:**
1. User initiates email-change → token minted at `iat=T1`, link emailed.
2. User detects compromise of email account, changes password → `tokens_invalidated_after` bumped to `T2 > T1`.
3. Attacker (who has inbox access) clicks the email-change link minted at `T1` → `confirm_email_change` succeeds because `T1 < T2` is never evaluated.
4. Attacker now controls the user's email address.

**Fix:** After decoding the email-change JWT in `confirm_email_change`, fetch the user record and check `if rs.auth.is_payload_bulk_revoked(token_payload, user.tokens_invalidated_after): raise HTTPException(400, "Email-change link is invalid or has expired.")`. The pattern mirrors the `_authenticate` dependency.

### W-4 (NEW) — OAuth `_resolve_user` unhandled `UserAlreadyExistsError` → HTTP 500

**Section:** §3 / §14 — Authentication & Authorization / OAuth Subsystem
**File:** `src/regstack/routers/oauth.py`, `_resolve_user` (line ~716), `oauth_callback` (line ~325)
**Severity rationale:** A race between a concurrent email registration and the OAuth sign-in flow creates an unhandled exception path that returns HTTP 500 to the user's browser, potentially exposing a stack trace depending on `debug` mode.

**Scenario:**
1. User clicks "Sign in with Google" with `email@example.com`.
2. `_resolve_user` calls `get_by_email("email@example.com")` → returns `None`.
3. Concurrently, another request completes `POST /register` with the same email.
4. `_resolve_user` calls `rs.users.create(new_user)` → raises `UserAlreadyExistsError`.
5. `oauth_callback` catches only `_LinkConflictError`; `UserAlreadyExistsError` propagates as HTTP 500.

**Fix:** In `_resolve_user`, wrap `rs.users.create(new_user)` in a `try/except UserAlreadyExistsError` and re-raise as `_LinkConflictError("email_in_use")`. This is consistent with how the auto-link policy already handles the known-email case.

### I-5 (NEW) — SNS backend uses ambient boto3 credential chain; no explicit credential config

**File:** `src/regstack/sms/sns.py`, line 29; `src/regstack/config/schema.py`
`aioboto3.Session()` is constructed with no credentials — always falls back to boto3's ambient chain (env vars, IAM instance profile). The `SmsConfig` model has no `sns_access_key_id` / `sns_secret_access_key` fields, unlike the SES email backend which offers explicit key configuration. Hosts cannot supply explicit SNS credentials via `regstack.toml`; they must rely on ambient IAM roles. This asymmetry with the SES backend should be documented in the operator guide and optionally addressed by adding explicit SNS credential config fields.

### I-6 (NEW) — GoogleProvider stores `client_secret` as plain `str` in-memory

**File:** `src/regstack/oauth/providers/google.py`, lines 79, 90
`OAuthConfig.google_client_secret` is correctly declared as `SecretStr | None` in `config/schema.py`. However, `GoogleProvider.__init__` takes `client_secret: str` (already extracted via `.get_secret_value()`) and stores it as `self._client_secret: str`. Once extracted from `SecretStr`, Pydantic's repr-masking is lost. No existing log call exposes the value — `exchange_code()` logs only the HTTP status code on error — but the protection now relies on code discipline rather than type enforcement. If a traceback or debug inspector serialises the `GoogleProvider` instance, the raw secret would appear.

Recommendation: Keep the `SecretStr` type through to storage (`self._client_secret: SecretStr`) and call `.get_secret_value()` only at the token-exchange call site.

### I-7 (NEW) — OAuth state expiry uses strict `<` (less-than); other token types use `<=`

**File:** `src/regstack/routers/oauth.py`, lines 302, 157
`oauth_callback` and `exchange` check `if state_row.expires_at < rs.clock.now()`. Pending registration expiry (`verify.py` line 46) uses `<=`; JWT expiry in `JwtCodec.decode` uses `>=` (equivalent to `exp <= now`). A state row whose `expires_at` is exactly `rs.clock.now()` passes in the OAuth path but would be rejected by the other two mechanisms. The difference is submicrosecond and practically unreachable, but the inconsistency should be unified to `<=` to match the conservative posture used elsewhere.

### I-8 (NEW) — TOML injection risk in `cli/init.py` `_render_toml()`

**File:** `src/regstack/cli/init.py`, `_render_toml()` function
User-supplied strings (app_name, base_url, from_address, smtp_host, etc.) are embedded into a TOML file via Python f-strings without escaping TOML-special characters. A value containing `"` followed by a newline and a valid TOML key could produce unexpected config keys. Exploitability is nil in interactive use (the attacker controls their own wizard and their own config file), but if the wizard is ever invoked non-interactively with environment-controlled defaults, corrupt TOML output is possible. Recommendation: use `tomlkit` to construct the output document programmatically rather than via f-string templating.

### I-9 (NEW) — Provider name echoed in JSON 404 from public `GET /oauth/{provider_name}/start`

**File:** `src/regstack/routers/oauth.py`, line 510
`detail=f"OAuth provider {name!r} is not configured."` is returned as a JSON 404 body from an unauthenticated endpoint. An unauthenticated caller can probe to confirm which provider names are not configured. Negligible in practice (configured providers are listed on the public login page), but the detail string could be trimmed to a generic message for consistency with the anti-enumeration posture elsewhere.

### I-12 (NEW) — Mongo `make_client(tz_aware=True)` not confirmed from audited files

**File:** `src/regstack/backends/mongo/client.py` (not directly read in this audit)
CLAUDE.md asserts `make_client` constructs `AsyncMongoClient(..., tz_aware=True)`. This is required for the bulk-revoke comparison to work correctly (`iat < tokens_invalidated_after` would raise `TypeError` on tz-naive datetimes). The SQL `UtcDateTime` TypeDecorator was confirmed clean in this audit; the Mongo equivalent (`tz_aware=True`) was not directly verified. Recommend a one-time manual check of `src/regstack/backends/mongo/client.py` and adding a CI assertion if not already present.

### I-13 (NEW) — Google token-exchange error response body logged at DEBUG level

**File:** `src/regstack/oauth/providers/google.py`, lines 163–167
On non-200 responses from Google's token endpoint, the full response body is logged at DEBUG. On 200 responses (which contain `access_token` and `id_token`), only the status code is logged. Google's error response bodies contain only `error` codes and descriptions — no live tokens — so no credential leakage is confirmed. However, if Google's error format ever changes to include partial token data, this log line would capture it. Recommendation: log only `response.status_code` on error and drop the body from the log call.

## 🟢 CLEAN

The following areas were reviewed and found to be secure:

- **§2 Hardcoded Secrets:** No API keys, private key material, live JWTs, credential-bearing connection strings, or sensitive files found in `src/`, `tests/`, `examples/`, `docs/`. `.gitignore` correctly covers all secret file patterns. Example TOML configs contain no real credentials.
- **§4 Storage-layer Injection:** Both MongoDB and SQL backends use fully parameterised queries. No unsafe Mongo operators (`$where`, `$expr`, `$function`, `$accumulator`). No regex from user input. All `ObjectId` coercions guarded by `is_valid()`. All SQL `purge_expired()` implementations use bound parameters.
- **§5 Input Validation (core):** Every API endpoint accepts a typed Pydantic model. `EmailStr` used on all email fields. E.164 validation on all phone inputs. Jinja2 autoescape enabled for HTML in both email and SSR environments.
- **§6 Rate Limiting:** `LockoutService.check()` runs before any password comparison. `record_failure` increments on every failure path. Admin list endpoint caps `limit` at 200 via `Query(le=200)`. OAuth state TTL wired on both Mongo and SQL backends.
- **§7 Session & Token Security (core):** JWT secret length enforced at construction (≥ 32 chars). Every JWT includes `jti`. `iat` emitted as `float` (microsecond precision) per CLAUDE.md requirement. `pyjwt` `exp`/`iat` validation disabled; Clock-based validation used. `_authenticate` revocation order is correct and complete.
- **§8 CSP & SSR Layer:** No `<style>` blocks or `style=` attributes in any SSR template. No inline `<script>` tags — only `<script src defer>` in `base.html`. `oauth_complete.html` follows the same discipline. SSR pages are stateless.
- **§9 Data Exposure (core):** All user-returning endpoints use `UserPublic.from_user()`. Database driver errors produce generic HTTP 500 messages. JWT decode errors produce generic 401 messages. OAuth callback failures redirect with short error codes. No log calls expose JWT secret, OAuth client_secret, or SMTP password.
- **§11 Third-party Integrations (core):** SMTP `smtp_password` as `SecretStr`, accessed only at send time. SES explicit credentials as `SecretStr`. Twilio `auth_token` as `SecretStr`. Google JWKS lookup has a 5-second timeout, offloaded to `asyncio.to_thread`. ID-token verification validates signature, `iss`, `aud`, `exp`, `iat`, and nonce.
- **§12 GitHub Actions:** All `uses:` directives SHA-pinned. No `${{ github.event.* }}` in `run:` blocks. `permissions: contents: read` at workflow level; `id-token: write` scoped to the publish job only. No `pull_request_target`. No self-hosted runners. No `PYPI_API_TOKEN` — OIDC trusted publishing. No cache keys on user-controlled input.
- **§13 PyPI Package Integrity:** Wheel contains only `src/regstack/` — no tests, docs, examples, or dev files. All base dependencies have lower bounds. Optional extras (`pymongo`, `asyncpg`, `aioboto3`, `twilio`, `pyjwt[crypto]`) correctly in `[optional-dependencies]` only. Version check reads `pyproject.toml` via `tomllib`, not by importing the package. Sigstore attestations enabled (`attestations: true`).
- **§14 OAuth Subsystem (core):** PKCE `code_verifier` stored server-side only; `code_challenge` sent to provider. State row lifecycle correct: missing → `bad_state`, expired → `state_expired`, expiry uses `rs.clock.now()`. Post-callback `consume` is atomic. Linking-policy enforcement for `email_in_use`, `identity_in_use`, `already_linked` all correct. Last-sign-in-method guard on unlink. Identity uniqueness `(provider, subject_id)` and `(user_id, provider)` enforced. `redirect_to` validated same-origin.
- **§15 Multi-backend Parity (core):** CI matrix exercises SQLite, Postgres, MongoDB, and SecantusDB. All three SQL migrations have working `upgrade()` and `downgrade()`; column alterations use `batch_alter_table`. Mongo unique indexes match SQL `UniqueConstraint` entries for `email`, `(provider, subject_id)`, and `(user_id, provider)`. `UtcDateTime` TypeDecorator used on all datetime columns in SQL schema and migrations.
- **§3 Auth & Authorization (core):** All authenticated endpoints correctly inject `current_user()` or `current_admin()`. `UserPublic.from_user()` used on every user-returning endpoint. OAuth-only users (`hashed_password=None`) handled correctly at login (same generic 401), `change-password`, `change-email`, `delete-account` (400 with forgot-password pointer). Constant-time comparison via `pwdlib`. JWT keys derived per-purpose via `derive_secret`. Bulk-revoke discipline met for password reset, password change, admin disable, and account deletion cascade. **Exception: email-change confirm (W-2, W-3 above).**
