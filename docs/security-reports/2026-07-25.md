## 🟡 INFO (Best practice recommendations)

Nine carry-forward items (I-1, I-2, I-5–I-11) remain open, unchanged. One new
INFO item (I-12) added.

### I-1 (carry-forward) — `UserPublic` exposes `tokens_invalidated_after`

`UserPublic` includes `tokens_invalidated_after: datetime | None`
(`src/regstack/models/user.py:105`). This is an intentional design choice
(SPAs compare it to the session JWT `iat` to detect bulk-revocation without
an extra round-trip). The exposure leaks the exact timestamp of the most
recent security event (password change, email change, admin-disable) to any
authenticated client. Acceptable for regstack defaults; hosts with stricter
data-minimisation requirements should subclass `UserPublic` or project out
the field. Recommend documenting the trade-off explicitly in `docs/security.md`.

### I-2 (carry-forward) — `admin_promote_pending` path parameter not validated as `EmailStr`

`POST /admin/pending/{email}/promote` (`src/regstack/routers/admin.py:204`)
accepts `email: str = Path(...)`. A syntactically invalid email address passes
parameter binding and returns 404. The endpoint is admin-gated so risk is low.
One-line fix: `email: Annotated[EmailStr, Path(...)]`.

### I-5 (carry-forward) — Email-change token JTI not blacklisted on first use

**File:** `src/regstack/routers/account.py:175` (`confirm_email_change`)

`POST /confirm-email-change` does not blacklist the token's `jti` after
successfully completing the email swap. The password-reset handler blacklists
its token's `jti` at `src/regstack/routers/password.py:71`. The email-change
token has a 1-hour TTL (default). An attacker who captures the URL from
browser history, proxy logs, or email forwarding can replay it within that
window; `update_email()` accepts the second call silently (same user, same
email — no constraint violation) and bumps `tokens_invalidated_after`, forcing
the user to re-authenticate.

The practical impact is low: no email hijacking is possible (the target address
is already set), but the attacker can cause repeated forced re-logins until
token expiry. Fix: call `await rs.blacklist.revoke(jti, exp)` after
`update_email()` succeeds, matching the reset-password pattern.

### I-6 (carry-forward) — "X attempt(s) remaining" count in 401 response body

**File:** `src/regstack/routers/login.py:42`

`_build_invalid()` includes the remaining failure count in the 401 detail
message: `f"Invalid email or password. {remaining} attempt(s) remaining."`.
This tells a credential-stuffing attacker exactly when to pause to avoid
lockout, enabling systematic pacing of brute-force attempts to stay under the
threshold indefinitely. Recommendation: return a static
`"Invalid email or password."` message regardless of remaining attempts.

### I-7 (carry-forward) — `jwt_audience` defaults to `None`; no multi-instance deployment guidance

**File:** `src/regstack/config/schema.py:189`

With `jwt_audience = None`, pyjwt skips audience validation on decode. If two
regstack instances share the same `jwt_secret` (a microservice topology where
one JWT secret is shared across services), a session token issued by instance A
would be accepted by instance B. No audience guidance appears in
`docs/configuration.md` or the examples. Recommendation: add a configuration
note advising hosts to set `jwt_audience` to a service-unique string in any
deployment where multiple regstack instances share a `jwt_secret`.

### I-8 (carry-forward) — No HTTP security headers set or demonstrated

**Scope:** SSR pages served by `ui_router`

regstack does not set `Content-Security-Policy`, `X-Frame-Options`,
`X-Content-Type-Options`, or `Referrer-Policy` headers. This is expected for
an embedded library — host middleware owns the response headers. However,
neither the `examples/` demos nor `docs/embedding.md` show a recommended
middleware stack for hosts that enable `ui_router`. Recommendation: add a
"Security hardening" section to the embedding guide showing a simple
security-headers middleware configured for the regstack SSR prefix.

### I-9 (carry-forward) — `twilio_account_sid` typed as `str | None` rather than `SecretStr`

**File:** `src/regstack/config/schema.py:98`

Every other credential field in `RegStackConfig` is `SecretStr | None`:
`smtp_password`, `ses_access_key_id`, `ses_secret_access_key`,
`twilio_auth_token`, `google_client_secret`. The Twilio Account SID
(`AC…`) is typed as plain `str`, which means it will appear unmasked in
`repr()` output, Pydantic model dumps, and exception tracebacks. One-line fix:
change to `SecretStr | None` and update the access site to `.get_secret_value()`.

### I-10 (carry-forward) — `GoogleProvider._client_secret` held as plain `str` in memory

**File:** `src/regstack/oauth/providers/google.py:88`

`GoogleProvider.__init__` receives `client_secret: str` and stores it as
`self._client_secret: str`. Once extracted from `SecretStr` at construction
in `app.py`, there is no in-memory masking. A crash dump or `__repr__` of the
provider object would include the secret in plain text. Adding a `__repr__`
override returning `GoogleProvider(client_id=..., client_secret=***)` provides
defense-in-depth against accidental log exposure.

### I-11 (carry-forward) — Lockout is per-email only; no per-IP protection

**File:** `src/regstack/auth/lockout.py`

`lockout.record_failure(email, ip=None)` — the `ip` argument is always `None`
in the login router (`src/regstack/routers/login.py:88, 102, 110, 116`). An
attacker with a list of target email addresses can distribute guesses across
accounts, advancing each account's lockout counter slowly while making
effectively unlimited aggregate attempts. Recommendation: document this gap in
`docs/security.md` and add a configuration guidance note in
`docs/embedding.md` recommending proxy-layer IP rate limiting as a complement
to the per-account lockout.

### I-12 (new) — `JwtCodec` does not enforce ≥32-char minimum on `jwt_secret`

**Files:** `src/regstack/auth/jwt.py` (constructor), `src/regstack/config/schema.py:85`,
`src/regstack/app.py` (`RegStack.__init__`)

The 2026-07-24 report's §7 stated "jwt_secret enforced ≥32 chars at
construction" — this is inaccurate. The actual code only rejects an empty
string. In `JwtCodec.__init__`, the guard is `if not jwt_secret: raise
ValueError(...)`. The `RegStackConfig` validator carries a comment:
"Validation that *requires* it lives at the RegStack façade boundary so test
fixtures can opt out" — but `RegStack.__init__` (in `app.py`) does not
enforce a minimum length either.

A `jwt_secret` of 1–31 characters is accepted silently. For HS256, NIST SP
800-117 recommends the key to be at least as long as the hash output (32
bytes). A short secret substantially reduces the brute-force cost of a
signature forgery attack. Recommendation: enforce `len(secret) >= 32` in
`JwtCodec.__init__` (or at the `RegStack` façade) and document an
escape-hatch path for tests (e.g., a `_skip_secret_validation` kwarg, or
accept any non-empty secret when the `jwt_algorithm` is set to a test-only
value). The current test fixture pattern passes a generated
`secrets.token_urlsafe(64)` secret, so the fix would not break the test
suite.
