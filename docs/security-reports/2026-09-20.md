## 2 — Secrets and credential handling

### 🟠 W-10 (carry-forward, day 2, SLA expires 2026-09-25) — `GoogleProvider.__init__` accepts `client_secret: str`

- **Issue:** [#219](https://github.com/jdrumgoole/regstack/issues/219)
- **File:** `src/regstack/oauth/providers/google.py`
- **Detail:** `client_secret` parameter is typed `str`, not `SecretStr`. The value
  is thus included in `repr()`/`str()` output and in structured logging if the
  provider object is ever logged, potentially leaking the OAuth client secret.
- **Remediation:** Change the parameter type to `SecretStr` and call `.get_secret_value()`
  when passing to the HTTP request. Audit any `__repr__` that includes `client_secret`.

`git log --all -p | grep -iE "(secret|password|token|key)\s*=" — no
plaintext credentials in history. Config loading uses `SecretStr` for
`jwt_secret`. The `regstack init` wizard writes secrets to
`regstack.secrets.env` (gitignored) and never to `regstack.toml`.

## 3 — Authentication and authorisation

### 🟠 W-2 (carry-forward, day 20, **13 days past SLA**) — Email-change JWT `jti` never blacklisted after use

- **Issue:** [#197](https://github.com/jdrumgoole/regstack/issues/197)
- **File:** `src/regstack/routers/account.py`, `confirm_email_change`
- **Detail:** `_decode_email_change_token` validates and decodes the JWT but the
  `jti` claim is never extracted and never inserted into `BlacklistRepo`. An
  attacker who intercepts the confirmation URL can replay the token within its
  TTL window (default 30 min) and change the email address again.
- **Remediation:** Extract `jti` from the decoded payload; call
  `await rs.blacklist.add(jti, exp)` before committing the email change; return
  400 if the jti is already present.

### 🟠 W-3 (carry-forward, day 20, **13 days past SLA**) — `confirm_email_change` skips bulk-revocation check

- **Issue:** [#198](https://github.com/jdrumgoole/regstack/issues/198)
- **File:** `src/regstack/routers/account.py`, `confirm_email_change`
- **Detail:** After decoding the email-change JWT the handler does not call
  `is_payload_bulk_revoked(payload, user)`. If the user changed their password
  after requesting an email change, the old email-change link should be
  invalidated by the `tokens_invalidated_after` bump — but currently is not.
- **Remediation:** Add `if is_payload_bulk_revoked(payload, user): raise credentials_exception`
  after the user lookup, mirroring the pattern in `_authenticate`.

### 🟢 `_authenticate` order is correct

decode → `is_revoked(jti)` → user lookup / `is_active` → `is_payload_bulk_revoked`.
No bypass path identified.

### 🟢 Admin deactivation invalidates sessions

`PATCH /admin/users/{id}` with `is_active=False` calls
`set_tokens_invalidated_after(user_id, now)`. All outstanding tokens are
immediately rejected on the next request.

## 5 — Storage-layer injection (SQL)

### 🟠 W-6 (carry-forward, day 12, **5 days past SLA**) — SQL `oauth_states.consume()` not atomic

- **Issue:** [#208](https://github.com/jdrumgoole/regstack/issues/208)
- **File:** `src/regstack/backends/sql/repositories/oauth_state_repo.py`
- **Detail:** `consume()` executes `SELECT` then `DELETE` in the same transaction
  but at PostgreSQL's default `READ COMMITTED` isolation level two concurrent
  calls can both read the row before either delete commits. Both get a valid
  `OAuthState`, breaking the one-shot guarantee required for PKCE state
  validation.
- **Remediation (PostgreSQL):** Use `DELETE … RETURNING *` in a single statement,
  which is atomic under any isolation level.
  ```sql
  DELETE FROM oauth_states WHERE id = :state_id RETURNING *
  ```
  **Remediation (SQLite):** SQLite serialises writes so the current code is safe
  there, but switching to DELETE … RETURNING aligns the two backends.

### 🟢 SQLAlchemy parameterised queries throughout

No raw SQL string formatting with user input observed. All `where()` clauses
use bound parameters.

## 7 — Rate limiting and lockout

### 🟡 I-1 (carry-forward, day 41) — SQL `purge_expired()` not automatically scheduled

- **Detail:** The SQL backends accumulate stale rows in `pending_registrations`,
  `mfa_codes`, and `oauth_states` unless the host calls `purge_expired()`
  manually (MongoDB uses TTL indexes). There is no background task or
  invocation in `RegStack.__init__`. Functional impact is bounded: stale rows
  are ignored by their consumers. Storage growth is the concern.
- **Remediation (optional):** Register a FastAPI `startup` handler in
  `RegStack` that calls `purge_expired()` on SQL backends and schedules a
  periodic `asyncio` task.

### 🟢 Login lockout implemented and tested

Sliding-window `LoginAttemptRepo` with TTL index (MongoDB) / `purge_expired`
(SQL). `rate_limit_disabled` short-circuits for tests. Correct `Retry-After`
header returned on HTTP 429.

## 8 — JWT and session security

### 🟠 W-8 (carry-forward, day 2, SLA expires 2026-09-25) — Timing oracle via skipped Argon2 verify

- **Issue:** [#217](https://github.com/jdrumgoole/regstack/issues/217)
- **File:** `src/regstack/routers/login.py`
- **Affected code:**
  ```python
  if user.hashed_password is None or not rs.password_hasher.verify(
      payload.password, user.hashed_password
  ):
  ```
- **Detail:** Python's short-circuit `or` skips `password_hasher.verify()` (~100 ms)
  when `hashed_password is None` (OAuth-only accounts). An attacker timing login
  responses can distinguish OAuth-only from password-capable accounts in ~50
  attempts, leaking account-type information without a valid password.
- **Remediation:** Always run a dummy Argon2 verification when `hashed_password`
  is `None`, discarding the result:
  ```python
  if user.hashed_password is None:
      rs.password_hasher.dummy_verify()  # constant-time guard
      raise credentials_exception
  if not rs.password_hasher.verify(payload.password, user.hashed_password):
      raise credentials_exception
  ```
  Add `dummy_verify()` to `PasswordHasher` (calls `verify` against a
  pre-computed dummy hash).

### 🟢 Per-purpose key derivation

`derive_secret(master, purpose)` — HMAC-SHA256. Session tokens cannot satisfy
password-reset or email-change endpoints and vice versa.

### 🟢 Float `iat` for microsecond-precision bulk revocation

`iat` emitted as `float`; bulk-revoke check is `iat <= cutoff` (conservative).
A login completing microseconds after a password change keeps its session.

### 🟢 Per-token `jti` blacklist with TTL

`jti = secrets.token_urlsafe(16)`. MongoDB TTL index / SQL purge reaps expired
rows. Blacklist checked before user lookup to fail fast on revoked tokens.

## 12 — Third-party integrations

### 🟠 W-9 (carry-forward, day 2, SLA expires 2026-09-25) — SNS backend lacks explicit credential configuration

- **Issue:** [#218](https://github.com/jdrumgoole/regstack/issues/218)
- **File:** `src/regstack/sms/backends/sns.py`
- **Detail:** `aioboto3.Session()` is constructed with no arguments, relying
  entirely on the ambient AWS credential chain (env vars, instance metadata,
  `~/.aws/credentials`). `RegStackConfig` has no `SmsConfig` fields for
  `aws_access_key_id`, `aws_secret_access_key`, or `aws_region`. Hosts using
  SNS must configure credentials out-of-band with no regstack-level
  validation or documentation path.
- **Remediation:** Add optional `sms_sns_access_key_id`,
  `sms_sns_secret_access_key`, `sms_sns_region` fields to `RegStackConfig`
  (SecretStr for the secret key). Pass them to `aioboto3.Session()` when
  present; fall back to ambient chain when absent. Document both paths.

### 🟢 Twilio backend credential handling

`TwilioSmsBackend` accepts `account_sid` and `auth_token` from
`RegStackConfig` fields typed as `SecretStr`. Not leaked by repr.

### 🟢 PKCE implementation correct

`code_verifier` stored server-side only. `code_challenge = SHA-256(verifier)`
sent to provider. `state` is a `secrets.token_urlsafe(32)` bound to the
session. State row consumed on first use (MongoDB atomic `find_one_and_delete`;
SQL W-6 above).

## 15 — OAuth subsystem

### 🟠 W-4 (carry-forward, day 20, **13 days past SLA**) — `_resolve_user` new-user branch unguarded against `UserAlreadyExistsError`

- **Issue:** [#199](https://github.com/jdrumgoole/regstack/issues/199)
- **File:** `src/regstack/routers/oauth.py`, `_resolve_user`
- **Affected code:**
  ```python
  new_user = await rs.users.create(new_user)  # UserAlreadyExistsError not caught
  ```
- **Detail:** A race between two concurrent OAuth callbacks with the same
  provider/subject (e.g. double-click on "Sign in with Google") lets both
  calls pass the `get_by_provider_subject` check, but the second `create()`
  raises `UserAlreadyExistsError`, which propagates as HTTP 500.
- **Remediation:** Wrap in `try/except UserAlreadyExistsError` and retry the
  `get_by_provider_subject` lookup, returning the now-existing user.
