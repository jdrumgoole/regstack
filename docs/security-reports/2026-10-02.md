## Section 1 — Dependency CVEs

### 🟠 W-1 — `cryptography` floor below 50.0.1 (day 53 — **38 days past SLA**)

`pyproject.toml` declares `cryptography>=48.0.1` in `optional-dependencies.oauth` and `dev`. The minimum safe floor is **50.0.1** (released 2026-08-25). Four CVEs tracked:

- **CVE-2026-69247** (Bleichenbacher oracle on PKCS#7 RSA PKCS#1 v1.5 decryption — CVSS HIGH; fixed in 50.0.1). On the live code path for OAuth-enabled deployments.
- **CVE-2026-69248** (wildcard DNS SAN escapes `permittedSubtrees` name constraints; fixed in 49.0.0). Relevant to the JWKS certificate chain during OAuth ID-token validation.
- **CVE-2026-69249** (CVSS 8.7 HIGH; fixed in 49.0.0): Duplicate self-signed intermediates in a certificate chain cause exponential path-building recursion. 48.0.1 is likely affected; the safe floor (50.0.1) resolves it unambiguously.
- **CVE-2026-39892** (buffer overflow in Hash.update() on non-contiguous buffers; affects 45.0.0–46.0.6, fixed in 46.0.7). The current floor 48.0.1 already exceeds the affected range — listed for completeness.

**Remediation:** Bump `cryptography>=50.0.1` in `optional-dependencies.oauth` and `dev`; run `uv lock`.

### 🟠 W-12 — `pyjwt` floor below 2.15.0 — thirteen-CVE cluster (day 4 — SLA 2026-10-06, **4 days remaining**) *(floor target updated)*

`pyproject.toml` declares `pyjwt>=2.13.0` in `dependencies` (base install, every consumer) and `pyjwt[crypto]>=2.13.0` in `optional-dependencies.oauth` and `dev`. Yesterday's report set the target floor at 2.14.0. Today's search reveals **CVE-2026-103001** is fixed only in **2.15.0** (released 2026-09-23, 0 known vulnerabilities), requiring a floor bump above 2.14.0. Additionally, four CVEs from the 2.14.0 release that were not enumerated yesterday are now confirmed:

**Fixed in 2.14.0 (nine CVEs from yesterday + four new):**
- **CVE-2026-102268 (CVSS 9.1 — CRITICAL):** `is_pem_format` whitespace/line-ending mutation bypasses the HS/asymmetric confusion guard.
- **CVE-2026-102267 (CVSS 7.4 — HIGH):** `PyJWKClient` follows HTTP redirects without validation on the JWKS fetch — directly on regstack's OAuth ID-token verification code path.
- **CVE-2026-102271 (HIGH):** DER-form public keys accepted as HMAC secrets, bypassing the CVE-2022-29217 guard.
- **CVE-2026-102266 (HIGH):** Empty HMAC keys accepted as symmetric `PyJWK`, bypassing empty-key validation.
- **CVE-2026-102272 (HIGH)** *(new — not in yesterday's count)*: Algorithm downgrade via crafted header claim.
- **CVE-2026-101917 (MODERATE)** *(new)*: Leaks key-type information via error side-channel.
- **CVE-2026-101918 (MODERATE)** *(new)*: Non-canonical header values cause incorrect key selection.
- **CVE-2026-102269 (MODERATE):** Non-Base64URL characters in compact JWS segments.
- **CVE-2026-102270 (MODERATE):** ReDoS in `is_pem_format`.
- **CVE-2026-102274 (MODERATE)** *(new)*: Malformed RSA JWK aborts parsing of an entire JWK Set; targeted input can prevent signature verification of valid tokens.

**Fixed in 2.15.0 only:**
- **CVE-2026-103001 (CVSS 6.5 — MODERATE)** *(new today)*: `PyJWT.decode()` mutates the caller-supplied options dict in-place when `verify_signature` is falsy. If application code reuses the same dict across calls, a later full-verification call silently inherits leftover `verify_exp=False`, `verify_iat=False` etc., bypassing claim verification entirely. regstack creates a fresh dict literal on every `JwtCodec.decode()` call, so regstack itself is not directly affected by this specific vector — however, the deficient floor ships with every `pip install regstack` and any host that reuses a dict across `pyjwt.decode()` calls is exposed.

Because `pyjwt` is in the base `dependencies` (not optional), the deficient floor reaches **every** downstream consumer of regstack.

**Remediation:** Bump both `pyjwt>=2.15.0` (base) and `pyjwt[crypto]>=2.15.0` (oauth, dev) in `pyproject.toml`; run `uv lock`. (Previous target was `>=2.14.0`; 2.15.0 is required to resolve CVE-2026-103001.)

## Section 3 — Authentication & Authorization Audit

### 🟢 CLEAN — Endpoint authentication, bulk-revoke discipline, OAuth-only user handling, JWT purpose derivation

No code changes. All authenticated endpoints inject `rs.deps.current_user()` or `rs.deps.current_admin()`. `UserPublic.from_user()` is the only projection used in API responses; `hashed_password` is absent from `UserPublic`. Bulk-revoke discipline intact: `change-password` bumps `tokens_invalidated_after`; admin deactivation calls `set_tokens_invalidated_after(now)`; password reset calls `update_password` (which bumps `tokens_invalidated_after`) + `lockout.clear`; account deletion cascades `oauth_identities` before deleting the user; `confirm-email-change` calls `users.update_email` which also bumps `tokens_invalidated_after`. `JwtCodec` uses per-purpose derived keys, disables pyjwt's `exp`/`iat` checks, validates against the injected `Clock`, requires `jti`, and emits `iat` as float. `AuthDependencies._authenticate` pipeline verified: decode → blacklist check → user lookup + `is_active` → bulk-revoke check. Token decode errors return generic 401.

Open W-2 (email-change `jti` never blacklisted) and W-3 (email-change handler skips bulk-revocation check) remain unresolved — see carry-forward section.

## Section 14 — OAuth Subsystem Audit

### 🟢 CLEAN — PKCE invariants, ID-token verification, linking policy, identity-row uniqueness, hooks

No code changes. `_begin_flow` stores `code_verifier` on the `OAuthState` row only; only `code_challenge = base64url(sha256(code_verifier))` goes to the provider URL. State expiry checked against `rs.clock.now()`. `exchange` calls `oauth_states.consume` atomically (`find_one_and_delete` on Mongo; transaction on SQL — pending W-6). `GoogleProvider.verify_id_token` validates signature, `iss`, `aud`, `exp`, `iat`, `nonce`, `sub`. `_resolve_user` raises `_LinkConflictError` for `email_in_use`, `identity_in_use`, and `already_linked`. `(provider, subject_id)` and `(user_id, provider)` uniqueness enforced at DB level on both backends. All four OAuth hook events present in `KNOWN_EVENTS` and fired at correct points.

### 🟠 W-4 — Race condition: new OAuth user creation raises unhandled 500 (day 32 — **25 days past SLA**)

`src/regstack/routers/oauth.py` (`_resolve_user`): `await rs.users.create(new_user)` not wrapped in `try/except UserAlreadyExistsError`. Two concurrent requests with the same Google `sub` can both reach this line; the second raises an unhandled 500. **Still open. No change.**

**Remediation:** Wrap in `try/except UserAlreadyExistsError` and fall back to `rs.users.get_by_email(info.email)`.

### 🟠 W-6 — SQL `OAuthStateRepo.consume` non-atomic under READ COMMITTED (day 24 — **17 days past SLA**)

`src/regstack/backends/sql/repositories/oauth_state_repo.py`: Under PostgreSQL's default READ COMMITTED isolation level, two concurrent connections can both `SELECT` the state row before either commits the `DELETE`; both callers receive the state row and can exchange it for a session token. **Still open. No change.**

**Remediation:** Replace the SELECT + DELETE with a single `DELETE FROM oauth_states WHERE id = ? RETURNING *`, or add `with_for_update()` to the SELECT.

## Carry-forward Findings Not Separately Discussed Above

### 🟠 W-2 — Email-change token `jti` never blacklisted (day 32 — **25 days past SLA**)

`src/regstack/routers/account.py` `confirm_email_change`: after successfully decoding the email-change JWT and calling `users.update_email(...)`, the handler never calls `blacklist.revoke(jti, exp)`. A valid email-change link can be replayed until it expires (default 60-min TTL). **Still open. No change.**

**Remediation:** After `_decode_email_change_token(token)`, extract `jti`/`exp`, check `await rs.blacklist.is_revoked(jti)` → 400 if consumed, then call `await rs.blacklist.revoke(jti, exp)` on success.

### 🟠 W-3 — Email-change handler skips bulk-revocation check (day 32 — **25 days past SLA**)

`src/regstack/routers/account.py` `confirm_email_change`: after `_decode_email_change_token`, the handler fetches the user but never calls `is_payload_bulk_revoked(payload, user.tokens_invalidated_after)`. A token minted before a `change-password` event would still be accepted, allowing a stolen email-change link to change a user's email even after the user has reset their password. **Still open. No change.**

**Remediation:** After `users.get_by_id(user_id)`, add `if is_payload_bulk_revoked(payload, user.tokens_invalidated_after): raise HTTPException(400, "Expired token.")`.

### 🟠 W-8 — Timing oracle distinguishes OAuth-only accounts on login (day 14 — **7 days past SLA**)

`src/regstack/routers/login.py`: `if user.hashed_password is None or not rs.password_hasher.verify(...)` — Python short-circuit evaluation skips the Argon2 `verify()` call entirely when `hashed_password is None`. Login returns measurably faster for OAuth-only accounts, enabling timing-based enumeration. **Still open. No change.**

**Remediation:** Always call `rs.password_hasher.dummy_verify()` when `hashed_password is None` before raising the 401.
