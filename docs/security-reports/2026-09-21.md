## Section 1 — Dependency CVEs

### 🟠 W-1 — `cryptography` floor below patched release (day 42 — **27 days past SLA**)

`pyproject.toml` declares `cryptography>=48.0.1`. CVE-2026-0001 (moderate; RSA PKCS#1 v1.5 timing side-channel, fixed in 50.0.0) and CVE-2026-0002 (low; X.509 parsing OOM on crafted input, fixed in 50.0.0) are both unaddressed by this floor. regstack does not call RSA decrypt directly, but the `pyjwt[crypto]` OAuth path loads the RSA primitives at import time, making the exposure real for any deployment using OAuth.

**Remediation:** Bump floor to `cryptography>=50.0.0` in `pyproject.toml`; run `uv lock` and push.

## Section 2 — Secrets Handling

### 🟢 CLEAN

`jwt_secret`, `smtp_password`, and `google_client_secret` are all `SecretStr` in `RegStackConfig`. `derive_secret` receives the raw bytes via `.get_secret_value()` only at the call site inside `JwtCodec._key` and is not logged. The `regstack.secrets.env` file is excluded from the sdist manifest and listed in `.gitignore`. No secrets appear in stack traces or response bodies.

### 🟠 W-9 — `SmsConfig` SNS credential fields not `SecretStr` (day 3 — SLA 2026-09-25)

`src/regstack/config/schema.py`: `SmsConfig` declares `twilio_auth_token: SecretStr | None` correctly, but the AWS SNS path relies on `boto3`/`aioboto3` ambient credential discovery and exposes no explicit credential fields — meaning a host that injects `AWS_SECRET_ACCESS_KEY` via an env var gets no `SecretStr` protection in the pydantic model. This is a documentation/guidance gap rather than a direct leak, but the config schema should at minimum document the expectation.

**Remediation:** Add `aws_secret_access_key: SecretStr | None = None` and `aws_access_key_id: str | None = None` to `SmsConfig` with a comment that regstack will pass them to the SNS client when provided, falling back to ambient credentials otherwise.

## Section 3 — Authentication and Authorisation

### 🟠 W-8 — Timing oracle on login for OAuth-only accounts (day 3 — SLA 2026-09-25)

`src/regstack/routers/login.py`: the password-check branch is:

```python
if user.hashed_password is None or not rs.password_hasher.verify(payload.password, user.hashed_password):
    ...
```

Python short-circuits on the first condition: if `hashed_password is None` (i.e., an OAuth-only account), the ~100 ms Argon2 verify is skipped and the response returns roughly 1 ms sooner. An attacker can probe whether a given email is OAuth-only vs password-enabled with ~200 requests and a simple latency histogram.

**Remediation:** Always run a dummy Argon2 verify when `hashed_password is None` to preserve constant time:

```python
if user.hashed_password is None:
    rs.password_hasher.dummy_verify()  # constant-time guard
    raise invalid_credentials
if not rs.password_hasher.verify(payload.password, user.hashed_password):
    raise invalid_credentials
```

### 🟢 CLEAN — Admin disable invalidates sessions immediately

`src/regstack/routers/admin.py`: `set_tokens_invalidated_after(user.id, rs.clock.now())` is called synchronously before the 200 response; all outstanding tokens for the disabled user are bulk-revoked at that instant.

## Section 4 — Storage-Layer Injection

### 🟢 CLEAN — MongoDB

All MongoDB queries use typed BSON document constructors; no string interpolation into query operators. `get_by_id` guards with `ObjectId.is_valid()` before casting.

### 🟢 CLEAN — SQL

All SQL queries use parameterised statements via aiosqlite/asyncpg placeholders. No f-string or `.format()` interpolation into SQL.

### 🟠 W-6 — SQL `OAuthStateRepo.consume` non-atomic read-delete (day 13 — **6 days past SLA**)

`src/regstack/backends/sql/repositories/oauth_state_repo.py`: `consume` performs a `SELECT` followed by a separate `DELETE` in the same transaction, but between the two statements another coroutine on the same connection pool could theoretically observe the same row. The MongoDB backend uses `find_one_and_delete` (atomic). The SQL path should use `DELETE … RETURNING` (PostgreSQL) or a `SELECT … FOR UPDATE` + `DELETE` pattern (SQLite) to close the window.

**Remediation:** Rewrite `consume` to `DELETE FROM oauth_states WHERE state = ? RETURNING *` for PostgreSQL and an equivalent serialised transaction for SQLite.

## Section 6 — JWT and Session Security

### 🟢 CLEAN — Token lifecycle

All tokens carry a `jti = secrets.token_urlsafe(16)`. `JwtCodec` disables pyjwt's built-in `exp`/`iat` validation and performs both checks against the injected `Clock`, preserving test determinism without weakening production checks.

### 🟢 CLEAN — `iat` float precision

`to_claims()` emits `iat` as `self.iat.timestamp()` (float). `is_payload_bulk_revoked` uses `payload.iat <= cutoff`. Tokens issued microseconds after a password-change cutoff are correctly not revoked.

### 🟠 W-2 — Email-change token `jti` never blacklisted (day 21 — **14 days past SLA**)

`src/regstack/routers/account.py` → `confirm_email_change`: after successfully decoding the email-change JWT, the handler calls `users.update_email(...)` but never extracts `jti` and never calls `blacklist.insert(jti, exp)`. A valid email-change link can therefore be replayed until it expires (default 30 min TTL), allowing an attacker with access to the email to re-trigger the change even after the user has subsequently changed back.

**Remediation:** After `_decode_email_change_token(token)`, extract `payload.jti` and `payload.exp`, call `await rs.blacklist.insert(jti, exp)`, and return 400 if `await rs.blacklist.is_revoked(jti)` is already true.

### 🟠 W-3 — Email-change handler skips bulk-revocation check (day 21 — **14 days past SLA**)

Immediately after `_decode_email_change_token`, the handler fetches the user by `sub` but never calls `is_payload_bulk_revoked(payload, user.tokens_invalidated_after)`. A token minted before a `change-password` (which bumps `tokens_invalidated_after`) would still be accepted to change the email.

**Remediation:** After `users.get_by_id(payload.sub)`, add:
```python
if is_payload_bulk_revoked(payload, user.tokens_invalidated_after):
    raise HTTPException(status_code=400, detail="Token has been invalidated.")
```

## Section 10 — Third-Party Integrations

### 🟠 W-5 — `aiosmtplib` floor below patched release (day 15 — **8 days past SLA**)

`pyproject.toml` declares `aiosmtplib>=5.1.1`. CVE-2026-0010 (moderate; STARTTLS stripping when the remote drops `EHLO` capabilities mid-handshake, fixed in 5.1.2) is unaddressed. Any deployment using `email_backend=smtp` with a server that supports STARTTLS is exposed.

**Remediation:** Bump floor to `aiosmtplib>=5.1.2` in `pyproject.toml`; run `uv lock`.

### 🟠 W-10 — `GoogleOAuthProvider` holds `client_secret` as plain `str` (day 3 — SLA 2026-09-25)

`src/regstack/oauth/providers/google.py`: `__init__` accepts `client_secret: str` and stores it as `self._client_secret = client_secret`. When pydantic serialises or logs the provider object the secret may appear in plaintext. The config layer correctly stores it as `SecretStr`, but the value is unwrapped before being passed to the provider constructor.

**Remediation:** Change the parameter type to `SecretStr`, store as-is, and unwrap only at the point of the token-exchange POST.

## Section 13 — OAuth Subsystem

### 🟠 W-4 — Race condition: new OAuth user creation does not catch `UserAlreadyExistsError` (day 21 — **14 days past SLA**)

`src/regstack/routers/oauth.py` → `_resolve_user`, branch 4 (new account):

```python
new_user = await rs.users.create(new_user)
```

If two requests with the same Google `sub` arrive within milliseconds (e.g., double-click), the second `create` raises `UserAlreadyExistsError` which is not caught and propagates as an unhandled 500. Under the MongoDB backend the unique index on `email` also raises on the second call.

**Remediation:** Wrap the `create` call in a `try/except UserAlreadyExistsError` and fall back to `get_by_oauth_provider(provider, sub)` to retrieve the just-created user.

### 🟢 CLEAN — PKCE implementation

`code_verifier = _secrets.token_urlsafe(64)` is generated server-side and stored only on the state row. `code_challenge = base64url(SHA-256(verifier))` is sent to the provider. The verifier is never transmitted to the client.

### 🟢 CLEAN — ID-token verification

`GoogleOAuthProvider` verifies signature, `iss`, `aud`, `exp`, `iat`, and `nonce` via `pyjwt` + `PyJWKClient`. JWKS fetch is offloaded to `asyncio.to_thread` with a 5-second timeout.
