## 🟠 WARNING (Address within 1 week)

### W-1 — CVE-2026-48710 (BadHost): Starlette 1.0.0 in lock file

**Finding:**

The dev lock file (`uv.lock`) pins Starlette at **1.0.0**. CVE-2026-48710 ("BadHost"),
disclosed 2026-05-22, is a Host-header authentication-bypass vulnerability in all
Starlette versions ≤ 1.0.0. Injecting a `/`, `?`, or `#` character into the HTTP
`Host` header causes `request.url.path` to return a different value than the ASGI
server actually routed against, allowing path-based middleware guards to be silently
bypassed. The patch ships in **Starlette 1.0.1** (released 2026-05-21).

**Direct impact on regstack:**

regstack's own authentication is route-level, not path-based: every protected
endpoint uses `Depends(rs.deps.current_user())` or `Depends(rs.deps.current_admin())`
which validates the Bearer JWT regardless of the URL path. BadHost cannot bypass
this dependency-injected check. The published PyPI wheel is therefore not itself
exploitable via this vector.

However:

1. **`pyproject.toml` floor is `fastapi>=0.120.0`**. FastAPI does not pin Starlette
   tightly; a host running `pip install regstack` today may resolve Starlette 1.0.0
   if their resolver doesn't pull 1.0.1. Hosts using Starlette-level path middleware
   (common for metrics, tracing, or RBAC guards) are at risk.
2. **The dev environment is running the vulnerable version**, so integration tests and
   the CI matrix are exercised against a server that misparses Host-injected URLs.

**Fix:**

Bump the `fastapi` floor in `pyproject.toml` to a version whose declared Starlette
dependency excludes 1.0.0. Based on FastAPI's release history, `fastapi>=0.136.3`
(the current latest) resolves to Starlette ≥ 1.0.1 in practice. Run
`uv lock --upgrade-package starlette` to confirm the lock file is updated.

```
# pyproject.toml — bump the floor:
"fastapi>=0.136.3",
```

## 🟡 INFO (Best practice recommendations)

### I-1 — CVE-2026-48526: PyJWT 2.12.1 installed, algorithm-confusion fix in 2.13.0

**Finding:**

The lock file pins PyJWT at **2.12.1**. CVE-2026-48526 (disclosed 2026-06) describes
an algorithm-confusion attack in PyJWT < 2.13.0: when an application decodes tokens
using a raw JSON Web Key (JWK) string as the key while simultaneously accepting both
symmetric and asymmetric algorithms, an attacker with access to the public JWK can
forge a token signed with HS256 using the public key string as the HMAC secret.

**Direct impact on regstack:**

The attack path is **not present** in regstack's core JWT codec. `JwtCodec` uses:

- `algorithms=[self._config.jwt_algorithm]` — a single, fixed algorithm (default HS256).
- `self._key(purpose)` — raw bytes derived via HMAC-SHA256, never a JWK string.

The `GoogleProvider.verify_id_token` path uses RS256 against Google's JWKS via
`PyJWKClient`, a completely separate flow with no mixed-algorithm ambiguity.

**Recommendation:**

Bump the `pyjwt` floor in `pyproject.toml` to `>=2.13.0` for defence-in-depth and
to protect hosts that extend regstack with asymmetric JWT signing.

```
# pyproject.toml
"pyjwt>=2.13.0",
```

### I-2 — `UserPublic` exposes `tokens_invalidated_after`

**Finding:**

`src/regstack/models/user.py:104` includes `tokens_invalidated_after` in `UserPublic`,
the model returned by `/me`, `/admin/users/{id}`, and related endpoints. The security
review prompt specifies that `UserPublic` should exclude this field alongside
`hashed_password` and internal IDs.

**Context:**

The field is intentionally exposed — the `UserPublic` docstring documents it as a
signal that SPAs can compare against a stored JWT's `iat` to detect when the token
has been invalidated by a password change, without making an extra server round-trip.
This is a deliberate trade-off, not an oversight.

**Remaining concern:**

An attacker who can read the `/me` response learns the exact timestamp of the user's
most recent bulk-revoke event (last password/email change or admin disable). This is
low-sensitivity metadata but is internal state. If the SPA convenience is not needed
(many host apps use opaque session management), consider omitting it:

```python
# Remove from UserPublic if not needed by the host:
# tokens_invalidated_after: datetime | None = None
```

Alternatively, document the exposure explicitly in the API reference so integrators
can make an informed choice.

### I-3 — `GoogleProvider._client_secret` held as plain `str` in memory

**Finding:**

`RegStackConfig.oauth.google_client_secret` is correctly typed as `SecretStr`
(`src/regstack/config/schema.py:120`). However, the value is unwrapped before
being passed to `GoogleProvider.__init__`:

```python
# In app.py (construction site)
GoogleProvider(
    client_id=...,
    client_secret=config.oauth.google_client_secret.get_secret_value(),  # → plain str
    ...
)
```

Inside `GoogleProvider`, `self._client_secret` is then a plain Python `str`. Any
code that prints, logs, or `repr()`s the provider object would expose the secret in
clear text.

**Impact:** Low. The secret is in process memory; this is not a secrets-in-git
finding. Production containers don't typically log `repr()` of service objects.
The secret is also already in use in the token-exchange POST body (over TLS), which
is appropriate.

**Fix:** Store as `SecretStr` inside the provider and unwrap at the call site:

```python
from pydantic import SecretStr

class GoogleProvider(OAuthProvider):
    def __init__(self, *, client_id: str, client_secret: SecretStr | str, ...):
        self._client_secret = (
            client_secret if isinstance(client_secret, SecretStr)
            else SecretStr(client_secret)
        )

    async def exchange_code(self, ...) -> OAuthTokens:
        ...
        data={"client_secret": self._client_secret.get_secret_value(), ...}
```
