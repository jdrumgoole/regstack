## 🟡 INFO (Best practice recommendations)

### I-1 · `regstack init` wizard still offers `"cookie"` transport — causes startup validation error

**Files:**
- `src/regstack/cli/init.py`, lines 94–95 (transport prompt)
- `src/regstack/cli/init.py`, lines 46–47 (cookie_domain prompt)
- `src/regstack/cli/init.py`, lines 212–213 (cookie_domain TOML output)
- `src/regstack/cli/init.py`, line 226 (transport TOML output)

**Background:** Finding I-7 in the 2026-05-15 / 2026-05-16 reviews identified that
`transport = "cookie"` was silently accepted by `RegStackConfig` even though no
`Set-Cookie` path exists. Commit `56afd64` narrowed
`TokenTransport = Literal["bearer"]` in `config/schema.py` — a correct fix.

**Incomplete remediation:** The `regstack init` wizard was not updated. It still
prompts:

```
Token transport [bearer/cookie] (default: bearer):
```

If an operator selects `cookie`, the wizard writes `transport = "cookie"` to
`regstack.toml`. When `RegStack` later loads this config, Pydantic raises:

```
ValidationError: 1 validation error for RegStackConfig
transport
  Input should be 'bearer' [type=literal_error, ...]
```

The app fails to start with a cryptic validation error rather than the wizard
giving an actionable message at generation time.

In addition, the wizard:
1. Prompts for `cookie_domain` (line 46) and defaults to the base URL's hostname,
   implying cookie session scope is being configured.
2. Writes `cookie_domain = "<hostname>"` to the TOML (line 212–213) even though
   nothing in the auth stack reads this field.

An operator who runs `regstack init` and selects "bearer" (the default) is
unaffected. An operator who selects "cookie" — a reasonable choice given that
the wizard offers it — ends up with a broken deployment and potentially wastes
significant debugging time before tracing the root cause back to the wizard.

**Remediation (three-line change in `init.py`):**

```python
# Line 94–95: Remove "cookie" from the choice
transport = click.prompt(
    "Token transport", type=click.Choice(["bearer"]), default="bearer"
)

# Lines 46–47: Remove the cookie_domain prompt entirely
# (delete the click.prompt call and its assignment)

# Lines 212–213: Remove the cookie_domain TOML output block
```

Optionally, remove `cookie_domain: str | None = None` from `RegStackConfig`
and the `_render_toml` signature entirely until cookie transport is
implemented, so hosts can't accidentally set a no-op field.

### I-2 · `tokens_invalidated_after` in `UserPublic` not documented as a deliberate data-exposure trade-off (carries over from 2026-05-15 / 2026-05-16)

**File:** `docs/security.md`

First raised 2026-05-15 (I-6 in that report), still open after 2026-05-16.
`docs/security.md` references `tokens_invalidated_after` at lines 64, 176,
190, and 258 exclusively in the context of the bulk-revoke mechanism itself.
It does not explain that the field is **intentionally included in `UserPublic`**
(the public API response), nor does it document the security trade-off: any
valid session token holder — including a stolen one — can read the exact
timestamp of the last password-change, email-change, or admin-disable event on
the account.

The `models/user.py` docstring on `UserPublic.tokens_invalidated_after` does
explain the SPA polling rationale:

```python
tokens_invalidated_after: datetime | None = None
"""Bulk-revoke cutoff. SPAs comparing this to their session JWT's
`iat` can tell when the token they hold has been invalidated by a
password change / email change without making another request."""
```

But `docs/security.md` is the externally-facing document host integrators read
when assessing what regstack exposes. Hosts making an informed decision about
data minimisation need to know this field is present in API responses by
design.

**Remediation:** Add a paragraph to `docs/security.md` under a
"Data exposure trade-offs" heading (or inline with the bulk-revocation section)
that explicitly notes:

- `tokens_invalidated_after` is included in `UserPublic` (and therefore in
  all `GET /me`, `GET /admin/users/{id}`, and `POST /confirm-email-change`
  responses) by design.
- The intended use is SPA polling: a client can compare the field to the local
  session JWT's `iat` to detect invalidation without a separate round-trip.
- The consequence is that any session token holder (legitimate or stolen) can
  observe the timestamp of the most recent security event. Hosts for whom this
  is unacceptable should strip the field from their own API wrapper layer.

### §7 Session and token security

`JwtCodec` disables pyjwt's `exp`/`iat` checks and validates both against the
injected `Clock`. `iat` is emitted as a float (verified in `TokenPayload.to_claims`

timeout applies.

### §14 OAuth subsystem

- **PKCE:** `code_verifier` (64-byte URL-safe random) stored on the
  `oauth_states` row; only `code_challenge` (SHA-256 with `S256`) goes in the
  provider redirect URL. Verified in `_begin_flow()`.
- **State row lifecycle:** Expiry checked with `rs.clock.now()` (clock-injected).
  SQL `consume()` uses `SELECT` + `DELETE` inside a single `engine.begin()`
  transaction; Mongo uses `find_one_and_delete`. Missing row → 404; expired row
  → 400. Note: `exchange` checks expiry AFTER `consume()` — an expired row is
  still deleted atomically, preventing replay.
- **ID-token verification:** Signature via JWKS, `iss`, `aud`, `exp`, `iat`,
  `nonce` all validated. `require=` claim list enforced. Failure raises
  `OAuthIdTokenError` with a generic outer message; specifics logged via
  `log.warning`.
- **OAuth callback log injection (I-3 from 2026-05-16 resolved):**
  `_sanitize_for_log()` strips control characters and caps length before
  logging provider-controlled error strings.
- **Linking policy:** `email_in_use` blocks silent account takeover.
  `auto_link_verified_emails=True` AND `email_verified=true` both required.
  `identity_in_use` and `already_linked` prevent silent identity transfer.
- **OAuth-only users:** `/login` with `hashed_password=None` returns same
  generic 401 as wrong password. `/change-password`, `/change-email`,
  `/account` (DELETE), `/phone/start` return 400 via `require_password_set()`.
  `/oauth/{provider}/link` (DELETE) returns 400 when unlinking the only
  sign-in method.
- **Identity uniqueness:** `(provider, subject_id)` and `(user_id, provider)`
  unique constraints enforced at DB level in both backends.
- **Mongo `oauth_states.mode` validator (I-5 from 2026-05-16 resolved):**
  `_ensure_oauth_states_validator()` installs a `$jsonSchema` validator
  (`mode IN ['signin','link']`) via `collMod` with `validationLevel="moderate"`.
- **Hooks:** `oauth_signin_started`, `oauth_signin_completed`,
  `oauth_account_linked`, `oauth_account_unlinked` present in `KNOWN_EVENTS`
  and fired at correct callsites.
