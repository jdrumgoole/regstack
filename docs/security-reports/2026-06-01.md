## 🟠 WARNING (Address within 1 week)

### W-1 — PyJWKClient missing `timeout` (`src/regstack/oauth/providers/google.py:83`) — persisted from 2026-05-22

**Status:** Unresolved since W-1 in the 2026-05-22 review.

```python
self._jwks_client = PyJWKClient(jwks_url, cache_keys=True)
```

No `timeout` argument is passed to `PyJWKClient`. PR #80 (2026-05-20) correctly offloaded
the synchronous JWKS fetch to `asyncio.to_thread`, so the event loop is no longer blocked.
However, the underlying `urllib.request.urlopen` call has no timeout, meaning a slow or
unreachable JWKS endpoint holds a worker thread indefinitely.

Under sustained OAuth load during a Google JWKS outage or network partition, concurrent
cache-miss fetches exhaust Python's default asyncio thread pool
(`min(32, cpu_count+4)` threads), blocking **all** `to_thread` calls across the entire
application — not just OAuth paths.

**Fix:**

```python
self._jwks_client = PyJWKClient(jwks_url, cache_keys=True, timeout=5)
```

`PyJWKClient` has accepted a `timeout` keyword since pyjwt 2.4.0; the project already
requires `pyjwt>=2.12.1`.

### W-2 — Starlette 1.0.0 in `uv.lock` — CVE-2026-48710 (BADHOST)

**Finding:**

```
# uv.lock
name = "starlette"
version = "1.0.0"
```

CVE-2026-48710 (BADHOST) affects all Starlette versions 0.8.3 through 1.0.0. The fix
ships in Starlette 1.0.1. CVSS base score: **7.5 HIGH** (OSTIF/NVD).

**Mechanism:** When an HTTP request carries a Host header containing characters that are
invalid per RFC 9112 (`/`, `?`, `#`), Starlette reconstructs `request.url.path`
incorrectly — shifting path, query, and fragment boundaries. Any security check using
`request.url.path` (e.g. middleware path-exclusion lists) sees a different path than the
one the ASGI router actually dispatched against, allowing a bypass.

**Impact on regstack:**

| Scope | Risk |
|---|---|
| regstack's own auth | **Low.** All auth decisions use `Authorization: Bearer <token>` — no path-based middleware reads `request.url.path` anywhere in `src/regstack/`. |
| Host apps embedding regstack | **Medium–High.** Any host that adds path-based middleware (e.g. CSRF exemptions, admin-path guards, request logging filters) on top of the FastAPI/Starlette app inherits the vulnerable Starlette and is exposed. |
| Supply-chain | **Medium.** Every consumer who runs `pip install regstack` gets the vulnerable Starlette transitively until the lockfile is updated and a new release ships. |

**Root cause in this repo:** `pyproject.toml` constrains `fastapi>=0.120.0` but places no
floor on `starlette` directly. FastAPI 0.136.1's own dependency range allows Starlette
1.0.0, so `uv lock` resolves to the vulnerable version.

**Fix:**

1. Update the lockfile: `uv lock --upgrade-package starlette` (pulls in ≥1.0.1).
2. Add an explicit floor to `pyproject.toml` so downstream consumers also receive the
   safe version:

   ```toml
   # starlette>=1.0.1 picks up CVE-2026-48710 (BADHOST — Host Header Auth Bypass).
   "starlette>=1.0.1",
   ```

   Alternatively, bump the `fastapi` floor to the first FastAPI release that explicitly
   requires `starlette>=1.0.1` — whichever is cleaner.

**References:** [OSTIF disclosure](https://ostif.org/disclosing-the-badhost-vulnerability-in-starlette/),
[BADHOST.org](https://badhost.org/), [HN thread](https://news.ycombinator.com/item?id=48277107).

## 🟡 INFO (Best practice recommendations)

### I-1 — `was_new_account` always `False` in OAuth exchange (`src/regstack/routers/oauth.py:176`) — persisted from 2026-05-22

The `ExchangeResponse.was_new_account` field is hardcoded to `False` in the
`/oauth/exchange` endpoint. The `was_new` boolean is computed correctly during
`_resolve_user` in the callback but is not persisted to the `oauth_states` row, so the
exchange endpoint cannot surface it. SPAs that display "Welcome! Account created." on a
true first sign-in will never see `was_new_account=True`.

Not a security issue — a SPA reading `False` for a new account does not create an
exploitable condition. Fix: add `result_was_new: bool = False` to the `oauth_states`
table and populate it in the callback.

### I-3 — Google token exchange response body logged at WARNING (`src/regstack/oauth/providers/google.py:143`) — persisted from 2026-05-22

```python
raise OAuthTokenExchangeError(
    f"google token exchange failed: {response.status_code} {response.text}"
)
```

Caught in `routers/oauth.py` and logged at `WARNING` level. Google's token responses are
standard JSON (`{"error": "...", "error_description": "..."}`) — no client secrets appear
there — so the direct risk is low. Recommended improvement: log status at WARNING and
body at DEBUG to reduce production log noise:

```python
log.warning("google token exchange failed: HTTP %s", response.status_code)
log.debug("google token exchange response body: %s", response.text)
```
