### §3 — Authentication & Authorization

- Every authenticated endpoint injects `rs.deps.current_user()` or `rs.deps.current_admin()`. Admin endpoints (`/admin/*`, `/admin/pending/{email}/promote`) all require `current_admin()`.
- Every state-mutating endpoint requires auth.
- All API responses use `UserPublic.from_user(user)`. `hashed_password` is never present in any serialised response.
- **Bulk-revoke discipline:**
  - `reset-password` → calls `update_password` (bumps `tokens_invalidated_after`) AND `lockout.clear` ✓
  - `change-password` → calls `update_password` (bumps `tokens_invalidated_after`) AND `lockout.clear` ✓
  - `confirm-email-change` → calls `update_email` (bumps `tokens_invalidated_after`) AND `lockout.clear` ✓
  - Admin disable (`is_active=False`) → calls `set_tokens_invalidated_after` ✓
  - Account delete → cascades `oauth_identities.delete_by_user_id` before `users.delete` ✓
  - Admin delete → cascades `oauth_identities.delete_by_user_id` before `users.delete` ✓
- OAuth-only users (`hashed_password=None`): `POST /login` returns the same generic 401 as a wrong-password attempt, with no observable timing difference — `hashed_password is None` is handled in the same `if` branch as a failed verify. `require_password_set()` rejects `change-password`, `change-email`, `delete-account`, and `phone/start` with a 400 pointing to `forgot-password`.
- Password verification via `pwdlib.PasswordHasher.verify()` (Argon2id), not `==`.
- JWT signing keys derived per-purpose via HMAC-SHA256 (`derive_secret(master, purpose)`). Compromise of a session key does not compromise password-reset, email-change, phone-setup, or login-MFA keys.

### §6 — Rate Limiting & DoS Prevention

- Login lockout: `lockout.check()` runs before user lookup. `record_failure()` runs on non-existent user, wrong password, disabled user, and unverified user (all with valid credentials) — blocked attacker cannot distinguish these cases by timing or HTTP code differences.
- MongoDB `login_attempts` TTL index: keyed on `when`, `expireAfterSeconds=config.login_lockout_window_seconds`. SQL backends rely on read-side `count_recent` + `purge_expired()`.
- Admin `/admin/users` listing: `limit: Annotated[int, Query(ge=1, le=200)]` — capped at 200 rows per page.
- OAuth state rows: 5-minute TTL (`oauth.state_ttl_seconds=300`) with a MongoDB TTL index on `expires_at`. SQL: `purge_expired()` method on `SqlOAuthStateRepo`.
- No file upload endpoints introduced.
- Per-route `slowapi` IP rate limits are optional but fully wired: configuration fields exist for every sensitive route including `phone_start_rate_limit`, `phone_confirm_rate_limit`.

## 🟡 INFO (Best practice recommendations)

### I-1 — Login: attempts-remaining count in 401 detail

**Location:** `src/regstack/routers/login.py:40`

```python
detail = f"Invalid email or password. {remaining} attempt(s) remaining."
```

When `remaining` is between 1 and `login_lockout_threshold - 1`, the 401 response body tells the caller exactly how many more attempts before lockout fires. A sophisticated attacker can use this count to pace a credential-stuffing campaign — rotating IPs or accounts when the counter approaches zero to avoid triggering the lockout. The counter does not help an attacker bypass lockout; it only helps them optimise their attack cadence.

This is intentional per the Review #15 comment in the source. The UX benefit (legitimate users know they're about to be locked out) may outweigh the marginal attacker advantage. No immediate action required; flag for team awareness.

**Recommendation:** Consider returning a generic "Invalid email or password." on all failures, or only disclosing `remaining = 1` ("one attempt remaining before temporary lockout") as a last-warning signal, rather than the full count.

### I-2 — No automated CVE advisory scanning in CI

The project tracks CVEs proactively via inline `pyproject.toml` comments, which is excellent discipline. However, new advisories published between reviews (or between pinned-bound bumps) would not surface automatically. No `pip-audit`, `safety check`, or `osv-scanner` step exists in `test.yml` or `publish.yml`.

**Recommendation:** Add a `pip-audit` or `uv run pip-audit` step to `test.yml` so any newly published advisory against a locked dependency is flagged on the next CI run. The daily review cadence is a reasonable backstop but not a substitute for automated scanning.

### I-3 — `UserPublic.tokens_invalidated_after` in API response

**Previously documented:** 2026-05-17 review I-2.

`tokens_invalidated_after` is still exposed in `UserPublic` (and therefore in `GET /me`, `/admin/users/{id}`, etc.). SPAs can use it to detect client-side session invalidation without polling. The value is a timestamp, not a secret.

Status: intentional design choice, documented in `docs/security.md`. Confirmed still present and still intentional. No action required; noting for continuity.
