## Section 3 — Authentication & Authorization Audit

### 🟠 W-2 · Email-change token not jti-blacklisted · day 50 (SLA expired +43 d)

Source re-verified today at `src/regstack/routers/account.py:177`. `confirm_email_change` decodes the email-change JWT via `_decode_email_change_token`, calls `rs.users.update_email` (which bumps `tokens_invalidated_after` for session tokens), but does **not** record the email-change token's `jti` in `BlacklistRepo`. A replay of the same email-change link within its TTL window re-invokes `update_email` to the same value — mostly harmless but the token is not single-use at the application layer.

**Fix:** after a successful `update_email`, call `await rs.blacklist.add_jti(jti, exp)` using the decoded token's `jti` and `exp` claims.

### 🟠 W-4 · OAuth new-user concurrent registration race → unhandled 500 · day 50 (SLA expired +43 d)

Source re-verified today at `src/regstack/routers/oauth.py` (`_resolve_user`, line ~716). Concurrent OAuth sign-ins for a brand-new email address can both pass the `find_by_subject` check (no identity row yet), both reach the "brand-new account" branch, and both call `rs.users.create(new_user)`. The second one raises an unhandled `UserAlreadyExistsError` that propagates as an uncaught 500 from the callback endpoint instead of redirecting to `?error=email_in_use` or returning a clean session for the winning call.

**Fix:** wrap the `rs.users.create` call in a `try/except UserAlreadyExistsError` block and raise `_LinkConflictError("email_in_use")` on conflict.

### 🟠 W-8 · Timing oracle on login for OAuth-only accounts · day 32 (SLA expired +25 d)

Confirmed present at `src/regstack/routers/login.py:99`: `if user.hashed_password is None or not rs.password_hasher.verify(payload.password, user.hashed_password)`. When `hashed_password is None`, the Argon2 `verify()` call is short-circuited, making the 401 response measurably faster (~1–2 ms) than a wrong-password 401 for a password-bearing account (~hundreds of ms). An attacker who harvests usernames can fingerprint which accounts are OAuth-only vs password-based.

**Fix:** when `hashed_password is None`, call `rs.password_hasher.verify(payload.password, <sentinel_hash>)` (a pre-computed hash of a dummy password) before returning the 401 to normalise timing.

### 🟠 W-13 · Admin `promote_pending` email path param not validated · day 17 (SLA expired +9 d)

Confirmed present at `src/regstack/routers/admin.py:210`: `email: str = Path(...)`. The email parameter in `POST /admin/pending/{email}/promote` is typed `str` rather than `EmailStr`. A malformed or excessively long email string reaches `rs.promote_pending(email)` without FastAPI/Pydantic validation. The downstream `rs.pending.find_by_email` call is parameterized so there is no injection risk, but the missing validation creates inconsistency with every other email-bearing endpoint.

**Fix:** change `email: str = Path(...)` to `email: EmailStr = Path(...)`.

## Section 14 — OAuth Subsystem Audit

### 🟠 W-6 · SQL `OAuthStateRepo.consume` non-atomic under READ COMMITTED · day 42 (SLA expired +35 d)

Source re-verified today at `src/regstack/backends/sql/repositories/oauth_state_repo.py:63–71`. The method wraps SELECT + DELETE in `engine.begin()` (one transaction), but PostgreSQL's default READ COMMITTED isolation means a concurrent request can read the same row between the SELECT and DELETE, allowing two `/oauth/exchange` calls with the same state ID to both return a session token. Mongo is safe (`find_one_and_delete` is atomic).

**Fix:** use `SELECT … FOR UPDATE` on the SELECT or `DELETE … RETURNING` for true atomicity on SQL backends.
