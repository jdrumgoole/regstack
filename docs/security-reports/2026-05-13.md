### W1 — CVE-2025-62727: Starlette DoS reachable via `fastapi>=0.110` lower bound

**Section §1 — Dependency Vulnerability Check**  
**File:** `pyproject.toml`

The base `dependencies` pin `fastapi>=0.110`. FastAPI 0.110–0.119.x transitively pins
Starlette to versions ≤ 0.48.0, which contain **CVE-2025-62727** (CVSS HIGH): a crafted
HTTP `Range` header causes quadratic-time processing in `FileResponse`, leading to CPU
exhaustion / DoS. A proof-of-concept is publicly available.

The fix landed in Starlette 0.49.1, which FastAPI 0.120.0+ requires. Any host that runs
`pip install regstack` on a fresh environment gets a resolver-selected FastAPI that may
be < 0.120.0, and therefore a vulnerable Starlette.

**Recommendation:** Tighten the lower bound to `fastapi>=0.120.0`.

Note: Starlette 0.47.2 also fixed a separate multipart DoS (CVE-2025-54121, MEDIUM), also
covered by the same `fastapi>=0.120.0` bump.

### W2 — CVE-2025-27516: Jinja2 sandbox breakout reachable via `jinja2>=3.1` lower bound

**Section §1 — Dependency Vulnerability Check**  
**File:** `pyproject.toml`

The base `dependencies` pin `jinja2>=3.1`. Jinja2 3.1.0–3.1.5 contain
**CVE-2025-27516** (CVSS HIGH): the `|attr` filter can be used to break out of the
Jinja2 sandbox and execute arbitrary Python code.

regstack does not enable the Jinja2 sandbox itself — the `MailComposer` and `ui_router`
environments both use `autoescape=select_autoescape(["html"])`, not the sandbox. The
immediate exploitability therefore depends on whether a host app adds sandbox-constrained
Jinja2 rendering on top of regstack, but the dependency constraint is an unnecessary
exposure: host apps inherit regstack's `Requires-Dist` entries via pip's resolver and can
be dragged down to a vulnerable Jinja2.

**Recommendation:** Tighten the lower bound to `jinja2>=3.1.6`.

### W3 — Open redirect bypass: `/\evil.com` and `////evil.com` pass `_validate_redirect`

**Section §5 — Input Validation & Injection**  
**File:** `src/regstack/routers/oauth.py:348-360`  
**File:** `src/regstack/ui/static/js/regstack.js:526-528`

`_validate_redirect` uses `urllib.parse.urlsplit` to check that `redirect_to` is same-
origin:

```python
parts = urlsplit(redirect_to)
if not parts.scheme and not parts.netloc:
    return redirect_to or "/account/me"          # ← accepts any path-only value
```

Two confirmed bypass vectors — both confirmed against Python 3.11 `urlsplit`:

**Vector A:** `urlsplit("/\\evil.com")` → `SplitResult(scheme='', netloc='', path='/\\evil.com')`.  
Both `scheme` and `netloc` are empty strings, so the value is accepted as a plain path.
Per the WHATWG URL standard, browsers normalise `\` to `/` in URL paths, so
`window.location.href = "/\\evil.com"` navigates to `//evil.com` (the external domain `evil.com`).

**Vector B:** `urlsplit("////evil.com")` → `SplitResult(scheme='', netloc='', path='//evil.com')`.  
Four leading slashes: `urlsplit` sees an empty netloc and puts `//evil.com` in the path.
`window.location.href = "////evil.com"` is interpreted by browsers as the protocol-
relative URL `//evil.com`, redirecting to `evil.com`.

When `regstack.js` executes:

```js
const target = res.body.redirect_to || (uiPrefix + "/me");
window.location.href = target;            // line 528
```

…either bypass value sends the user to an attacker-controlled domain after sign-in.

**Attack scenario:** An attacker crafts the URL
`/oauth/google/start?redirect_to=////attacker.com` and shares it. When the victim
clicks it and authenticates with Google, they land on the attacker's site — a highly
effective phishing vector because the authentication step is genuine.

**Recommendation:** Add a prefix check before the `urlsplit` path:

```python
def _validate_redirect(rs: RegStack, redirect_to: str) -> str:
    # Browsers normalise /\ and //// → // (protocol-relative) — reject proactively.
    if redirect_to.startswith(("//", "/\\")):
        raise HTTPException(status_code=400, detail="redirect_to must be same-origin.")
    parts = urlsplit(redirect_to)
    ...
```

A stricter fix is to require the path starts with `/` followed by a non-`/` character
(i.e. `re.match(r"^/[^/\\]", redirect_to)`) before the full scheme/netloc check.

### W4 — pywebview, uvicorn, tomlkit in base `dependencies` (supply-chain concern)

**Section §1 / §13c — Dependency Vulnerability Check / PyPI Package Integrity**  
**File:** `pyproject.toml`

Three packages that are only used by the optional CLI wizard commands (`regstack oauth
setup`, `regstack theme design`) are listed in the mandatory `dependencies` array:

```
pywebview>=5.0
tomlkit>=0.13
uvicorn[standard]>=0.29
```

The Python-level imports are correctly lazy (guarded by `_LazyOauthGroup` /
`_LazyThemeGroup` + `try/except` in the window modules), so `import regstack` does not
fail on headless systems. However, **`pip install regstack` unconditionally resolves and
installs these packages** regardless of whether the host ever runs the wizard.

`pywebview>=5.0` pulls in native GUI backend trees:
- Linux: GObject Introspection libraries (GTK/WebKit)
- Windows: Microsoft Edge WebView2 runtime COM components
- macOS: Cocoa / WKWebView

These are significant non-trivial attack surface on production servers (Kubernetes pods,
AWS Lambda, Cloud Run) that will never display a GUI. Any CVE in pywebview or its
platform backends becomes a regstack transitive exposure for all consumers.

**Recommendation:** Move all three into a new optional extra:

```toml
[project.optional-dependencies]
wizard = ["pywebview>=5.0", "tomlkit>=0.13", "uvicorn[standard]>=0.29"]
```

Note that `uvicorn[standard]>=0.29` already appears in the `dev` extra; removing it from
`dependencies` requires only the `pyproject.toml` change. The `regstack oauth setup` and
`regstack theme design` CLI entry points already perform lazy imports, so no code changes
are needed beyond the metadata.

### W7 — `enforce_mfa_on_oauth_signin` is dead code: OAuth bypasses SMS MFA

**Section §14 — OAuth Subsystem Audit**  
**File:** `src/regstack/routers/oauth.py`  
**File:** `src/regstack/config/schema.py`

`OAuthConfig.enforce_mfa_on_oauth_signin: bool = False` is documented as:
> "When True, an OAuth sign-in for a user with SMS MFA enabled still goes through the
> second-factor step."

The OAuth callback handler (`oauth_callback` in `routers/oauth.py`) and the user
resolution helper (`_resolve_user`) **never read this config field** and **never check
`user.is_mfa_enabled`**. A regstack user who has configured SMS 2FA and an OAuth
provider can completely bypass the SMS second factor by signing in via the OAuth flow.
This is true regardless of whether `enforce_mfa_on_oauth_signin` is `True` or `False` —
the flag has no effect.

**Impact:** Any host that has enabled SMS MFA to meet a security policy (e.g., compliance
requirements, high-risk account protection) and also allows OAuth sign-in has a silent
bypass for every user who has both a linked OAuth identity and an MFA-enrolled phone.

**Recommendation:** Implement the guard in `oauth_callback` / `_resolve_user`:
after a successful OAuth user resolution (step 1: existing identity found), check
`user.is_mfa_enabled and rs.config.oauth.enforce_mfa_on_oauth_signin` and, if true,
mint a short-lived MFA pending JWT and return a redirect to the MFA confirm page (similar
to the password-login MFA path).

Until the implementation is complete, **remove `enforce_mfa_on_oauth_signin` from
`OAuthConfig`** or clearly document that it is not yet implemented — hosts who set it
`True` believing it provides protection are currently getting no security benefit.

### W8 — Admin resend-verification stores `"None"` password hash for OAuth-only users

**Section §3 — Authentication & Authorization Audit**  
**File:** `src/regstack/routers/admin.py:158-169`

`POST /admin/users/{id}/resend-verification` constructs a `PendingRegistration` using
the target user's `hashed_password`:

```python
pending = PendingRegistration(
    email=user.email,
    hashed_password=user.hashed_password,   # ← None for OAuth-only users
    full_name=user.full_name,
    ...
)
```

OAuth-only users have `hashed_password = None`. If `PendingRegistration.hashed_password`
is typed as `str` (not `str | None`), Pydantic (in lax coercion mode) converts `None` to
the literal string `"None"` and stores it. Subsequent flows that load the pending
registration and use the `hashed_password` field would then be working with a corrupted
hash. If `PendingRegistration.hashed_password` is `str | None`, this is likely a silent
no-op — but the verification flow would then hand back an `is_verified=True` account with
no usable password, which is the expected OAuth-only state. The outcome depends on the
exact Pydantic model definition.

In either case, an admin calling resend-verification on an OAuth-only unverified account
gets unexpected behaviour. The endpoint does not guard against this case with a 400.

**Recommendation:** Add a guard at the top of `admin_resend_verification`:

```python
if user.hashed_password is None:
    raise HTTPException(
        status_code=status.HTTP_400_BAD_REQUEST,
        detail="Cannot resend verification for an OAuth-only account.",
    )
```

### W6 — GitHub Actions: missing `permissions:` blocks

**Section §12c — Workflow permissions and GITHUB_TOKEN scope**  
**Files:** `.github/workflows/test.yml`, `.github/workflows/publish.yml` (build job)

The `test.yml` workflow has **no `permissions:` block** at the workflow or job level.
The `build` job in `publish.yml` also has no `permissions:` block (only the `publish` job
correctly declares `permissions: { id-token: write }`).

Without an explicit `permissions:` declaration, GitHub uses the repository's default token
permissions, which in many organisation settings include `contents: write`,
`pull-requests: write`, and other write scopes. The principle of least privilege requires
declaring the minimum needed permissions explicitly.

**Recommendation:**

In `test.yml`, add at the workflow level:
```yaml
permissions:
  contents: read
```

In `publish.yml`, add to the `build` job:
```yaml
jobs:
  build:
    permissions:
      contents: read
```

The `publish` job already correctly scopes to `id-token: write` only.

### I1 — MongoDB "MongoBleed" CVE-2025-14847: deployment guidance needed

**Section §1**

CVE-2025-14847 ("MongoBleed", CVSS HIGH, actively exploited): MongoDB server leaks heap
memory — which can include credentials, tokens, and other connection state — via zlib
decompression when the `zlib` network compression protocol is enabled. The vulnerability
is in the MongoDB server, not the `pymongo` driver; regstack's `pymongo>=4.9` pin is not
the remediation path.

Deployments using MongoDB with the default `zlib` compressor are at risk.
**Recommendation:** Add a deployment note to `docs/security.md` recommending:
```
networkMessageCompressors: snappy,zstd   # or "disabled"
```
MongoDB 7+ supports `snappy` and `zstd` without additional packages.

### I3 — JWT secret length not enforced at construction time

**Section §7 — Session & Token Security**  
**File:** `src/regstack/auth/jwt.py:118-122`

`JwtCodec.__init__` rejects an empty `jwt_secret` but accepts secrets of 1–31 characters
without complaint. `regstack doctor` warns at runtime when the secret is shorter than
32 characters, but `doctor` is advisory — a misconfigured deployment proceeds silently.

HMAC-SHA256 derived keys from a short master secret are significantly weaker. The
`derive_secret` function provides key separation across purposes, but the security margin
collapses if the master secret is low-entropy.

**Recommendation:** Add a length check to `RegStack.__init__` (or `JwtCodec.__init__`):

```python
secret = config.jwt_secret.get_secret_value()
if len(secret) < 32:
    raise ValueError(
        "jwt_secret must be at least 32 characters. "
        "Run `regstack init` to generate a secure one."
    )
```

### I4 — Disabled accounts bypass login lockout and disclose account existence

**Section §6 — Rate Limiting & DoS Prevention**  
**File:** `src/regstack/routers/login.py:73-77`

When a user exists but `user.is_active is False`, the login handler returns HTTP 403
(`"Account is disabled."`) without calling `rs.lockout.record_failure(payload.email)`.
Two consequences:

1. **Unlimited password spraying:** An attacker with a known disabled account email can
   attempt passwords without ever consuming lockout quota.
2. **Account enumeration:** The 403 response distinguishes a valid-but-disabled account
   from a non-existent account (which gets 401). If disabled-account status is meant to
   be opaque, the endpoint should call `record_failure` and return 401 consistently.

**Recommendation (if enumeration matters for your threat model):** Record a failure and
return 401 for disabled accounts, as for any other failed credential check. If the 403 is
intentional UX (so a legitimate user understands why they can't log in), consider at
least calling `record_failure` to close the spraying window.

### I5 — OAuthTokenExchangeError may include full Google response body in server logs

**Section §9 — Data Exposure**  
**File:** `src/regstack/oauth/providers/google.py:154-155`

If Google returns HTTP 200 but the JSON body is missing `access_token` or `id_token`,
the error message includes the complete response body:

```python
raise OAuthTokenExchangeError(
    f"google token response missing field {exc.args[0]!r}: {body!r}"
)
```

If the response body contains partial token data under unexpected keys, the values would
appear in server logs via `log.warning("oauth token exchange failed: %s", exc)`. This
path is triggered only by an anomalous Google response (extremely unlikely), but the
log entry is permanent.

**Recommendation:** Log the missing key name only, not the full body:
```python
raise OAuthTokenExchangeError(
    f"google token response missing field {exc.args[0]!r}"
) from exc
```

### I6 — Hook payloads include verification URLs and email-change JWTs

**Section §9 — Data Exposure**  
**Files:** `src/regstack/routers/register.py:97`, `src/regstack/routers/account.py:145`,
`src/regstack/routers/admin.py:175`

PR #40 ("drop plaintext OTP from hook payloads") removed raw SMS codes from hook
payloads. However, three hooks still carry URL-embedded tokens:

- `verification_requested` → `url=url` (raw 32-byte verification token in URL)
- `email_change_requested` → `url=url` (signed email-change JWT in URL)
- Admin `verification_requested` → `url=url` (same as above)

Any hook handler that forwards events to a third-party observability platform (Datadog,
Splunk, Slack) would expose these tokens. Unlike OTPs, the URL-embedded tokens have a
longer TTL (24 h for verification, `email_change_token_ttl_seconds` for email change) and
enable direct account state changes if intercepted.

**Recommendation:** Either strip the `url=` from hook payloads (hosts who genuinely need
the URL can construct it from the `email` claim they receive), or document clearly in
`HookRegistry` docstrings that hook payloads may contain security-sensitive tokens and
handlers must not forward them to untrusted third parties.

### I10 — SQL backends accumulate expired rows: no scheduled reaper

**Section §6 / §15 — Rate Limiting & DoS Prevention / Multi-backend Parity**  
**File:** `src/regstack/backends/sql/repositories/`

MongoDB backends automatically delete expired rows via TTL indexes on every collection
with an `expires_at` or `exp` field. SQL backends (SQLite, Postgres) provide
`purge_expired()` methods on every repo but **regstack never calls them internally**.
There is no background task, lifespan hook, or scheduler. Hosts using SQL backends must
schedule periodic `purge_expired()` calls themselves or every table with an expiry column
grows without bound.

Affected collections: `token_blacklist`, `pending_registrations`, `mfa_codes`,
`login_attempts`, `oauth_states`.

For `login_attempts`, unbounded growth also slows the lockout count query (a full-table
count after the window filter degrades as the table grows). For long-running deployments,
this is a latent DoS vector.

**Recommendation:** Document the `purge_expired()` requirement prominently in
`docs/embedding.md` and `docs/architecture.md`. Consider adding an opt-in background
task (e.g., a lifespan event handler that regstack can register) for SQL backends.

### I11 — Mongo UserRepo mutation methods: some paths lack `ObjectId.is_valid()` guard

**Section §4a — MongoDB Injection Safety**  
**File:** `src/regstack/backends/mongo/repositories/user_repo.py`

`get_by_id()` (line 54) and `delete()` (line 139) correctly guard with
`ObjectId.is_valid(user_id)` before calling `ObjectId(user_id)`. However, the mutation
methods (`set_last_login`, `update_password`, `set_active`, `set_superuser`, `set_full_name`,
`set_phone`, `set_mfa_enabled`, `update_email`, `set_tokens_invalidated_after`) all call
`ObjectId(user_id)` without an `is_valid` guard.

In practice the `user_id` reaching these methods is always sourced from a prior
`get_by_id()` call (which already validated it), so there is no direct injection risk.
However, if an invalid ObjectId string reaches these methods (corrupted DB document, bug in
future code), the uncaught `bson.errors.InvalidId` propagates as an unhandled 500 rather
than a clean 404 or 400.

**Recommendation:** Add `if not ObjectId.is_valid(user_id): return` (or raise a 404) at
the top of each mutation method, matching the guard pattern already in `get_by_id` and
`delete`.

### I12 — Email-change JWT emits `iat` as `int` rather than `float`

**Section §7 — Session & Token Security**  
**File:** `src/regstack/routers/account.py:240`

`_encode_email_change_token` at line 240 uses `"iat": int(now.timestamp())` rather than
`"iat": now.timestamp()` (float). All other regstack-issued JWTs (session tokens via
`JwtCodec`, MFA pending tokens, phone-setup tokens) emit a float `iat` per the codebase's
stated bulk-revoke precision guarantee (see CLAUDE.md "Bulk revocation: float iat and <=
cutoff").

The email-change token does not participate in the session bulk-revoke comparison, so the
practical security impact today is nil. However, it violates the established pattern and
could become a subtle bug if the email-change flow is ever extended.

**Recommendation:** Change line 240 to `"iat": now.timestamp()`.

### I9 — `was_new_account` always `False` in `ExchangeResponse` (correctness bug)

**Section §14 — OAuth Subsystem Audit**  
**File:** `src/regstack/routers/oauth.py:138-155`

The `/oauth/exchange` endpoint hardcodes `was_new_account=False` in its response. The
actual new-account flag is computed in `_resolve_user` (called from the callback), but it
is not stored on the `OAuthState` row before the exchange endpoint reads it. Clients that

`was_new_account: bool = False` field) and return it from `exchange`.
