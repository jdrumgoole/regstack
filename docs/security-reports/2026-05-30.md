## 🟠 WARNING (Address within 1 week)

### W-1 (Carried from 2026-05-22) — PyJWKClient missing timeout (`src/regstack/oauth/providers/google.py:83`)

No change since the 2026-05-22 report. The constructor call is still:

```python
self._jwks_client = PyJWKClient(jwks_url, cache_keys=True)
```

No `timeout=` argument is passed. PR #80 correctly offloaded the JWKS network call to `asyncio.to_thread` (preventing event-loop blocking), but the underlying `urllib.request.urlopen` has no deadline. A slow or unresponsive Google JWKS endpoint holds a worker thread indefinitely; under concurrent OAuth load during a JWKS outage, this exhausts Python's default asyncio thread pool.

**Fix (one line):**
```python
self._jwks_client = PyJWKClient(jwks_url, cache_keys=True, timeout=5)
```
`pyjwt>=2.4` accepts this argument; the project floor is `pyjwt>=2.12.1`.

### W-2 (New) — Starlette 1.0.0 pinned; CVE-2026-48710 (BadHost) unfixed

**Advisory:** GHSA-86qp-5c8j-p5mr / CVE-2026-48710 / PYSEC-2026-161  
**CVSS:** 6.5 Medium (CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:L/A:N)  
**Fixed in:** Starlette 1.0.1, released 2026-05-21  
**Locked version:** `starlette==1.0.0` (confirmed in `uv.lock`)

**Finding:**  
Starlette reconstructs `request.url` by concatenating the raw HTTP `Host` header with the request path and re-parsing the result. Injecting `/`, `?`, or `#` into the `Host` header shifts where path boundaries fall in the reconstructed URL. Any code that gates access by checking `request.url.path` (rather than ASGI's `scope["path"]`) sees a manipulated path, enabling unauthenticated requests to bypass those guards.

**Impact on regstack specifically:**  
regstack's auth machinery uses FastAPI `Depends(rs.deps.current_user())` wired at the *endpoint* level. FastAPI resolves those dependencies via `scope["path"]` matching (not `request.url.path`), so regstack's own `current_user` / `current_admin` checks are NOT directly bypassable via this CVE.

**Impact on host applications:**  
regstack is a library. Host applications that embed regstack and apply additional path-based security with Starlette middleware (e.g. `TrustedHostMiddleware`, custom middleware reading `request.url.path`) are exposed. The library ships with Starlette 1.0.0 locked, so `pip install regstack` from the current wheel resolves the vulnerable version.

**Note:** Starlette 1.0.1 was released on 2026-05-21 — one day before the 2026-05-22 security review. That review marked §1 (Dependencies) as clean; this was a miss.

**Fix:**  
Add a direct Starlette floor to `pyproject.toml` following the project's established CVE-comment pattern:

```toml
# starlette>=1.0.1 picks up CVE-2026-48710 (BadHost — host-header path-
# poisoning bypass of request.url.path-based middleware guards).
"starlette>=1.0.1",
```

Then run `uv lock` to update `uv.lock`. This is safe: FastAPI 0.136.1 already allows Starlette 1.0.1 (its constraint is `starlette>=0.46.0`).

### I-1 (Carried from 2026-05-22) — `was_new_account` always `False` in OAuth exchange response (`src/regstack/routers/oauth.py:176`)

No change. The `ExchangeResponse.was_new_account` field is hardcoded to `False` in both code paths of `/oauth/exchange`:

```python
return ExchangeResponse(
    access_token=state.result_token,
    redirect_to=state.redirect_to,
    was_new_account=False,  # ← always False
    ...
)
```

The correct `was_new` boolean is computed during `_resolve_user` in the callback but not persisted to the `oauth_states` row. Not a security issue — a SPA receiving `False` when an account was genuinely new creates no exploitable condition. It is an API accuracy gap that may mislead host implementors building "Welcome! Account created." UX. Fix: add a `result_was_new: bool = False` column to `oauth_states` and populate it in the callback.

### I-3 (Carried from 2026-05-22) — Google token-exchange logs full response body at `WARNING` level (`src/regstack/oauth/providers/google.py:145`)

No change. `OAuthTokenExchangeError` is constructed with:

```python
raise OAuthTokenExchangeError(
    f"google token exchange failed: {response.status_code} {response.text}"
)
```

This exception is logged at `WARNING` level in `routers/oauth.py`. Google's token endpoint errors are standard JSON and do not contain the client secret or authorization code. No client-visible data leaks; risk is low. Suggested improvement: log the status code at `WARNING` and the response body at `DEBUG` to keep production logs clean:

```python
log.warning("google token exchange failed: HTTP %s", response.status_code)
log.debug("google token exchange response body: %s", response.text)
```

### §7 — Session & Token Security

- HS256 algorithm (configurable), secret ≥32 chars enforced at `JwtCodec` construction.
- Every JWT includes a `jti` generated with `secrets.token_urlsafe(16)`.
- `iat` emitted as `float` (RFC 7519 NumericDate) in `TokenPayload.to_claims()` — microsecond precision enables correct `iat <= cutoff` bulk-revoke comparison when a login completes in the same wall-clock second as a password change.
- pyjwt's automatic `exp`/`iat`/`nbf` checks explicitly disabled in `JwtCodec.decode`; both validated against the injected `Clock`. `FrozenClock` test determinism and production correctness both depend on this seam.
- `_authenticate` validates in the correct order: decode → blacklist (jti) → active user → bulk-revoke cutoff.
- Token decode errors return a single static `"Invalid or expired token."` 401 — the pyjwt exception text is never echoed to the client.
- Password-reset tokens are blacklisted on first successful use (`blacklist.revoke` called in `reset` endpoint), preventing replay of the same reset link.
- No token values appear in log messages.

- **PKCE:** `code_verifier` generated server-side with `secrets.token_urlsafe(64)`, stored on the `oauth_states` row. Only `code_challenge = sha256(verifier)` sent to the provider. Verifier never appears in a redirect URL.

- **Identity uniqueness:** `(provider, subject_id)` UNIQUE and `(user_id, provider)` UNIQUE enforced at DB level on both backends (Mongo: unique indexes; SQL: `UniqueConstraint`).
- **Hooks:** `oauth_signin_started`, `oauth_signin_completed`, `oauth_account_linked`, `oauth_account_unlinked` present in `KNOWN_EVENTS` and fired at correct points.
