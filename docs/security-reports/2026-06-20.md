## 🔴 CRITICAL

### C-1 · CVE-2026-48710 (BadHost) — Starlette host-header auth bypass (locked to 1.0.0; fix is 1.0.1)

**Severity:** CRITICAL  
**CVE:** CVE-2026-48710 / GHSA-86qp-5c8j-p5mr  
**Affected:** `starlette==1.0.0` (pinned in `uv.lock`). FastAPI depends on Starlette transitively; regstack depends on FastAPI.

**What it does:** Starlette < 1.0.1 reconstructs `request.url` by concatenating `http://{Host}{path}` and re-parsing the result. A Host header containing characters invalid under RFC 9112 §3.2 (e.g. `/`, `?`, or `#`) causes the parser to misalign the `path`/`query` boundary, producing a forged `request.url.path`. Any middleware or route guard that reads `request.url.path` for access-control decisions can be bypassed with no credentials. The attack requires a single malformed header — no prior auth, no victim interaction.

**Impact on regstack:** regstack's own auth is JWT-based (the `Authorization: Bearer` header), not path-based, so `_authenticate` in `auth/dependencies.py` is not directly affected. However:

1. Host applications commonly add path-based auth middleware (e.g., `TrustedHostMiddleware`, custom `BaseHTTPMiddleware`, or framework guards) in front of the mounted regstack router. Those middleware layers are vulnerable.
2. Starlette's routing table itself uses `request.url.path` to dispatch incoming requests. A crafted Host could potentially route a request to a different FastAPI path handler than intended.
3. The OAuth callback and SSR routers use path matching (`/{provider_name}/callback`, `/account/*`); a poisoned path could affect which route handler receives a request.
4. Public exploit code for this CVE is already circulating (GitHub: Bhanunamikaze/BadHost-CVE-2026-48710-Exploit). The coordinated disclosure came from X41 D-Sec / OSTIF. Millions of Starlette-based services are exposed.

**Fix:** Bump `starlette` to `>=1.0.1`. Because fastapi pins `starlette` in its own dependencies, the correct lever is to add a floor on `fastapi` that transitively pulls starlette 1.0.1. Check whether the latest `fastapi` release already pins `starlette>=1.0.1`; if so, bumping `fastapi>=<that version>` in `pyproject.toml` is sufficient. Also update `uv.lock` (`uv lock --upgrade-package starlette`).

### W-1 · PyJWT 2.12.1 locked — four CVEs fixed in 2.13.0

**CVEs:** CVE-2026-48526, CVE-2026-48525, CVE-2026-48524, CVE-2026-48523  
**Locked version:** `pyjwt==2.12.1` (`uv.lock`). `pyproject.toml` already requires `pyjwt>=2.12.1`; just `uv lock --upgrade-package pyjwt` is needed.

| CVE | Description | Regstack exposure |
|-----|-------------|-------------------|
| CVE-2026-48526 | Public-key JWK accepted as HMAC secret → forged HS256 tokens when mixed algorithm families are allowed | Low: regstack uses a single algorithm family per decode call (HS256 in `JwtCodec`, RS256 in `GoogleProvider`). Never mixed in one `pyjwt.decode` call. The advisory itself notes exploitation requires "both symmetric and asymmetric algorithms and a raw-JSON JWK as the key argument, both contrary to documented usage." Still worth patching. |
| CVE-2026-48525 | Unauthenticated DoS: decoding work (Base64URL + buffer alloc) occurs before signature rejection, enabling CPU/memory amplification | **Moderate**: Any caller who sends a token to a regstack endpoint (login, verify, etc.) triggers `JwtCodec.decode`. An attacker can send large crafted tokens to any auth endpoint and amplify work. No auth required. |
| CVE-2026-48524 | `PyJWKClient`: unbounded JWKS endpoint fetches when `kid` lookup fails on cache miss | **Moderate**: The `GoogleProvider` wraps `PyJWKClient`. An attacker who can supply a crafted `id_token` with an unknown `kid` can trigger repeated outbound JWKS fetches. Partially mitigated by the 5-second `timeout` on `PyJWKClient` and the `asyncio.to_thread` offload (previous W-1 fix), but the unbounded-retry path is still present. |
| CVE-2026-48523 | Unlimited outbound requests via `kid` header; surfaces only when JWKS fetch fails | Same as CVE-2026-48524. |

**Fix:** `uv lock --upgrade-package pyjwt` (resolves to 2.13.x). Also bump the floor in `pyproject.toml`: `pyjwt>=2.13.0` (base) and `pyjwt[crypto]>=2.13.0` (oauth extra). Add a comment noting the CVE batch.

### W-2 · IP address never collected for `record_failure` — `behind_proxy` config flag is inert

**File:** `src/regstack/routers/login.py`, `src/regstack/auth/lockout.py`

`LockoutService.record_failure` accepts an `ip: str | None = None` keyword argument, and `RegStackConfig` has a `behind_proxy: bool = False` field that implies per-IP tracking. However, every call site in `login.py` (lines 88, 102, 110, 116) calls `await rs.lockout.record_failure(payload.email)` with no `ip=` argument. The `login_attempts` collection/table always stores `NULL` for the IP field. The `behind_proxy` flag is read by no code path at runtime.

**Impact:** Per-IP audit logs are unavailable. Operators who want to know which IP is credential-stuffing a specific account have no data. The current email-based lockout still fires correctly, but it is trivially bypassed by rotating the target email address; IP-based lockout or alerting would provide the defence-in-depth. Any future rate-limit feature that reads `ip` from the stored attempts will see only NULLs.

**Fix (minimal):** In the login route, read `request.client.host` (or the appropriate proxy header when `rs.config.behind_proxy` is set) and pass it as `ip=` to each `record_failure` call. The `Request` object is already available in the endpoint signature.

### W-3 · `aiosmtplib` is a base dependency, not an optional extra

**File:** `pyproject.toml` line 42 (`dependencies` block)

`aiosmtplib>=3.0` is listed in the unconditional `dependencies` block. It is only used by `SmtpEmailService` (email backend `smtp`), which hosts opt into via `config.email.backend = "smtp"`. Hosts using the default `console` backend or the `ses` backend install `aiosmtplib` unconditionally — widening the supply-chain attack surface without benefit.

The `ses`, `sns`, `twilio`, and `oauth` backends are all correctly gated behind optional extras. `aiosmtplib` should join them in an `smtp` optional extra (or a bundled `email` extra).

**Fix:** Move `aiosmtplib>=3.0` from `[project.dependencies]` to `[project.optional-dependencies]` under a new key (e.g. `smtp = ["aiosmtplib>=3.0"]`). Update `pyproject.toml`, import guards, and any `uv sync` invocations in docs/CI that need SMTP.

## 🟡 INFO

### I-1 · `phone_number` and `tokens_invalidated_after` exposed in `UserPublic`

`UserPublic` includes both `phone_number` and `tokens_invalidated_after`. The `POST /verify` endpoint returns `UserPublic` to whoever clicks the verification link — this is correct since the phone belongs to the verified user — but admin list endpoints (`GET /admin/users`) return `UserPublic` for other users, meaning admins can read every user's phone number. The `tokens_invalidated_after` field is exposed to the SPA by design (so it can detect session invalidation without an extra request) but may surprise operators reviewing the wire format.

No change required unless the operator's threat model treats admin access to phone numbers as sensitive. Worth documenting in the `UserPublic` model docstring.

### I-2 · MFA pending-token encode/decode logic is triplicated

The MFA pending JWT is encoded in `routers/login.py:_encode_mfa_token` and `routers/oauth.py` (for OAuth-triggered MFA), and decoded in `routers/login.py:_decode_mfa_token`. Any change to the claim set (e.g. adding a `phone_number` hint claim) must be applied in three places in sync. A missed update could create a purpose-boundary bypass where a login-MFA token satisfies the OAuth-MFA verify path or vice versa.

**Fix:** Extract `encode_mfa_pending_token` / `decode_mfa_pending_token` helpers to `auth/tokens.py` (alongside the existing verification-token helpers). Both call sites import from a single module.

### I-3 · OAuth `state_row.id` appears in the browser address bar on `oauth-complete`

The `/{provider}/callback` handler redirects to `{ui_prefix}/oauth-complete?id={state_id}`. The `state_id` is a 32-byte URL-safe random value and the row is deleted within `completion_ttl_seconds` (default 30 s) after the exchange. However, while the SPA page is loaded, the ID is in the browser history and in the `Referer` header sent to any third-party resource the page loads (analytics scripts, fonts, etc.).

An attacker who captures the `state_id` within the 30-second window can call `POST /oauth/exchange` and obtain a session JWT — no additional credentials required.

**Mitigation options:** Use `history.replaceState` in `regstack.js` to strip the `id` parameter from the URL immediately after it is read; or switch to a `POST` redirect so the `state_id` never enters the URL at all (requires a JS-driven form submit). The 30-second window and the requirement for a co-present third-party leak make this low-urgency.

### I-4 · `POST /confirm-email-change` is unauthenticated by design but not documented

The email-change confirmation endpoint accepts a token in the request body and requires no `Authorization` header. This is intentional — the change-email flow bumps `tokens_invalidated_after`, which would sign the user out, so the confirmation link needs to work even without an active session. The decision is correct but is not documented in the function body, which could confuse a future reviewer into adding an auth dependency and breaking the flow.

**Fix:** Add a short comment above the endpoint explaining why it is unauthenticated.
