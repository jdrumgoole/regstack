### W-1 · CVE-2026-42561 — python-multipart DoS carries over from 2026-05-15 (unresolved)

**File:** `pyproject.toml`, line `"python-multipart>=0.0.26"`
**CVE:** [CVE-2026-42561](https://github.com/advisories/GHSA-pp6c-gr5w-3c5g)
**CVSS:** 7.5 (HIGH) — network-based, no auth required

This finding was first raised in the 2026-05-15 review (W-1) and has **not
been remediated**. `pyproject.toml` still declares:

```toml
# python-multipart>=0.0.26 picks up CVE-2026-40347 (DoS via oversized
# multipart preamble).
"python-multipart>=0.0.26",
```

Prior to 0.0.27, `MultipartParser` has no limit on the number or total size
of individual part headers inside a `multipart/form-data` request. An
unauthenticated attacker can send a request with thousands of repeated
headers (or one very large header value) without a terminator, causing the
event-loop worker to spin on CPU-exhaustive parsing before the request is
rejected. Every regstack consumer inherits this floor because
`python-multipart` is declared in the main `dependencies` list.

The latest release is 0.0.28 (2026-05-10). Upgrading the floor to `>=0.0.27`
closes CVE-2026-42561. The `>=0.0.28` floor is also safe and gives additional
distance from the two preamble/epilogue CVEs in 0.0.26.

**Remediation (one-line):** In `pyproject.toml`, change:

```toml
"python-multipart>=0.0.26",
```

to:

```toml
# python-multipart>=0.0.27 picks up CVE-2026-40347 (DoS via oversized
# multipart preamble/epilogue) and CVE-2026-42561 (DoS via unlimited
# part-header count/size; CVSS 7.5).
"python-multipart>=0.0.27",
```

### I-1 · Eight Mongo set_* methods lack ObjectId.is_valid() guard (carries over, unresolved)

**File:** `src/regstack/backends/mongo/repositories/user_repo.py`, lines 59–134

First raised 2026-05-15 (I-1). Still unresolved. `get_by_id()` (line 54) and
`delete()` (line 139) both call `ObjectId.is_valid(user_id)` before converting.
Eight mutation methods do not:

- `set_last_login` (line 59)
- `set_tokens_invalidated_after` (line 65)
- `update_password` (line 76)
- `set_active` (line 89)
- `set_superuser` (line 95)
- `set_full_name` (line 101)
- `set_phone` (line 107)
- `set_mfa_enabled` (line 113)
- `update_email` (line 119)

There is no current exploit path because all callers receive `user.id` already
validated via `get_by_id`. A future direct call with attacker-controlled input
would raise `bson.errors.InvalidId` — an unhandled 500 rather than a clean
404/400. The fix is to prepend `if not ObjectId.is_valid(user_id): return`
(or raise a `ValueError`) to each affected method, matching the existing
pattern.

### I-3 · OAuth callback logs provider-controlled error string without sanitization (carries over, unresolved)

**File:** `src/regstack/routers/oauth.py`, line 282

```python
log.info("oauth callback error from provider %s: %s", provider_name, error)
```

First raised 2026-05-15 (I-3). Still unresolved. The `error` query parameter
comes from the OAuth provider redirect and is attacker-controllable. A
compromised or misconfigured provider can inject newlines or ANSI escape
sequences into the server log stream. The HTTP redirect correctly uses the
hardcoded string `"oauth_failed"` rather than echoing `error`, so there is
no API-level injection. The risk is confined to log integrity.

**Remediation:**
```python
safe_error = (error or "")[:200].replace("\n", " ").replace("\r", " ")
log.info("oauth callback error from provider %s: %s", provider_name, safe_error)
```

### I-4 · Migration 0002 downgrade() comment describes a guard that is absent from the code (carries over, unresolved)

**File:** `src/regstack/backends/sql/migrations/versions/0002_oauth.py`, lines 79–91

First raised 2026-05-15 (I-4). Still unresolved. The comment on `downgrade()`
states "Refuse to roll back a NULL→NOT NULL column if any OAuth-only users
exist", but the implementation performs the `ALTER COLUMN … NOT NULL`
unconditionally. On PostgreSQL this raises a constraint violation at runtime
if OAuth-only users exist (noisy, but safe). On SQLite, `batch_alter_table`
silently completes the rewrite without enforcing the NOT NULL constraint,
leaving the database in a corrupt state that downstream code may rely on.

**Remediation:** Add a pre-check to `downgrade()`:
```python
def downgrade() -> None:
    import sqlalchemy as _sa
    conn = op.get_bind()
    count = conn.execute(
        _sa.text("SELECT COUNT(*) FROM users WHERE hashed_password IS NULL")
    ).scalar()
    if count:
        raise RuntimeError(
            f"Cannot downgrade: {count} OAuth-only user(s) with NULL hashed_password exist."
        )
    with op.batch_alter_table("users") as batch_op:
        batch_op.alter_column("hashed_password", existing_type=_sa.Text(), nullable=False)
    # ... rest of downgrade
```

### I-5 · oauth_states.mode validity not enforced at database level in MongoDB (carries over, unresolved)

**File:** `src/regstack/backends/mongo/indexes.py` vs `src/regstack/backends/sql/schema.py`

First raised 2026-05-15 (I-5). Still unresolved. The SQL schema enforces:

```python
CheckConstraint("mode IN ('signin', 'link')", name="ck_oauth_states_mode_valid")
```

The MongoDB backend has no equivalent. `OAuthState.model_validate()` runs on
every read, so no invalid value survives to a router in practice, but the
parity gap means a direct MongoDB write (admin script, migration tool) could
insert an invalid row that survives indefinitely until the next read cycle.

**Remediation:** Add a `$jsonSchema` validator on the `oauth_states`
collection in `install_indexes()`, or document the app-layer enforcement as
a deliberate design decision.

### I-6 · tokens_invalidated_after exposure in UserPublic not documented as security trade-off (carries over, unresolved)

**File:** `src/regstack/models/user.py`, line 99; `docs/security.md`

First raised 2026-05-15 (I-6). `docs/security.md` mentions
`tokens_invalidated_after` in the context of bulk revocation (lines 64, 176,

trade-off of exposing the last bulk-revoke timestamp to any session token
holder (including a stolen one). A host integrator who reads `docs/security.md`

documenting the consequence that the exact timestamp of the last

session token holder.

### I-7 · transport = "cookie" silently accepted but never implemented (carries over, unresolved)

**File:** `src/regstack/config/schema.py`, lines 12 and 99

First raised 2026-05-15 (I-7). `TokenTransport = Literal["bearer", "cookie"]`
is still defined, and `cookie_domain` is still a valid config field. However,
`AuthDependencies._authenticate` reads only `HTTPBearer` tokens — no
`Set-Cookie` response headers are ever set. A host that sets
`transport = "cookie"` in `regstack.toml` receives a silent no-op rather than
cookie-based session management, creating a security misconfiguration risk.

**Remediation:** Either implement cookie transport (with CSRF protection), or
restrict the type to `Literal["bearer"]` and add a `TODO: cookie transport`
comment pointing to the relevant milestone. Silently accepting the value is
the worst option.

### §6 Rate limiting
`LockoutService.check()` fires **before** password verification in the login
route — a locked-out attacker cannot determine whether their guess was correct.
Even with correct credentials, disabled/unverified accounts increment the
counter. MongoDB `login_attempts` has a TTL index sized to
`login_lockout_window_seconds`. SQL backends use `count_recent()` with a
parameterised cutoff + `purge_expired()`. `rate_limit_disabled=True`
short-circuits lockout only in tests. OAuth state TTL defaults to 300 seconds;
Mongo has a TTL index (`oauth_state_ttl`); SQL `purge_expired()` reaps expired
rows. `limit` is capped at 200 on paginated admin endpoints.

### §7 Session and token security

### §14 OAuth subsystem
- **PKCE:** `code_verifier` (`secrets.token_urlsafe(64)`) stored on the
  `oauth_states` row. Only `code_challenge` (its SHA-256 with `S256` method)
  appears in the provider redirect URL. Verified in `_begin_flow()`.
- **State row lifecycle:** Expiry checked with `rs.clock.now()` (clock-injected,
  not `datetime.now(UTC)` directly). `consume()` is atomic — SQL backend uses
  `SELECT` + `DELETE` inside a single `engine.begin()` transaction; Mongo uses
  `find_one_and_delete`. Missing row → 404; expired row → 400 with `state_expired`.
- **ID-token verification:** signature via JWKS, `iss`, `aud`, `exp`, `iat`,
  `nonce` all validated. `require=` claim list enforced. Any failure raises
  `OAuthIdTokenError` with a generic outer message; specifics logged via
  `log.warning`.
- **Linking policy:** `email_in_use` blocks silent account takeover.
  `auto_link_verified_emails=True` AND provider `email_verified=true` both
  required for auto-link. `identity_in_use` and `already_linked` prevent
  silent identity transfer or re-linking attacks.
- **OAuth-only users:** `/login` with `hashed_password=None` returns same
  generic 401 as wrong password. `/change-password`, `/change-email`,
  `/account` (DELETE), `/phone/start` return 400 via `require_password_set()`.
  `/oauth/{provider}/link` (DELETE) returns 400 when unlinking the only
  sign-in method.
- **Identity uniqueness:** `(provider, subject_id)` and `(user_id, provider)`
  unique constraints enforced at DB level — `provider_subject_unique` and
  `user_provider_unique` in both Mongo indexes and SQL `UniqueConstraint`
  declarations.
