## 🟠 WARNING (Address within 1 week)

### W-1 — PyJWKClient missing explicit timeout (`src/regstack/oauth/providers/google.py:83`)

**Status:** Open — carried forward from 2026-05-22 review (W-1), 2026-05-21 review, 2026-05-20 review (I-3).

**Finding:**

```python
# google.py:83
self._jwks_client = PyJWKClient(jwks_url, cache_keys=True)
```

No `timeout` argument is passed to `PyJWKClient`. pyjwt 2.4+ defaults this to `30` seconds internally, but the absence is a standing audit gap. The JWKS fetch was correctly offloaded to `asyncio.to_thread` (PR #80, 2026-05-20) so the event loop is no longer blocked. The remaining risk is **asyncio thread-pool exhaustion**: under sustained OAuth load, if Google's JWKS endpoint becomes slow or unreachable, each cache-miss request parks a worker thread for up to 30 s. Python's default thread pool is bounded (`min(32, cpu_count + 4)` threads); exhausting it stalls all `asyncio.to_thread` calls across the process.

**Fix:** One-line change in `google.py`:

```python
self._jwks_client = PyJWKClient(jwks_url, cache_keys=True, timeout=5)
```

PyJWT >= 2.4.0 (project requires >= 2.12.1) accepts `timeout` on `PyJWKClient.__init__`.

### I-1 — `was_new_account` always `False` in `/oauth/exchange` response (`src/regstack/routers/oauth.py:171,179`)

**Status:** Open — carried forward from 2026-05-22 review (I-1).

**Finding:**

```python
# oauth.py:171
return ExchangeResponse(
    access_token=state.result_token,
    redirect_to=state.redirect_to,
    was_new_account=False,   # ← always hardcoded
    ...
)
```

`_resolve_user` correctly computes and returns `was_new` but the value is never threaded through `oauth_states` to the `/oauth/exchange` endpoint. The `ExchangeResponse.was_new_account` field therefore always returns `False`. Hosts or UIs that rely on this field to show a "Welcome, thanks for signing up!" flow will never trigger it via OAuth paths.

**Impact:** Low — not a security vulnerability; a feature correctness bug. Documented here for tracking continuity. The authentication and identity lifecycle are unaffected.

**Fix:** Store `was_new` on the `oauth_states` row (new boolean column) and populate `was_new_account` from that row on exchange.

### I-2 — OAuth token-exchange logs full Google error response body (`src/regstack/oauth/providers/google.py:145`)

**Status:** Open — carried forward from 2026-05-22 review (I-3).

**Finding:**

```python
# google.py:143-146
if response.status_code != 200:
    raise OAuthTokenExchangeError(
        f"google token exchange failed: {response.status_code} {response.text}"
    )
```

`response.text` is the full body of Google's token-endpoint error response. The router catches this as a warning log:

```python
# oauth.py:315-316
except OAuthTokenExchangeError as exc:
    log.warning("oauth token exchange failed: %s", exc)
```

Google error responses for `invalid_grant` or `invalid_client` contain structured JSON that is entirely safe to log. However, if the token endpoint ever echoes back attacker-controlled content (e.g., a carefully crafted `code` parameter that triggers reflection in an error body), it would flow into server logs. This is a low-probability risk since Google's token endpoint is well-behaved, but inconsistent with the principle of not echoing provider-controlled data.

**Impact:** Very low under normal circumstances; theoretical under a rogue/compromised provider scenario.

**Fix:** Log only `response.status_code` and a truncated or sanitised excerpt:

```python
raise OAuthTokenExchangeError(
    f"google token exchange failed: {response.status_code}"
)
```

### I-3 — Login lockout: `record_failure` called after password check, not before (`src/regstack/routers/login.py`)

**Status:** New finding (not in prior reviews).

**Finding:**

The current login flow in `login.py` is:

1. `rs.lockout.check(email)` → if locked, return 429
2. Look up user by email
3. If user not found → `record_failure` → 401
4. **Verify password** → if wrong → `record_failure` → 401
5. `is_active` check → `record_failure` → 403
6. `is_verified` check → `record_failure` → 403

`record_failure` runs **after** the password check completes. This means: on the final attempt that reaches the lockout threshold (attempt `N = threshold`), the attacker observes a **401** ("Invalid email or password") rather than a **429**. They therefore know their `N`th guess was wrong. On attempt `N+1`, they get 429 and are locked out.

The security prompt mandates: *"record_failure must run before the password is verified so a locked-out attacker can't probe whether their guess was right."* The current implementation satisfies the spirit for **already-locked** attackers (they always see 429), but not for the **lockout-triggering** attempt.

**Mitigation consideration:** The current ordering is partly intentional — the comment in `login.py` notes that checking `is_active` / `is_verified` only after a correct password prevents account-state enumeration (an attacker who can't verify the password can't reach the 403 path to discover the account exists but is disabled). Moving `record_failure` unconditionally before the password check would reintroduce that enumeration risk. A compliant fix needs to handle this carefully:

```python
# Option: record failure + re-check lockout after verifying password
if not password_correct:
    await rs.lockout.record_failure(email)
    post_failure_decision = await rs.lockout.check(email)
    if post_failure_decision.locked:
        return JSONResponse(429, ...)  # don't reveal password was wrong
    raise 401
```

**Impact:** Marginal — the attacker could have learned the same information by observing that their previous N-1 attempts returned 401, so the Nth one tells them nothing new. Defence-in-depth recommendation only.
