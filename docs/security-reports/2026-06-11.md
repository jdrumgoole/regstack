## 🟠 WARNING (Address within 1 week)

### W-1 — CVE-2026-48710 (Starlette Host-Header Auth Bypass) — Starlette 1.0.0 in lockfile

**CVE:** CVE-2026-48710 ("BadHost")  
**CVSS:** HIGH  
**Affected:** Starlette < 1.0.1  
**Pinned version:** `starlette==1.0.0` (via FastAPI 0.136.1 in `uv.lock`)  

**Finding:**

`uv.lock` resolves `fastapi==0.136.1` → `starlette==1.0.0`. Starlette 1.0.0 does not validate the HTTP `Host` header before using it to reconstruct `request.url`. A malformed Host header (containing `/`, `?`, or `#`) shifts the apparent path boundary, causing path-based authentication middleware to evaluate the wrong path. Starlette 1.0.1 patches this by validating the Host value against RFC 9112 §3.2 / RFC 3986 §3.2.2.

**Impact on regstack specifically:**

regstack's own authentication is via `HTTPBearer` + FastAPI `Depends(rs.deps.current_user())` on each endpoint, not path-matching middleware. A malformed Host header cannot cause regstack's JWT bearer checks to be skipped because those checks are not predicated on the request path. So regstack's own auth surface is not directly exploitable via CVE-2026-48710.

The risk is downstream: a host app that adds a path-based auth middleware (e.g., "everything under `/admin` requires auth") on top of regstack may be bypassable via this vector. Since regstack is an embeddable library and its `fastapi>=0.120.0` floor allows `starlette==1.0.0` to resolve, hosts installing regstack today silently inherit the vulnerable Starlette.

**Fix:**

1. **Immediate:** Bump `uv.lock` by upgrading the FastAPI version to one whose `starlette>=` dependency constraint excludes 1.0.0. Starlette 1.1.0 is the latest release; confirm the FastAPI pin pulls `starlette>=1.0.1`.
2. **Floor:** Once the fixing FastAPI version is identified, update the `pyproject.toml` lower bound and add a comment per the project's CVE-comment pattern:

   ```toml
   # fastapi>=X.Y.Z requires starlette>=1.0.1, which fixes CVE-2026-48710
   # (Host-header path poisoning / auth bypass in Starlette ≤ 1.0.0).
   "fastapi>=X.Y.Z",
   ```

3. **Note for hosts:** Until the floor is bumped, any host app deploying path-based auth middleware alongside regstack should lock `starlette>=1.0.1` explicitly.

## 🟡 INFO (Best practice recommendations)

### I-1 — CVE-2026-48526 (PyJWT algorithm confusion) — floor below fix version

**CVE:** CVE-2026-48526  
**Fixed in:** PyJWT >= 2.13.0  
**Pinned version:** `pyjwt==2.12.1` (current floor: `pyjwt>=2.12.1`)  

**Finding:**

CVE-2026-48526 is an algorithm-confusion vulnerability: when an application decodes JWTs using a raw JWK JSON string as the verification key while the key might be interpreted as either HMAC or RSA material, an attacker can sign a forged token using the public JWK as an HMAC secret. Fixed in PyJWT 2.13.0.

**Assessment of regstack's exposure:**

Regstack's own JWT codec (`src/regstack/auth/jwt.py`) uses HS256 exclusively with bytes derived from `config.jwt_secret` via `derive_secret`. It never passes JWK JSON strings as keys. The `GoogleProvider` uses `PyJWKClient.get_signing_key_from_jwt()` which returns a typed key object (not a raw JSON string), and decodes with `algorithms=["RS256"]` — a single asymmetric algorithm, no mixing.

The exploitation requirement ("mixed algorithm families, raw JWK string as key") is not present in regstack's codebase. Direct exploitability is therefore **low**. Nonetheless, `pyjwt>=2.13.0` is the security-maintained floor.

**Fix:**

Bump the PyJWT floor in `pyproject.toml`:

```toml
# pyjwt>=2.13.0 fixes CVE-2026-48526 (JWK algorithm confusion;
# direct impact on regstack is low — HMAC and RS256 are never mixed —
# but the floor keeps hosts on the patched branch).
"pyjwt>=2.13.0",
```

Also update `uv.lock` with `uv sync` after the bump.

### §7 — Session & Token Security

- HS256 algorithm (configurable), `jwt_secret` validated non-empty at `JwtCodec` construction.
- Every JWT includes a `jti` generated with `secrets.token_urlsafe(16)`.
- `iat` emitted as `float` (RFC 7519 NumericDate); `exp` stored as `int`. Float `iat` enables correct `iat <= cutoff` bulk-revoke comparisons in the same wall-clock second as a password change.
- pyjwt's `exp`/`iat`/`nbf` automatic checks disabled; both are validated against the injected `Clock` so `FrozenClock`-driven tests remain deterministic.
- `_authenticate` validates in order: decode → blacklist (`jti`) → active user → bulk-revoke cutoff. All four gates in place.
- Token decode errors produce a single static "Invalid or expired token." 401; the pyjwt exception text is never echoed to the client.
- Password-reset tokens blacklisted on first use (`blacklist.revoke(jti, exp)` after successful reset), preventing replay.
- **PyJWKClient timeout:** `PyJWKClient(jwks_url, cache_keys=True, timeout=JWKS_FETCH_TIMEOUT_SECONDS)` with `JWKS_FETCH_TIMEOUT_SECONDS = 5`. W-1 from 2026-05-22 review — fixed in PR #96 ✓.
- JWKS fetch offloaded to `asyncio.to_thread` to avoid blocking the event loop on cache misses (W-1 from 2026-05-20, fixed in PR #80 ✓).
- No token values appear in log messages.
