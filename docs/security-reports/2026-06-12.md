## 🟠 WARNING (Address within 1 week)

### W-1 — CVE-2026-48710 (Starlette BadHost): `starlette==1.0.0` in lock below patched `1.0.1`

**CVE:** CVE-2026-48710 ("BadHost")  
**CVSS:** High / Critical (widely reported as critical for AI/agent deployments)  
**Affected:** Starlette < 1.0.1 — fixed in Starlette 1.0.1 (shipped 2026-05-21)

**Finding:**

`uv.lock` resolves `starlette` to **1.0.0**, which is one patch release below the CVE fix:

```
name = "starlette"
version = "1.0.0"
```

The vulnerability: prior to 1.0.1, the HTTP `Host` request header was not validated before being used to reconstruct `request.url`. A single malformed character in the `Host` header can cause `request.url.path` to diverge from the actual routed path in `scope["path"]`. Middleware or endpoints that apply security checks against `request.url.path` (e.g. CORS allow-lists, path-prefix deny rules) can therefore be bypassed.

**Regstack's direct exposure is low**: every regstack endpoint authenticates via `Authorization: Bearer <token>` (HTTPBearer), and FastAPI's internal route-matching uses `scope["path"]`, not `request.url.path`. No regstack endpoint or middleware makes security decisions from `request.url.path`.

**Host app risk is real**: any host that wraps regstack's mounted router with path-based middleware (rate limiting, CORS, IP allow-lists, WAF-like checks keyed on `request.url`) is exposed. Because regstack ships a `uv.lock`, a host that runs `uv sync` against the library would pull in the vulnerable version.

**Fix:**

```bash
uv lock --upgrade-package starlette
# Verify lock resolves to starlette>=1.0.1
```

Also update the lower-bound comment in `pyproject.toml` if a FastAPI version constraint is needed to pull the new Starlette:

```toml
# fastapi>=0.116.0 pulls Starlette>=0.46.2 (Starlette 1.0.1 is the 1.x branch fix).
"fastapi>=0.120.0",  # existing lower bound already satisfies this
```

The existing `fastapi>=0.120.0` lower bound already surpasses 0.116.0; only the `uv.lock` needs refreshing.

### W-2 — CVE-2026-48526 (PyJWT Algorithm Confusion): `pyjwt==2.12.1` in lock below patched `2.13.0`

**CVE:** CVE-2026-48526  
**Affected:** PyJWT < 2.13.0 — fixed in PyJWT 2.13.0  

**Finding:**

`uv.lock` resolves `pyjwt` to **2.12.1**, and `pyproject.toml` declares:

```toml
"pyjwt>=2.12.1",
```

CVE-2026-48526: when an application decodes tokens using a raw JSON Web Key (JWK) string while simultaneously supporting mixed algorithm families (symmetric + asymmetric), PyJWT < 2.13.0 does not validate that the key matches its intended algorithm context. An attacker can sign a forged token with the raw bytes of a public JWK string treated as an HMAC-SHA256 secret, bypassing authentication.

**Regstack's direct exposure is limited**: regstack's HMAC-signed tokens (session, password reset, email change, phone setup, login-MFA) derive keys via `config/secrets.derive_secret(jwt_secret, purpose)` — raw bytes from an HMAC derivation, never JWK strings. The `GoogleProvider.verify_id_token` path restricts to `algorithms=["RS256"]` only, so a symmetric/asymmetric confusion attack cannot flip an RS256 verification to HMAC. None of regstack's decode calls pass a JWK string as the key.

**Host app risk**: a host that imports `pyjwt` for its own token handling, or that uses a mixed-algorithm path alongside regstack's installation, could be vulnerable through the `pyjwt==2.12.1` pin in the lock.

**Fix** — two changes required:

1. Update `pyproject.toml` lower bound (also the `oauth` extra):
```toml
"pyjwt>=2.13.0",        # was >=2.12.1; CVE-2026-48526 fix
# oauth extra:
"pyjwt[crypto]>=2.13.0",
```

2. Refresh the lock:
```bash
uv lock --upgrade-package pyjwt
```

## 🟡 INFO (Best practice recommendations)

### I-1 — Registration endpoint reveals email existence (deliberate trade-off, review annually)

**Location:** `src/regstack/routers/register.py:34`

```python
existing = await rs.users.get_by_email(payload.email)
if existing is not None:
    raise HTTPException(status_code=409, detail="An account with that email already exists.")
```

`POST /register` returns HTTP 409 when the email is already registered, making it trivially possible to enumerate registered addresses. `POST /forgot-password` and `POST /resend-verification` both apply anti-enumeration (always 202). The registration 409 is a documented trade-off — eliminating it would require sending a "you already have an account" email on every duplicate attempt, with no change to the happy path. Re-evaluate if the user base contains high-value targets (executives, regulated data subjects).

**No code change recommended at this time.** Note the asymmetry in the threat model when updating `docs/security.md`.

### I-2 — Per-route IP rate limits all default to `None`

**Location:** `src/regstack/config/schema.py:224–241`

Every `*_rate_limit` config option (`login_rate_limit`, `register_rate_limit`, `forgot_password_rate_limit`, …) defaults to `None`, meaning no per-IP rate limiting unless the operator explicitly configures it. The per-account login lockout (`LockoutService`) provides protection against credential-stuffing on a single account but does not bound the rate at which different accounts can be targeted from one IP.

The `rate_limit` optional extra (`slowapi>=0.1.9`) is available and documented; operators must opt in. Consider adding recommended default strings (e.g. `"10/minute"` for login) to the documentation or the `regstack init` wizard output to reduce the chance of a misconfigured deployment.
