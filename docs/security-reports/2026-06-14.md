### W-1 · Starlette 1.0.0 in `uv.lock` — CVE-2026-48710 (BadHost)

**Affected:** `uv.lock` → `starlette 1.0.0`  
**CVE:** CVE-2026-48710 (CVSS not yet published at review time)  
**Fixed in:** Starlette 1.0.1 (shipped 2026-05-21)

Starlette ≤ 1.0.0 reconstructs `request.url` by concatenating the raw HTTP `Host`
header with the request path and re-parsing the result. A `Host` value containing
`/`, `?`, or `#` shifts the `path`/`query` boundaries, so `request.url.path` can
return a value different from the path the ASGI server actually dispatched to. An
attacker who controls the `Host` header (trivial for clients) can therefore make
`request.url.path` return an arbitrary alternative string.

**regstack-specific impact:** regstack's own auth is entirely endpoint-level (JWT
Bearer via `Depends(rs.deps.current_user())`), not path-based middleware. A crafted
`Host` header cannot bypass regstack's `_authenticate()`. However:

1. Hosts that deploy path-based auth middleware (e.g. `if request.url.path.startswith("/admin")`)
   alongside regstack inherit the vulnerable Starlette and can be bypassed.
2. The SSR `build_ui_router` pages resolve routes via Starlette's dispatch internals.
3. Good library hygiene requires shipping known-unvulnerable transitive dependencies.

**Remediation:**
```toml
# pyproject.toml — add an explicit floor for downstream consumers
dependencies = [
    "fastapi>=0.120.0",
    "starlette>=1.0.1",   # ← add: CVE-2026-48710 BadHost fix
    ...
]
```
```bash
uv lock --upgrade-package starlette
```

### W-2 · PyJWT 2.12.1 in `uv.lock` — CVEs -48523 and -48526 require 2.13.0+

**Affected:** `uv.lock` → `pyjwt 2.12.1`; `pyproject.toml` floor `pyjwt>=2.12.1`  
**CVEs:**
- CVE-2026-48523: Improper signature verification via `jwt.decode` with a `PyJWK` key
- CVE-2026-48526: Algorithm-confusion attack when decoding with mixed RS256+HS256 and a raw JWK string  
**Fixed in:** PyJWT 2.13.0

**regstack-specific exposure:**

*CVE-2026-48526* (mixed-algorithm confusion) requires the application to accept both
symmetric (HS256) and asymmetric (RS256) algorithms and pass a raw JWK JSON string as
the verification key. regstack's `JwtCodec` uses HS256 with HMAC-derived secrets
(`derive_secret(jwt_secret, purpose)`), never JWK. This CVE **does not apply** to
the internal session/purpose token path.

*CVE-2026-48523* ("improper signature verification via `jwt.decode` with a `PyJWK`
key") is more relevant: `GoogleProvider.verify_id_token` in
`src/regstack/oauth/providers/google.py` calls `PyJWKClient.get_signing_key_from_jwt()`
and passes the resulting key object to `pyjwt.decode(..., algorithms=["RS256"])`.
While regstack uses a single algorithm (`RS256`), not a mixed set, the NVD description
is broad enough that the exact exploit surface is unclear pending a full PyJWT 2.13.0
changelog review. Upgrading is the safe and straightforward action.

Additionally, the `pyproject.toml` floor `pyjwt>=2.12.1` means downstream consumers
who rely on the lower bound could resolve to a version with open advisories.

**Remediation:**
```toml
# pyproject.toml
"pyjwt>=2.13.0",         # was 2.12.1 — bumps past CVE-2026-48523/48526
...
# oauth extra
oauth = ["pyjwt[crypto]>=2.13.0", "cryptography>=46.0.7"]
```
```bash
uv lock --upgrade-package pyjwt
```

## 🟡 INFO (Best-practice recommendations)

### I-1 · JWT secret minimum length not enforced at config layer

**Location:** `src/regstack/config/schema.py:186-297`, `src/regstack/auth/jwt.py:118-122`

`RegStackConfig.jwt_secret` only validates that the value is non-empty at the
`JwtCodec` constructor. A very short secret (e.g. `jwt_secret = "abc"`) passes config
validation and would significantly weaken HMAC-SHA256. The CLAUDE.md documents
"≥32 chars enforced at construction" but this is not in the code.

The `generate_secret()` helper produces 64-byte URL-safe secrets; the wizard uses it.
The gap is that a host who skips the wizard and sets a short secret in `regstack.toml`
gets no warning.

**Recommendation:** Add a minimum-length validator in `RegStackConfig` (suggest ≥ 32
characters) that fires a `UserWarning` (not a hard error, to keep tests using
`FrozenClock` unaffected) when the secret length is between 1 and 31 characters:

```python
@field_validator("jwt_secret")
@classmethod
def _warn_empty_secret(cls, v: SecretStr) -> SecretStr:
    secret = v.get_secret_value()
    if 0 < len(secret) < 32:
        import warnings
        warnings.warn(
            "jwt_secret is shorter than 32 characters; use `regstack init` "
            "to generate a cryptographically strong secret.",
            stacklevel=2,
        )
    return v
```

### I-2 · Registration endpoint reveals email existence via HTTP 409

**Location:** `src/regstack/routers/register.py:34-39`

`POST /register` returns `409 Conflict` with `"An account with that email already
exists."` when the email is already registered. This lets an unauthenticated attacker
enumerate valid email addresses.

**Assessment:** This is a standard and widely accepted trade-off for registration UX.
The alternative (silent no-op for duplicate emails) is confusing and breaks many
email-on-sign-up flows. `/forgot-password` and `/resend-verification` already use the
anti-enumeration 202 pattern. This finding is noted for completeness; the current
behaviour is intentional and documented.

No code change required unless the host's threat model explicitly forbids email
enumeration at registration time (e.g. high-privacy applications). If hardening is
desired: respond 201/202 to every registration with the same body, then email the
address either a confirmation link or a "someone tried to register with your email"
notice.

### I-3 · `UserPublic.tokens_invalidated_after` exposes bulk-revoke timestamp

**Location:** `src/regstack/models/user.py:104-108`

`GET /me` and all admin user-read endpoints include `tokens_invalidated_after` in the
response JSON. A user holding a valid access token can observe the exact UTC timestamp
of their last password change / email change / admin disable event.

**Assessment:** The exposure is documented and intentional (docstring: "SPAs comparing
this to their session JWT's `iat` can tell when the token they hold has been
invalidated … without making another request"). It does not create an exploitable path
because the field only becomes visible after a successful authentication. It does leak
the timestamp of sensitive account events, which hosts with strict privacy requirements
may wish to suppress.

**Recommendation:** If any host's privacy policy prohibits disclosing the time of
security events, document a pattern for overriding `UserPublic` with a subclass that
excludes the field. No change to regstack core required.
