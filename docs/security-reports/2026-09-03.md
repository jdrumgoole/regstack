## 🟠 WARNING

### W-1 (carry-over, day 24 — SLA MISSED 2026-08-18)

**Section:** §1 — Dependency Vulnerability Check
**CVE:** CVE-2026-69247 — `cryptography` Bleichenbacher oracle (`pkcs7_decrypt`)
**Affected range:** `cryptography` ≥ 44.0.0, < 50.0.0
**Resolved in:** `cryptography==50.0.0` (released 2026-07-31 — 34 days ago)
**Current resolved version in `uv.lock`:** 49.0.0 (within affected range)
**Current floor in `pyproject.toml`:** `cryptography>=48.0.1` (does not exclude affected versions)
**Fix required:** Bump floor to `cryptography>=50.0.0` in both the `oauth` and `dev` extras in
`pyproject.toml`; run `uv lock`.
**Tracking:** GitHub issue #181 (`[security] Raise cryptography floor to >=50.0.0`), open since
2026-08-19 — no fix PR, no assignee, no comment — **16 days unacknowledged.**

**Technical impact:** `pkcs7_decrypt_der`, `pkcs7_decrypt_pem`, and `pkcs7_decrypt_smime` expose
distinguishable error paths and timing differences during RSA `RecipientInfo.encryptedKey` decryption,
constituting a Bleichenbacher-style oracle. regstack does not call these functions directly, but
`pip install regstack[oauth]` resolves to 49.0.0 by default, shipping a version with an open advisory
to all downstream consumers. The fix (cryptography 50.0.0+) substitutes a random key on RSA
decryption failure per RFC 3218.

**Urgency:** The fix version has been on PyPI for 34 days. The 7-day SLA lapsed 2026-08-18. This
finding will appear daily until resolved.

### W-2 (carry-over, day 3 — NEW 2026-09-01) — `POST /confirm-email-change` email-change JWT not revoked after use

**Section:** §3 — Authentication & Authorization Audit
**File:** `src/regstack/routers/account.py`, `confirm_email_change` handler
**Status:** Unresolved. No change to `account.py` since first flagged.

The `confirm_email_change` endpoint successfully updates the user's email address but does not
call `await rs.blacklist.revoke(token_payload.jti, token_payload.exp)` after doing so. The
password-reset path (`password.py`) correctly performs this revocation after every successful
reset. Within the email-change token's TTL, the same confirmation URL can be submitted repeatedly.
Each subsequent submission attempts `update_email`, which succeeds as a no-op when the address is
already the user's own, and the endpoint returns HTTP 200 — confirming the link is still usable.

**Fix:** Add `await rs.blacklist.revoke(token_payload.jti, token_payload.exp)` immediately after
the successful `update_email` call. The `jti` and `exp` claims are already decoded by
`_decode_email_change_token`; pass them through to the handler via a `TokenPayload`-like object
or by expanding `_decode_email_change_token` to return them.

### W-3 (carry-over, day 3 — NEW 2026-09-01) — `POST /confirm-email-change` bulk-revoke not applied to email-change tokens

**Section:** §3 — Authentication & Authorization Audit
**File:** `src/regstack/routers/account.py`, `confirm_email_change` handler
**Status:** Unresolved. No change to `account.py` since first flagged.

`AuthDependencies._authenticate` calls `is_payload_bulk_revoked(payload, user.tokens_invalidated_after)`
for session tokens. The `confirm_email_change` endpoint decodes the email-change JWT and calls
`get_by_id` + `update_email` with no equivalent temporal cutoff check. Because the purpose-derived
key correctly prevents session tokens from satisfying this endpoint, the purpose isolation is sound —
but a stale email-change token minted before a password-change event can still be used after
`tokens_invalidated_after` has been bumped.

**Attack scenario:**
1. User initiates email-change → token minted at `iat=T1`, link emailed.
2. User detects compromise of email account, changes password → `tokens_invalidated_after` bumped to `T2 > T1`.
3. Attacker (who has inbox access) clicks the email-change link minted at `T1` → `confirm_email_change`
   succeeds because `T1 < T2` is never evaluated.
4. Attacker now controls the user's email address.

**Fix:** After decoding the email-change JWT in `confirm_email_change`, fetch the user record and check
`if rs.auth.is_payload_bulk_revoked(token_payload, user.tokens_invalidated_after): raise HTTPException(400, ...)`.
The pattern mirrors the `_authenticate` dependency. Both W-2 and W-3 can be fixed in a single pass
through `confirm_email_change`.

### W-4 (carry-over, day 3 — NEW 2026-09-01) — OAuth `_resolve_user` unhandled `UserAlreadyExistsError` → HTTP 500

**Section:** §3 / §14 — Authentication & Authorization / OAuth Subsystem
**File:** `src/regstack/routers/oauth.py`, `_resolve_user` (brand-new account path, line ~716),
`oauth_callback` (line ~325)
**Status:** Unresolved. No change to `oauth.py` since first flagged.

A race between a concurrent email registration and the OAuth sign-in flow creates an unhandled
exception path that returns HTTP 500 to the user's browser. `oauth_callback` catches only
`_LinkConflictError`; `UserAlreadyExistsError` from `rs.users.create()` propagates unhandled.

**Scenario:**
1. User clicks "Sign in with Google" with `email@example.com`.
2. `_resolve_user` calls `get_by_email("email@example.com")` → returns `None`.
3. Concurrently, another request completes `POST /register` with the same email.
4. `_resolve_user` calls `rs.users.create(new_user)` → raises `UserAlreadyExistsError`.
5. `oauth_callback` catches only `_LinkConflictError`; `UserAlreadyExistsError` propagates as HTTP 500.

**Fix:** In `_resolve_user`, wrap `rs.users.create(new_user)` in a `try/except UserAlreadyExistsError`
and re-raise as `_LinkConflictError("email_in_use")`. This is consistent with how the auto-link
policy already handles the known-email case.

### I-5 — SNS backend uses ambient boto3 credential chain; no explicit credential config (carry-over)

**File:** `src/regstack/sms/sns.py`, line 29
`aioboto3.Session()` is constructed with no credentials — always falls back to boto3's ambient chain
(env vars, IAM instance profile). The `SmsConfig` model has no `sns_access_key_id` /
`sns_secret_access_key` fields, unlike the SES email backend which offers explicit key
configuration. Hosts cannot supply explicit SNS credentials via `regstack.toml`; they must rely on
ambient IAM roles. This asymmetry with the SES backend should be documented in the operator guide
and optionally addressed by adding explicit SNS credential config fields.

### I-6 — GoogleProvider stores `client_secret` as plain `str` in-memory (carry-over)

**File:** `src/regstack/oauth/providers/google.py`, lines 79, 90
`OAuthConfig.google_client_secret` is correctly declared as `SecretStr | None` in
`config/schema.py`. However, `GoogleProvider.__init__` takes `client_secret: str` (already
extracted via `.get_secret_value()`) and stores it as `self._client_secret: str`. Once extracted
from `SecretStr`, Pydantic's repr-masking is lost. No existing log call exposes the value —
`exchange_code()` logs only the HTTP status code on error — but the protection now relies on
code discipline rather than type enforcement. Recommendation: keep the `SecretStr` type through
to storage (`self._client_secret: SecretStr`) and call `.get_secret_value()` only at the
token-exchange call site.

### I-7 — OAuth state expiry uses strict `<` (less-than); other token types use `<=` (carry-over)

**File:** `src/regstack/routers/oauth.py`, lines 157, 302
`oauth_callback` and `exchange` check `if state_row.expires_at < rs.clock.now()`. Pending
registration expiry (`verify.py`) uses `<=`; JWT expiry in `JwtCodec.decode` uses `>=`
(equivalent to `exp <= now`). A state row whose `expires_at` is exactly `rs.clock.now()` passes
in the OAuth path but would be rejected by the other two mechanisms. The difference is
submicrosecond and practically unreachable, but the inconsistency should be unified to `<=` to
match the conservative posture used elsewhere.

### I-8 — TOML injection risk in `cli/init.py` `_render_toml()` (carry-over)

**File:** `src/regstack/cli/init.py`
User-supplied strings (app_name, base_url, from_address, smtp_host, etc.) are embedded into a
TOML file via Python f-strings without escaping TOML-special characters. A value containing `"`
followed by a newline and a valid TOML key could produce unexpected config keys. Exploitability
is nil in interactive use (the attacker controls their own wizard and their own config file), but
if the wizard is ever invoked non-interactively with environment-controlled defaults, corrupt
TOML output is possible. Recommendation: use `tomlkit` to construct the output document
programmatically rather than via f-string templating.

### I-9 — Provider name echoed in JSON 404 from public `GET /oauth/{provider_name}/start` (carry-over)

**File:** `src/regstack/routers/oauth.py`
`detail=f"OAuth provider {name!r} is not configured."` is returned as a JSON 404 body from an
unauthenticated endpoint. An unauthenticated caller can probe to confirm which provider names are
not configured. Negligible in practice (configured providers are listed on the public login
page), but the detail string could be trimmed to a generic message for consistency with the
anti-enumeration posture elsewhere.

### I-10 — `oauth` extra pulls `httpx` beyond the minimum declared scope (carry-over)

**File:** `pyproject.toml`
The `oauth` extra declares `["pyjwt[crypto]>=2.13.0", "cryptography>=48.0.1", "httpx>=0.27"]`.
The review prompt expects only `pyjwt[crypto]` (+ transitive `cryptography`). `httpx` is a
direct runtime dependency of `src/regstack/oauth/providers/google.py` (used for the token
exchange), is validated by `tests/unit/test_extra_declares_its_imports.py`, and is documented
inline. Not a security gap, but worth noting for supply-chain surface awareness.

### I-11 — Multiple packages pinned at exact CVE-floor versions (zero headroom) (carry-over)

**Files:** `pyproject.toml`, `uv.lock`
`starlette>=1.3.1` (lock: 1.3.1), `pyjwt>=2.13.0` (lock: 2.13.0), `jinja2>=3.1.6` (lock:

### I-12 — Google token-exchange error response body logged at DEBUG level (carry-over)

**File:** `src/regstack/oauth/providers/google.py`
On non-200 responses from Google's token endpoint, the full response body is logged at DEBUG.
Google's error response bodies contain only `error` codes and descriptions — no live tokens —
so no credential leakage is confirmed. However, if Google's error format ever changes to include
partial token data, this log line would capture it. Recommendation: log only
`response.status_code` on error and drop the body from the log call.

## 🟢 CLEAN

The following areas were reviewed and found to be secure:

- **§2 Hardcoded Secrets:** No API keys, private key material, live JWTs, credential-bearing
  connection strings, or sensitive files found in `src/`, `tests/`, `examples/`, `docs/`.
  `.gitignore` correctly covers `.env`, `.env.*`, `regstack.secrets.env`, `*.pem`, `*.key`,
  `*.p12`, `*.pfx`, `htmlcov/`, `.coverage`.
- **§4 Storage-layer Injection:** Both MongoDB and SQL backends use fully parameterised queries.
  No unsafe Mongo operators (`$where`, `$expr`, `$function`, `$accumulator`). No regex built from
  user input. All `ObjectId` coercions guarded by `ObjectId.is_valid()`. SQL `text()` calls limited
  to a connectivity-check `SELECT 1` and a migration data-integrity query — no user input involved.
  All SQL `purge_expired()` implementations use bound parameters.
- **§5 Input Validation:** Every API endpoint accepts a typed Pydantic model. `EmailStr` used on
  all email-bearing fields. E.164 validation on all phone-number inputs. Jinja2 autoescape enabled
  for HTML in both email composer and SSR environment. No `| safe` filters or
  `{% autoescape false %}` in SSR templates.
- **§6 Rate Limiting:** `LockoutService.check()` runs before any password comparison.
  `record_failure` increments on every failure path. Admin list endpoint caps `limit` at 200.
  OAuth state TTL wired on both Mongo and SQL.
- **§7 Session & Token Security:** JWT secret length enforced at construction (≥ 32 chars).
  Every JWT includes `jti`. `iat` emitted as `float` (microsecond precision). `pyjwt` `exp`/`iat`
  validation disabled; Clock-based validation used throughout. `_authenticate` revocation order
  is correct: decode → blacklist.is_revoked → is_payload_bulk_revoked → is_active check.
- **§8 CSP & SSR Layer:** No `<style>` blocks or `style=` attributes in any SSR template.
  No inline `<script>` tags — only `<script src defer>` in `base.html`. `oauth_complete.html`
  confirmed clean. SSR pages are stateless (no auth state rendered into HTML).
- **§9 Data Exposure:** All user-returning endpoints use `UserPublic.from_user()`. Database driver
  errors produce generic HTTP 500 messages. JWT decode errors produce generic 401 messages.
  OAuth callback failures redirect with short error codes. No log calls expose JWT secret,
  OAuth client_secret, or SMTP password.
- **§10 Git History:** No commits since 2026-09-02 security report. No accidentally committed
  secrets (`.env`, `.key`, `.pem`, `*secret*`) in full git history.
- **§11 Third-party Integrations:** SMTP `smtp_password` stored as `SecretStr`. SES explicit
  credentials stored as `SecretStr`. Twilio `auth_token` stored as `SecretStr`. Google JWKS lookup
  has a 5-second timeout. ID-token verification validates signature, `iss`, `aud`, `exp`, `iat`,
  and nonce.
- **§12 GitHub Actions:** All `uses:` directives SHA-pinned. No `${{ github.event.* }}`
  interpolations in `run:` blocks. `permissions: contents: read` at workflow level; `id-token:
  write` scoped to the publish job only. No `pull_request_target`. No self-hosted runners.
  No `PYPI_API_TOKEN` — OIDC trusted publishing with sigstore attestations. No cache keys on
  user-controlled input. Tag-push is the only publish trigger.
- **§13 PyPI Package Integrity:** Wheel contains only `src/regstack/` — no tests, docs, examples,
  tasks, or dev files. All base dependencies have correct lower bounds. Optional extras
  (`pymongo`, `asyncpg`, `aioboto3`, `twilio`, `pyjwt[crypto]`) correctly in
  `[optional-dependencies]` only. Version check reads `pyproject.toml` via `tomllib`.
  Sigstore attestations enabled. No developer machine paths or test-fixture strings in wheel.
  No yanked versions detected.
- **§14 OAuth Subsystem (structural):** PKCE `code_verifier` stored server-side on state row;
  only `code_challenge` (SHA-256 of verifier) sent to provider. State row lifecycle correct:
  missing → `bad_state`, expired → `state_expired`, expiry uses `rs.clock.now()`. Post-callback
  `consume` (read + delete) is atomic. Linking-policy enforcement for `email_in_use`,
  `identity_in_use`, `already_linked` all correct. Last-sign-in-method guard on unlink. Identity
  uniqueness `(provider, subject_id)` and `(user_id, provider)` enforced at DB level. `redirect_to`
  validated same-origin via `_validate_redirect`. OAuth hooks fire at correct points.
  Exception: W-4 race condition in `_resolve_user`.
- **§15 Multi-backend Parity:** CI matrix covers SQLite, Postgres, MongoDB, and SecantusDB.
  All three SQL migrations have working `upgrade()` and `downgrade()`; column alterations use
  `batch_alter_table` for SQLite compatibility. Mongo unique indexes match SQL `UniqueConstraint`
  entries. `make_client(tz_aware=True)` confirmed in `src/regstack/backends/mongo/client.py`.
  `UtcDateTime` TypeDecorator used on all datetime columns.
