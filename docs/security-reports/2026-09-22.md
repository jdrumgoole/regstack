## Section 3 — Authentication and Authorisation Audit

### 🟢 CLEAN — Endpoint authentication coverage

All mutating endpoints inject `rs.deps.current_user()` or `rs.deps.current_admin()`. Admin endpoints (`/admin/stats`, `/admin/users`, `/admin/users/{id}`, `PATCH /admin/users/{id}`, `DELETE /admin/users/{id}`, `/admin/users/{id}/resend-verification`, `/admin/pending/{email}/promote`) all depend on `rs.deps.current_admin()`. All data responses use `UserPublic.from_user()`.

### 🟢 CLEAN — Bulk-revoke discipline

Password reset calls `users.update_password()` (which bumps `tokens_invalidated_after`) and `lockout.clear()`. Password change calls `users.update_password()` and `lockout.clear()`. Admin disable calls `users.set_tokens_invalidated_after()` before the 200 response. Account deletion cascades OAuth identities before deleting the user.

### 🟠 W-8 — Timing oracle on login for OAuth-only accounts (day 4 — SLA 2026-09-25)

`src/regstack/routers/login.py:99`:

```python
if user.hashed_password is None or not rs.password_hasher.verify(payload.password, user.hashed_password):
```

Python short-circuits on `hashed_password is None`: if the account is OAuth-only, the ~100 ms Argon2 verify is skipped and the response returns in ~1 ms. An attacker can probe whether a given email is OAuth-only vs password-enabled with ~200 requests and a simple latency histogram.

**Remediation:** Always run a dummy Argon2 verify when `hashed_password is None` to preserve constant time (e.g., `rs.password_hasher.dummy_verify()` or equivalent constant-time guard), then raise the same generic 401.

### 🟢 CLEAN — `hashed_password is None` side effects

`change-password`, `change-email`, `delete-account` all call `require_password_set(user)` before proceeding. OAuth unlink refuses if it would remove the only sign-in method. Login returns the same generic 401 for missing password as for a wrong password.

### 🟢 CLEAN — Constant-time password comparison

`pwdlib` (`argon2`) is used for all password hashing and verification. `if not rs.password_hasher.verify(...)` uses the library's constant-time comparison. No `==` comparison is used on raw password strings.

### 🟢 CLEAN — Per-purpose JWT key derivation

`derive_secret(jwt_secret, purpose)` in `src/regstack/config/secrets.py` uses `hmac.new(master, purpose.encode(), hashlib.sha256).digest()`. Each purpose (`session`, `password_reset`, `email_change`, `phone_setup`, `login_mfa`) gets a distinct derived key. A captured session token cannot satisfy the password-reset endpoint.

### 🟢 CLEAN — MongoDB backend

No unbounded `$in` arrays from user input.

### 🟢 CLEAN — SQL backend

All SQL queries use SQLAlchemy Core with parameterised binds. No `f"..."` or `%` interpolation into raw SQL. No `text(...)` calls found. `purge_expired()` implementations use bound `cutoff` parameters.

### 🟢 CLEAN — `UtcDateTime` TypeDecorator

`src/regstack/backends/sql/types.py` consistently re-attaches UTC tzinfo on result values. No regression found.

### 🟠 W-6 — SQL `OAuthStateRepo.consume` non-atomic read-delete (day 14 — **7 days past SLA**)

`src/regstack/backends/sql/repositories/oauth_state_repo.py:63`: `consume` performs a `SELECT` followed by a `DELETE` within a single transaction on a single connection. The comment says "so a second concurrent /oauth/exchange call sees the row as already-gone" — but this is not true for concurrent requests on different connections. Under both PostgreSQL and SQLite, two concurrent connections can each execute the SELECT and observe the row before either has committed the DELETE, allowing both to receive the same state row and exchanging the OAuth token twice.

The MongoDB backend uses `find_one_and_delete` which is atomic at the server level. The SQL path should match this guarantee.

**Remediation:** Rewrite `consume` to use `DELETE … RETURNING *` (PostgreSQL) or an equivalent serialised exclusive transaction pattern (SQLite) so the SELECT and DELETE are one atomic server-side operation.

## Section 7 — Session & Token Security

### 🟢 CLEAN — JWT configuration

`JwtCodec.__init__` enforces `len(jwt_secret) >= MIN_JWT_SECRET_LENGTH (32)` at construction. Algorithm defaults to HS256.

### 🟢 CLEAN — `jti` presence

Every token minted by `JwtCodec.encode()` receives `jti=secrets.token_urlsafe(16)`. The email-change and MFA tokens minted inline also set `jti`. The `require` list in `pyjwt.decode` enforces presence of `jti` on decode.

### 🟢 CLEAN — `iat` float precision

`to_claims()` emits `iat` as `self.iat.timestamp()` (float). `is_payload_bulk_revoked` uses `payload.iat <= cutoff`. Tokens issued microseconds after a password-change cutoff are correctly not revoked.

### 🟢 CLEAN — Clock injection

`JwtCodec` disables pyjwt's built-in `exp`/`iat` validation (options `verify_exp=False`, `verify_iat=False`). Both are re-validated against the injected `Clock`. `FrozenClock`-driven tests remain deterministic.

### 🟢 CLEAN — Token revocation discipline

`_authenticate` checks: decode → 401 on failure; `blacklist.is_revoked(jti)` → 401 if blacklisted; `users.get_by_id(sub)` must return an `is_active=True` user; `is_payload_bulk_revoked(payload, user.tokens_invalidated_after)` → 401 if past cutoff. Order is correct.

### 🟢 CLEAN — No token leakage in logs

`_authenticate` catches `TokenError` and raises a static 401 detail without echoing pyjwt's specific reason. OAuth callback errors are logged as generic codes, not token values.

### 🟠 W-2 — Email-change token `jti` never blacklisted (day 22 — **15 days past SLA**)

`src/regstack/routers/account.py:177` → `confirm_email_change`: after successfully decoding the email-change JWT, the handler calls `users.update_email(...)` but never extracts `jti` and never calls `blacklist.insert(jti, exp)`. A valid email-change link can therefore be replayed until it expires (default 30 min TTL), allowing an attacker who intercepts or obtains a copy of the link to repeatedly swap the email address even after the legitimate user has already completed the flow.

**Remediation:** After `_decode_email_change_token(token)`, extract `payload.jti` and `payload.exp`. Check `await rs.blacklist.is_revoked(jti)` first (→ 400 if already revoked). On success, call `await rs.blacklist.insert(jti, exp)` before returning.

### 🟠 W-3 — Email-change handler skips bulk-revocation check (day 22 — **15 days past SLA**)

Immediately after `_decode_email_change_token`, the handler fetches the user by `sub` but never calls `is_payload_bulk_revoked(payload, user.tokens_invalidated_after)`. A token minted before a `change-password` (which bumps `tokens_invalidated_after`) would still be accepted to change the email, post-dating the revocation event.

**Remediation:** After `users.get_by_id(user_id)`, add:
```python
if is_payload_bulk_revoked(payload, user.tokens_invalidated_after):
    raise HTTPException(status_code=400, detail="Email-change link has been invalidated.")
```

## Section 14 — OAuth Subsystem Audit

### 🟢 CLEAN — PKCE invariants

`code_verifier = _secrets.token_urlsafe(64)` is generated server-side in `_begin_flow` and stored on the `OAuthState` row (`state.code_verifier`). Only the SHA-256 challenge (`code_challenge`) is sent to the provider as a query parameter. The verifier never appears in any URL visible to the browser.

### 🟢 CLEAN — State row lifecycle

The OAuth callback validates the state row exists, that its `provider` matches, and that `expires_at` is checked against `rs.clock.now()` (not `datetime.now(UTC)` — clock injection preserved). After success, `set_result_token()` shortens the row's expiry to `oauth.completion_ttl_seconds` (default 30 s) to bound the window in which a stolen state_id could yield a session token.

### 🟠 W-4 — Race condition: new OAuth user creation unhandled 500 (day 22 — **15 days past SLA**)

`src/regstack/routers/oauth.py:716` → `_resolve_user`, branch 4 (brand-new account):

```python
new_user = await rs.users.create(new_user)
```

A double-tap (two concurrent requests with the same Google `sub` arriving within milliseconds) lets both coroutines reach this line. The second `create` raises `UserAlreadyExistsError`, which is not caught, propagating as an unhandled 500. The MongoDB unique index on `email` also raises on the second call.

**Remediation:** Wrap the `create` call in a `try/except UserAlreadyExistsError` and fall back to `rs.users.get_by_email(info.email)` (or the identity lookup) to retrieve the just-created user.

### 🟢 CLEAN — ID-token verification

`GoogleProvider.verify_id_token` validates signature via `PyJWKClient` against Google's JWKS, verifies `iss`, `aud`, `exp`, `iat`, `nonce`, and `sub`. JWKS fetch has a 5-second timeout. Algorithm is pinned to `RS256`.

### 🟢 CLEAN — Linking-policy enforcement

`_resolve_user` raises `_LinkConflictError("email_in_use")` when auto-link is off and an existing user has the same email. `_LinkConflictError("identity_in_use")` fires when the identity is already linked to a different user. `_LinkConflictError("already_linked")` fires when the same identity is re-linked to the same user.

### 🟢 CLEAN — OAuth-only user side effects

`POST /login` returns the same generic 401 for `hashed_password is None` as for a wrong password. `change-password`, `change-email`, and `delete-account` call `require_password_set(user)` before proceeding. `DELETE /oauth/{provider}/link` refuses when the user has no password and only one provider identity.

### 🟢 CLEAN — Identity-row uniqueness

`(provider, subject_id)` and `(user_id, provider)` are both enforced as unique at the database level (Mongo unique indexes in `indexes.py`; SQL `UniqueConstraint` in `schema.py`).

### 🟢 CLEAN — Hooks

`oauth_signin_started`, `oauth_signin_completed`, `oauth_account_linked`, `oauth_account_unlinked` are in `KNOWN_EVENTS`. The router fires them at the correct points.
