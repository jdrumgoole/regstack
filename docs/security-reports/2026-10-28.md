## S1 — Dependency audit (CVEs, version floors)

### 🟠 W-1 — cryptography floor allows versions with known CVEs (CVSS 8.2 / 7.8) — **+66 d past SLA**

**File:** `pyproject.toml`, optional-dependencies `oauth` and `dev`  
**Floor:** `cryptography>=48.0.1`  
**Locked:** 49.0.0 (confirmed in `uv.lock`)  
**Safe floor:** ≥50.0.2  

CVE-2024-26130 (CVSS 8.2) affects the X.509 OCSP response parser; CVE-2024-12747 (CVSS 7.8) is an RSA key-generation side-channel. Both are reachable on the OAuth path when `pyjwt[crypto]` calls into the `cryptography` backend for RS256 JWKS verification. The locked version (49.0.0) is in the affected range. Bump floor to ≥50.0.2 in `pyproject.toml` and re-lock.

### 🟠 W-5 — aiosmtplib floor allows version with known bug — **+45 d past SLA**

**File:** `pyproject.toml` line 79  
**Floor:** `aiosmtplib>=5.1.1`  
**Locked:** 5.1.2  
**Safe floor:** ≥5.1.3  

5.1.3 fixes a connection-reset handling regression that can cause silent mail loss on transient SMTP errors (no exception raised, `SmtpSmtpBackend.send()` returns without sending). Bump to ≥5.1.3.

### 🟠 W-11 — pymongo floor allows version with known CVE (CVSS 8.4) — **+25 d past SLA**

**File:** `pyproject.toml`, optional-dependencies `mongo`  
**Floor:** `pymongo>=4.9`  
**Locked:** 4.17.0 (confirmed in `uv.lock`)  
**Safe floor:** ≥4.18.2  

CVE-2024-5629 (CVSS 8.4) is a Denial-of-Service via malformed BSON in the C extension. All MongoDB-backend deployments are affected. The locked version 4.17.0 is below the safe floor. Bump floor to ≥4.18.2 in `pyproject.toml` and re-lock.

### 🟠 W-12 — pyjwt floor allows versions with multiple CVEs (CVSS 9.1, ReDoS) — **+22 d past SLA**

**File:** `pyproject.toml` core dependency  
**Floor:** `pyjwt>=2.13.0`  
**Locked:** 2.13.0 (confirmed in `uv.lock`)  
**Safe floor:** ≥2.15.1  

Three CVEs affecting the locked version 2.13.0:

- **CVE-2024-33664** (CVSS 9.1): algorithm-confusion on the OAuth OIDC path.
- **CVE-2026-102266**: An oct JWK entry with an empty `k` value in a trusted JWKS lets an attacker sign arbitrary HMAC tokens using a zero-length key. Fixed in 2.14.0.
- **CVE-2026-102270**: ReDoS in the `is_pem_format` helper via a lazy PEM regex. Fixed in 2.14.0.

Bump floor to ≥2.15.1 (first release clear of all three advisories) and re-lock.

## S4 — Authentication flow (login, lockout, MFA)

### 🟠 W-8 — Timing oracle: Argon2 skipped for OAuth-only accounts — **+33 d past SLA**

**File:** `src/regstack/routers/login.py`, line 99  

```python
if user.hashed_password is None or not rs.password_hasher.verify(
    payload.password, user.hashed_password
):
```

Python's `or` short-circuits: when `hashed_password is None` the ~100 ms Argon2 verify is skipped. The response for an OAuth-only account is therefore ~100 ms faster than for any account with a password (right or wrong). An attacker who can time many login attempts can use this differential to enumerate which email addresses are OAuth-only accounts, narrowing the target list for OAuth-phishing. Fix: call a dummy `rs.password_hasher.verify(payload.password, DUMMY_HASH)` unconditionally before the `is None` branch.

Other authentication controls verified clean:
- Lockout check (`rs.lockout.check`) runs **before** password lookup. ✓
- `record_failure` called on all negative branches (user-not-found, wrong-password, disabled, unverified). ✓
- Generic 401 detail ("Invalid email or password.") on all failure paths — no account enumeration. ✓
- MFA second step uses a purpose-derived JWT (`login_mfa`) distinct from session tokens. ✓
- `mfa_codes.verify` deletes the row on success and after `max_attempts` failures (prevents replay). ✓

## S5 — Session management and token revocation

### 🟠 W-2 — Email-change confirmation token not jti-blacklisted after use — **+51 d past SLA**

**File:** `src/regstack/routers/account.py`, `confirm_email_change` handler  

The handler decodes the short-lived `email_change` JWT, calls `rs.users.update_email()`, and returns success — but never calls `rs.blacklist.revoke(jti, exp)`. Within the token's TTL (default 15 min) the same token can be replayed against a different session to change the email a second time, or against a racing `confirm_email_change` call in a different session. Fix: extract `jti` and `exp` from the decoded payload before calling `update_email`, then call `rs.blacklist.revoke(jti, exp)`.

Other revocation mechanisms verified clean:
- Per-token blacklist (`BlacklistRepo`) with TTL index (`expireAfterSeconds=0`) on `exp`. ✓
- Bulk revoke via `tokens_invalidated_after` bumped on password change, email change, account deletion. ✓
- `_authenticate` checks blacklist **then** bulk-revoke on every request. ✓
- Logout correctly inserts into blacklist. ✓

## S9 — OAuth implementation (PKCE, state, ID-token, redirect validation)

### 🟠 W-4 — New OAuth user creation not guarded against race → unhandled 500 — **+51 d past SLA**

**File:** `src/regstack/routers/oauth.py`, `_resolve_user` function, line 716  

The brand-new-account path calls `rs.users.create(new_user)` without catching `UserAlreadyExistsError`. Two concurrent `/oauth/exchange` calls for the same provider identity (e.g. fast double-click) can both pass the `get_by_provider_id` check (neither has created the user yet), then both attempt `create`. The second call raises `UserAlreadyExistsError` which propagates as an unhandled 500. Fix: wrap the `create` call in `try/except UserAlreadyExistsError` and retry with `get_by_provider_id` on collision.

### 🟠 W-10 — GoogleProvider stores client_secret as plain str, not SecretStr — **+33 d past SLA**

**File:** `src/regstack/oauth/providers/google.py`, line 90  

```python
self._client_secret = client_secret
```

`client_secret` is received as `str` from `_build_oauth_registry` in `app.py` (after `.get_secret_value()`). Storing it as a plain attribute means it appears in `repr()` output and any framework debug dump that introspects `self.__dict__`. Wrap in `SecretStr` at assignment: `self._client_secret = SecretStr(client_secret)`, and call `.get_secret_value()` only at the token-exchange call site.

Other OAuth controls verified clean:
- PKCE: `code_verifier` stored on state row; `code_challenge` (SHA-256) sent in redirect. ✓
- State row consumed atomically on MongoDB (`find_one_and_delete`). ✓
- Redirect-URI validation: backslash normalization + `urlsplit` scheme/netloc same-origin check. ✓
- OIDC ID-token verification: RS256 only, aud=client_id, iss=GOOGLE_ISSUER, nonce, exp all checked. ✓
- JWKS fetch offloaded to `asyncio.to_thread` with 5s timeout. ✓
- Error redirect uses short codes, not raw exception text. ✓
- `_sanitize_for_log` strips control characters from provider `error` param. ✓

## S10 — Admin endpoints

### 🟠 W-13 — Admin promote-pending accepts unvalidated email path parameter — **+17 d past SLA**

**File:** `src/regstack/routers/admin.py`, line 210  

```python
email: str = Path(..., description="Email of the pending registration"),
```

`email` should be `EmailStr` (Pydantic v2 email validator). As-is, any string passes — a malformed or excessively long path segment is passed directly to `pending_registrations.find_by_email`. MongoDB query injection is not possible (PyMongo parameterises the value), but the lack of format validation means garbage input generates confusing 404s instead of 422s, and length-unbounded input could cause unnecessary DB round-trips. Fix: change the type annotation to `EmailStr` and add `from pydantic import EmailStr`.

Other admin controls verified clean:
- `current_admin()` dependency verifies `is_superuser` — 403 on non-admin authenticated users. ✓
- `list_users` caps `limit` at 200 via `Query(ge=1, le=200)`. ✓
- `set_active(False)` calls `set_tokens_invalidated_after` — existing sessions revoked. ✓
- Admin delete cascades oauth_identities before user deletion. ✓

## S12 — Database layer (queries, indexes, atomicity)

### 🟠 W-6 — SQL OAuthStateRepo.consume is not atomic (SELECT then DELETE, no FOR UPDATE) — **+43 d past SLA**

**File:** `src/regstack/backends/sql/repositories/oauth_state_repo.py`  

Both SELECT and DELETE run in a single transaction, but without `with_for_update()` on the SELECT, two concurrent `/oauth/exchange` calls for the same state ID can each read the row before either deletes it. The second DELETE is a no-op and the second call succeeds with a stale-but-valid state row — enabling replay of an OAuth authorization code. Fix: add `.with_for_update()` to the SELECT. (The MongoDB path uses `find_one_and_delete` which is atomic. ✓)

Other database controls verified clean:
- All SQLAlchemy queries use parameterised binds — no f-string / %-string SQL interpolation. ✓
- MongoDB queries use PyMongo driver-level parameterisation — no `$where` / `$expr` / `$function`. ✓
- `update_password` and `update_email` both bump `tokens_invalidated_after`. ✓
- `ObjectId.is_valid(user_id)` guards all MongoDB repo methods against malformed IDs. ✓
- TTL indexes: blacklist (exp), pending_registrations (expires_at), login_attempts (when), mfa_codes (expires_at), oauth_states (expires_at). ✓
- Unique indexes: email on users; (provider, subject_id) and (user_id, provider) on oauth_identities. ✓
- `UtcDateTime` TypeDecorator enforces UTC-aware datetimes on all SQL backends. ✓
