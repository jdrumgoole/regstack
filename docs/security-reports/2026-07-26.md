## 🟠 WARNING (Address within 1 week)

### W1 — JWT secret minimum length not enforced at construction time

**File:** `src/regstack/auth/jwt.py:118`

`JwtCodec.__init__` only checks that `config.jwt_secret` is non-empty. The `regstack doctor` CLI warns when the secret is shorter than 32 characters, but that check is advisory only and runs only when the operator explicitly invokes `doctor`. A secret set via `REGSTACK_JWT_SECRET=x` (one character) passes `JwtCodec` construction without error and is used to sign all session tokens. Because HMAC-SHA256 pads short keys with zero bytes, a 1-character secret reduces the effective signing entropy to ~7 bits.

**Remediation:** Add a runtime guard in `JwtCodec.__init__`:
```python
raw = config.jwt_secret.get_secret_value()
if len(raw) < 32:
    raise ValueError(
        f"jwt_secret must be at least 32 characters; got {len(raw)}. "
        "Run `regstack init` or set REGSTACK_JWT_SECRET to a strong secret."
    )
```
This is a library — the host app's `RegStack(config=...)` call is the right place to surface this as an early, hard error rather than a runtime signing weakness that only shows up in a `doctor` scan.

### W2 — One-time token URLs passed verbatim to hook events

**Files:** `src/regstack/routers/register.py:97`, `src/regstack/routers/password.py:70`, `src/regstack/routers/admin.py:194`, `src/regstack/routers/verify.py:120`

`rs.hooks.fire(event, ..., url=url)` passes the full verification or password-reset URL (containing the raw single-use token as a query parameter) as a keyword argument to every registered hook handler. `HookRegistry.fire()` swallows exceptions but not arguments. Any host-supplied hook that logs its `**kwargs` — a common pattern for analytics or audit-logging webhooks — will inadvertently write the live, usable token to a log system.

This is particularly sensitive for password-reset URLs: a log-aggregation service that indexes these tokens gives anyone with log-read access the ability to take over accounts.

**Remediation (two-part):**
1. Add a `url_without_token` (token query parameter replaced with `[REDACTED]`) alongside the existing `url` kwarg so hosts have a safe loggable form.
2. Add a note to the hook event documentation (and/or a `HookRegistry.fire` docstring) warning that the `url` kwarg for verification/reset events contains a single-use credential.

## 🟡 INFO (Best practice recommendations)

### I1 — No per-IP rate limiting on unauthenticated endpoints by default

**File:** `src/regstack/config/schema.py:224–241`

All per-IP rate-limit fields (`register_rate_limit`, `forgot_password_rate_limit`, `resend_rate_limit`, `verify_rate_limit`) default to `None`. A freshly deployed regstack instance has per-account lockout on `/login` but zero IP-level rate limiting on unauthenticated endpoints (`/register`, `/forgot-password`, `/resend-verification`, `/verify`, phone routes). An attacker can drive unbounded email sends or registration attempts from a single IP until the operator explicitly configures limits.

**Recommendation:** Document the default-off status prominently in the configuration reference and consider switching the defaults to a conservative non-`None` value (e.g., 20 requests per minute) with a clear opt-out path.

### I2 — `UserPublic.tokens_invalidated_after` exposed in API responses

**File:** `src/regstack/models/user.py:105`

`tokens_invalidated_after` is included in every `/me`, `/admin/users/{id}`, and `UserPublic` response. Per the architectural notes this is intentional — SPAs can compare the field against their stored JWT's `iat` to detect stale sessions without an extra roundtrip. The field leaks the timestamp of the user's last forced-logout event (password change, admin disable, email change) to the authenticated user and to admins.

This is a documented design trade-off, not a defect. Flag for operator awareness: if the threat model treats internal event timing as sensitive, the field should be excluded from `UserPublic` and SPAs should instead poll `/me` to detect invalidity.

### I3 — Admin error messages echo the `email` path parameter

**File:** `src/regstack/routers/admin.py:218, 223`

Two admin-only error responses include the email address from the URL path:
```python
f"No pending registration for {email}."
f"A user with email {email} already exists."
```
These endpoints require `is_superuser=True`, so there is no current security risk. However, if a future refactor accidentally drops the admin guard, these messages would enumerate whether a given email exists in the system — contradicting the anti-enumeration discipline applied to `/forgot-password` and `/resend-verification`. Recommend using a generic message that does not include the email.

### I4 — `oauth` extra explicitly pins `cryptography>=48.0.1` alongside `pyjwt[crypto]`

**File:** `pyproject.toml:98`

The `oauth` extra definition is:
```toml
oauth = ["pyjwt[crypto]>=2.13.0", "cryptography>=48.0.1"]
```
The security review prompt notes the extra should add "only `pyjwt[crypto]`". The explicit `cryptography` floor was added to close four CVEs (CVE-2026-26007, CVE-2026-34073, CVE-2026-39892, CVE-2026-45447) that `pyjwt[crypto]` would pull transitively but without a sufficiently high minimum. This is correct defensive behaviour. The item is flagged as INFO so future reviewers understand the intent: once `pyjwt` raises its own `cryptography` floor past 48.0.1, the explicit pin can be removed.

### I5 — SNS SMS backend uses boto3 default credential chain with no explicit config

**File:** `src/regstack/sms/sns.py:29`

`aioboto3.Session()` is constructed with no credential arguments — the SNS backend relies entirely on boto3's default credential chain (environment variables, instance profile, `~/.aws/`). This is asymmetric with the SES email backend, which exposes `ses_access_key_id` / `ses_secret_access_key` fields in `SmsConfig`. Operators expecting the SES-style explicit credential config for SNS will find no such knobs. Using IAM roles/instance profiles is the preferred AWS pattern, but the asymmetry is worth documenting.

### I6 — OAuth exchange endpoint consumes expired state before returning 400

**File:** `src/regstack/routers/oauth.py:151–161`

`/oauth/exchange` calls `consume()` (which atomically deletes the row) and _then_ checks `state.expires_at < rs.clock.now()`. An expired-but-otherwise-valid state row is permanently consumed before the 400 error is returned. The user must restart the full OAuth flow. This is secure — no replay is possible since the row is gone — but the behaviour is slightly surprising compared to a check-then-consume ordering and offers no recovery path for the user if their browser lingers past the 5-minute window.

---

### I7 — `cmd:` log-source kind executes user-supplied shell commands

**File:** `src/regstack/cli/validate/logtail.py:106`

The `cmd:<arbitrary shell command>` log-source kind runs `sh -c <target>` where `<target>` comes from the operator's config file. This is the declared contract for this source kind and is intentional operator-level behaviour, not user input. Noted for auditors: this is a shell-exec surface in the CLI that cannot be exercised through the HTTP API.
