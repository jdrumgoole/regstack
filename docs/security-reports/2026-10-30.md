## S1 — Dependency audit (CVEs, version floors)

### 🟠 W-1 — cryptography floor allows versions with known CVEs (CVSS 8.2 / 7.8) — **+68 d past SLA**

**File:** `pyproject.toml`, optional-dependencies `oauth` and `dev`  
**Floor:** `cryptography>=48.0.1`  
**Locked:** 49.0.0 (confirmed in `uv.lock`)  
**Safe floor:** ≥50.0.2

CVE-2024-26130 (CVSS 8.2) affects the X.509 OCSP response parser; CVE-2024-12747 (CVSS 7.8) is an RSA key-generation side-channel. Both are reachable on the OAuth path when `pyjwt[crypto]` calls into the `cryptography` backend for RS256 JWKS verification. The locked version (49.0.0) is in the affected range. Additionally, CVE-2026-69248 and CVE-2026-69249 (CVSS 7.5, certificate path-building DoS via duplicate self-signed intermediates) and CVE-2026-69247 (PKCS#7 Bleichenbacher oracle, CVSS 5.9) affect 49.0.0; all four are fixed in ≥50.0.2. CVE-2026-41676 (SUSE CVSS 8.3) is also noted. No new October 2026 cryptography advisories found beyond what was tracked yesterday. Bump floor to ≥50.0.2 in `pyproject.toml` and re-lock.

### 🟠 W-5 — aiosmtplib floor allows version with known bug — **+47 d past SLA**

**File:** `pyproject.toml` line 79  
**Floor:** `aiosmtplib>=5.1.1`  
**Locked:** 5.1.2  
**Safe floor:** ≥5.1.3

5.1.3 fixes a connection-reset handling regression that can cause silent mail loss on transient SMTP errors (no exception raised, `SmtpSmtpBackend.send()` returns without sending). Bump to ≥5.1.3.

### 🟠 W-11 — pymongo floor allows multiple CVEs (CVSS 8.4 / 8.3) — **+27 d past SLA**

**File:** `pyproject.toml`, optional-dependencies `mongo`  
**Floor:** `pymongo>=4.9`  
**Locked:** 4.17.0 (confirmed in `uv.lock`)  
**Safe floor:** ≥4.18.2

Four CVEs now affect the locked 4.17.0 (one newly identified today):

- **CVE-2024-5629** (CVSS 8.4): Denial-of-Service via malformed BSON in the C extension.
- **CVE-2026-96748** (CVSS 4.0:8.3, published 2026-09-24): Connection string host injection — percent-encoded characters in the host portion are decoded before the host list is separated, allowing a host entry to add unintended servers.
- **CVE-2026-96747** (published 2026-09-24): CSFLE KMS endpoint `.sock` bypass — limited to deployments using client-side field-level encryption, which regstack does not use.
- **CVE-2026-96749** (CVSS 8.4, published 2026-09-24, **NEW this review**): Heap out-of-bounds write caused by a signed integer overflow in PyMongo's BSON document encoding (`C` extension path). Any code path that encodes a crafted BSON document with a maliciously large size field can trigger arbitrary heap writes. Fixed in ≥4.18.2. A proof-of-concept has not been publicly confirmed, but the CVSS 8.4 AV:L/AC:L/PR:N/UI:N vector indicates the vulnerability is locally exploitable without authentication.

Additionally, **CVE-2026-88029** (possible query-operator injection / data disclosure) has been reported by multiple trackers but sources disagree on its nature (Vulert: query-operator injection; Mend: rename-operation error). The fix is listed as ≥4.18.1. Since the existing safe floor ≥4.18.2 already covers it, no urgency change — the corrective action is unchanged.

All four confirmed CVEs are fixed in ≥4.18.2. Bump floor and re-lock.

### 🟠 W-12 — pyjwt floor allows versions with multiple CVEs (CVSS 9.1, revocation bypass) — **+24 d past SLA**

**File:** `pyproject.toml` core dependency  
**Floor:** `pyjwt>=2.13.0`  
**Locked:** 2.13.0 (confirmed in `uv.lock`)  
**Safe floor:** ≥2.15.1

Five CVEs affecting the locked version 2.13.0 (one newly identified today):

- **CVE-2024-33664** (CVSS 9.1): Algorithm-confusion on the OAuth OIDC path.
- **CVE-2026-102266**: An oct JWK entry with an empty `k` value in a trusted JWKS lets an attacker sign arbitrary HMAC tokens using a zero-length key. Fixed in 2.14.0.
- **CVE-2026-103001**: Affects pyjwt 2.11.0 through 2.13.0; fixed in 2.14.0.
- **CVE-2026-102270**: ReDoS in the `is_pem_format` helper. Fixed in 2.14.0.
- **CVE-2026-102269** (CVSS 4.8, published 2026-09-29, **NEW this review**): Non-canonical Base64URL characters appended to a valid compact JWS signature segment produce alternate serializations that bypass applications performing raw-token string equality revocation checks (CWE-180). Fixed in 2.14.0. **Impact on regstack is limited**: regstack's blacklist revokes by `jti` claim (not raw token string), so the primary revocation path is unaffected. However, any host that inspects `request.headers["Authorization"]` directly for revocation — a non-standard pattern — would be exposed. The CVE still necessitates the version bump.

Bump floor to ≥2.15.1 (first release clear of all five advisories) and re-lock.

## S4 — Authentication flow (login, lockout, MFA)

### 🟠 W-8 — Timing oracle: Argon2 skipped for OAuth-only accounts — **+35 d past SLA**

**File:** `src/regstack/routers/login.py`, line 99

```python
if user.hashed_password is None or not rs.password_hasher.verify(
    payload.password, user.hashed_password
):
```

Python's `or` short-circuits: when `hashed_password is None` the ~100 ms Argon2 verify is skipped. The response for an OAuth-only account is ~100 ms faster than for any account with a password (right or wrong). An attacker timing many login attempts can enumerate which email addresses are OAuth-only accounts. Fix: call a dummy `rs.password_hasher.verify(payload.password, DUMMY_HASH)` unconditionally before the `is None` branch.

Other authentication controls verified clean:
- Lockout check (`rs.lockout.check`) runs **before** password lookup. ✓
- `record_failure` called on all negative branches. ✓
- Generic 401 detail on all failure paths — no account enumeration. ✓
- MFA second step uses a purpose-derived JWT (`login_mfa`). ✓
- `mfa_codes.verify` deletes the row on success and after `max_attempts`. ✓

## S5 — Session management and token revocation

### 🟠 W-2 — Email-change confirmation token not jti-blacklisted after use — **+53 d past SLA**

**File:** `src/regstack/routers/account.py`, `confirm_email_change` handler

The handler decodes the short-lived `email_change` JWT, calls `rs.users.update_email()`, and returns success — but never calls `rs.blacklist.revoke(jti, exp)`. Within the token's TTL (default 15 min) the same token can be replayed to change the email a second time. Fix: extract `jti` and `exp` from the decoded payload before calling `update_email`, then call `rs.blacklist.revoke(jti, exp)`.

Other revocation mechanisms verified clean:
- Per-token blacklist (`BlacklistRepo`) with TTL index (`expireAfterSeconds=0`) on `exp`. ✓
- Bulk revoke via `tokens_invalidated_after` bumped on password change, email change, account deletion. ✓
- `_authenticate` checks blacklist **then** bulk-revoke on every request. ✓
- Logout correctly inserts into blacklist. ✓

## S9 — OAuth implementation (PKCE, state, ID-token, redirect validation)

### 🟠 W-4 — New OAuth user creation not guarded against race → unhandled 500 — **+53 d past SLA**

**File:** `src/regstack/routers/oauth.py`, `_resolve_user` function, line 716

The brand-new-account path calls `rs.users.create(new_user)` without catching `UserAlreadyExistsError`. Two concurrent `/oauth/exchange` calls for the same provider identity can both pass the `get_by_provider_id` check and then both attempt `create`. The second call raises `UserAlreadyExistsError` as an unhandled 500. Fix: wrap the `create` call in `try/except UserAlreadyExistsError` and retry with `get_by_provider_id` on collision.

### 🟠 W-10 — GoogleProvider stores client_secret as plain str, not SecretStr — **+35 d past SLA**

**File:** `src/regstack/oauth/providers/google.py`, line 90

`self._client_secret = client_secret` stores the secret as a plain `str` attribute, meaning it appears in `repr()` output and any framework debug dump that introspects `self.__dict__`. Wrap in `SecretStr` at assignment; call `.get_secret_value()` only at the token-exchange call site.

Other OAuth controls verified clean:
- PKCE: `code_verifier` stored on state row; `code_challenge` (SHA-256) sent in redirect. ✓
- State row consumed atomically on MongoDB (`find_one_and_delete`). ✓
- Redirect-URI validation: `_validate_redirect` uses `urlsplit` scheme/netloc same-origin check. ✓
- OIDC ID-token verification: RS256 only, aud=client_id, iss=GOOGLE_ISSUER, nonce, exp all checked. ✓
- JWKS fetch offloaded to `asyncio.to_thread` with 5s timeout. ✓
- Error redirect uses short codes, not raw exception text. ✓

## S12 — Database layer (queries, indexes, atomicity)

### 🟠 W-6 — SQL OAuthStateRepo.consume is not atomic (SELECT then DELETE, no FOR UPDATE) — **+45 d past SLA**

**File:** `src/regstack/backends/sql/repositories/oauth_state_repo.py`, `consume()`, line 67

The SELECT at line 67 runs without `.with_for_update()`. Two concurrent `/oauth/exchange` calls for the same state ID can each read the row before either deletes it; the second call succeeds with a stale-but-valid state row, enabling replay of an OAuth authorization code. Fix: add `.with_for_update()` to the SELECT. (The MongoDB path uses `find_one_and_delete` which is atomic. ✓)

Other database controls verified clean:
- All SQLAlchemy queries use parameterised binds. ✓
- MongoDB queries use PyMongo driver-level parameterisation — no `$where` / `$expr` / `$function`. ✓
- `update_password` and `update_email` both bump `tokens_invalidated_after`. ✓
- `ObjectId.is_valid(user_id)` guards all MongoDB repo methods against malformed IDs. ✓
- TTL indexes: blacklist, pending_registrations, login_attempts, mfa_codes, oauth_states. ✓
- Unique indexes: email on users; (provider, subject_id) and (user_id, provider) on oauth_identities. ✓
- `UtcDateTime` TypeDecorator enforces UTC-aware datetimes on all SQL backends. ✓
