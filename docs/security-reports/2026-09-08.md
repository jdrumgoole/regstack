## 🟠 WARNING

### W-1 (carry-over, day 29 — SLA MISSED 2026-08-18)

**Section:** §1 — Dependency Vulnerability Check
**CVE:** CVE-2026-69247 — `cryptography` Bleichenbacher oracle (`pkcs7_decrypt`)
**Affected range:** `cryptography` ≥ 44.0.0, < 50.0.0
**Resolved in:** `cryptography==50.0.0` (released 2026-07-31 — 39 days ago)
**Current resolved version in `uv.lock`:** 49.0.0 (within affected range)
**Current floor in `pyproject.toml`:** `cryptography>=48.0.1` (does not exclude affected versions)
**Fix required:** Bump floor to `cryptography>=50.0.0` in both the `oauth` and `dev` extras in
`pyproject.toml`; run `uv lock`.
**Tracking:** GitHub issue #181 (`[security] Raise cryptography floor to >=50.0.0`), open since
2026-08-19 — 21 days unacknowledged. No fix PR, no assignee, no comment.

**Technical impact:** `pkcs7_decrypt_der`, `pkcs7_decrypt_pem`, and `pkcs7_decrypt_smime` expose
distinguishable error paths and timing differences during RSA `RecipientInfo.encryptedKey` decryption,
constituting a Bleichenbacher-style oracle. regstack does not call these functions directly, but
`pip install regstack[oauth]` resolves to 49.0.0 by default, shipping a version with an open advisory
to all downstream consumers. The fix (cryptography 50.0.0+) substitutes a random key on RSA
decryption failure per RFC 3218.

**Urgency:** The fix version has been on PyPI for 39 days. The 7-day SLA lapsed 2026-08-18.
This finding will appear daily until resolved.

### W-2 (carry-over, day 8 — NEW 2026-09-01) — `POST /confirm-email-change` email-change JWT not revoked after use

**Section:** §3 — Authentication & Authorization Audit
**File:** `src/regstack/routers/account.py`, `confirm_email_change` handler
**Status:** Unresolved. No code change in `account.py` since first flagged.

The `confirm_email_change` endpoint successfully updates the user's email address but does not
call `await rs.blacklist.revoke(token_payload.jti, token_payload.exp)` after doing so. The
password-reset path (`password.py`) correctly performs this revocation after every successful reset.
Within the email-change token's TTL, the same confirmation URL can be submitted repeatedly. Each
subsequent submission attempts `update_email`, which succeeds as a no-op when the address is already
the user's own, and the endpoint returns HTTP 200 — confirming the link is still usable.

The `_decode_email_change_token` helper currently returns only `(user_id, new_email)` and discards
the `jti` and `exp` claims. Any fix must thread these through to the caller so `blacklist.revoke()`
can be called after a successful `update_email`.

### W-3 (carry-over, day 8 — NEW 2026-09-01) — `POST /confirm-email-change` bulk-revoke not applied to email-change tokens

**Section:** §3 — Authentication & Authorization Audit
**File:** `src/regstack/routers/account.py`, `confirm_email_change` handler
**Status:** Unresolved. No code change in `account.py` since first flagged.

If a user changes their password (bumping `tokens_invalidated_after`) after requesting an email
change, the already-issued email-change JWT should be treated as bulk-revoked. The current
`confirm_email_change` handler does not call
`is_payload_bulk_revoked(payload, user.tokens_invalidated_after)` after decoding the token and
fetching the user. The `_decode_email_change_token` helper also discards the `iat` claim, so the
comparison cannot be performed without extending the return signature.

The pattern mirrors the `_authenticate` dependency. Both W-2 and W-3 can be fixed in a single pass
through `confirm_email_change`.

### W-4 (carry-over, day 8 — NEW 2026-09-01) — OAuth `_resolve_user` unhandled `UserAlreadyExistsError` → HTTP 500

**Section:** §14 — OAuth Subsystem Audit
**File:** `src/regstack/routers/oauth.py`, `_resolve_user` (branch 4 — brand-new account creation)
**Status:** Unresolved. No code change in `oauth.py` since first flagged.

In `_resolve_user`, branch 4 (new account via OAuth) calls `await rs.users.create(new_user)`.
`UserRepo.create` raises `UserAlreadyExistsError` (wrapping a `DuplicateKeyError` or
`IntegrityError`) when a concurrent request inserts the same email between the `get_by_email`
lookup and the `create` call. This exception propagates out of `_resolve_user` unhandled; the outer
`oauth_callback` catches only `_LinkConflictError`, so the race turns into an HTTP 500 — a
database error message may appear in FastAPI's default exception handler depending on host
configuration.

The fix is to catch `UserAlreadyExistsError` in the branch-4 block and raise
`_LinkConflictError("email_in_use")` instead, matching what the non-racy lookup returns.

### W-5 (carry-over, day 2 — NEW 2026-09-07) — `aiosmtplib` floor does not formally exclude CVE-2026-55558

**Section:** §1 — Dependency Vulnerability Check
**CVE:** CVE-2026-55558 — STARTTLS command injection in `aiosmtplib`
**Affected version:** `aiosmtplib==5.1.1`
**Resolved in:** `aiosmtplib==5.1.2`
**Current floor in `pyproject.toml`:** `aiosmtplib>=5.1.1` (includes the vulnerable 5.1.1)
**Current resolved version in `uv.lock`:** 5.1.2 (unaffected)
**Fix required:** Bump floor to `aiosmtplib>=5.1.2` in `pyproject.toml` `[project.dependencies]`
and run `uv lock`.

**Technical impact:** aiosmtplib 5.1.1 does not reject CRLF sequences in certain SMTP command
parameters, allowing injection of SMTP protocol commands below the Jinja2 rendering layer.
regstack's SMTP backend is on the `require_verification=True` code path (the default), making
it a default-on attack surface. The current lock resolves 5.1.2 so regstack's own published wheel
isn't shipping the vulnerable code — but hosts that independently pin `aiosmtplib>=5.1.1` would
be placed within the vulnerable range. The floor needs to be correct. One-line fix.

### I-2 — Email template `style=` attributes in email HTML (§8, carry-over)

Email templates (`src/regstack/email/templates/`) contain inline `style=` attributes in HTML
email bodies. This is intentional and correct for email client compatibility — CSS is inlined
for email (most clients strip `<style>` blocks and `<link>` refs). This is NOT a CSP finding
because email templates are never rendered in a browser context. The SSR UI templates
(`src/regstack/ui/templates/`) have zero inline styles confirmed — no `style=` or `<style>`
attributes (grep returned no matches). No action needed; noted for completeness.

### I-3 — `UtcDateTime` `process_bind_param` raises on non-datetime input (§4/§15, carry-over)

`src/regstack/backends/sql/types.py` `UtcDateTime.process_bind_param` raises a `TypeError` if a
non-`datetime` value arrives (e.g. a stray `str` from a caller). Raises rather than silently
coerces — this is correct defensive behaviour. SQLAlchemy Core parameterisation prevents SQL
injection; the TypeError only affects calling code that passes the wrong type, surfacing the bug
at ORM call time rather than silently writing a corrupt timestamp. No action needed; noted for
cross-reference.

### I-4 — `oauth_complete.html` / `_token_handoff.html` passes result token via JS variable (§8, carry-over)

The SSR `oauth_complete.html` template includes the result state-id in a JavaScript variable used
to POST to `/oauth/exchange`. The state-id is a random URL-safe nonce (32 bytes) that becomes
invalid once consumed; the underlying session JWT is never in the HTML. No `{{ user.email }}`
or auth-state rendering in the page. No action needed; noted for completeness.

### I-5 — `purge_expired()` in SQL backends uses `datetime.now(UTC)` rather than injected `Clock` (§15, carry-over)

`login_attempt_repo.py` and `oauth_state_repo.py` SQL implementations call `datetime.now(UTC)` in
`purge_expired()` rather than the injected `Clock`. This means FrozenClock-driven tests don't
exercise these code paths deterministically. Production correctness is not affected (both call
sites produce the same UTC-aware timestamp). Refactoring to thread the clock through `purge_expired()`
is a code-quality improvement, not a security fix.

### I-6 — SecantusDB pre-release in `secantus` and `dev` extras (§1, carry-over)

`SecantusDB>=0.6.0b2` is a pre-release package in both the `secantus` and `dev` extras. Pre-release
packages bypass the normal supply-chain audit process. Acceptable for a test-only dependency that
embeds its own MongoDB-wire server. Not a production dependency. Note it when evaluating the test
backend matrix.

### I-7 — GitHub Actions SHA pins slightly behind latest minor releases (§12, carry-over)

All third-party actions in `publish.yml` and `test.yml` are SHA-pinned (not tag-based): correct
practice. The pinned SHAs (`actions/checkout@de0fac2e...`, `astral-sh/setup-uv@08807647...`,
`pypa/gh-action-pypi-publish@cef221092...`, `actions/upload-artifact@043fb46d...`,
`actions/download-artifact@3e5f45b2...`) correspond to known-good versions but may not be the
latest patch. Routine SHA refresh is recommended quarterly.

### I-8 — SNS backend uses ambient boto3 credential chain; no explicit credential config (§11, carry-over)

The SNS SMS backend delegates credential resolution to the boto3 default chain (env vars, shared
credential file, instance metadata). There is no `config.sms.sns_access_key_id` field —
intentionally avoided to prevent credential hardcoding. Document in operator docs that IAM role
attachment is the recommended deployment pattern.

### I-9 — `regstack doctor` does not verify Mongo TTL index matches `login_lockout_window_seconds` at runtime (§6, carry-over)

The `regstack doctor` CLI checks that indexes exist but does not compare the `expireAfterSeconds`
value of the `login_attempts.when_ttl` TTL index against `config.login_lockout_window_seconds`. A
misconfigured (or manually modified) TTL index would result in failed-attempt rows lingering longer
(or shorter) than expected. Low risk: the index is created by `install_indexes` with the correct
value; only an operator with direct Mongo admin access could change it post-install.

### I-10 — `workflow_dispatch` trigger in `test.yml` (§12, carry-over)

`test.yml` includes `workflow_dispatch:` which allows manual runs. No `${{ github.event.* }}`
interpolation into `run:` blocks; all inputs are via the matrix env. No untrusted content flows
into shell commands. Retained as informational.

### I-11 — PEP 740 sigstore attestations are enabled — ✓ clean (§13, carry-over)

`publish.yml` includes `attestations: true` in the `pypa/gh-action-pypi-publish` step, enabling
PEP 740 sigstore attestations that cryptographically bind each wheel/sdist to the Actions run.
This finding is retained in INFO only for cross-reference; no action needed.
