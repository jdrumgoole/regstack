## Section 3 — Authentication & Authorization Audit

### 🟠 W-2 · Email-change JWT not jti-blacklisted after confirm · day 46 (SLA expired +45 d)

Re-verified today at `src/regstack/routers/account.py:177–205`. `confirm_email_change` decodes the email-change JWT and immediately calls `rs.users.update_email(...)`. There is no `rs.blacklist.add(jti, exp)` call. The token is valid until its `exp`; a second call within the TTL window would be rejected only if the new email is already taken (the `UserAlreadyExistsError` path). A replay attack with a captured token targeting a user who then changes their email again is theoretically possible.

**Fix:** call `rs.blacklist.add(payload.jti, payload.exp)` after the `update_email` succeeds in `confirm_email_change`.

---

### 🟠 W-4 · OAuth new-user concurrent registration → unhandled `UserAlreadyExistsError` · day 46 (SLA expired +45 d)

Re-verified today at `src/regstack/routers/oauth.py:704–727`. The "Brand-new account" branch in `_resolve_user` calls `rs.users.create(new_user)` with no `try/except UserAlreadyExistsError`. A concurrent OAuth callback (two browser tabs, race on the same subject ID at first sign-in) would cause the second call to bubble `UserAlreadyExistsError` to FastAPI as a 500 Internal Server Error.

**Fix:** wrap `rs.users.create(new_user)` in a `try/except UserAlreadyExistsError` and raise `_LinkConflictError("email_in_use")`.

---

### 🟠 W-8 · Timing oracle on login for OAuth-only accounts · day 28 (SLA expired +27 d)

Re-verified today at `src/regstack/routers/login.py:99`. The `or`-short-circuit in:

```python
if user.hashed_password is None or not rs.password_hasher.verify(
    payload.password, user.hashed_password
):
```

skips the Argon2 call entirely when `hashed_password is None`. Argon2 verification takes ~100 ms; the short-circuit takes microseconds. An attacker who can measure response time can distinguish OAuth-only accounts from password-bearing accounts, undermining the anti-enumeration design.

**Fix:** always call `rs.password_hasher.verify(payload.password, DUMMY_HASH)` when `hashed_password is None` (where `DUMMY_HASH` is a pre-hashed sentinel computed at startup), discarding the result before returning 401. This maintains constant timing regardless of account type.

### 🟠 W-13 · Admin `promote_pending` email path parameter not validated · day 12 (SLA expired +11 d)

Re-verified today at `src/regstack/routers/admin.py:210`. The `email` parameter is typed `str = Path(...)`, not `EmailStr`. Any string passes FastAPI's path-param extraction without format validation. Additionally, line 223's error message echoes the raw path value: `f"No pending registration for {email}."` — low risk given the admin-only guard but technically an unvalidated reflection.

## Section 4 — Storage-layer Injection Safety

### 🟠 W-6 · SQL `OAuthStateRepo.consume` non-atomic under READ COMMITTED · day 44 (SLA expired +37 d)

Re-verified at `src/regstack/backends/sql/repositories/oauth_state_repo.py`. SELECT + DELETE in `engine.begin()` is not atomic under PostgreSQL's default READ COMMITTED: a concurrent `/oauth/exchange` call can read the same row between the SELECT and DELETE, allowing two exchange calls with the same `state_id` to both succeed and return a session token. The Mongo implementation uses `find_one_and_delete` which is atomic.

**Fix:** use `DELETE … RETURNING` on SQL backends, or add `SELECT … FOR UPDATE SKIP LOCKED` before the delete.

---

## Section 5 — Input Validation & Injection

### 🟡 I-5 · TOML injection risk in wizard writer · day 19

Carry-forward. The `regstack oauth setup` wizard writes TOML via `tomlkit`. If a user enters a value with `]` or `=` chars that tomlkit doesn't escape, the resulting `regstack.toml` could have a malformed TOML structure. Low severity — wizard runs locally, not as a server-side attack surface.

### 🟡 I-6 · `current_password` fields lack `max_length` · day 19

Carry-forward. `ChangePasswordRequest.current_password: str` and `ChangeEmailRequest.current_password: str` have no `max_length` bound. Argon2 input length is bounded by pwdlib defaults, but an unauthenticated attacker can't reach these endpoints.

### 🟡 I-7 · Token confirm-flow fields lack `max_length` · day 19

Carry-forward. `ConfirmEmailChangeRequest.token: str`, `VerifyRequest.token: str`, and similar token fields have no `max_length`. A very long string wastes decode time before the base64/JWT parser rejects it.

### 🟢 CLEAN — other input validation

All API inputs go through Pydantic models. `EmailStr` validation on all email-bearing fields. `is_valid_e164()` called on every phone-number input. Email templates use Jinja2 with autoescape on for HTML — no `autoescape False` blocks. SSR templates have no `| safe` filters or `{% autoescape false %}`. `regstack init` CLI wizard does not feed any user input into shell commands. `redirect_to` query parameters validated same-origin against `config.base_url` in `_validate_redirect()` — backslash pre-screen, `//`-prefix check, scheme+netloc comparison.

## Section 11 — Third-Party Integration Security

### 🟠 W-10 · `GoogleProvider` client_secret stored as plain `str` · day 34 (SLA expired +27 d)

Re-verified at `src/regstack/oauth/providers/google.py`. `self._client_secret = client_secret` — stored as a plain `str`. The value is extracted from `SecretStr` at the call site in `app.py` before construction. A `repr()` of `GoogleProvider` or an unhandled exception propagated to a Sentry-style crash handler would expose the client secret in plain text.

**Fix:** accept `client_secret: str | SecretStr` in `GoogleProvider.__init__`, wrap in `SecretStr` on store, unwrap only at the HTTP call site (`exchange_code`).
