### W-1 — CVE-2026-48710 (BadHost): Starlette 1.0.0 locked in `uv.lock`

**Finding:**

The lock file (`uv.lock`) pins Starlette at **1.0.0**. Starlette **1.0.1** (released 21 May
2026) fixes CVE-2026-48710 "BadHost" (CVSS 6.5–7.0, reported as Critical by downstream
researchers at OSTIF and X41 due to ecosystem blast radius).

**Vulnerability mechanics:** Starlette reconstructs `request.url` by concatenating the raw
HTTP `Host` header with the path and re-parsing the result. Before 1.0.1, the `Host` value
was never validated against RFC 9112 / RFC 3986 grammar. An attacker who injects `/`, `?`,
or `#` into the `Host` header shifts the path/query/fragment boundaries during re-parse, so
`request.url.path` returns a completely different value than the path the ASGI router
dispatched against. Any middleware or security code that uses `request.url.path` (rather than
`request.scope["path"]`) for access-control decisions can be bypassed.

**Impact on regstack specifically:**

regstack's own authentication uses FastAPI's standard `Depends()` injection with `HTTPBearer`
(reading from `request.headers["Authorization"]`). The BadHost researchers explicitly confirm:
*"standard FastAPI `Depends()` security uses route matching and is safe."* regstack's
`_validate_redirect` in `routers/oauth.py` compares against `rs.config.base_url` (a
config-time constant, not reconstructed from the request), so the open-redirect guard is also
unaffected. **regstack's own security functions are not directly exploitable via BadHost.**

However, regstack is a library:

1. `uv.lock` pins Starlette 1.0.0. Any release artefact cut from this lock ships the
   vulnerable version.
2. `pyproject.toml` has no `starlette>=1.0.1` floor. A host that resolves dependencies
   freshly (no lock) may get 1.0.0.
3. Host apps that wrap regstack with custom `BaseHTTPMiddleware` or raw ASGI middleware for
   path-based routing decisions (e.g. an additional admin-area guard) **are** exploitable.

The pattern used for CVE-2025-62727 (adding `fastapi>=0.120.0`) should be applied here.

**Fix:**

```toml
# pyproject.toml — add a security floor matching the BadHost fix
dependencies = [
    ...
    # starlette>=1.0.1 picks up CVE-2026-48710 (BadHost — Host-header path
    # boundary shift; middleware doing path-based auth can be bypassed).
    # FastAPI pulls starlette transitively; this floor makes the fix explicit
    # and ensures hosts resolve at least 1.0.1 without a locked lockfile.
    "starlette>=1.0.1",
    ...
]
```

Then run `uv lock --upgrade-package starlette` to update `uv.lock`.

### W-2 — PyJWKClient missing timeout — **CARRIED** from 2026-05-22 (W-1)

**Finding** (unchanged since 2026-05-22):

```python
# src/regstack/oauth/providers/google.py:83
self._jwks_client = PyJWKClient(jwks_url, cache_keys=True)
```

No `timeout` argument is passed. PR #80 correctly offloaded the synchronous `urllib`
JWKS fetch to `asyncio.to_thread`, preventing event-loop blocking. The underlying thread
still has no deadline: `urllib.request.urlopen` blocks indefinitely on `timeout=None`.

**Consequences:**
- On a JWKS cache miss, each concurrent OAuth sign-in that cannot hit the cache holds a
  worker thread indefinitely if Google's JWKS endpoint is slow or unreachable.
- Python's asyncio thread pool is bounded (≤ 32 threads by default). Sustained JWKS
  timeouts exhaust the pool and stall all other `asyncio.to_thread` calls in the process.
- The 5-minute default cache TTL means JWKS refreshes happen regularly; an extended Google
  JWKS outage would systematically cycle through the pool.

This finding was also present in the 2026-05-20 review (I-2) and the 2026-05-22 review
(W-1) without being addressed.

**Fix:**

```python
# src/regstack/oauth/providers/google.py:83
# pyjwt>=2.4 supports a timeout argument; the project already requires >=2.12.1.
self._jwks_client = PyJWKClient(jwks_url, cache_keys=True, timeout=5)
```

## 🟡 INFO (Best practice recommendations)

### I-1 — `was_new_account` always `False` in OAuth exchange response — **CARRIED** from 2026-05-22

`ExchangeResponse.was_new_account` is hardcoded to `False` at
`src/regstack/routers/oauth.py:176–180`. The `was_new` flag is correctly computed during
`_resolve_user` inside the callback but is not persisted to the `oauth_states` row.
SPAs relying on this field to display a "Welcome, new user" prompt will never see it set.
Not a security issue; an API accuracy gap.

**Fix:** Add `result_was_new: bool = False` to the `oauth_states` model and schema, populate
it in `_resolve_user`, and surface it via the exchange response.

### I-2 — OAuth token-exchange exception includes full Google response body in server logs — **CARRIED** from 2026-05-22

`src/regstack/oauth/providers/google.py:143–145`:

```python
raise OAuthTokenExchangeError(
    f"google token exchange failed: {response.status_code} {response.text}"
)
```

This exception propagates as `%s` in a `log.warning` in `routers/oauth.py:315`. The full
Google error body (which may contain error descriptions, scopes, or request details) is
logged at WARNING in production. Google's token endpoint error responses are standardised
JSON (`{"error": "invalid_grant", ...}`) and do not contain the client secret, but the full
response body in production WARNING-level logs is noisier than necessary.

**Fix:**

```python
log.warning("google token exchange failed: HTTP %s", response.status_code)
log.debug("google token exchange response body: %s", response.text)
```

### I-3 — aiosmtplib version floor is two major versions behind locked version

`pyproject.toml` specifies `aiosmtplib>=3.0`; the lock file resolves to **5.1.0**. The
floor is two major versions behind the locked version. This is not a known-CVE issue, but
the gap between floor and locked version means a regression to 3.x (if 5.x is yanked for
any reason) would silently install an older release. Consider raising the floor to `>=5.0`
to match the current release train.

### §3 — Authentication & Authorization

- Every authenticated endpoint injects `rs.deps.current_user()` or `rs.deps.current_admin()`.
- All user-state-mutating endpoints require authentication.
- All API responses use `UserPublic.from_user()` — `hashed_password` never returned.
  `tokens_invalidated_after` is intentionally included (documented trade-off in
  `docs/security.md`, closed as I-2 in the 2026-05-17 review via PR #63).
- Bulk-revoke discipline confirmed on both backends: `update_password` bumps
  `tokens_invalidated_after` on both MongoDB and SQL; `update_email` same; admin
  `set_active(id, False)` calls `set_tokens_invalidated_after`; account deletion cascades
  `oauth_identities` before `users.delete`.
- OAuth-only users (`hashed_password=None`): login returns the same generic 401 as a
  wrong-password attempt; `change-password`, `change-email`, `delete-account` block via
  `require_password_set()`.
- Password comparison uses `rs.password_hasher.verify()` (pwdlib Argon2id constant-time).
- JWT signing keys use per-purpose HMAC-SHA256 derivation. Compromise of one purpose key
  cannot be used for another purpose.

### §4 — Storage-Layer Injection Safety

**MongoDB:** No `$where`, `$expr`, `$function`, or `$accumulator` operators. All query
filters use static keys with user input as bound values. Every `get_by_id` path guards via
`ObjectId.is_valid()` before `ObjectId(...)` conversion. No regex built from user input. The
OAuth state collection has a `$jsonSchema` validator enforcing `mode ∈ {signin, link}` at
the DB layer.

**SQL:** All queries use SQLAlchemy Core parameterised binds. The two `text()` calls are
static (`text("SELECT 1")` health check; `text("SELECT COUNT(*) …")` in migration 0002
downgrade pre-check) — no user input interpolated. `UtcDateTime` TypeDecorator correctly
re-attaches UTC on reads, keeping bulk-revoke comparisons tz-consistent.

### §6 — Rate Limiting & DoS Prevention

  correct, preventing oracle attacks.
- MongoDB `login_attempts` TTL index keyed to `login_lockout_window_seconds`. SQL backend
  relies on `purge_expired()` reaper.
- Admin `GET /admin/users` caps `limit` via `Query(ge=1, le=200)` — no unbounded page.
- OAuth state rows expire via `state_ttl_seconds` (default 300 s). MongoDB has a TTL index
  on `expires_at`; SQL `purge_expired()` sweeps the table. No unbounded accumulation.
- No file-upload endpoints.

### §7 — Session & Token Security

- HS256 by default; `jwt_secret` ≥ 1 character enforced at `JwtCodec.__init__` (empty

- Every JWT includes `jti` (16-byte URL-safe random). Per-token revocation via
  `BlacklistRepo` works.
- `JwtCodec.encode` emits `iat` as `float` (confirmed at `jwt.py:69`:
  `"iat": self.iat.timestamp()`). Float precision preserves the bulk-revoke `<=` comparison

### §14 — OAuth Subsystem

**14a. PKCE invariants:** `code_verifier` generated in `_begin_flow`, stored on the
`oauth_states` row. The `code_challenge` (SHA-256 of verifier) is what goes in the
provider redirect URL. The verifier never appears in the browser URL. Confirmed in
`routers/oauth.py:596–622`.

**14b. State row lifecycle:** Callback checks for missing row (`bad_state`) and expired row
(`state_expired`) using `rs.clock.now()` (not `datetime.now(UTC)`), preserving FrozenClock
test fidelity. `rs.oauth_states.consume()` is atomic on both backends:
- Mongo: `find_one_and_delete` (single operation).
- SQL: read + delete inside a single `engine.begin()` transaction.

**14c. ID-token verification:** `GoogleProvider.verify_id_token` validates: signature
(PyJWKClient against configured JWKS URL), `iss` matches `GOOGLE_ISSUER`, `aud` matches
`client_id`, `exp > now` (pyjwt's standard exp check is active — note the codec
deliberately disables it for regstack session tokens, but Google ID-token decoding does
NOT disable exp), `nonce` matches state row. Required claims: `sub`, `iss`, `aud`, `exp`,
`iat`, `nonce`. Any failure raises `OAuthIdTokenError`, logged at WARNING; only a short
error code reaches the redirect.

**14d. Linking-policy enforcement:** `auto_link_verified_emails` defaults to `False`.
When `False`, a Google sign-in for an existing email-registered user returns
`?error=email_in_use`. An identity linked to a different user returns
`?error=identity_in_use`. Re-linking the same identity to the same user returns
`?error=already_linked`. All paths confirmed in `_resolve_user`.

**14e. OAuth-only user side effects:** `POST /login` returns the same generic 401 for
`hashed_password=None` users. `change-password`, `change-email`, `delete-account` block
via `require_password_set()`. `DELETE /oauth/{provider}/link` returns 400 when the user
has no password and only one linked provider — "Cannot unlink your only sign-in method."

**14f. Identity-row uniqueness:** `(provider, subject_id)` and `(user_id, provider)` unique
constraints enforced at DB level on both backends (SQL `UniqueConstraint`; Mongo
`provider_subject_unique` and `user_provider_unique` indexes).

**14g. Hook events:** `oauth_signin_started`, `oauth_signin_completed`, `oauth_account_linked`,
`oauth_account_unlinked` are all present in `KNOWN_EVENTS` (`hooks/events.py`) and fired
at the correct points in the router.
