## 🟠 WARNING

### W-1 (carry-over, day 18 — SLA MISSED 2026-08-18)

**Section:** §1 — Dependency Vulnerability Check
**CVE:** CVE-2026-69247 — `pkcs7_decrypt` Bleichenbacher oracle
**Affected:** `cryptography` ≥ 44.0.0, < 50.0.0
**Fix available on PyPI:** `cryptography==50.0.0` released **2026-07-31** (28 days ago)
**Fix required:** Bump floor to `cryptography>=50.0.0` in `oauth` and `dev` extras in `pyproject.toml`; run `uv lock`
**Tracking:** GitHub issue #181 (`[security] Raise cryptography floor to >=50.0.0`), open since 2026-08-19 — no fix PR, no assignee, no activity (10 days)

`pyproject.toml` HEAD (`c1b0626`) still declares:
```toml
oauth = ["pyjwt[crypto]>=2.13.0", "cryptography>=48.0.1", "httpx>=0.27"]
...
"cryptography>=48.0.1",   # in dev extra
```

`uv.lock` resolved version: **49.0.0** — within the affected range (≥44.0.0, <50.0.0).

**Technical impact:** `pkcs7_decrypt_der`, `pkcs7_decrypt_pem`, and `pkcs7_decrypt_smime` expose distinguishable error paths and timing differences during RSA `RecipientInfo.encryptedKey` decryption, constituting a Bleichenbacher oracle. An attacker submitting adaptive chosen ciphertext to a service reflecting the outcome can recover the RSA content-encryption key. regstack itself does not call PKCS#7 decrypt, but `pip install regstack[oauth]` resolves to 49.0.0 by default, shipping a version with an open advisory to all consumers. The fix (cryptography 50.0.0) substitutes a random key on RSA decryption failure per RFC 3218.

**Urgency escalation (day 18):** The fix version has been available on PyPI for 28 days. The 7-day SLA was missed on 2026-08-18. Issue #181 has been open since 2026-08-19 with no PR, no assignee, and no activity — 10 days unacknowledged. A two-line `pyproject.toml` change plus `uv lock` is the entire fix. This finding will continue to appear daily until resolved.

### §14 — OAuth Subsystem Audit

- **PKCE:** `code_verifier` generated server-side in `_begin_flow()`, stored on `OAuthState` row, never placed in the redirect URL; only `code_challenge` (SHA-256 of verifier) goes to the provider ✓
- **State row lifecycle:** Callback rejects missing row (`bad_state`), expired row (`state_expired`) using `rs.clock.now()` ✓. `oauth_states.consume()` is atomic read+delete — a second exchange with the same state id returns 404 ✓
- **ID-token verification:** `GoogleProvider.verify_id_token` validates signature via `PyJWKClient`, `iss`, `aud` (`client_id`), `exp`, and nonce. Failures raise `OAuthIdTokenError`; callback redirects to `?error=id_token_failed` ✓
- **Linking policy:** Existing email-registered user → `?error=email_in_use` by default; auto-link only when `oauth.auto_link_verified_emails=True` AND `email_verified=true` ✓. Duplicate identity → `?error=identity_in_use`; already-linked same identity → `?error=already_linked` ✓
- **OAuth-only user side effects:** Login → generic 401; `change-password`/`change-email`/`delete-account` → 400 with forgot-password pointer; `DELETE /oauth/{provider}/link` → 400 when last auth method ✓
- **Identity uniqueness:** `(provider, subject_id)` unique at DB level; `(user_id, provider)` unique at DB level ✓
- **Hook events:** `oauth_signin_started`, `oauth_signin_completed`, `oauth_account_linked`, `oauth_account_unlinked` all in `KNOWN_EVENTS`; router fires them at correct points ✓
