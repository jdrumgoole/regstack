## 🟠 WARNING (Address within 1 week)

### W-1 · Admin `DELETE /admin/users/{id}` does not cascade `oauth_identities`

**File:** `src/regstack/routers/admin.py:120–135`

The admin user-delete endpoint deletes the user row and pending-registration row but does **not** call `rs.oauth_identities.delete_by_user_id(user.id)`. The user's own `DELETE /account` endpoint correctly cascades (`account.py:233`), but the admin path does not. This leaves `oauth_identities` rows pointing at a non-existent `user_id`.

Immediate consequence: orphaned rows cause a duplicate-key error if an admin later creates a new account with the same email and that user links the same Google identity. Longer-term risk: if a provider ever recycles `subject_id` values, the orphaned row could grant a new user an unexpected pre-linked identity on their first OAuth sign-in — an ownership-transfer issue.

CLAUDE.md explicitly requires: *"Account deletion must cascade `oauth_identities` first (anti-orphan), then delete the user."*

There is no SQL foreign-key `ON DELETE CASCADE` on `oauth_identities.user_id` (no `ForeignKey` defined in `schema.py`), so the cascade must be done in application code.

**Fix:** Add `await rs.oauth_identities.delete_by_user_id(user.id)` before `await rs.users.delete(user.id)` in `delete_user`.

### W-2 · JWT decode error detail echoed verbatim in 401 responses

**File:** `src/regstack/auth/dependencies.py:120`

```python
raise HTTPException(
    status_code=status.HTTP_401_UNAUTHORIZED,
    detail=f"Invalid token: {exc}",   # <-- leaks pyjwt internals
    headers={"WWW-Authenticate": "Bearer"},
) from exc
```

`{exc}` expands to pyjwt's raw message string (e.g. `"Signature has expired"`, `"algorithm was not allowed"`, `"Not enough segments"`). The security review prompt (§9) requires: *"JWT decode errors → 401 generic, never the specific reason."* Exposing exact decode failure reasons leaks token-expiry timing, algorithm negotiation state, and structural information that helps an attacker craft well-formed forgeries more efficiently.

All other token-decode paths in the codebase (`password.py`, `account.py`, `phone.py`) correctly raise a generic string without `{exc}`. Only `_authenticate` (the main session-auth path) is affected.

**Fix:**
```python
raise HTTPException(
    status_code=status.HTTP_401_UNAUTHORIZED,
    detail="Authentication required.",
    headers={"WWW-Authenticate": "Bearer"},
) from exc
```

### W-3 · GitHub Actions: all third-party actions use mutable version tags, not commit SHAs

**Files:** `.github/workflows/test.yml`, `.github/workflows/publish.yml`

Every `uses:` directive references a floating tag:

| Workflow | Action | Tag |
|---|---|---|
| test.yml | `actions/checkout` | `@v4` |
| test.yml | `astral-sh/setup-uv` | `@v3` |
| test.yml | `actions/upload-artifact` | `@v4` |
| publish.yml | `actions/checkout` | `@v4` |
| publish.yml | `astral-sh/setup-uv` | `@v3` |
| publish.yml | `actions/upload-artifact` | `@v4` |
| publish.yml | `actions/download-artifact` | `@v4` |
| publish.yml | `pypa/gh-action-pypi-publish` | `@release/v1` |

Tags can be silently force-pushed by the action author to point at arbitrary code. The `publish.yml` workflow runs with `id-token: write` permission and has access to PyPI OIDC credentials — a compromised `pypa/gh-action-pypi-publish` at `@release/v1` could exfiltrate the OIDC token and publish a malicious wheel.

**Fix:** Pin every action to a full commit SHA. Example:
```yaml
uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683  # v4.2.2
```
Use Dependabot's `github-actions` ecosystem or `pin-github-action` to keep SHAs updated.

### W-6 · `pywebview`, `uvicorn[standard]`, and `tomlkit` are in base `dependencies`

**File:** `pyproject.toml:37–39`

```toml
dependencies = [
    ...
    "pywebview>=5.0",
    "tomlkit>=0.13",
    "uvicorn[standard]>=0.29",
    ...
]
```

These three packages are only needed for the `regstack oauth setup` and `regstack theme design` wizard CLI commands. Every `pip install regstack` forces them onto all downstream consumers — including production servers, CI pipelines, and Lambda/container images — that have no use for a native desktop GUI library.

- `pywebview>=5.0` pulls in a native WebView implementation (Cocoa/WKWebView on macOS, WebKit2GTK on Linux, WebView2/EdgeHTML on Windows) and its Python bindings. Its transitive footprint is substantial, and native binary dependencies increase the attack surface and complicate reproducible builds.
- `uvicorn[standard]` re-duplicates the dev dependency and forces a production ASGI server onto library consumers.
- `tomlkit` is needed only by the wizard's config-writer.

The 0.2.1 release was broken precisely because optional-extra imports leaked into the base install (`bson`, etc.). This is the same class of problem — these packages are transitively imported only through lazy `_LazyOauthGroup` / `_LazyThemeGroup` CLI groups, but they are unconditionally declared as runtime dependencies.

**Fix:** Move all three to a new `wizard` optional extra:
```toml
[project.optional-dependencies]
wizard = ["pywebview>=5.0", "tomlkit>=0.13"]
```
`uvicorn[standard]` is already in `dev`; remove the duplicate from `dependencies`. Update the install instructions accordingly.

### W-7 · `POST /phone/start` and `DELETE /phone` crash with 500 for OAuth-only users

**Files:** `src/regstack/routers/phone.py:65`, `src/regstack/routers/phone.py:149`

Both the phone-setup and phone-disable endpoints call:

```python
rs.password_hasher.verify(payload.current_password, user.hashed_password)
```

without first checking `user.hashed_password is None`. For an OAuth-only user (one who signed up via Google and never set a password), `hashed_password` is `None`. `pwdlib.PasswordHash.verify` expects a non-`None` `str` for its second argument; passing `None` raises `TypeError`, which FastAPI surfaces as a 500 Internal Server Error.

By contrast, `account.py` routes (`/change-password`, `/change-email`, `/delete-account`) all call `_require_password_set(user)` first and return HTTP 400 with a helpful forgot-password pointer. The phone router is missing this guard.

The security impact: an attacker who can infer a user is OAuth-only (e.g. by observing the login page's OAuth buttons) can cause unhandled 500 errors on demand for those users; stack traces in debug mode could leak internal paths/config.

**Fix:** Add `_require_password_set(user)` (import it from `routers.account` or duplicate it in `phone.py`) at the top of both `start` and `disable` handlers.

### I-2 · `mfa_login_started` and `phone_setup_started` hooks receive raw OTP code

**Files:** `src/regstack/routers/login.py:158`, `src/regstack/routers/phone.py:103`

```python
await rs.hooks.fire("mfa_login_started", user=user, code=raw_code)
await rs.hooks.fire("phone_setup_started", user=user, phone=..., code=raw_code)
```

A host hook that generically logs all event kwargs (common in audit-log integrations) would inadvertently log the plaintext 6-digit OTP. This is the same token that controls account access for the duration of the MFA window.

**Recommendation:** Document in `KNOWN_EVENTS` or the hook API docstring that `code` is a sensitive claim and should not be logged. Alternatively, rename the kwarg to `debug_code` or omit it from production events and rely on the SMS delivery confirmation instead.

### I-3 · Admin resend-verification crashes for OAuth-only unverified users (SQL backends)

**File:** `src/regstack/routers/admin.py:155–165`

`POST /admin/users/{user_id}/resend-verification` creates a `PendingRegistration`:

```python
pending = PendingRegistration(
    email=user.email,
    hashed_password=user.hashed_password,   # None for OAuth-only users
    ...
)
```

`PendingRegistration.hashed_password` is typed `str` (non-optional). Passing `None` raises a Pydantic `ValidationError` before the database is touched, resulting in a 500 Internal Server Error for the admin. An OAuth-only user who signed up with `email_verified=False` can be in an unverified state and trigger this code path.

**Fix:** Guard against `user.hashed_password is None` at the top of `admin_resend_verification` and return HTTP 400 ("OAuth-only accounts can verify email on next sign-in; no verification email is sent.") or handle it by not storing a password hash in the pending row (updating the flow to re-use the existing hashed_password from the user row rather than pending registration for re-verification).

### I-4 · PyPI wheel has no sigstore attestation

**File:** `.github/workflows/publish.yml`

`pypa/gh-action-pypi-publish` is called without `attestations: true`. PyPI supports sigstore-based provenance attestations that let consumers verify the wheel was built by this repository's CI and not tampered with post-build. As an opt-in feature this is not a vulnerability, but it is a supply-chain transparency gap. Regstack is a security-relevant library; attestations are especially valuable here.

**Fix:** Add `attestations: true` to the `pypa/gh-action-pypi-publish` step.
