## Section 3 — Authentication & Authorization Audit

### 🟠 W-2 · Email-change JWT not jti-blacklisted after confirm · day 47 (SLA expired +46 d)

**Source:** `src/regstack/routers/account.py:177` — `confirm_email_change` re-verified today.

`confirm_email_change` decodes the email-change JWT, updates the user's email, and returns — it never calls `rs.blacklist.revoke(token_payload.jti, token_payload.exp)`. An email-change link can be replayed until its TTL expires: clicking the link a second time after the first confirmation issues `users.update_email` against the already-changed address (a 409 if the address changed again, or a silent no-op if not). The risk is a phishing scenario where an attacker captures the confirmation link before the user clicks it, uses it themselves, then the legitimate user also clicks it and gets a 409 with no indication their email was swapped.

**Fix:** after `rs.users.update_email` succeeds, call `rs.blacklist.revoke(token_payload.jti, token_payload.exp)`. Pattern identical to `reset-password` at `password.py:123`.

### 🟠 W-4 · OAuth new-user concurrent registration → unhandled `UserAlreadyExistsError` · day 47 (SLA expired +46 d)

**Source:** `src/regstack/routers/oauth.py` — `_resolve_user` new-account branch, re-verified today.

The brand-new-account creation path (`# 4. Brand-new account.`) calls `rs.users.create(new_user)` without catching `UserAlreadyExistsError`. Under concurrent requests (two simultaneous Google sign-ins for a new email-address user), the second request will receive an unhandled 500 instead of a graceful redirect to `?error=email_in_use`.

**Fix:** wrap `rs.users.create(new_user)` in `try/except UserAlreadyExistsError` and raise `_LinkConflictError("email_in_use")`.

### 🟠 W-8 · Timing oracle on login for OAuth-only accounts · day 29 (SLA expired +28 d)

**Source:** `src/regstack/routers/login.py:99` — re-verified today.

```python
if user.hashed_password is None or not rs.password_hasher.verify(
    payload.password, user.hashed_password
):
```

Python's short-circuit `or` skips the Argon2 `verify()` call when `hashed_password is None`. An attacker making timing measurements can distinguish OAuth-only accounts (fast 401, ~microseconds) from password-bearing accounts (slow 401, ~100-300 ms Argon2) or non-existent accounts (fast 401, no user lookup). This allows enumeration of which accounts use Google-only sign-in.

**Fix:** always run a dummy Argon2 verify when `hashed_password is None`:
```python
if user.hashed_password is None:
    rs.password_hasher.dummy_verify()
    raise await _build_invalid(rs, payload.email)
```
Alternatively, use `hmac.compare_digest`-style constant-time path with a placeholder hash.

## Section 4 — Storage-layer Injection Safety

### 🟠 W-6 · SQL `OAuthStateRepo.consume` non-atomic under READ COMMITTED · day 45 (SLA expired +38 d)

Carried from prior reviews. Under READ COMMITTED isolation (the PostgreSQL default), the read-then-delete in `OAuthStateRepo.consume` is not atomic: two concurrent exchange calls can each read the row before either deletes it, allowing a state id to be exchanged twice. The Mongo backend uses `find_one_and_delete` (atomic). The fix (a SELECT FOR UPDATE or a combined UPDATE+RETURNING with a deletion flag, wrapped in a transaction) has been documented since the initial finding. Source: `src/regstack/backends/sql/repositories/oauth_state_repo.py`.

## Section 9 — Data Exposure

### 🟠 W-10 · `GoogleProvider` client_secret stored as plain `str` · day 35 (SLA expired +28 d)

**Source:** `src/regstack/oauth/providers/google.py:90` — carried from prior reviews.

```python
self._client_secret = client_secret  # plain str, not SecretStr
```

`client_secret` is stored as a plain `str`. Any code path that calls `repr(provider)`, logs the provider object, or serialises it could leak the Google OAuth client secret into logs or error messages. `EmailConfig.smtp_password` is correctly typed as `SecretStr` — `GoogleProvider` should match that discipline.

**Fix:** accept `client_secret: SecretStr` (or `str | SecretStr`), store as `SecretStr`, and call `.get_secret_value()` at the token-exchange call site.
