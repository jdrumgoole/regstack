### 🟠 W-2 · Email-change JWT not jti-blacklisted after confirm · day 61 (SLA expired +47 d)

**Source:** `src/regstack/routers/account.py` `confirm_email_change` — re-verified today.

`POST /confirm-email-change` consumes the email-change JWT (a short-lived signed token carrying `sub`, `jti`, and `new_email`) and swaps the address, but never writes `jti` to the blacklist. Within the token's TTL window, the same token can be replayed to swap the address again — if a second swap fails with a `UserAlreadyExistsError`, an attacker learns the new address (from the 409 response), contradicting anti-enumeration intent.

**Fix:** after calling `users.update_email`, call `rs.blacklist.add(payload.jti, payload.exp)` to tombstone the spent token.

### 🟠 W-4 · OAuth new-user concurrent registration → unhandled 500 · day 61 (SLA expired +47 d)

**Source:** `src/regstack/routers/oauth.py` `_resolve_user` — re-verified today (line ~716 `rs.users.create(new_user)`).

In the brand-new-account path of `_resolve_user`, when two concurrent OAuth callbacks for the same identity arrive simultaneously (race on the provider's side or a retry), both can pass the `existing = None` check and both call `rs.users.create(new_user)`. The second `create` hits the `users.email` UNIQUE constraint and raises `UserAlreadyExistsError`, which is not caught here, producing a 500. The `oauth_identities.create` call that follows is similarly vulnerable.

**Fix:** wrap `rs.users.create` in a `try/except UserAlreadyExistsError` and redirect to `?error=email_in_use` on conflict, consistent with how the explicit email-in-use path is handled above it.

### 🟠 W-6 · SQL OAuthStateRepo.consume non-atomic under READ COMMITTED · day 53 (SLA expired +39 d)

**Source:** `src/regstack/backends/sql/repositories/oauth_state_repo.py` `consume` — re-verified today.

```python
async with self._engine.begin() as conn:
    row = (await conn.execute(select(self._t).where(...))).first()
    if row is None:
        return None
    await conn.execute(delete(self._t).where(...))
return _row_to_state(row)
```

Under PostgreSQL's default READ COMMITTED isolation, two concurrent `exchange` calls can both SELECT the row before either DELETE runs — both see `row is not None` and both return the state. The second caller gets a valid session JWT from a state row they shouldn't be able to claim (e.g. a stolen state_id used twice). The Mongo backend uses `find_one_and_delete` (atomic). This is an inconsistency between backends.

**Fix:** replace the SELECT + DELETE pair with `SELECT ... FOR UPDATE` (a SQLAlchemy `with_for_update()` on the select) inside the `engine.begin()` transaction, or use a single `DELETE ... RETURNING` statement.

### 🟠 W-8 · Timing oracle on login for OAuth-only accounts · day 43 (SLA expired +29 d)

**Source:** `src/regstack/routers/login.py:99` — re-verified today.

```python
if user.hashed_password is None or not rs.password_hasher.verify(
    payload.password, user.hashed_password
):
```

Python's short-circuit `or` evaluation means the Argon2 verify call is *skipped* when `hashed_password is None`. A standard login attempt against an OAuth-only account returns the 401 significantly faster than one with an incorrect password against a password-bearing account, because the ~100 ms Argon2 work is omitted. This timing difference is measurable and allows an attacker to enumerate which accounts have no password set, enabling targeted phishing toward OAuth-only users.

**Fix:** call `rs.password_hasher.dummy_verify()` (or an equivalent constant-time dummy) when `hashed_password is None`, before raising the generic 401.

### 🟠 W-10 · GoogleProvider client_secret stored as plain str · day 43 (SLA expired +29 d)

**Source:** `src/regstack/oauth/providers/google.py:90` — re-verified today.

```python
self._client_secret = client_secret   # plain str, line 90
```

The `client_secret` is sent to Google's token endpoint in the POST body on every authorization-code exchange. Storing it as a plain `str` means it can appear in heap dumps, repr() output, `pprint(vars(provider))` debug output, and any logging that captures object state. It should be a `pydantic.SecretStr` so `.get_secret_value()` is required to access the raw bytes and `repr()` emits `'**********'`.

**Fix:** change the `__init__` parameter type to `SecretStr` and update call sites in `OAuthConfig` and the `regstack oauth setup` wizard to pass a `SecretStr`.
