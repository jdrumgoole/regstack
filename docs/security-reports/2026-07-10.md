(vulnerable).

already tracked.

### W-4 — CVE-2026-53533: `aiosmtplib 5.1.0` SMTP command injection (CVSS 6.5 Moderate) — carry-forward (day 15)

**Package:** `aiosmtplib` (base dependency: `aiosmtplib>=3.0`)
**Resolved (lock):** `5.1.0` · **Safe version:** `>=5.1.1`
**Advisory:** GHSA-v3q9-hj7j-63hq · Published: June 15, 2026
**Tracked:** GitHub issue #124

The locked version (`5.1.0`) **is** the vulnerable version. `5.1.1` rejects C0
control characters (CR, LF, NUL, etc.) in SMTP command arguments. Prior versions
accept them, allowing SMTP injection via a crafted email address such as
`attacker@evil.com\r\nBcc: victim@example.com`, which can silently add blind-copy
recipients to verification, password-reset, or MFA emails. This is directly on
regstack's security-critical email delivery paths.

No new aiosmtplib advisories were found in the July 9–10 window.

**Action required:**
1. Bump `"aiosmtplib>=5.1.1"` in `pyproject.toml` with updated CVE comment.
2. Run `uv lock`.

### W-5 — CVE-2026-58203: `pydantic-settings 2.14.0` symlink path traversal — carry-forward (day 15)

**Package:** `pydantic-settings` (base dependency: `pydantic-settings>=2.2`)
**Resolved (lock):** `2.14.0` · **Safe version:** `>=2.14.2`
**Advisory:** GHSA-4xgf-cpjx-pc3j (CVE-2026-58203) · Published: 2026-07-06
**Tracked:** GitHub issue #125

The locked version (`2.14.0`) is in the vulnerable range. When a `BaseSettings`
subclass reads from a secrets directory, the size-check does not follow symlinks
but the file-loader does. An attacker with write access to the secrets directory
can create a symlink to an arbitrary filesystem path; `pydantic-settings` reads
the target file and exposes it as a config value. `RegStackConfig` extends
`BaseSettings` and reads from `secrets_env_path` (`regstack.secrets.env`).

## 🟡 INFO (Best practice recommendations)

### I-1 — `UserPublic` exposes `tokens_invalidated_after` and `phone_number` (carry-forward)

`UserPublic` exposes `tokens_invalidated_after` (intentional — allows SPA clients
to detect bulk-revocation without an extra round-trip) and `phone_number` (design
decision). Hosts with stricter PII requirements should subclass `UserPublic` or
add a projection step. No code change required in regstack itself.

### I-2 — `admin_promote_pending` path parameter not validated as `EmailStr` (carry-forward)

`POST /admin/pending/{email}/promote` (`src/regstack/routers/admin.py:204`)
accepts `email: str = Path(...)`. A syntactically invalid email address passes
parameter binding and returns a 404 (LookupError path). The endpoint is
admin-gated so the risk is low. Fix is a one-liner:
`email: Annotated[EmailStr, Path(...)]`.

### I-3 — Duplicate tracking issue for python-multipart cluster (carry-forward, day 14)

Issues #118 (2026-06-23) and #120 (2026-06-24) both track the python-multipart
floor bump. Issue #120 should be updated to enumerate all four CVEs
(CVE-2026-53537/53538/53539/53540) and record the `>=0.0.32` safe floor; issue
#118 should then be closed as a duplicate. (Tracked within W-1 above.)

### I-4 — CVE-2026-48524 missing from pyjwt comment in `pyproject.toml` (carry-forward)

**Package:** `pyjwt` · **CVE:** CVE-2026-48524 · **CVSS:** 3.7 (Low)
**Advisory:** GHSA-fhv5-28vv-h8m8

`PyJWKClient.get_signing_key()` forces a fresh HTTP request to the JWKS endpoint
on every call when the `cache_keys=True` path encounters a key not present in its
in-memory cache. Under sustained load this can exhaust connection pools (DoS). The
vulnerability is already fixed by the `pyjwt>=2.13.0` floor; the gap is that
`CVE-2026-48524` is not enumerated in the `pyproject.toml` comment alongside
CVE-2026-48522/48523/48525/48526. Add it to the comment when making the next
`pyproject.toml` edit (e.g. during the W-1 or W-4 floor bumps).

### §3 — Authentication & authorization

All endpoints that mutate user state or return user data are gated by
`rs.deps.current_user()` or `rs.deps.current_admin()`. `UserPublic.from_user()`
is the only serialisation path used in responses — `hashed_password` is excluded.
Bulk-revoke discipline confirmed:

- **Password reset** (`POST /reset-password`): calls `users.update_password` (bumps
  `tokens_invalidated_after`) AND `lockout.clear`, then blacklists the reset
  token's `jti` to prevent replay. ✓
- **Password change** (`POST /change-password`): calls `users.update_password`
  (bumps `tokens_invalidated_after`) AND `lockout.clear`. ✓
- **Email-change confirm** (`POST /confirm-email-change`): calls `users.update_email`
  which bumps `tokens_invalidated_after`. ✓
- **Admin disable** (`PATCH /admin/users/{id}` with `is_active=False`): calls
  `set_tokens_invalidated_after` immediately after `set_active`. ✓
- **Account deletion**: cascades `oauth_identities` first, then deletes user. ✓

OAuth-only user (`hashed_password=None`) handling: `POST /login` returns the same
generic 401 as a wrong-password attempt (no enumeration). `change-password`,
`change-email`, `delete-account` return 400 via `require_password_set()`. ✓

Password verification uses `pwdlib.PasswordHasher.verify()` (Argon2id). ✓

JWT signing keys derived per-purpose via HMAC-SHA256
(`config/secrets.py:derive_secret`). ✓

### §4 — Storage-layer injection safety

**MongoDB:** All queries use pymongo's parameterised dict API. No `$where`,
`$expr`, `$function`, or `$accumulator` operators. No user-input-derived regex.
`ObjectId.is_valid()` checked before `ObjectId(user_id)` on every Mongo repo
method. No unbounded `$in` arrays from user input.

**SQL:** All queries use SQLAlchemy Core with bound parameters. Two `text()` calls
exist: `SELECT 1` (ping) and a migration `SELECT COUNT(*)` — both with no
user-controlled inputs. `UtcDateTime` TypeDecorator correctly re-attaches UTC on
all reads. `purge_expired()` uses bound timestamp parameters.

### §5 — Input validation & injection

All API input bodies use Pydantic models with `extra="forbid"`. `EmailStr`
validation on all email-bearing fields. E.164 phone validation via
`is_valid_e164()` called in `routers/phone.py` before storage. Email and SSR
templates use Jinja2 `select_autoescape(["html"])`. No `| safe` filters or
`{% autoescape false %}` blocks in any template. OAuth `redirect_to` validated
same-origin in `_validate_redirect()` including backslash and protocol-relative
URL rejection.

### §6 — Rate limiting & DoS prevention

Login lockout called before password verification. Mongo `login_attempts` TTL
index sized to `login_lockout_window_seconds`. Admin pagination caps `limit` at
`le=200`. OAuth state TTL 300s default, completion window 30s. No file uploads.

### §7 — Session & token security

JWT HS256; `jwt_secret` non-empty enforced at construction. Every JWT includes
`jti`. `iat` emitted as float. `JwtCodec` disables pyjwt's `exp`/`iat` checks
and re-validates against injected `Clock`. `_authenticate`: decode → blacklist →
bulk-revoke → `is_active`. No token values in logs — static generic 401 on all
decode failures.

### §8 — CSP and the SSR layer

No `<style>` blocks or `style="..."` attributes in any template. No inline
`<script>` tags — JS loaded via `<script src defer>`. `oauth_complete.html` is
clean. Pages are stateless (no auth state rendered into HTML).

### §9 — Data exposure

All responses use `UserPublic.from_user()` — `hashed_password` excluded. HTTP
error bodies use static strings; no `f"...{exc}"` in routers. JWT decode errors →
generic 401. OAuth failures → `?error=<short_code>` redirect. SMTP password,
OAuth `client_secret`, JWT secret all `SecretStr`. Google token error body logged
only at DEBUG on failure paths.

### §10 — Git history & recent changes

Only report squash commits since 0.8.4. No changes to `auth/`, `config/secrets.py`,
OAuth subsystem, routers, or JWT codec. No accidentally committed credentials.

### §11 — Third-party integration security

SMTP password `SecretStr`, not echoed. SES credentials `SecretStr` or boto3
chain, mutually exclusive with profile. Twilio auth token `SecretStr`, lazy

All action `uses:` pinned to commit SHAs. No `${{ github.event.* }}` in `run:`
