## 🟠 WARNING

### W-1 — CVE-2026-32597: PyJWT accepts unknown `crit` header extensions (CVSS 7.5 HIGH)

**Location:** `pyproject.toml:28` (`pyjwt[crypto]>=2.8`)

PyJWT < 2.12.0 silently accepts JWS tokens whose `crit` array contains extension header names the library does not understand, violating RFC 7515 §4.1.11. The lower bound in `pyproject.toml` is `pyjwt>=2.8`, so a host's resolver can pin any version below 2.12.0.

regstack does not use the `crit` extension itself, which limits exploitability within regstack's own token flows. However, the advisory is confirmed, the fix is a one-line version bump, and downstream consumers resolve the constraint.

**Fix:** Raise lower bound to `pyjwt[crypto]>=2.12.0` in `[project.optional-dependencies].oauth` and in `[dependency-groups].dev`.

### W-2 — `TokenError` message exposed in 401 HTTP response detail

**Location:** `src/regstack/auth/dependencies.py:120`

`AuthDependencies._authenticate` raises:

```python
raise HTTPException(status_code=401, detail=f"Invalid token: {exc}")
```

where `exc` is a `TokenError` wrapping a `pyjwt.PyJWTError`. PyJWT error strings contain structural details such as `"Signature verification failed"`, `"Invalid header string: must start with a letter"`, and `"Claim 'exp' is missing"`. This gives a caller more information about token structure than a generic 401 and could aid crafting of malformed tokens.

**Fix:** Replace with a fixed string, e.g. `detail="Authentication required."`.

---

### W-3 — GitHub Actions use mutable tag pinning, not SHA pinning

**Location:** `.github/workflows/test.yml` and `.github/workflows/publish.yml`

All `uses:` directives reference mutable version tags:

| Action | Reference used |
|---|---|
| `actions/checkout` | `@v4` |
| `astral-sh/setup-uv` | `@v3` |
| `actions/upload-artifact` | `@v4` |
| `actions/download-artifact` | `@v4` |
| `pypa/gh-action-pypi-publish` | `@release/v1` |

Tags can be force-pushed by the action author. A compromised or hijacked action repository could silently inject malicious code into CI, including the publish job that pushes to PyPI. `pypa/gh-action-pypi-publish` runs with `id-token: write` during the publish job — the highest-impact target.

**Fix:** Pin every `uses:` to its full commit SHA. Use Dependabot or Renovate with `versioning-strategy: pin-digest` to keep them current automatically.

## 🟡 INFO

### I-1 — CVE-2026-40347: python-multipart DoS via large multipart preamble/epilogue (CVSS 3.1 MEDIUM)

**Location:** `pyproject.toml:29` (`python-multipart>=0.0.9`)

python-multipart < 0.0.26 allows a denial-of-service attack by sending `multipart/form-data` bodies with excessively large preamble or epilogue data. Fixed in 0.0.26. FastAPI uses python-multipart for form-data endpoints (login form POSTs in the SSR layer).

**Fix:** Raise lower bound to `python-multipart>=0.0.26`.

---

### I-2 — `pywebview>=5.0` is in base dependencies, not an optional extra

**Location:** `pyproject.toml` `[project.dependencies]`

`pywebview` is a desktop GUI framework used only by the interactive CLI wizards (`regstack oauth setup`, `regstack theme design`). Every `pip install regstack` — including headless server deployments — pulls in pywebview and its transitive GUI dependencies (GTK/WebKit2GTK on Linux, WKWebView on macOS). This unnecessarily inflates the attack surface and install size for servers that never run the wizards.

**Fix:** Move `pywebview>=5.0` to a new optional extra (e.g. `[project.optional-dependencies].wizard`).

---

### I-3 — `enforce_mfa_on_oauth_signin` config flag is declared but never read

**Location:** `src/regstack/config/schema.py:64` (defined), `src/regstack/routers/oauth.py` (no reference)

`OAuthConfig.enforce_mfa_on_oauth_signin` is documented in the wizard and in CLAUDE.md as enforcing SMS 2FA on OAuth sign-ins in regulated environments. The oauth router callback never reads this flag, so enabling it has no effect. An admin who sets it expecting enforcement gets false security.

**Fix:** Either implement the enforcement gate in the callback, or remove the field and documentation until M6/later milestone.

---

### I-4 — `user_logged_out` hook event is declared but never fired

**Location:** `src/regstack/hooks/events.py:18` (in KNOWN_EVENTS), `src/regstack/routers/logout.py` (no `fire` call)

The logout router calls `rs.blacklist.revoke(jti, exp)` and returns without firing `hooks.fire("user_logged_out", ...)`. Hosts that subscribe to `user_logged_out` to invalidate sessions in external systems (Redis caches, audit logs) will never receive the event.

**Fix:** Add `await rs.hooks.fire("user_logged_out", user_id=user.id)` in the logout handler before returning.

---

### I-5 — Admin `DELETE /admin/users/{user_id}` does not cascade `oauth_identities`

**Location:** `src/regstack/routers/admin.py:131`

The self-service `DELETE /account` endpoint correctly calls `rs.oauth_identities.delete_by_user_id(user.id)` before `rs.users.delete(user.id)`. The admin deletion endpoint skips this step, leaving orphan `oauth_identities` rows behind.

There is no active security risk because the user row is deleted and the orphan rows have no active subject. UUIDs and ObjectIds are never reused, so the orphans cannot be re-claimed. However, this is data-integrity debt and inconsistent with the stated "anti-orphan" discipline in CLAUDE.md.

**Fix:** Add `await rs.oauth_identities.delete_by_user_id(user_id)` in `admin.py` before `rs.users.delete(user_id)`.

---

### I-6 — `was_new_account` always returns `False` in `/oauth/exchange` response

**Location:** `src/regstack/routers/oauth.py:153`

`_resolve_user` correctly computes a `was_new: bool`, but this value is never stored on the `OAuthState` row. The exchange endpoint always returns `was_new_account=False`. SPAs using this field to present "Welcome, new user!" flows will always see `False`.

This is a functional bug rather than a security issue, but it is noted for completeness.

---

### I-7 — No top-level `permissions:` block in `test.yml`

**Location:** `.github/workflows/test.yml`

`test.yml` does not declare `permissions:` at the workflow level, relying on the repository's default token permissions. If the repository default is `read-write`, the test workflow runs with unnecessarily broad access. `publish.yml` correctly limits `id-token: write` to only the publish job.

**Fix:** Add `permissions: contents: read` at the top of `test.yml`.

---

### I-8 — No sigstore build-provenance attestations in `publish.yml`

**Location:** `.github/workflows/publish.yml:60-64`

PyPI now supports and recommends build-provenance attestations via sigstore to enable downstream consumers to verify that a published wheel was built by a specific GitHub Actions run. `pypa/gh-action-pypi-publish` supports `attestations: true` but it is not enabled.

**Fix:** Add `attestations: true` to the `pypa/gh-action-pypi-publish` step.

---

### I-9 — `login_max_per_minute` / `login_max_per_hour` config fields are stubs

**Location:** `src/regstack/config/schema.py:148-149`

These two fields are defined with the comment `"Reserved for future route-level rate limiting (slowapi-style)"` but neither is read anywhere in the codebase. The per-account lockout (`LockoutService`) is the only rate-limiting mechanism. There is no global IP-based or per-minute rate limiting at the library level.

This is not a vulnerability (hosts should add reverse-proxy rate limiting), but the documented fields create a false impression of protection.

**Fix:** Either implement the rate-limiting gate or remove the fields and document that IP-level rate limiting is the host's responsibility.

---

### I-10 — `.gitignore` does not cover `*.pem`, `*.key`, `*.p12`, `*.pfx`

**Location:** `.gitignore`

The current `.gitignore` covers `.env`, `regstack.secrets.env`, and `htmlcov/`, but does not include `*.pem`, `*.key`, `*.p12`, or `*.pfx`. A developer generating a TLS certificate or private key inside the repository root could accidentally commit it. No such files are currently tracked.

**Fix:** Add `*.pem`, `*.key`, `*.p12`, `*.pfx` to `.gitignore`.

---

### I-11 — Wheel ships `http://localhost:8000` as default `base_url`

**Location:** `src/regstack/config/schema.py:93` (inside the published wheel)

`base_url` defaults to `http://localhost:8000` in `RegStackConfig`. This is intentional for local development and must be overridden in production, but it ships in the wheel and could be a misleading default if a host never configures it. This is a documentation/UX concern, not a security issue.

No action required; flagged for awareness.

## 🟢 CLEAN

### §1 — Dependencies

- `fastapi>=0.110`, `pydantic>=2.6`, `sqlalchemy>=2.0`, `alembic>=1.13`, `pwdlib[argon2]>=0.2.1`, `aiosmtplib>=3.0`, `dnspython>=2.6`, `jinja2>=3.1`, `cryptography>=42`: no active CVEs in the past 90 days.
- Optional-extra hygiene correct: `oauth` adds only `pyjwt[crypto]`; `postgres` adds only `asyncpg`; `ses`/`sns` add only `aioboto3`; `twilio` adds only `twilio`.
- `pymongo`, `asyncpg`, `aioboto3`, `twilio` are correctly in `[project.optional-dependencies]`, not the base dependency list.

### §2 — Hardcoded Secrets

- No hardcoded API keys (`sk-`, `pk_`, `AKIA`), connection strings with credentials, private key headers, or base64-encoded JWTs found in `src/`, `tests/`, `examples/`, or `docs/`.
- All credentials (`jwt_secret`, `smtp_password`, `twilio_auth_token`, `google_client_secret`, `database_url`) are stored as `SecretStr` or equivalent and never echoed in logs.
- `git ls-files` finds no `.env`, `.key`, `.pem`, or credential files tracked in the repository.

### §3 — Authentication & Authorization

- Bulk-revoke discipline correct across all flows: password reset calls `update_password` + `lockout.clear`; change-password bumps `tokens_invalidated_after`; email-change confirm bumps `tokens_invalidated_after`; admin user-disable bumps `tokens_invalidated_after`.
- Self-service account deletion cascades `oauth_identities` before `users.delete`.
- OAuth-only users (`hashed_password=None`) receive an identical 401 to wrong-password attempts — no account enumeration.
- Constant-time password verification via `pwdlib.PasswordHash.verify` (Argon2id).
- JWT signing keys are per-purpose derived via HMAC-SHA256 (`derive_secret(jwt_secret, purpose)`).
- Anti-enumeration on `/forgot-password` and `/resend-verification` — both always return 202.
- `UserPublic` projection used on all public endpoints; `hashed_password` and `tokens_invalidated_after` absent from API responses.

### §4 — Storage-layer Injection

- All MongoDB queries use typed ObjectId filters or string equality; no `$where`, `$expr`, `$function`, or `$accumulator` operators; `ObjectId.is_valid()` guards every `ObjectId()` call on URL parameters.
- All SQL queries use SQLAlchemy Core parameterized expressions; no f-string or `%` interpolation into raw SQL; `text('SELECT 1')` health-check carries no user input.
- `UtcDateTime` TypeDecorator correctly re-attaches UTC tzinfo on read.

### §5 — Input Validation

- Every endpoint accepts only Pydantic models with `extra='forbid'`; no raw `dict` parsing.
- `EmailStr` on all email-bearing request fields.
- `is_valid_e164()` called on all phone inputs before storage.
- Jinja2 autoescape enabled for HTML in both email and SSR environments; no `| safe` filters or `Markup()` wrappers in any template.
- `redirect_to` validated as same-origin against `config.base_url` before storage in OAuth state row.
- CLI wizards use Click prompts and pywebview; no `shell=True` subprocess calls.

### §6 — Rate Limiting

- `LockoutService.check()` runs before password verification; `record_failure()` called on both "user not found" and "wrong password" paths.
- `login_attempts` TTL index correct in MongoDB; `purge_expired()` with bound parameter in SQL backends.
- Admin `/users` list capped at `limit` max 200 via `Query(ge=1, le=200)`.
- OAuth state TTL: Mongo TTL index on `expires_at`; SQL `purge_expired()` with bound parameter.
- No file upload endpoints.

### §7 — Session & Token Security

- JWT algorithm constrained to `HS256/HS384/HS512` (Literal type).
- Every JWT includes a unique `jti` (`secrets.token_urlsafe(16)`).
- `iat` emitted as `float` for microsecond-precision bulk-revoke comparison.
- pyjwt's `exp`/`iat` checks disabled; both validated against injected `Clock`.
- `_authenticate` flow: decode → `blacklist.is_revoked(jti)` → `users.get_by_id` → `is_active` check → `is_payload_bulk_revoked(iat <= cutoff)`.
- No JWT secret, SMTP password, or OAuth client_secret appears in any log call.

### §8 — CSP and the SSR Layer

- All SSR templates contain zero `<style>` blocks and zero `style="..."` attributes.
- Only one `<script src="..." defer>` tag per page; no inline `<script>` blocks.
- `oauth_complete.html` follows the same CSP discipline.
- No server-side auth state rendered into HTML (all account data fetched client-side by `regstack.js`).

### §9 — Data Exposure

- DB `IntegrityError` mapped to a fixed 409 message; no raw driver error text in HTTP responses.
- OAuth callback failures redirect with short error codes (`bad_state`, `state_expired`, `oauth_failed`); no exception detail exposed.
- `smtp_password` accessed via `.get_secret_value()` only at send time.

### §10 — Git History

- No `.env`, `.key`, `.pem`, credential, or secret files in any commit across all branches.
- Recent 30 commits are all legitimate feature/fix/release commits with no suspicious patterns.

### §11 — Third-Party Integration Security

- SMTP, SES, SNS, Twilio, and Google OAuth credentials loaded from config and never logged.
- Lazy imports for `aioboto3` and `twilio`; base install does not pull optional extras.
- Google ID-token verification uses `PyJWKClient` against the configured JWKS URL, validates signature, `iss`, `aud`, `exp`, `iat`, and `nonce`.

### §12 — GitHub Actions (partial)

- No `${{ github.event.* }}` in `run:` blocks; no untrusted-input injection.
- No `pull_request_target` trigger.
- No self-hosted runners.
- No `PYPI_API_TOKEN`; publish uses OIDC trusted publishing.
- `publish.yml` triggers on tag push (`v*`) only.
- Cache keys use `uv.lock` hash, not user-controlled input.
- Tag-matches-version verification step reads version from `pyproject.toml` via `tomllib`.

### §13 — PyPI Package Integrity

- Wheel contents verified: `tests/`, `docs/`, `tasks/`, `examples/`, `.github/` are NOT included.
- No test fixture strings (`alice@example.com`, `hunter2hunter2`, `/Users/`, `/home/`) found in wheel source files.
- `pyproject.toml` version `0.5.0` matches `src/regstack/version.py`.
- OIDC trusted publishing in use; no `PYPI_API_TOKEN`.

### §14 — OAuth Subsystem

- PKCE: `code_verifier` stored server-side on the state row; only `code_challenge` (SHA-256) sent to the provider.
- State row atomically consumed (`find_one_and_delete` on Mongo; `SELECT + DELETE` transaction on SQL).
- ID-token verification checks signature, `iss`, `aud`, `exp`, `iat`, and `nonce`.
- Linking-policy gates (`auto_link_verified_emails`, `identity_in_use`, `already_linked`) all correct.
- Last-provider unlink blocked when user has no password.
- `(provider, subject_id)` and `(user_id, provider)` UNIQUE enforced at DB level on both Mongo and SQL.
- All four OAuth hook events present in `KNOWN_EVENTS`.

### §15 — Multi-backend Parity & Schema Migration Safety

- CI matrix covers SQLite, Postgres, and MongoDB on every push.
- Both migrations have `upgrade()` and `downgrade()`; `hashed_password` nullable change uses `batch_alter_table` for SQLite compatibility.
- Mongo index parity with SQL unique constraints for `users.email`, `oauth_identities (provider, subject_id)`, and `oauth_identities (user_id, provider)`.
- `AsyncMongoClient(tz_aware=True)` and `UtcDateTime` TypeDecorator consistently applied.
