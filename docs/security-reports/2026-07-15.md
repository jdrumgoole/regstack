### W-4 — CVE-2026-53533: `aiosmtplib` SMTP command injection (CVSS 6.5) — carry-forward (day 19)

**Package:** `aiosmtplib`
**Floor:** `>=3.0` · **Locked:** `5.1.0` (vulnerable) · **Safe:** `>=5.1.1`
**Tracked:** GitHub issue #124

The locked `5.1.0` is the vulnerable version. `SMTP.mail()`, `SMTP.rcpt()`,
`SMTP.vrfy()`, and `SMTP.expn()` pass caller-supplied email addresses to
the SMTP server without rejecting C0 control characters (0x00–0x1F
including CR, LF, NUL). An email address containing a CRLF sequence can
inject arbitrary SMTP commands into the session at the wire level — below
Jinja2 template rendering, which cannot protect against wire-level injection.

**regstack exposure:** The SMTP backend sends verification, password-reset,
MFA, and email-change emails to user-supplied addresses. Practical risk is
reduced by `EmailStr` validation (which rejects literal CR/LF), but the
dependency floor must still be corrected.

**Action required:**
1. Bump `"aiosmtplib>=5.1.1"` in `pyproject.toml`. Update the inline
   comment to add CVE-2026-53533 and cite `5.1.1` as safe floor.

## 🟡 INFO (Best practice recommendations)

### I-1 (carry-forward) — `UserPublic` exposes `tokens_invalidated_after`

`UserPublic` includes `tokens_invalidated_after: datetime | None`. This is
an intentional design choice (SPAs compare it to the session JWT `iat` to
detect bulk-revocation without an extra round-trip). The exposure leaks the
exact timestamp of the most recent security event (password change, email
change, admin-disable) to any authenticated client. Acceptable for regstack
defaults; hosts with stricter data-minimisation requirements should subclass
`UserPublic` or project out the field. No code change required in regstack
itself; document the trade-off explicitly in `docs/security.md`.

### I-2 (carry-forward) — `admin_promote_pending` path parameter not validated as `EmailStr`

`POST /admin/pending/{email}/promote` (`src/regstack/routers/admin.py:204`)
accepts `email: str = Path(...)`. A syntactically invalid email address
passes parameter binding and returns 404. The endpoint is admin-gated so
risk is low. One-line fix: `email: Annotated[EmailStr, Path(...)]`.

### I-3 (carry-forward) — Duplicate tracking issue for python-multipart

Issues #118 (2026-06-23) and #120 (2026-06-24) both track the
python-multipart floor bump. Close #118 as duplicate of #120; update #120
to enumerate all four CVEs and record `>=0.0.32` as the safe floor.

### I-4 (carry-forward) — CVE-2026-48524 missing from pyjwt comment in `pyproject.toml`

`PyJWKClient.get_signing_key()` causes a fresh JWKS fetch on every cache
miss, which can exhaust connection pools under load. Fixed at `>=2.13.0`
(current lock and floor). Add `CVE-2026-48524` alongside the existing
CVE-2026-48522/48523/48525/48526 entries during the next `pyproject.toml`
edit.

### I-5 (new) — Email-change token JTI is not blacklisted on first use

**File:** `src/regstack/routers/account.py:175`

`POST /confirm-email-change` does not blacklist the token's `jti` after
successfully completing the email swap. The `reset-password` handler does
blacklist its token's JTI at `src/regstack/routers/password.py:117`. The
email-change token has a 1-hour TTL (default). An attacker who captures
the URL from browser history, proxy logs, or email forwarding can replay
it within that window; `update_email()` accepts the second call silently
(same user, same email — no constraint violation) and bumps
`tokens_invalidated_after`, forcing the user to re-authenticate.

The practical impact is low: no email hijacking is possible (the target
address is already set), but the attacker can cause repeated forced
re-logins until token expiry. The fix is a one-liner matching the
reset-password pattern: call `await rs.blacklist.revoke(jti, exp)` after
`update_email()` succeeds.

### I-6 (new) — "X attempt(s) remaining" count in 401 response body

**File:** `src/regstack/routers/login.py:35–43`

`_build_invalid()` includes the remaining failure count in the 401 detail
message: `f"Invalid email or password. {remaining} attempt(s) remaining."`.
This tells a credential-stuffing attacker exactly when to pause to avoid
lockout, enabling systematic pacing of brute-force attempts to stay under
the threshold indefinitely. Recommendation: return a static `"Invalid email
or password."` message regardless of remaining attempts. The lockout
behaviour is unchanged; only the count disclosure is removed.

### I-7 (new) — `jwt_audience` defaults to `None`; no multi-instance deployment guidance

**File:** `src/regstack/config/schema.py`

With `jwt_audience = None`, pyjwt skips audience validation on decode. If
two regstack instances share the same `jwt_secret` (a microservice topology
where one JWT secret is shared across services), a session token issued by
instance A would be accepted by instance B. No audience guidance appears in
`docs/configuration.md` or the examples. Recommendation: add a
configuration note advising hosts to set `jwt_audience` to a service-unique
string in any deployment where multiple regstack instances share a
`jwt_secret`.

### I-8 (new) — No HTTP security headers set or demonstrated

**Scope:** SSR pages served by `ui_router`

regstack does not set `Content-Security-Policy`, `X-Frame-Options`,
`X-Content-Type-Options`, or `Referrer-Policy` headers. This is expected
for an embedded library — host middleware owns the response headers. However,
neither the `examples/` demos nor `docs/embedding.md` show a recommended
middleware stack for hosts that enable `ui_router`. The absence of guidance
means hosts may ship regstack's SSR pages without appropriate defensive
headers. Recommendation: add a "Security hardening" section to the embedding
guide showing `starlette.middleware.trustedhost.TrustedHostMiddleware` and a
simple security-headers middleware configured for the regstack SSR prefix.

### I-9 (new) — `twilio_account_sid` typed as `str | None` rather than `SecretStr`

**File:** `src/regstack/config/schema.py:98`

Every other credential field in `RegStackConfig` is `SecretStr | None`:
`smtp_password`, `ses_access_key_id`, `ses_secret_access_key`,
`twilio_auth_token`, `google_client_secret`. The Twilio Account SID
(`AC…`) is a semi-public identifier that appears in Twilio URLs and console
output, but it is still a credential. Typing it as plain `str` means it
will appear unmasked in `repr()` output, Pydantic model dumps, and
exception tracebacks. One-line fix: change to `SecretStr | None` and
update the access site to `.get_secret_value()`.

### I-10 (new) — `GoogleProvider._client_secret` held as plain `str` in memory

**File:** `src/regstack/oauth/providers/google.py`

`GoogleProvider.__init__` receives `client_secret: str` and stores it as
`self._client_secret: str`. Once extracted from `SecretStr` at construction
in `app.py:188`, there is no in-memory masking. A crash dump or
`__repr__` of the provider object would include the secret in plain text.
There is no exploitable vector here given the current codebase, but adding
a `__repr__` override returning `GoogleProvider(client_id=..., client_secret=***)`
provides defense-in-depth against accidental log exposure.

### I-11 (new) — Lockout is per-email only; no per-IP protection

**File:** `src/regstack/auth/lockout.py`

`lockout.record_failure(email, ip=None)` — the `ip` argument is always
`None` in the login router (request IP is never sourced). An attacker with
a list of target email addresses can distribute guesses across accounts,
advancing each account's lockout counter slowly while making effectively
unlimited aggregate attempts. For deployments expecting credential-stuffing
attacks, per-IP rate limiting at the reverse-proxy layer is the standard
mitigation. Recommendation: document this gap in `docs/security.md` and
add a configuration guidance note in `docs/embedding.md` recommending
proxy-layer IP rate limiting (e.g., nginx `limit_req_zone`, Cloudflare
Rate Limiting) as a complement to the per-account lockout.
