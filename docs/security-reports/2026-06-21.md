## 🟡 INFO (Best practice recommendations)

### I-1 — CVE-2026-48524 absent from `pyproject.toml` tracking comment

The June-2026 PyJWT advisory cluster fixed in 2.13.0 comprises five CVEs:
48522 (SSRF via URI scheme), 48523 (algorithm allow-list bypass), **48524**
(unbounded JWKS endpoint requests per unknown `kid`), 48525 (DoS in
detached-payload JWS), and 48526 (algorithm confusion via public JWK as
HMAC secret). The tracking comment added in commit #114 (`pyproject.toml`
lines 37–44) lists all five *except* CVE-2026-48524.

The codebase is correctly protected: the lock file pins `pyjwt 2.13.0` and
`GoogleProvider` constructs `PyJWKClient(..., cache_keys=True)`, mitigating
the amplification. The gap is purely in the audit-trail comment that future
reviewers will read to understand why the version floor exists.

**Recommendation:** Append `CVE-2026-48524 (unbounded JWKS requests per
unknown kid)` to the comment block around line 44 of `pyproject.toml`.

### I-2 — `UserPublic` exposes `tokens_invalidated_after`

The security review specification states that `UserPublic` excludes
`hashed_password`, `tokens_invalidated_after`, and internal IDs.
`src/regstack/models/user.py:104` deliberately includes
`tokens_invalidated_after`, with this docstring:

> Bulk-revoke cutoff. SPAs comparing this to their session JWT's `iat`
> can tell when the tokens they hold have been invalidated by a password
> change / email change without making another request.

The rationale is sound: authenticated SPA clients benefit from knowing
when their session was bulk-revoked without polling `/me` continuously.
However, the field also exposes the precise UTC timestamp of the user's
most-recent security event (password change, email change, admin-forced
logout) to any caller who obtains a valid session — including an attacker
who briefly holds a stolen token or an insider who captures a single API
response.

There is no cross-user leakage (the field is only returned about the
authenticated user to themselves, or to an admin). The risk is marginal.
However, the conflict with the spec creates a gap in external auditors'
expectations.

**Recommendation:** Gate the field behind a `RegStackConfig` flag
(`expose_revoke_cutoff_to_client: bool = False`) defaulting to off, and
strip it from `UserPublic.from_user()` when off. Hosts that want the SPA
optimisation opt in explicitly. This resolves the spec conflict without
breaking existing hosts — they set the flag on the same day they update.

### I-3 — `${{ matrix.python-version }}` interpolated directly in a `run:` block

`.github/workflows/test.yml` line 68:

```yaml
- name: Pin Python ${{ matrix.python-version }}
  run: uv python pin ${{ matrix.python-version }}
```

The GitHub Actions expression `${{ matrix.python-version }}` is expanded by
the runner into the shell command before the shell sees it. The current
matrix values (`"3.11"`, `"3.12"`) are developer-controlled constants, so
there is no exploitable injection path today. GitHub's official hardening
guidance still recommends routing all expression values through an `env:`
intermediary before using them in shell commands, to prevent a future matrix
refactor from accidentally widening the surface:

```yaml
- name: Pin Python ${{ matrix.python-version }}
  env:
    PY_VER: ${{ matrix.python-version }}
  run: uv python pin "$PY_VER"
```

**Recommendation:** Apply the env-var pattern in the next routine workflow
cleanup. Low urgency.

### §3 Authentication & Authorization Audit

All authenticated endpoints inject `rs.deps.current_user()` or
`rs.deps.current_admin()`; all admin endpoints additionally require
`is_superuser=True`.

**Bulk-revoke discipline — all branches verified:**

| Event | Mechanism |
|-------|-----------|
| `POST /reset-password` | `users.update_password()` bumps `tokens_invalidated_after`; reset token's `jti` added to blacklist |
| `POST /change-password` | `users.update_password()` bumps `tokens_invalidated_after`; `lockout.clear()` |
| `POST /confirm-email-change` | `users.update_email()` bumps `tokens_invalidated_after` |
| `PATCH /admin/users/{id}` with `{is_active: false}` | `users.set_tokens_invalidated_after()` called explicitly |
| `DELETE /account` (user) + `DELETE /admin/users/{id}` | `oauth_identities.delete_by_user_id()` called before `users.delete()` |

**OAuth-only users (`hashed_password=None`):**
- `POST /login`: verifies password first; `None` hashed-password returns the
  same generic 401 as a wrong guess — no account-existence enumeration.
- `POST /change-password`, `POST /change-email`, `DELETE /account`,
  `POST /phone/start`, `DELETE /phone`: `require_password_set()` returns 400
  with a pointer to the forgot-password flow.

Password comparison uses `pwdlib.verify()` (Argon2id) — constant-time.
JWT signing keys are derived per-purpose via `derive_secret(master, purpose)`
(HMAC-SHA256); a captured session token cannot satisfy the password-reset
endpoint.

### §4 Storage-layer Injection Safety

**MongoDB:** All queries use PyMongo's structured document API. No `$where`,
`$expr`, `$function`, or `$accumulator` operators anywhere in
`src/regstack/backends/mongo/`. `ObjectId.is_valid(user_id)` guards every
`_id`-based query in `UserRepo` and related repos. No regex is constructed
from user input.

**SQL (SQLite + Postgres):** All queries use SQLAlchemy Core parameterized
binds. The only `text()` calls are:
- `text("SELECT 1")` in `SqlBackend.ping()` — no user input.
- `text("SELECT COUNT(*) FROM users WHERE hashed_password IS NULL")` in
  migration 0002's `downgrade()` — no user input.

`UtcDateTime` TypeDecorator (`src/regstack/backends/sql/types.py`):
`process_result_value()` re-attaches UTC tzinfo when the driver returns a
naive datetime (SQLite path), preventing a tz-mismatch `TypeError` in the
bulk-revoke comparison.

### §6 Rate Limiting & DoS Prevention

- `lockout.check()` runs before password verification; a locked-out attacker
  cannot distinguish a correct guess from an incorrect one.
- Disabled and unverified accounts still record a failure after password
  verification — prevents a "probe with correct password on a disabled
  account" side-channel.
- MongoDB `login_attempts` collection: TTL index sized to
  `login_lockout_window_seconds` (`indexes.py:52`).
- Admin `/users` pagination: `limit` capped via `Query(ge=1, le=200)`.
- OAuth state rows: Mongo TTL index on `expires_at`; SQL `purge_expired()`
  for the same. `completion_ttl_seconds` (default 30 s) shortens the
  result-token window after the callback arrives.
- No file-upload endpoints exist.

### §7 Session & Token Security

- Algorithm constrained to `Literal["HS256", "HS384", "HS512"]`; `none` is
  not representable.
- Empty `jwt_secret` rejected at `JwtCodec.__init__` before the first token
  is ever minted.
- Every JWT includes `jti` (`secrets.token_urlsafe(16)`).
- `iat` emitted as `float` (`.timestamp()`) so a login in the same
  wall-clock second as a bulk-revoke event is not falsely rejected (see
  CLAUDE.md "Bulk revocation: float `iat` and `<=` cutoff").
- `verify_exp`/`verify_iat` disabled in pyjwt's options dict; both are
  re-validated against the injected `Clock`, keeping `FrozenClock`-driven
  tests deterministic.
- `_authenticate` pipeline: decode → `blacklist.is_revoked(jti)` → 
  `users.get_by_id(sub)` → `is_active` check → `is_payload_bulk_revoked()`.
- JWT decode errors collapse to a single generic 401 (`"Invalid or expired
  token."`) — specific pyjwt reason strings are never echoed to clients
  (`src/regstack/auth/dependencies.py:156-165`).
- No `access_token`, `id_token`, or `jwt_secret` values appear in any log
  call.

### §14 OAuth Subsystem Audit

- **PKCE:** `code_verifier` stored on the `oauth_states` row; only
  `code_challenge` (SHA-256 base64url of verifier) goes to the provider
  (`routers/oauth.py:598-603`).
- **State lifecycle:** missing row → `bad_state`; expiry check uses
  `rs.clock.now()` (not `datetime.now(UTC)`) for `FrozenClock` parity;
  expired row → `state_expired`.
- **Atomic consume:** SQL `consume()` uses a single `engine.begin()` block
  (select + delete in one transaction); Mongo uses `find_one_and_delete()`
  — a second `/oauth/exchange` call with the same id returns 404.
- **ID-token verification:** JWKS key fetched via `PyJWKClient`, then
  `pyjwt.decode()` with `algorithms=["RS256"]`, explicit `audience`,
  `issuer`, and `options={"require": ["sub", "iss", "aud", "exp", "iat",
  "nonce"]}`. Nonce is additionally compared post-decode.
- **Linking policy:** `email_in_use`, `identity_in_use`, `already_linked`
  all enforced with distinct short error codes — no silent ownership transfer.
- **Last-sign-in-method guard:** `DELETE /oauth/{provider}/link` refuses if
  `hashed_password is None` and no other identity remains.
- **DB uniqueness:** `(provider, subject_id)` and `(user_id, provider)`
  enforced at DB level in both Mongo (unique indexes in `indexes.py:72-86`)
  and SQL (`UniqueConstraint` in `schema.py:143-144`).
- **Hooks:** `oauth_signin_started`, `oauth_signin_completed`,
  `oauth_account_linked`, `oauth_account_unlinked` all present in
  `KNOWN_EVENTS` and fired at the correct points in `routers/oauth.py`.
