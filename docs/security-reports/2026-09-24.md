## Section 3 — Authentication & Authorisation Audit

### 🟢 CLEAN — Endpoint authentication coverage

All mutating endpoints inject `rs.deps.current_user()` or `rs.deps.current_admin()`. Admin endpoints (`/admin/stats`, `/admin/users`, `/admin/users/{id}`, `PATCH /admin/users/{id}`, `DELETE /admin/users/{id}`, `/admin/users/{id}/resend-verification`, `/admin/pending/{email}/promote`) all depend on `rs.deps.current_admin()`. All data responses use `UserPublic.from_user()`.

### 🟢 CLEAN — Bulk-revoke discipline

Password reset calls `users.update_password()` (which bumps `tokens_invalidated_after`) and `lockout.clear()`. Password change calls `users.update_password()` and `lockout.clear()`. Admin disable calls `users.set_tokens_invalidated_after()` before the 200 response. Account deletion cascades OAuth identities before deleting the user.

### 🟠 W-8 — Timing oracle on login for OAuth-only accounts (day 6 — **SLA tomorrow 2026-09-25**)

`src/regstack/routers/login.py:99`: the login handler contains:

```python
if user.hashed_password is None or not rs.password_hasher.verify(
    payload.password, user.hashed_password
):
```

Python short-circuits on `hashed_password is None`: if the account is OAuth-only, the ~100 ms Argon2 verify is skipped and the response returns in ~1 ms. An attacker can probe whether a given email is OAuth-only vs password-enabled with ~200 requests and a simple latency histogram.

**Remediation:** Always run a dummy Argon2 verify when `hashed_password is None` to preserve constant time (e.g., `rs.password_hasher.dummy_verify()` or equivalent constant-time guard), then raise the same generic 401.

### 🟢 CLEAN — `hashed_password is None` side effects

`change-password`, `change-email`, `delete-account` all call `require_password_set(user)` before proceeding. OAuth unlink refuses if it would remove the only sign-in method. Login returns the same generic 401 for missing password as for a wrong password (modulo the timing gap, W-8).

### 🟢 CLEAN — Constant-time password comparison

`pwdlib` (`argon2`) is used for all password hashing and verification. No `==` comparison is used on raw password strings.

### 🟢 CLEAN — Per-purpose JWT key derivation

`derive_secret(jwt_secret, purpose)` in `src/regstack/config/secrets.py` uses `hmac.new(master, purpose.encode(), hashlib.sha256).digest()`. Each purpose (`session`, `password_reset`, `email_change`, `phone_setup`, `login_mfa`) gets a distinct derived key.

## Section 4 — Storage-layer Injection Safety

### 🟢 CLEAN — MongoDB backend

All MongoDB queries use typed BSON document constructors with literal operator names. No user input is interpolated into query operators, no `$where`/`$expr`/`$function` operators are used, no regex patterns are built from user input. `get_by_id` guards with `ObjectId.is_valid(user_id)` before casting.

### 🟢 CLEAN — SQL backend

All SQL queries use SQLAlchemy Core with parameterised binds. Two `text(...)` usages exist: `src/regstack/backends/sql/backend.py` uses `text("SELECT 1")` for a health-ping (no user input); the migration `0002_oauth.py` uses a bound-parameter `text("SELECT COUNT(*) FROM users WHERE ...")` for a row-count check. Neither accepts user input. `purge_expired()` implementations use bound `cutoff` parameters.

### 🟢 CLEAN — `UtcDateTime` TypeDecorator

`src/regstack/backends/sql/types.py` consistently re-attaches UTC tzinfo on result values.

### 🟠 W-6 — SQL `OAuthStateRepo.consume` non-atomic read-delete (day 16 — **9 days past SLA**)

`src/regstack/backends/sql/repositories/oauth_state_repo.py:63`: `consume` performs a `SELECT` followed by a `DELETE` within a single transaction. Under both PostgreSQL (READ COMMITTED isolation) and SQLite, two concurrent connections can each execute the SELECT and observe the row before either has committed the DELETE, allowing both to receive the same state row and exchanging the OAuth token twice.

The MongoDB backend uses `find_one_and_delete` which is atomic at the server level. The SQL path should match this guarantee.

**Remediation:** Rewrite `consume` to use `DELETE … RETURNING *` (PostgreSQL) or an equivalent serialised exclusive transaction pattern (SQLite) so the SELECT and DELETE are one atomic server-side operation.

## Section 7 — Session & Token Security

### 🟢 CLEAN — JWT configuration, `jti`, `iat` float, clock injection, revocation discipline

`JwtCodec.__init__` enforces `len(jwt_secret) >= MIN_JWT_SECRET_LENGTH (32)`. Every token minted by `JwtCodec.encode()` receives `jti=secrets.token_urlsafe(16)`. `iat` is emitted as a float. pyjwt's built-in `exp`/`iat` validation is disabled; both are validated against the injected `Clock`. `_authenticate` checks decode → blacklist → bulk-revoke → `is_active` in correct order.

### 🟢 CLEAN — No token leakage in logs

`_authenticate` catches `TokenError` and raises a static 401. OAuth callback errors log generic codes only.

### 🟠 W-2 — Email-change token `jti` never blacklisted (day 24 — **17 days past SLA**)

`src/regstack/routers/account.py` → `confirm_email_change`: after successfully decoding the email-change JWT, the handler calls `users.update_email(...)` but never extracts `jti` and never calls `blacklist.insert(jti, exp)`. A valid email-change link can therefore be replayed until it expires (default 60 min TTL), allowing an attacker who intercepts or obtains a copy of the link to repeatedly swap the email address.

**Remediation:** After `_decode_email_change_token(token)`, extract `payload.jti` and `payload.exp`. Check `await rs.blacklist.is_revoked(jti)` first (→ 400 if already revoked). On success, call `await rs.blacklist.insert(jti, exp)` before returning.

### 🟠 W-3 — Email-change handler skips bulk-revocation check (day 24 — **17 days past SLA**)

`src/regstack/routers/account.py` → `confirm_email_change`: after `_decode_email_change_token`, the handler fetches the user by `sub` but never calls `is_payload_bulk_revoked(payload, user.tokens_invalidated_after)`. A token minted before a `change-password` event (which bumps `tokens_invalidated_after`) would still be accepted to change the email.

**Remediation:** After `users.get_by_id(user_id)`, add:
```python
if is_payload_bulk_revoked(payload, user.tokens_invalidated_after):
    raise HTTPException(status_code=400, detail="Email-change link has been invalidated.")
```

## Section 14 — OAuth Subsystem Audit

### 🟢 CLEAN — PKCE invariants

`code_verifier` is generated server-side in `_begin_flow` and stored on the `OAuthState` row. Only the SHA-256 challenge goes to the provider as a query parameter. The verifier never appears in any URL visible to the browser.

### 🟢 CLEAN — State row lifecycle and ID-token verification

State row existence, provider match, and `expires_at` are validated against `rs.clock.now()`. `GoogleProvider.verify_id_token` validates signature, `iss`, `aud`, `exp`, `iat`, `nonce`, and `sub`. Algorithm pinned to `RS256`.

### 🟠 W-4 — Race condition: new OAuth user creation unhandled 500 (day 24 — **17 days past SLA**)

`src/regstack/routers/oauth.py:716`: `_resolve_user`, branch for brand-new accounts:

```python
new_user = await rs.users.create(new_user)
```

A double-tap (two concurrent requests with the same Google `sub` arriving within milliseconds) lets both coroutines reach this line. The second `create` raises `UserAlreadyExistsError`, which is not caught, propagating as an unhandled 500.

**Remediation:** Wrap the `create` call in a `try/except UserAlreadyExistsError` and fall back to `rs.users.get_by_email(info.email)` to retrieve the just-created user.

### 🟢 CLEAN — Linking-policy enforcement, OAuth-only user side effects, identity-row uniqueness, hooks

`_resolve_user` raises the correct `_LinkConflictError` variants for email-in-use, identity-in-use, and already-linked cases. `change-password`, `change-email`, `delete-account` call `require_password_set(user)`. OAuth unlink refuses when the user has no password and only one provider. `(provider, subject_id)` and `(user_id, provider)` uniqueness enforced at the DB level. OAuth hook events are in `KNOWN_EVENTS` and fired correctly.
