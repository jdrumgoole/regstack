## 🟠 WARNING (Address within 1 week)

### W-1 · `cryptography` floor misses CVE-2026-69247 (Bleichenbacher oracle in PKCS7 decrypt) — **carry-over**

**Section:** §1 — Dependency Vulnerability Check
**File:** `pyproject.toml` line 108 (oauth extra) and line 154 (dev extra)
**Tracking issue:** #172
**First reported:** 2026-08-11

The `oauth` extra declares `cryptography>=48.0.1` and the `dev` extra similarly; the
lockfile resolves to 49.0.0. `cryptography` 50.0.0 (released 2026-07-31) fixes
CVE-2026-69247: the `pkcs7_decrypt_der`, `pkcs7_decrypt_pem`, and
`pkcs7_decrypt_smime` functions previously exposed distinguishable errors and timing
when unwrapping a `RecipientInfo.encryptedKey`, acting as a Bleichenbacher oracle for
callers that decrypt untrusted messages.

regstack does not call PKCS7 decrypt — the `cryptography` dependency is exercised only
for JWKS-backed JWT signature verification via `pyjwt[crypto]`. Nevertheless, the open
floor means:

1. `pip install regstack[oauth]` resolves to a version with an open advisory.
2. Hosts that use `cryptography` for PKCS7 in the same virtual environment inherit the
   exposure.
3. Auditors scanning transitive dependencies will flag the advisory.

No code was committed today that changes this status; the fix requires bumping the floor
in `pyproject.toml` from `>=48.0.1` to `>=50.0.0` in both the `oauth` extra and the
`dev` extra, then running `uv lock`. See issue #172 for tracking.

## 🟡 INFO (Best practice recommendations)

### I-1 · `UserPublic` exposes `tokens_invalidated_after` — acknowledged intentional design

**Section:** §9 — Data Exposure
**File:** `src/regstack/models/user.py`
**Carry-over from:** 2026-08-11 (and prior reviews)

`UserPublic.tokens_invalidated_after` is included in API responses; the field carries
an inline docstring documenting the design intent: SPAs compare this value to their
session JWT's `iat` to detect server-side revocation without an extra round-trip.
The field reveals when a password or email change occurred, which is low-sensitivity
metadata. No action recommended unless future privacy requirements tighten.

### I-2 · CLI `cmd:` log-source variant passes operator input to shell

**Section:** §5 — Input Validation & Injection
**File:** `src/regstack/cli/validate/logtail.py`
**Carry-over from:** 2026-08-11 (and prior reviews)

The `regstack validate --log-source cmd:<command>` path passes the user-supplied
value via `["sh", "-c", target]`. This is an operator-facing tool explicitly
documented as accepting arbitrary shell commands, running only on operator
workstations under the operator's own credentials. No HTTP endpoint can reach
this code path. Noted for awareness; the design is intentional. If ever exposed
to untrusted input, the `cmd:` variant must be removed or sandboxed.

### I-3 · PyJWT floor sits exactly at minimum CVE-fixed version

**Section:** §1 — Dependency Vulnerability Check
**File:** `pyproject.toml` line 55
**Carry-over from:** 2026-08-11 (and prior reviews)

The floor `pyjwt>=2.13.0` is the exact version that fixes the June-2026 PyJWT
cluster (CVE-2026-48522 through CVE-2026-48526). PyJWT 2.13.0 (released
2026-05-21) remains the latest upstream release as of this review — no 2.14.x
exists yet. The moment a new PyJWT advisory is published, the current floor will
fall below it. Continue monitoring; raise as soon as upstream releases a higher
version.

### §3 — Authentication & Authorization Audit

Reviewed `src/regstack/app.py`, `src/regstack/routers/__init__.py`, and every router
module under `src/regstack/routers/`.

**Router composition:** `build_router` always mounts `register`, `verify`, `login`,
`logout`, `account`. Optional routers (`password`, `phone`, `admin`, `oauth`) are
conditionally included via config flags — `enable_password_reset`, `enable_sms_2fa`,
`enable_admin_router`, `enable_oauth`. Every conditional router was confirmed present
before conditional inclusion.

**Per-endpoint authentication:**
- All endpoints that return or mutate user data require `Depends(rs.deps.current_user())`
  or `Depends(rs.deps.current_admin())`.
- The only fully public endpoints are `POST /register`, `POST /login`, `GET /verify`,
  `POST /login/mfa-confirm`, `POST /forgot-password`, `POST /reset-password`, `POST
  /resend-verification`, and the OAuth start/callback pair — all appropriately unauthenticated.
- `POST /confirm-email-change` is public (token in body is the authentication); the token
  is a short-lived signed JWT with purpose `email_change` — correct.

**All responses use `UserPublic`:** No endpoint returns `BaseUser` directly; `hashed_password`,
`tokens_invalidated_after`, and internal fields not in `UserPublic` are never serialised
in HTTP responses.

**Bulk-revoke discipline — verified:**
- Password reset (`POST /reset-password`): calls `users.update_password` (bumps
  `tokens_invalidated_after`) and `lockout.clear`. ✅
- Password change (`POST /change-password`): calls `users.update_password` (same). ✅
- Email-change confirm (`POST /confirm-email-change`): calls `users.update_email` which
  bumps `tokens_invalidated_after` in both the Mongo and SQL repos. ✅
- Admin disable (`PATCH /admin/users/{id}` with `is_active=false`): calls
  `rs.users.set_tokens_invalidated_after(user.id, rs.clock.now())` at `admin.py:112`. ✅
- Account deletion (`DELETE /account`): cascades `rs.oauth_identities.delete_by_user_id`
  before `rs.users.delete` — no orphan identity rows. ✅

**OAuth-only user (`hashed_password=None`) handling:**
- `POST /login`: the branch `if user.hashed_password is None or not rs.password_hasher.verify(...)`
  returns the same generic 401 as a wrong-password attempt. No account enumeration. ✅
- `POST /change-password`, `POST /change-email`, `DELETE /account`: all call
  `require_password_set(user)` which returns HTTP 400 pointing at the password-reset
  flow — no special error that reveals the account is OAuth-only. ✅
- `DELETE /oauth/{provider}/link`: refuses when the user has no password and only one
  linked provider, returning 400 `"Cannot unlink your only sign-in method."` ✅

**Login lockout ordering:** `lockout.check()` runs at `login.py:73`, before password
verification at line 99. A locked-out attacker cannot probe whether their guess is correct. ✅

**Password comparison:** via `rs.password_hasher.verify()` (pwdlib/Argon2id), never `==`. ✅

**JWT per-purpose key derivation:** `derive_secret(jwt_secret, purpose)` uses
HMAC-SHA256. Compromise of one derived key does not expose the master or other purposes.
Verified in `src/regstack/config/secrets.py:17–26`. ✅

### §6 — Rate Limiting & DoS Prevention

- Login lockout wired: `LockoutService.check()` runs before password verification.
  `record_failure()` is called on every failure branch including wrong password,
  non-existent user, disabled account, and unverified account (login.py:88–120). ✅
- MongoDB `login_attempts` collection has a TTL index with
  `expireAfterSeconds=config.login_lockout_window_seconds` (indexes.py:52–57). ✅
- Admin listing `limit` is `Annotated[int, Query(ge=1, le=200)]` — bounded at 200
  with a default of 50 (admin.py:69–70). No unbounded enumeration. ✅
- OAuth state rows have `state_ttl_seconds`-bounded TTL with a Mongo TTL index on
  `expires_at` (`expireAfterSeconds=0`). After a successful callback, the state row's
  expiry is shortened to `completion_ttl_seconds` (default 30 s), limiting the window
  in which a stolen `state_id` could yield a session token. ✅
- No file upload endpoints exist anywhere in `src/regstack/routers/`. ✅

### §7 — Session & Token Security

- **HS256 by default**, secret read from `config.jwt_secret`, minimum 32 chars
  enforced at `JwtCodec` construction (`jwt.py:127`). ✅
- **`iat` emitted as `float`** (`self.iat.timestamp()` at `jwt.py:69`), preserving
  microsecond precision for the bulk-revoke `iat <= cutoff` comparison. ✅
- **pyjwt's `exp`/`iat` checks disabled** (`"verify_exp": False, "verify_iat": False`
  at `jwt.py:213–215`); both are re-validated against the injected `Clock` so
  `FrozenClock`-driven tests are deterministic. ✅
- **Every JWT includes `jti`** — enforced via `"require": ["sub", "exp", "iat", "jti",
  "purpose"]` at decode (`jwt.py:212`). ✅
- **`_authenticate` flow** verified at `auth/dependencies.py:146–186`:
  1. Bearer scheme check → 401 if missing/wrong.
  2. `jwt.decode()` → generic `"Invalid or expired token."` 401 on any `TokenError`
     (specific pyjwt error text never echoed per inline comment at line 157–160).
  3. `blacklist.is_revoked(jti)` → 401 if revoked.
  4. `users.get_by_id(sub)` + `is_active` check → 401 if inactive or not found.
  5. `is_payload_bulk_revoked(payload, user.tokens_invalidated_after)` → 401 if past cutoff.
- **Per-purpose key derivation:** `derive_secret(jwt_secret, purpose)` uses
  `hmac.new(master, purpose.encode(), sha256).digest()`. Compromise of one derived
  key cannot expose the master or other purposes. ✅
- **No token logging:** log calls in routers log only exception strings from
  `OAuthTokenExchangeError` / `OAuthIdTokenError` (not raw tokens). No `access_token`
  or `id_token` values appear in any `log.*()` call. ✅

### §14 — OAuth Subsystem Audit

**14a — PKCE invariants:** `code_verifier` is generated server-side and stored on
the `oauth_states` row at creation (`_begin_flow`, oauth.py:598). Only
`code_challenge` (SHA-256 of the verifier, base64url without padding) goes to
Google as a query parameter. The verifier never appears in the browser-facing URL. ✅

**14b — State row lifecycle:**
- Missing row → `?error=bad_state` (oauth.py:301). ✅
- Expired row uses `rs.clock.now()` at oauth.py:302 — not `datetime.now(UTC)`. ✅
- Exchange endpoint calls `rs.oauth_states.consume(payload.id)` (oauth.py:151),
  which is `find_one_and_delete` — atomic read-and-delete prevents replay. ✅

**14c — ID-token verification** (`google.py:183–222`):
- Signature validated via `PyJWKClient` (JWKS-fetched RSA key). ✅
- `iss` matched via pyjwt `issuer=self._issuer`. ✅
- `aud` matched via pyjwt `audience=self._client_id`. ✅
- `exp` validated by pyjwt (not disabled for the id-token path). ✅
- `nonce` manually checked at google.py:211. ✅
- All failures raise `OAuthIdTokenError` with a generic message; specific reason
  is logged at DEBUG/WARNING but never echoed to the redirect. ✅

**14d — Linking-policy enforcement:**
- Google sign-in for existing email-registered user → `_LinkConflictError("email_in_use")`
  → `?error=email_in_use`. ✅
- Auto-link fires only when `oauth.auto_link_verified_emails=True AND
  info.email_verified=True` (oauth.py:686). ✅
- Identity already linked to a different user → `_LinkConflictError("identity_in_use")`. ✅
- Same identity, same user → `_LinkConflictError("already_linked")`. ✅

**14e — OAuth-only user side effects:**
- `POST /login` gives the same 401 for `hashed_password=None` as for wrong-password
  (`login.py:99`). No probing vector. ✅
- `change-password`, `change-email`, `delete-account` return 400 with a
  forgot-password pointer via `require_password_set()`. ✅
- `DELETE /oauth/{provider}/link` refuses with 400 when no password and only one
  linked provider (`oauth.py:253`). ✅

**14f — Identity-row uniqueness:** enforced at DB level:
- Mongo: `provider_subject_unique` index (`indexes.py:74–79`). ✅
- Mongo: `user_provider_unique` index (`indexes.py:80–85`). ✅
- SQL: `UniqueConstraint("provider", "subject_id", name="provider_subject_unique")`. ✅
- SQL: `UniqueConstraint("user_id", "provider", name="user_provider_unique")`. ✅

**14g — Hooks:** `oauth_signin_started`, `oauth_signin_completed`,
`oauth_account_linked`, `oauth_account_unlinked` are in `hooks/events.KNOWN_EVENTS`
and fired by the router at the appropriate points (including the MFA-gate branch
and the link flow). ✅
