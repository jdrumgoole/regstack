## 🟡 INFO (Best practice recommendations)

### I-1 · Wizard preview template ships well-known example credentials in the wheel

**File:** `src/regstack/wizard/theme_designer/templates/designer.html`, lines 57 and 61

**Observation:** The theme designer's login-form mockup hardcodes two values that the
review checklist explicitly asks to flag:

```html
<input class="rs-input" id="d-preview-email" type="email" value="alice@example.com" />
<input class="rs-input" id="d-preview-pw" type="password" value="hunter2hunter2" />
```

Both strings appear in the built wheel (`regstack-0.7.0-py3-none-any.whl`) under
`regstack/wizard/theme_designer/templates/designer.html`.

**Context:** These are intentional UI preview values used by the theme designer wizard
to show developers what a styled login form looks like. They are _not_ leaked test
fixtures — no test file has a regstack account with `alice@example.com` / `hunter2hunter2`
credentials. The wizard is an optional developer tool loaded only with `pip install regstack[wizard]`.
`hunter2hunter2` is not a real password anyone would use in production.

**Risk:** No direct exploitability. However:
- Any host running `pip show --files regstack` or unpacking the wheel sees these strings.
- Static-analysis tools and secret scanners that flag well-known example passwords (e.g.
  `hunter2hunter2`, which is sometimes in scanner wordlists) will produce false positives,
  requiring allow-list entries.
- Per published review policy, sample emails and passwords should not appear in wheel
  contents regardless of intent.

**Remediation:** Replace the hardcoded form values with HTML `placeholder` attributes and
empty `value=""`, so the mockup still shows realistic preview text but the strings don't
appear as DOM values:

```html
<input class="rs-input" id="d-preview-email" type="email" value=""
       placeholder="alice@example.com" />
<input class="rs-input" id="d-preview-pw" type="password" value=""
       placeholder="••••••••••" />
```

If the preview requires pre-filled values, use a JavaScript default applied on page
load rather than a static HTML attribute, keeping the strings out of the rendered
source that tools scan.

### I-2 · `exchange_code()` includes full Google token response body in exception message

**File:** `src/regstack/oauth/providers/google.py`, lines 153–156

```python
except KeyError as exc:
    raise OAuthTokenExchangeError(
        f"google token response missing field {exc.args[0]!r}: {body!r}"
    ) from exc
```

**Router log site:** `src/regstack/routers/oauth.py`, line 315

```python
log.warning("oauth token exchange failed: %s", exc)
```

**Observation:** When Google's token endpoint returns HTTP 200 but the JSON body is
missing `access_token` or `id_token`, the full `body!r` dict is stringified into the
exception message and logged at WARNING. In the specific case where `id_token` is
absent but `access_token` is present, the server log would contain Google's raw
OAuth access token value.

**Context:**
- This code path existed unchanged through the 2026-05-15/16/17 security reviews;
  those reviews deemed §11 (third-party integrations) CLEAN.
- The scenario (Google returning 200 without `id_token`) requires an unusual provider
  failure — a scope change at the Google Console that removes the `openid` scope, or a
  transient provider bug. It is not attacker-triggerable from outside.
- Google's OAuth `access_token` is short-lived (~1 hour), not usable to authenticate
  against regstack, and only grants access to Google's own APIs (e.g. userinfo).
- Exploitation requires server-log access, which is a far more serious compromise vector
  in its own right.

**Risk:** A server-log reader with restricted access could obtain a short-lived Google
access token and use it to call `GET https://www.googleapis.com/oauth2/v3/userinfo`,
recovering the affected user's Google email and profile. The token's value to an
attacker is limited and time-bounded.

**Remediation:** Omit the response body from the exception message; log only the
missing field name:

```python
except KeyError as exc:
    raise OAuthTokenExchangeError(
        f"google token response missing required field {exc.args[0]!r}"
    ) from exc
```

If the full body is needed for debugging, log it at DEBUG (never WARNING) and only
after scrubbing known token fields:

```python
safe_body = {k: v for k, v in body.items() if k not in {"access_token", "id_token", "refresh_token"}}
log.debug("google token response (tokens scrubbed): %s", safe_body)
```

### §7 Session and token security

`JwtCodec` disables pyjwt's `exp`/`iat` checks and validates both against the injected
`Clock`. This preserves `FrozenClock`-driven test determinism and avoids any
`time.time()` dependency.

`iat` is emitted as a float (`self.iat.timestamp()` in `TokenPayload.to_claims()`).
Float precision ensures a login completing microseconds after a bulk-revoke cutoff
has `iat > cutoff` and is not falsely revoked.

Every JWT carries a 16-byte URL-safe `jti` (`secrets.token_urlsafe(16)`).

Algorithm restricted to `Literal["HS256", "HS384", "HS512"]` in `config/schema.py`.

`AuthDependencies._authenticate` checks in order:
1. Bearer token present and decodable → static 401 on `TokenError` (pyjwt message not echoed).
2. `blacklist.is_revoked(jti)` → 401 if revoked.
3. `users.get_by_id(sub)` → 401 if user missing or `is_active=False`.
4. `is_payload_bulk_revoked(payload, tokens_invalidated_after)` → 401 if `iat ≤ cutoff`.

No token values appear in any `log.info`/`log.warning`/`log.error` call in the
authentication path.

`PyJWKClient(jwks_url, cache_keys=True)` — no explicit `timeout` parameter, but
pyjwt 2.12.1 (the locked and minimum version) defaults `PyJWKClient.timeout = 30 s`.
The JWKS network call will timeout in at most 30 seconds.

(wait — `tokens_invalidated_after` is intentionally included; documented trade-off
described in `docs/security.md` and in `models/user.py` docstring).

`UserPublic.from_user(user)`.

generic messages. Raw exception strings are not surfaced to HTTP clients.

**See I-2** regarding `exchange_code()` logging the full Google token response body —
this is the only data-exposure concern identified this cycle.

### §14 OAuth subsystem

**§14a PKCE invariants:** `code_verifier` (64-byte URL-safe random, `_secrets.token_urlsafe(64)`)
stored on the `oauth_states` row. Only `code_challenge` (SHA-256 with URL-safe base64,
no padding) goes in the provider redirect URL. Confirmed in `_begin_flow()`,
`routers/oauth.py:596–614`. The verifier never appears in any URL or log.

**§14b State row lifecycle:**
- Expiry checked with `rs.clock.now()` (not `datetime.now(UTC)`).
- SQL `consume()` uses `SELECT` + `DELETE` inside a single `engine.begin()` transaction.
- MongoDB uses `find_one_and_delete` — atomic.
- Missing row or missing `result_token` → 404. Expired row → 400 (after atomic deletion,
  preventing replay).
- Note: `exchange` checks expiry after `consume()` so expired rows are still deleted,
  preventing a second exchange with the same state ID from seeing the row as unexpired.

**§14c ID-token verification:** `GoogleProvider.verify_id_token` validates: JWKS
signature, `iss == GOOGLE_ISSUER`, `aud == client_id`, `exp`, `iat`, `nonce`.
`require=["sub","iss","aud","exp","iat","nonce"]` enforced. nonce compared explicitly.
Failure raises `OAuthIdTokenError` with a generic outer message; specifics logged only
at `log.warning`. **See I-2** for the `exchange_code()` body-logging issue in the
adjacent token exchange path.

**§14d Linking-policy enforcement:**
- Default: Google sign-in for existing email user → `?error=email_in_use`.
- `auto_link_verified_emails=True` AND `info.email_verified=True` both required for
  auto-link (off by default).
- Identity linked to different user → `?error=identity_in_use`.
- Same identity re-linking to same user → `?error=already_linked`.

**§14e OAuth-only user side effects:**
- `POST /login` with `hashed_password=None` → same generic 401 as wrong password.
- `POST /change-password`, `POST /change-email`, `DELETE /account` → 400 via
  `require_password_set()`.
- `DELETE /oauth/{provider}/link` → 400 (`"Cannot unlink your only sign-in method"`)
  when user has no password and only one linked provider.

**§14f Identity-row uniqueness:**
- SQL: `UniqueConstraint("provider","subject_id")` and `UniqueConstraint("user_id","provider")` in `schema.py`.
- Mongo: `provider_subject_unique` and `user_provider_unique` indexes in `indexes.py`.

**§14g Hooks:** `oauth_signin_started`, `oauth_signin_completed`, `oauth_account_linked`,
`oauth_account_unlinked` present in `hooks/events.py:KNOWN_EVENTS`. Fired at correct
callsites in `routers/oauth.py`.

### §15 Multi-backend parity and schema migration safety

**§15a CI matrix:** `test.yml` runs the parametrized suite (SQLite + PostgreSQL +
MongoDB) on Python 3.11 and 3.12. MongoDB 7 and Postgres 16 declared as job services
with health checks. `fail-fast: false` ensures all matrix legs run even if one fails.

**§15b Schema migration safety:** Two migrations in `backends/sql/migrations/versions/`:

- `0001_initial_schema.py`: initial tables. `upgrade()` and `downgrade()` both present.
- `0002_oauth.py`: OAuth tables + `hashed_password` nullable. `upgrade()` and
  `downgrade()` both present. `downgrade()` includes a pre-check (`COUNT(*) WHERE
  hashed_password IS NULL`) that raises `RuntimeError` on OAuth-only users before
  attempting the `NOT NULL` constraint — protects SQLite's silent-rewrite path (I-4 from
  2026-05-15/16 resolved by commit `86ddf35`). `batch_alter_table` used for SQLite
  compatibility.
