### W-1 · GitHub Actions: non-SHA-pinned actions in publish workflow (§12a)

**File:** `.github/workflows/publish.yml`

The `publish` job carries `permissions: { id-token: write }` for OIDC trusted publishing. Four of the five `uses:` directives in the full `publish.yml` workflow use mutable version tags instead of commit SHAs:

| Step | Reference | Job | SHA-pinned? |
|---|---|---|---|
| `actions/checkout` | `@v4` | `build` | ✗ |
| `astral-sh/setup-uv` | `@v3` | `build` | ✗ |
| `actions/upload-artifact` | `@v4` | `build` | ✗ |
| `actions/download-artifact` | `@v4` | **`publish`** | ✗ |
| `pypa/gh-action-pypi-publish` | `@cef221092ed1bacb1cc03d23a2d87d1d172e277b` | `publish` | ✓ |

`pypa/gh-action-pypi-publish` is correctly pinned (the PR #37 comment confirms intent). However, `actions/download-artifact@v4` in the **`publish` job** is not SHA-pinned. The `publish` job is the only one with elevated permissions (`id-token: write`). A tag swap on `actions/download-artifact` while a publish run is in flight could enable an attacker to exfiltrate the OIDC token and publish a rogue wheel under the project's identity.

`test.yml` is lower risk (no privileged secrets) but also uses un-pinned tags for `actions/checkout@v4`, `astral-sh/setup-uv@v3`, and `actions/upload-artifact@v4`.

**Remediation:** Pin all `uses:` directives to full commit SHAs. Resolve the SHA by checking the action repo's `v4`/`v3` tag. Priority: `actions/download-artifact` in `publish.yml` first.

### W-2 · `pywebview`, `tomlkit`, and `uvicorn` as mandatory base dependencies (§1, §13c)

**File:** `pyproject.toml`, `dependencies` list (lines 38–43)

`pywebview>=5.0`, `tomlkit>=0.13`, and `uvicorn[standard]>=0.29` are in the base `dependencies` array, so every `pip install regstack` host — including production services that only want the embeddable auth module — transitively pulls in:

- **pywebview**: a platform browser engine (WebKitGTK on Linux, WKWebView on macOS, Edge WebView2 on Windows). This is one of the largest transitive attack surfaces in the Python ecosystem. It pulls in system-level GUI / browser libraries that are outside PyPI's security audit scope.
- **tomlkit**: safe on its own, but still not needed by a library that only exposes a FastAPI router.
- **uvicorn**: already in `dev` extras. The duplication is harmless but signals that the split between "library" and "tool" deps was not made carefully.

These three packages exist solely to power the `regstack oauth setup` and `regstack theme design` CLI wizards. The wizards are developer tooling, not part of the embeddable library surface. Shipping a browser engine as a mandatory library dependency is inconsistent with the supply-chain principle of minimal footprint and is likely to surprise hosts doing dependency audits.

**Remediation:** Move `pywebview`, `tomlkit`, and `uvicorn` into an optional `wizard` extra (or split into `wizard-oauth` and `wizard-theme`). Adjust `cli/__main__.py` to raise an informative error if the extra is missing when a wizard subcommand is invoked.

### W-3 · Disabled account bypasses login lockout accumulation (§3, §6)

**File:** `src/regstack/routers/login.py:73–77`

```python
if not user.is_active:
    raise HTTPException(
        status_code=status.HTTP_403_FORBIDDEN,
        detail="Account is disabled.",
    )
```

This check fires *before* password verification and *without* calling `rs.lockout.record_failure()`. Consequently:

1. An attacker who determines a target account is disabled can submit unlimited password-guessing attempts against it — lockout never accumulates.
2. If the account is later re-enabled (e.g., support ticket resolves a suspension), the attacker arrives with zero accumulated failures and can immediately attempt the same volume of guesses on a live account.

The disabled-account 403 response also gives slightly more information than the generic 401 returned for unknown users. Combined with the lockout bypass, this creates a window where disabled accounts are softer targets than active ones.

**Remediation:** Call `await rs.lockout.record_failure(payload.email)` before (or alongside) the `is_active` check, or restructure so the disabled check follows the password check (matching the order: existence → password → is_active → verification). Either approach closes the accumulation gap.

### W-4 · Authenticated email enumeration via `POST /change-email` (§9)

**File:** `src/regstack/routers/account.py:127–131`

```python
clash = await rs.users.get_by_email(payload.new_email)
if clash is not None:
    raise HTTPException(
        status_code=status.HTTP_409_CONFLICT,
        detail="That email address is already in use.",
    )
```

After password verification succeeds, the endpoint reveals whether any registered account uses the candidate `new_email` via a deterministic 409 vs 202 response. Any authenticated user can enumerate the full registered-email namespace by iterating addresses through this endpoint. The anti-enumeration protections on `/forgot-password` and `/resend-verification` do not extend here.

The threat requires a valid account and correct password, which limits exposure compared to unauthenticated probing. However, multi-tenant or high-value deployments where users should not learn which emails are registered are at real risk — a compromised account (or a user who registered specifically to probe) can silently map the user base.

**Remediation options:**
- Return 202 unconditionally and let the email itself be the signal (same pattern as `/forgot-password`). Only send the confirmation email if the address is available; silently no-op otherwise.
- Rate-limit the endpoint aggressively (already possible via `change_email_rate_limit`; document this as required mitigation for sensitive deployments).

### I-1 · Missing explicit `permissions:` declarations in GitHub Actions workflows (§12c)

**Files:** `.github/workflows/test.yml`, `.github/workflows/publish.yml` (`build` job)

Neither `test.yml` nor the `build` job in `publish.yml` declares an explicit `permissions:` block. Absence defaults to the repository's "default permissions" setting, which is `read-all` for most organizations but could be `write-all` in legacy repositories. Even a `contents: read` declaration is a meaningful defense-in-depth signal.

**Remediation:** Add `permissions: { contents: read }` at the workflow or job level for `test.yml` and the `build` job in `publish.yml`.

### I-3 · `tokens_invalidated_after` exposed in `UserPublic` (§9)

**File:** `src/regstack/models/user.py:99`

`UserPublic` includes `tokens_invalidated_after`, which leaks the exact UTC timestamp of the user's most recent bulk-revoke event (password change, email change, or admin disable). Per `CLAUDE.md`, this is intentional: "SPAs comparing this to their session JWT's `iat` can tell when the token they hold has been invalidated." The SPA can achieve the same check locally using the `iat` in its own JWT without needing this field from the server.

Exposing it reveals security event timing to:
- The user themselves (low risk: they caused the event).
- Admin endpoints listing all users (`GET /admin/users`), where an admin can see the revoke timestamp for every user (medium risk: reveals when every user last had a security event).

**Remediation:** Consider omitting `tokens_invalidated_after` from `UserPublic` and instead exposing a dedicated client-side invalidation signal only when the JWT itself is being evaluated. If keeping the field, document the privacy implication in the public API reference.

### I-4 · Password-correctness signal on unverified account login (§3)

**File:** `src/regstack/routers/login.py:87–91`

The login flow verifies the password *before* checking `is_verified`. A correct password on an unverified account returns HTTP 403 "Email address has not been verified." while a wrong password returns HTTP 401. An attacker targeting an unverified account can distinguish a correct guess (403) from a wrong one (401) without lockout applying to the 403 path (lockout only increments on the 401 path).

**Mitigating factors:** Unverified accounts cannot be used for any auth flow, and exploiting correct-password knowledge requires independent email access to complete verification. The risk is low in practice.

**Remediation:** Move the `is_verified` check to *before* the password check, or return the same generic 401 for all non-success outcomes (and record a lockout failure in all cases). This collapses the 403 information channel.

### Top 3 priorities for the development team

1. **W-1 (GitHub Actions SHA-pinning)** — The `actions/download-artifact@v4` action in the `publish` job runs alongside OIDC `id-token: write` access and is not SHA-pinned. This is the highest-impact single-point fix: a tag swap in that action during a publish run could yield a rogue wheel under the project's PyPI identity. Pin all `uses:` directives to full commit SHAs, starting with the `publish` job.

2. **W-2 (pywebview in base deps)** — Shipping a platform browser engine as a mandatory transitive dependency of an embeddable auth library is an unusual and hard-to-justify supply-chain posture. Moving `pywebview`, `tomlkit`, and `uvicorn` to a `wizard` optional extra shrinks the attack surface of every production host running `pip install regstack` with no behavioral change for developers who use the wizards.

3. **W-3 (Disabled account lockout gap)** — An attacker who identifies a disabled account can guess its password indefinitely without lockout. The fix is a one-liner (call `record_failure` before the `is_active` check), and closing this gap before the account is ever re-enabled is important.
