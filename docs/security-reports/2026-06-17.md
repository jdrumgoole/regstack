### W-1 — PyJWT 2.12.1 locked; 5 CVEs fixed in 2.13.0 (`pyproject.toml`, `uv.lock`)

**Finding:**

`uv.lock` pins `pyjwt = "2.12.1"`. PyJWT 2.13.0 was released in June 2026 and fixes
five CVEs, all affecting `pyjwt >= 2.9.0` through `2.12.1`:

| CVE | Description | Impact on regstack |
|---|---|---|
| CVE-2026-48524 | PyJWKClient forces a fresh HTTP request to the JWKS endpoint for **every** JWT with an unknown `kid`, with no rate-limiting | High — directly affects `GoogleProvider.verify_id_token()`. An attacker who can craft JWTs with arbitrary `kid` headers can drive unbounded JWKS requests from the server, exhausting outbound connections or budget. |
| CVE-2026-48525 | Unauthenticated DoS via unbounded Base64URL decoding when `b64=false` header is present in a detached JWS | Medium — `JwtCodec.decode()` calls `pyjwt.decode()` on attacker-supplied tokens from the `Authorization: Bearer` header; a crafted `b64=false` token triggers excessive memory allocation before any signature check. |
| CVE-2026-48522 | `PyJWKClient` passes its `uri` to `urllib.request.urlopen()` with no scheme allowlist, enabling SSRF via `file://`, `ftp://`, `data:` URIs | Low in default config — `GoogleProvider` hardcodes `GOOGLE_JWKS_URL` and the `jwks_url` parameter is tested-only. Risk exists for operators who override `jwks_url` pointing at attacker-controlled config. |
| CVE-2026-48523 | Algorithm allow-list bypass: when `jwt.decode()` is called with a `PyJWK` object rather than raw key bytes, the caller-supplied `algorithms=` list is not enforced — the algorithm bound to the `PyJWK` at creation time is used instead | Low direct impact — regstack's `GoogleProvider` extracts the raw cryptographic key via `signing_key_obj.key` before passing it to `pyjwt.decode()`, so the PyJWK object is not passed directly. Still should be patched. |
| CVE-2026-48526 | Algorithm confusion: public-key JWK accepted as HMAC secret when both asymmetric and symmetric algorithms appear in the `algorithms=` list | Not directly exploitable — `JwtCodec` uses HS256 only; `GoogleProvider` uses RS256 only. Neither mixes algorithm families. Still should be patched. |

`pyproject.toml` currently sets `"pyjwt>=2.12.1"` in both `dependencies` (base) and
the `oauth` optional-dependency. CVE-2026-48524 and CVE-2026-48525 affect the base
dependency; CVE-2026-48522, CVE-2026-48523, and CVE-2026-48526 affect the `oauth` extra.

**Fix:**

1. In `pyproject.toml`, bump both floors and add CVE comment:
   ```diff
   -    "pyjwt>=2.12.1",
   +    # pyjwt>=2.13.0 fixes CVE-2026-48524 (unbounded JWKS requests),
   +    # CVE-2026-48525 (b64=false DoS), and three algorithm-confusion
   +    # issues in the oauth extra (CVE-2026-48522/48523/48526).
   +    "pyjwt>=2.13.0",
   ```
   and in `optional-dependencies.oauth`:
   ```diff
   -    oauth = ["pyjwt[crypto]>=2.12.1", "cryptography>=46.0.7"]
   +    oauth = ["pyjwt[crypto]>=2.13.0", "cryptography>=46.0.7"]
   ```

2. Regenerate the lock file:
   ```bash
   uv lock --upgrade-package pyjwt
   ```

### W-2 — Starlette 1.0.0 locked; CVE-2026-48710 (BadHost) fixed in 1.0.1 (`uv.lock`)

**Finding:**

`uv.lock` pins `starlette = "1.0.0"`. Starlette 1.0.1 (released 2026-05-21) fixes
**CVE-2026-48710 ("BadHost")**, a host-header authentication bypass.

**Mechanics:** Starlette reconstructs `request.url` by concatenating the HTTP `Host`
header with the request path and re-parsing the result. The `Host` value is not
validated against the RFC 9112 / RFC 3986 grammar before use. An attacker injects
`/`, `?`, or `#` into the `Host` header, which shifts the path, query, and fragment
boundaries on reconstruction. Any middleware or guard that makes a security decision
on `request.url.path` sees a different path than the one the server actually received.

**Impact on regstack:**
- regstack's own authentication is JWT Bearer — `_authenticate()` in
  `auth/dependencies.py` reads the `Authorization: Bearer <token>` header, not
  `request.url`. So BadHost does **not** bypass regstack's own auth endpoints.
- However, regstack ships as a library. Host applications embedding regstack that also
  use path-based middleware guards for their own routes (e.g. a `Middleware` that
  allows `/api/auth/*` while protecting everything else) are fully exposed.
- `pyproject.toml` declares `fastapi>=0.120.0`; `uv.lock` already resolves to
  `fastapi = "0.136.1"` (which permits Starlette 1.0.x) but the lock pins
  Starlette at 1.0.0, not 1.0.1.

**Fix:**

Update the lock to pull in Starlette 1.0.1:
```bash
uv lock --upgrade-package starlette
```

Optionally pin a direct floor to prevent future regressions:
```toml
# In pyproject.toml dependencies:
"starlette>=1.0.1",  # CVE-2026-48710 (BadHost host-header auth bypass)
```

### §3 — Authentication & Authorization

- Every authenticated endpoint injects `rs.deps.current_user()` or
  `rs.deps.current_admin()`. Verified across all routers: account, admin, login,
  logout, password, phone, register, verify, oauth.
- Bulk-revoke discipline intact: `update_password` and `update_email` bump
  `tokens_invalidated_after` on both SQL and Mongo backends; admin `set_active(False)`
  calls `set_tokens_invalidated_after`; account deletion cascades `oauth_identities`
  before `users.delete`.
- OAuth-only users (`hashed_password=None`): login returns the same generic 401 as
  wrong-password; `change-password`, `change-email`, `delete-account` route through
  `require_password_set()` → 400.
- Admin `PATCH /admin/users/{id}` with `is_active=False` bumps
  `tokens_invalidated_after` in `admin.py:111`.
- Password reset calls `update_password` (bumps `tokens_invalidated_after`) AND
  `lockout.clear` AND blacklists the reset token's `jti` on first use (replay
  prevention confirmed in `password.py:97-117`).
- Password comparison via `rs.password_hasher.verify()` (pwdlib/Argon2id), not `==`.
- JWT keys derived per-purpose (`derive_secret(master, purpose)` via HMAC-SHA256);
  compromise of one purpose key does not expose the master.

### §14 — OAuth Subsystem

- **PKCE:** `code_verifier` generated server-side with `secrets.token_urlsafe(64)`,
  stored on the `oauth_states` row. Only `code_challenge = sha256(verifier)` in the
  provider redirect. Verifier never in a browser-visible URL.
- **State row lifecycle:** Mongo uses `find_one_and_delete` (atomic); SQL uses
  SELECT + DELETE in one `engine.begin()` transaction. Second exchange → 404. Expiry
  checked against `rs.clock.now()` (not bare `datetime.now(UTC)`).
- **ID-token verification:** RS256 + PyJWKClient, `iss` = Google issuer, `aud` =
  `client_id`, `exp > now`, `nonce` match required. Failure → `OAuthIdTokenError`
  (generic outer message); detail logged server-side only.
- **Linking policy:** Existing-email sign-in → `email_in_use`. Auto-link only when
  `auto_link_verified_emails=True` AND `email_verified=True`. Already-linked to
  different user → `identity_in_use`. Same identity same user → `already_linked`.
  Unlink last method with no password → 400.
- **OAuth-only users:** login → generic 401; `change-password`/`change-email`/
  `delete-account` → `require_password_set()` 400.
- **Identity uniqueness:** `(provider, subject_id)` and `(user_id, provider)` UNIQUE
  enforced at DB level on both Mongo (unique indexes in `indexes.py`) and SQL
  (`UniqueConstraint` in `schema.py`).
- **`was_new_account`:** Migration 0003 adds `result_was_new BOOL NOT NULL DEFAULT
  FALSE` to `oauth_states`; the callback writes it; the exchange endpoint reads it.
  I-1 from 2026-05-22 closed. ✅
- **Hooks:** `oauth_signin_started`, `oauth_signin_completed`, `oauth_account_linked`,
  `oauth_account_unlinked` all present in `KNOWN_EVENTS` and fired at correct
  router points.
