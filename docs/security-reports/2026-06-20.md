## 🟠 WARNING (Address within 1 week)

### W-1 — PyJWT < 2.13.0 vulnerable on the OAuth ID-token path (FIXED in this review)

**Finding:** The dependency floor was `pyjwt>=2.12.1` (resolved `2.12.1` in
`uv.lock`). A cluster of PyJWT advisories published in **June 2026** affect
the `PyJWKClient` flow that regstack's Google OAuth ID-token verification
uses directly (`src/regstack/oauth/providers/google.py:192-206`):

| CVE | Title | Affected | Fixed |
|---|---|---|---|
| CVE-2026-48523 | Algorithm allow-list bypass via `PyJWK` / `PyJWKClient` keys | 2.9.0–2.12.1 | 2.13.0 |
| CVE-2026-48526 | Algorithm confusion (public JWK used as HMAC secret) | < 2.13.0 | 2.13.0 |
| CVE-2026-48522 | SSRF via `PyJWKClient` URI-scheme handling | < 2.13.0 | 2.13.0 |
| CVE-2026-48525 | Unauthenticated DoS in detached-payload JWS decode | 2.8.0–2.12.1 | 2.13.0 |

CVE-2026-48523 is the headline one: the GitHub advisory (GHSA-jq35-7prp-9v3f)
states it **directly affects the documented
`PyJWKClient.get_signing_key_from_jwt(...)` flow** — the exact call regstack
makes before `jwt.decode(..., algorithms=["RS256"])`. PyJWT checks the
header's `alg` against the caller's allow-list but then verifies the
signature using the algorithm bound to the `PyJWK` object, so the
`algorithms=["RS256"]` guard can be bypassed. Exploitation requires an
attacker controlling a registered JWK in the trusted JWKS — for regstack
that is Google's JWKS, so the practical exposure for the default Google
provider is low, but the floor is the correct, zero-effort defence and the
SSRF/DoS members of the cluster widen the surface for any host pointing
`jwks_url` elsewhere.

**Fix applied:** bumped the floor to `pyjwt>=2.13.0` in the base
`dependencies`, the `oauth` extra, and the `dev` extra. `uv lock` resolves
`pyjwt 2.13.0`.

### W-2 — Starlette < 1.0.1 vulnerable to CVE-2026-48710 "BadHost" (FIXED in this review)

**Finding:** `fastapi>=0.120.0` pulled `starlette 1.0.0` transitively
(resolved in `uv.lock`). CVE-2026-48710 ("BadHost") affects Starlette
≤ 1.0.0: Starlette reconstructs `request.url` by concatenating the `Host`
header with the path and re-parsing, so injecting `/`, `?`, or `#` into the
`Host` header shifts the path/query/fragment boundaries and poisons
`request.url.path`, bypassing any path-based auth check. Fixed in Starlette
**1.0.1**.

regstack does not route its own auth decisions off `request.url.path`, so it
is not directly exploitable through regstack's own code — but Starlette
ships transitively to every host and a host running path-based middleware
inherits the flaw. Pinning the floor closes the door for them.

**Fix applied:** added an explicit `starlette>=1.0.1` floor to the base
`dependencies` (with a CVE comment). `uv lock` resolves `starlette 1.3.1`,
well above the fix version; FastAPI 0.136.1 is compatible.

**Side effect handled:** Starlette ≥ 1.3 deprecates its `TestClient`'s use
of `httpx` in favour of `httpx2`, raising `StarletteDeprecationWarning`. The
suite runs with `filterwarnings = ["error", …]`, so the wizard route tests
(which use FastAPI's sync `TestClient`) began erroring at collection. This is
a **test-client-only** deprecation — the production ASGI path doesn't touch
it — so it is silenced via a targeted `filterwarnings` ignore rather than by
capping the Starlette floor (an upper bound would deny hosts future
framework fixes).

## 🟡 INFO (Best practice recommendations)

### I-1 — `python-multipart` CVE-2026-24486 (path traversal) — not applicable

CVE-2026-24486 is a path-traversal in `python-multipart` that only triggers
with the non-default `UPLOAD_DIR` + `UPLOAD_KEEP_FILENAME=True` configuration,
fixed in 0.0.22. regstack pins `python-multipart>=0.0.27` (already above the
fix) and has no file-upload endpoints. No action.

### I-2 — `pydantic` CVE-2026-25580 — not applicable

CVE-2026-25580 (SSRF) is in **Pydantic AI**, a separate package, not
`pydantic` core. regstack does not depend on Pydantic AI. No action.

### I-3 — `tokens_invalidated_after` / admin `phone_number` exposure (carry-forward)

Both remain conscious, documented design trade-offs in `docs/security.md`
(self-service SPA polling and the simple shared `UserPublic` projection,
respectively). No code change in regstack; hosts that need them hidden wrap
the response model. Carried forward unchanged from the 2026-05-21 review
(I-1, I-2).
