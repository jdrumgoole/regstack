## 🟠 WARNING (Address within 1 week)

### W-1 · JWT decode error detail echoed in HTTP 401 response

**File:** `src/regstack/auth/dependencies.py:120`

```python
raise HTTPException(
    status_code=status.HTTP_401_UNAUTHORIZED,
    detail=f"Invalid token: {exc}",   # ← leaks internal reason
    headers={"WWW-Authenticate": "Bearer"},
)
```

`TokenError` wraps raw `pyjwt.PyJWTError` messages (e.g. `"Signature verification failed"`, `"Not enough segments"`, `"Invalid header string"`) and custom messages (`"token purpose mismatch"`, `"Signature has expired"`). These are returned verbatim in the JSON response body where API consumers — or attackers — can read them.

The audit spec is explicit: *"JWT decode errors → 401 generic, never the specific reason."*

**Fix:** Replace with a fixed string:

```python
raise HTTPException(
    status_code=status.HTTP_401_UNAUTHORIZED,
    detail="Invalid or expired token.",
    headers={"WWW-Authenticate": "Bearer"},
) from exc
```

Log the specific reason at DEBUG level if diagnostics are needed.

### W-2 · Admin `DELETE /admin/users/{id}` omits OAuth identity cascade

**File:** `src/regstack/routers/admin.py:129–135`

The admin user-delete endpoint:

```python
await rs.users.delete(user.id)
await rs.pending.delete_by_email(user.email)
await rs.lockout.clear(user.email)
# ← MISSING: await rs.oauth_identities.delete_by_user_id(user.id)
```

The user self-delete (`DELETE /account`, `routers/account.py:233`) correctly cascades first:

```python
await rs.oauth_identities.delete_by_user_id(user.id)   # ✓
await rs.users.delete(user.id)
```

When an admin deletes a user who has linked OAuth identities, the `oauth_identities` rows survive with `user_id` pointing to a now-deleted record. On backends with a unique `(user_id, provider)` constraint (both SQL and Mongo), these orphan rows permanently block re-registration of that provider identity. `CLAUDE.md` documents this as a mandatory anti-orphan requirement.

**Fix:** Add before `rs.users.delete(user.id)`:

```python
await rs.oauth_identities.delete_by_user_id(user.id)
```

### W-3 · Wizard-only packages (`pywebview`, `uvicorn`, `tomlkit`) are in main `dependencies`

**File:** `pyproject.toml:37–39`

```toml
"pywebview>=5.0",
"tomlkit>=0.13",
"uvicorn[standard]>=0.29",
```

These three packages are used exclusively by the CLI wizards (`regstack oauth setup`, `regstack theme design`). They are not needed by any embedded library functionality. Shipping them in the main `dependencies` list means every `pip install regstack` on every host application pulls them in. Consequences:

- **`pywebview`** requires native GUI frameworks (GTK on Linux, WKWebView on macOS, WebView2 on Windows) and will produce import errors or undefined behaviour in headless server/container environments. This is a hard reliability failure for the common embed use case.
- Supply-chain surface: three additional dependency trees (pywebview's CE/GTK stack, uvicorn's websockets/httptools, tomlkit) are forced onto every downstream consumer whether or not they ever run the wizard.
- `uvicorn[standard]` is already present in the `dev` extra — the duplication confirms this belongs outside the base install.

**Fix:** Create a `wizard` optional extra:

```toml
[project.optional-dependencies]
wizard = ["pywebview>=5.0", "tomlkit>=0.13", "uvicorn[standard]>=0.29"]
```

Document in the CLI that `pip install 'regstack[wizard]'` is required before running `regstack oauth setup` or `regstack theme design`.

### W-4 · GitHub Actions: all third-party actions pinned to mutable version tags

**Files:** `.github/workflows/test.yml`, `.github/workflows/publish.yml`

Every `uses:` directive references a moveable version tag rather than an immutable commit SHA:

| Workflow | Action | Tag used |
|----------|--------|----------|
| test.yml | `actions/checkout` | `@v4` |
| test.yml | `astral-sh/setup-uv` | `@v3` |
| test.yml | `actions/upload-artifact` | `@v4` |
| publish.yml | `actions/checkout` | `@v4` |
| publish.yml | `astral-sh/setup-uv` | `@v3` |
| publish.yml | `actions/upload-artifact` | `@v4` |
| publish.yml | `actions/download-artifact` | `@v4` |
| publish.yml | `pypa/gh-action-pypi-publish` | `@release/v1` |

Tag references can be silently re-pointed by the action author (or an attacker who compromises the author account). A poisoned tag on `pypa/gh-action-pypi-publish` with publish-job access to `id-token: write` could exfiltrate the OIDC token and publish a malicious wheel.

**Fix:** Pin every action to a specific commit SHA. Example:

```yaml
uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683  # v4.2.2
```

Use a tool such as `pin-github-actions` or Renovate's `github-actions` manager to automate SHA maintenance.

### W-5 · `test.yml` has no `permissions:` block

**File:** `.github/workflows/test.yml`

Neither the workflow level nor any job within `test.yml` declares a `permissions:` block. On GitHub, the repository-wide default for `push` events from the same repo includes `contents: write` and `pull-requests: write`. The CI jobs need only `contents: read`.

**Fix:** Add at the workflow level:

```yaml
permissions:
  contents: read
```

Override per-job only where elevated permissions are genuinely needed.

### W-6 · Raw MFA OTP passed to hook handlers

**File:** `src/regstack/routers/login.py:158`

```python
await rs.hooks.fire("mfa_login_started", user=user, code=raw_code)
```

The plaintext 6-digit one-time password is passed as the `code` kwarg to every handler subscribed to `mfa_login_started`. Any host hook that logs its arguments (a common pattern for audit trails) will capture live OTPs in application logs or observability pipelines.

The `code` value has already been delivered via SMS before the hook fires, so hooks receive no legitimate operational need for it. Even notification hooks (e.g. "send an audit event") only need to know that an MFA login was started, not what the code is.

**Fix:** Remove the `code` argument from the hook call:

```python
await rs.hooks.fire("mfa_login_started", user=user)
```

If hosts need the code for custom SMS delivery, they should implement an `SmsService` subclass rather than receive it through the hook.

## 🟡 INFO (Best practice recommendations)

### I-1 · `cryptography` 47.0.0 is one release behind current (48.0.0)

Three CVEs affecting older `cryptography` releases landed in early 2026:

| CVE | CVSS | Description | Fixed in |
|-----|------|-------------|----------|
| CVE-2026-26007 | 8.2 HIGH | ECC subgroup attack — private-key leakage via small-subgroup ECDH via `load_pem_public_key` | 46.0.5 |
| CVE-2026-34073 | — | DNS name-constraint bypass — excluded subtree constraints not enforced against peer names | 46.0.6 |
| CVE-2026-39892 | — | Buffer overflow in `Hash.update()` on non-contiguous buffers | 46.0.7 |

The locked version 47.0.0 is patched for all three. However, 48.0.0 shipped on 2026-05-04. Plan an upgrade to maintain forward headroom.

### I-2 · `python-multipart` at exact minimum safe version (0.0.26)

CVE-2026-40347 (DoS via oversized multipart preamble) and CVE-2026-24486 (path-traversal) are both fixed at 0.0.26 — the version currently locked. With zero version headroom, any regression or new CVE in 0.0.26 would require an immediate patch cycle. Bump the lower bound to `>=0.0.27` when the next release is available.

### I-3 · MongoDB Server CVE-2025-14847 ("MongoBleed") — actively exploited

CVE-2025-14847 is a memory-disclosure vulnerability in the MongoDB server process (not the `pymongo` driver) that allows unauthenticated remote attackers to read server memory. It is under active exploitation. Hosts using the MongoDB backend should verify their MongoDB server version is patched. This is outside regstack's codebase but is a material operational risk for any deployment using `database_url = mongodb://...`.

### I-5 · `.gitignore` missing private-key extensions

The `.gitignore` covers `.env`, `regstack.secrets.env`, build artefacts, and IDE caches. It does not exclude private-key file extensions (`*.pem`, `*.key`, `*.p12`, `*.pfx`). If a developer generates a TLS certificate or an OAuth service-account key locally for testing, it could be accidentally committed.

### I-6 · `workflow_dispatch` on `publish.yml` bypasses the version-tag check

**File:** `.github/workflows/publish.yml`

The publish workflow includes `workflow_dispatch` in its `on:` triggers. The "verify tag matches package version" step runs only `if: startsWith(github.ref, 'refs/tags/v')`. A manually-triggered dispatch skips the version check and builds an artifact (though the publish job is gated on the same `startsWith` condition and would not push to PyPI). The risk is an artifact that could be manually downloaded and published out-of-band. Consider removing `workflow_dispatch` from `publish.yml` or adding a version-consistency check that is not conditioned on the `refs/tags/v` prefix.

### I-7 · Sigstore provenance attestations not enabled

**File:** `.github/workflows/publish.yml`

`pypa/gh-action-pypi-publish` is called without `attestations: true`. Sigstore attestation would create a cryptographic link between the published wheel and the specific workflow run that produced it, allowing downstream consumers to verify provenance. This is low friction to add given the existing OIDC trusted-publisher setup.

**Fix:**

```yaml
- uses: pypa/gh-action-pypi-publish@release/v1
  with:
    attestations: true
```

### I-8 · Disabled-account `is_active=False` returns HTTP 403, distinguishable from 401

**File:** `src/regstack/routers/login.py:73–76`

A login attempt against a disabled account (`is_active=False`) returns HTTP 403 (`"Account is disabled."`), distinct from the 401 returned for a non-existent email or wrong password. An attacker who possesses a valid email address can probe whether that account is currently disabled by observing the 403 vs 401 status code. This is a coarse enumeration vector. Consider unifying to 401 for all non-verified, non-active, or missing-user paths.

### I-9 · Plaintext token URLs passed to hook handlers for password-reset and verification flows

**Files:** `src/regstack/routers/password.py:67`, `src/regstack/routers/register.py:97`, `src/regstack/routers/verify.py:101`, `src/regstack/routers/admin.py:171`

The `password_reset_requested` hook receives `url=<reset_url_with_jwt>` and `verification_requested` receives `url=<url_with_raw_token>`. A host hook that logs its kwargs (or forwards them to an analytics platform) will capture live authentication tokens. This is intentional for custom delivery use cases but should be called out in documentation as a credential-handling responsibility for hook authors.

### I-10 · `jinja2` 3.1.6 — sandbox-breakout CVE, patched

CVE-2025-27516 describes a Jinja2 sandbox escape via the `|attr` filter that can bypass `str.format` restrictions, leading to arbitrary Python execution if untrusted content is passed as template *source*. The locked version 3.1.6 is the fix. The concern for regstack is `add_template_dir` — if a host supplies an untrusted directory as a template override, and that directory contains malicious template source, execution is possible. This is a host-configuration concern, not a regstack bug, but worth documenting in the `add_template_dir` docstring.
