## 🟠 WARNING

### W-1 · CVE-2026-32597 — pyjwt `crit` header bypass (CVSS 7.5)

**Section:** §1  
**File:** `pyproject.toml:24` (`"pyjwt>=2.8"`)

PyJWT prior to **2.12.0** silently accepts JWS tokens whose `crit` (Critical Header
Parameter) lists unknown extensions, violating RFC 7515 §4.1.11. In a multi-library
deployment a crafted token with an unknown critical extension could bypass verification
in one verifier while being processed normally in another.

The current lower bound `>=2.8` admits all vulnerable releases.

**Recommended fix:** Raise to `pyjwt>=2.12.0` in `pyproject.toml`.  
**References:** CVE-2026-32597, Red Hat RHSA-2026, SUSE advisory SA-2026-32597.

### W-2 · CVE-2026-40347 — python-multipart DoS via oversized preamble (Moderate)

**Section:** §1  
**File:** `pyproject.toml:29` (`"python-multipart>=0.0.9"`)

python-multipart before **0.0.26** is vulnerable to a DoS: an attacker sends a
multipart request with an oversized preamble or epilogue before/after the boundary,
causing byte-by-byte parsing to exhaust CPU. Affected endpoints: any FastAPI route
that accepts `multipart/form-data`, including `POST /login` and `POST /register`
(which accept JSON, but FastAPI's default content-negotiation still loads the
`python-multipart` parser for ambiguous content types).

**Recommended fix:** Raise to `python-multipart>=0.0.26`.  
**References:** CVE-2026-40347, CVE-2026-24486 (path traversal, also fixed in 0.0.22).

### W-3 · CVE-2026-26007 — cryptography ECDH SECT-curve key leak (CVSS 8.2)

**Section:** §1  
**Transitive path:** `pyjwt[crypto]` → `cryptography`

The `cryptography` package before **46.0.5** lacks subgroup validation in
`EllipticCurvePublicNumbers.public_key()` and `load_pem_public_key()`, allowing a
subgroup attack on SECT curves that leaks private-key bits via ECDH. Two additional
CVEs follow:

| CVE | Fix in | Summary |
|-----|--------|---------|
| CVE-2026-26007 | 46.0.5 | ECDH SECT-curve private-key leak via subgroup attack |
| CVE-2026-34073 | 46.0.6 | Name-constraint bypass (DNS SAN vs. peer name) |
| CVE-2026-39892 | 46.0.7 | Out-of-bounds read in non-contiguous `Hash.update()` |

Additionally, `cryptography==45.0.0` was yanked from PyPI in May 2025 due to an
OpenSSL regression.

The attack surface for regstack is limited because cryptography is used only for
Google OAuth ID-token verification (RS256 JWKS) and the JWKS keys are server-fetched
from Google's well-known endpoint. However, any host app or test runner that upgrades
`cryptography` without a lower bound could land on a vulnerable version.

**Recommended fix:** Add `cryptography>=46.0.7` as an explicit constraint (either in
the `oauth` extra or as a base constraint that resolves transitively).  
**References:** CVE-2026-26007, CVE-2026-34073, CVE-2026-39892 (GitLab advisories).

### W-4 · JWT decode error reason leaked to clients

**Section:** §7, §9  
**File:** `src/regstack/auth/dependencies.py:118`

```python
raise HTTPException(
    status_code=status.HTTP_401_UNAUTHORIZED,
    detail=f"Invalid token: {exc}",   # ← leaks reason
    ...
)
```

`TokenError` carries human-readable reasons such as:

- `"Signature verification failed"` — tells an attacker the token format was valid
  but the signature was wrong (wrong algorithm, wrong secret, etc.)
- `"Signature has expired"` — reveals the token was once valid
- `"token purpose mismatch"` — reveals a replay attempt across purposes was detected
- `"Not enough segments"` — reveals the token is not even JWT-shaped

CLAUDE.md §9 explicitly states: _"JWT decode errors → 401 generic, never the specific
reason."_ The detail string should be a constant such as `"Authentication required."`.

**Recommended fix:**

```python
except TokenError:
    raise HTTPException(
        status_code=status.HTTP_401_UNAUTHORIZED,
        detail="Authentication required.",
        headers={"WWW-Authenticate": "Bearer"},
    )
```

### W-5 · Admin `DELETE /admin/users/{id}` does not cascade `oauth_identities`

**Section:** §3  
**File:** `src/regstack/routers/admin.py:121–134`

The user-facing `DELETE /account` endpoint correctly cascades:

```python
await rs.oauth_identities.delete_by_user_id(user.id)  # cascade
await rs.users.delete(user.id)
```

The admin equivalent `delete_user` does not:

```python
await rs.users.delete(user.id)               # no oauth_identities cascade
await rs.pending.delete_by_email(user.email)
```

This leaves orphaned rows in `oauth_identities` pointing to a non-existent `user_id`.
The rows cannot be re-linked to another account (the unique index prevents it), but
they accumulate silently and would confuse any future identity-auditing or GDPR
erasure request. The threat model requires _"account deletion must cascade
`oauth_identities` first (anti-orphan), then delete the user."_

**Recommended fix:** Add `await rs.oauth_identities.delete_by_user_id(user.id)` before
`await rs.users.delete(user.id)` in `admin.py:delete_user`.

### W-6 · `POST /phone/start` may panic on OAuth-only users (`hashed_password=None`)

**Section:** §3, §14e  
**File:** `src/regstack/routers/phone.py:58–63`

```python
if not rs.password_hasher.verify(payload.current_password, user.hashed_password):
    raise HTTPException(400, "Current password is incorrect.")
```

`user.hashed_password` is `str | None`. For OAuth-only users it is `None`. Passing
`None` to `pwdlib`'s `Argon2Hasher.verify()` triggers a `TypeError` before comparison
succeeds, which FastAPI surfaces as HTTP 500. The account router's equivalent flows
(`change-password`, `change-email`, `delete-account`) correctly guard this with
`_require_password_set(user)` first; the phone router does not.

An OAuth-only user who sends a valid JWT to `POST /phone/start` will receive a 500,
revealing a server-side exception and potentially leaking stack details in debug mode.

**Recommended fix:** Add `_require_password_set(user)` (imported from `account.py` or
moved to `_schemas.py`) as the first check in `build_phone_router.start`.

### W-7 · GitHub Actions — `pypa/gh-action-pypi-publish` pinned to floating branch, not SHA

**Section:** §12a  
**File:** `.github/workflows/publish.yml:47`

```yaml
- uses: pypa/gh-action-pypi-publish@release/v1
```

`release/v1` is a **branch reference** — intentionally designed to receive ongoing
updates. This means the action code the publishing job runs can change at any time,
without any PR or review on this repository. The publishing job holds PyPI OIDC trust
and the `id-token: write` permission. A malicious push to `pypa/gh-action-pypi-publish`
at branch `release/v1` would immediately affect regstack's next release without any
indication.

The same issue applies (at lower severity) to the other actions:
`actions/checkout@v4`, `astral-sh/setup-uv@v3`, `actions/upload-artifact@v4`,
`actions/download-artifact@v4` — all use mutable tag references rather than commit
SHAs.

**Recommended fix:** Pin all `uses:` directives to a commit SHA, e.g.:

```yaml
- uses: pypa/gh-action-pypi-publish@76f52bc884c9a56c5441b04d7ff7e3576c46e19d  # release/v1 @ 2025-12-17
```

Use `actions/workflow-tools`, `zizaing/actions-update-sha`, or Dependabot
`ecosystem: github-actions` to keep SHAs current.

### W-8 · `pywebview` and `uvicorn` in core `dependencies` widen supply-chain footprint

**Section:** §13c  
**File:** `pyproject.toml:37–39`

```toml
dependencies = [
    ...
    "pywebview>=5.0",
    "tomlkit>=0.13",
    "uvicorn[standard]>=0.29",
]
```

`pywebview` is a GUI framework that pulls in OS-level WebKit/WinRT/WebView2 bindings.
It is only required by `regstack oauth setup` and `regstack theme design` (the wizard
CLI commands). `uvicorn[standard]` (with `websockets`, `watchfiles`, `httptools`) is
similarly only needed by the wizards.

Every host app that runs `pip install regstack` for library use gets these heavy
GUI/server transitive deps forced on them. This widens the supply-chain attack surface
unnecessarily for the common case. The correct design is an `[optional-dependencies]`
extra (e.g., `wizard = ["pywebview>=5.0", "tomlkit>=0.13", "uvicorn[standard]>=0.29"]`)
with the CLI entry-points using lazy imports that fail gracefully if the extra is
missing.

### I-2 · GitHub Actions — no `permissions:` block on `test.yml` or `publish.yml` build job

**Section:** §12c

`test.yml` has no workflow-level or job-level `permissions:` block. The `build` job in
`publish.yml` also lacks one. Without explicit permissions the effective scope depends
on the repository's organisation-level setting, which defaults to `read-all` on GitHub
but can be changed by org admins without touching workflow files. Declaring explicit
minimal permissions is defence in depth:

```yaml
permissions:
  contents: read
```

The `publish.yml` publish job already correctly declares `permissions: { id-token: write }`.

### I-5 · `OAuthTokenExchangeError` may log sensitive Google API response body

**Section:** §11  
**File:** `src/regstack/oauth/providers/google.py:143–146`

```python
raise OAuthTokenExchangeError(
    f"google token exchange failed: {response.status_code} {response.text}"
)
```

`response.text` is the raw Google token-endpoint response body. On error this can
include an `error_description` field with details Google considers internal. This
string is logged at WARNING level in `routers/oauth.py:273`:

```python
log.warning("oauth token exchange failed: %s", exc)
```

It is not returned to the client (only the short error code `"token_exchange_failed"`
is), so this is server-side only. Recommend truncating or redacting `response.text`
to, say, the first 200 characters or an allow-listed set of fields to avoid
accidentally logging tokens that Google may include in future responses.

### I-6 · `ExchangeResponse.was_new_account` hardcoded `False`

**Section:** §14  
**File:** `src/regstack/routers/oauth.py:138–155`

The `/oauth/exchange` endpoint always returns `was_new_account=False` regardless of
whether the OAuth callback created a new user. The `was_new` flag is correctly
computed by `_resolve_user` and used by hooks, but never stored on the state row or
retrieved by the exchange endpoint. This is a functional inconsistency (host
JavaScript expecting to detect new-account vs returning-user flows will always see
`False`), not a security vulnerability, but worth fixing.

## 🟢 CLEAN

The following areas were explicitly reviewed and found to be secure:

### §2 — Hardcoded secrets
No API keys, connection strings with credentials, private keys, or hardcoded JWTs found
in `src/`, `tests/`, `examples/`, or `docs/`. `src/regstack/config/secrets.py` tracked
by git is the code module containing `derive_secret()`, not a secrets file. Example
configs in `examples/*/regstack.toml` reference env-var names, not values.

### §3 — Authentication & authorisation
- All authenticated endpoints inject `rs.deps.current_user()` or `rs.deps.current_admin()`.
- All state-mutating endpoints require authentication.
- All API responses go through `UserPublic.from_user()`, which excludes `hashed_password`,
  `tokens_invalidated_after`, and internal fields.
- Bulk-revoke discipline: `update_password` bumps `tokens_invalidated_after` on password
  change and reset; `update_email` bumps it on email confirm; `set_tokens_invalidated_after`
  is called on admin disable. `lockout.clear` called after reset.
- `hashed_password=None` (OAuth-only) returns same 401 as wrong-password on login
  (enumeration-safe).
- Constant-time comparison via `pwdlib`'s `Argon2Hasher` — no `==` comparisons.
- JWT keys are per-purpose HMAC-SHA256 derivations via `derive_secret`; session tokens
  cannot satisfy password-reset or email-change endpoints.

### §4a — MongoDB injection safety
- All filters use typed literals (`ObjectId`, exact string matches).
- `ObjectId.is_valid()` guards every URL-parameter parse before construction.
- No `$where`, `$expr`, `$function`, `$accumulator`, or user-controlled regexes.
- No unbounded `$in` arrays from user input.

### §4b — SQL injection safety
- All queries use SQLAlchemy Core parameterised binds.
- `text("SELECT 1")` in `sql/backend.py:75` is a health-check ping with no user input.
- `UtcDateTime` TypeDecorator correctly re-attaches UTC tzinfo on read for both SQLite
  and Postgres, preventing tz-aware vs. tz-naive `TypeError` in bulk-revoke comparisons.

### §5 — Input validation
- Every API input goes through a Pydantic model with `extra="forbid"`.
- `EmailStr` on all email fields.
- `is_valid_e164()` called before phone number storage in `POST /phone/start`.
- Email templates use `autoescape=select_autoescape(["html"])` — HTML templates are
  auto-escaped; host-supplied templates are rendered through the same loader.
- SSR templates have no `| safe` filters or `{% autoescape false %}` blocks.
- CLI wizard (`regstack init`) reads input via `click.prompt()` and writes to TOML via
  `tomlkit` — no shell interpolation.
- `redirect_to` parameters validated same-origin in `_validate_redirect()` — off-site
  targets return 400.

### §6 — Rate limiting
- `LockoutService.check()` called before password verification in `POST /login`.
- `record_failure` recorded on every failed authentication attempt (user not found,
  wrong password), not on account-disabled or unverified paths.
- Admin `GET /admin/users` caps `limit` at `le=200` via `Annotated[int, Query(...)]`.
- OAuth state rows have a 5-minute TTL; Mongo enforces via TTL index, SQL via
  `consume()` + `purge_expired()`.
- No file-upload endpoints exist.

### §7 — Session & token security
- HS256 algorithm; `jwt_secret` enforced non-empty at `JwtCodec` construction.
- Every JWT includes `jti` (16-byte `secrets.token_urlsafe`).
- `iat` emitted as `float` in `TokenPayload.to_claims()` — microsecond precision
  preserved for the `iat <= cutoff` bulk-revoke comparison.
- `pyjwt` `verify_exp=False`, `verify_iat=False` — both validated against the injected
  `Clock`; no system-clock drift between codec and tests.
- `_authenticate` chain: decode → blacklist check → user active check → bulk-revoke check.
- No JWT secrets, OAuth client secrets, or SMTP passwords found in log calls.

### §8 — CSP
- No `<style>` blocks or `style=` attributes in any SSR template including the newly
  added `oauth_complete.html`.
- `<script>` loaded via `<script src="{{ static_prefix }}/js/regstack.js" defer>` —
  no inline scripts.
- SSR pages are stateless (no `{{ user.email }}` or similar rendered into HTML).

### §9 — Data exposure
- Database driver errors are not echoed; FastAPI's default exception handlers return
  500 with a generic message.
- OAuth callback failures redirect to `/login?error=<short-code>`; the underlying
  exception is logged server-side only.

### §10 — Git history
- `git log --oneline -30` shows 30 commits since launch; no secrets-handling commits
  are present in recent history.
- `git log --diff-filter=A -- '*.env' '*.key' '*.pem' '*secret*' '*credential*'` shows
  only the initial commit adding `src/regstack/config/secrets.py` (the code module).

### §11 — Third-party integrations
- SMTP password stored as `SecretStr` in `EmailConfig.smtp_password`; `get_secret_value()`
  called inline and not stored or logged.
- SES region/profile from config; no hardcoded AWS credentials.
- Twilio auth token stored as `SecretStr` in `SmsConfig.twilio_auth_token`.
- Google `client_secret` stored as `SecretStr` in `OAuthConfig.google_client_secret`.
- `GoogleProvider.verify_id_token` validates signature (JWKS), `iss`, `aud`, `exp`, and
  `nonce`. JWKS lookup uses `PyJWKClient(jwks_url, cache_keys=True)` which uses
  `urllib.request.urlopen` with a default timeout.

### §12 — GitHub Actions (partial)
- No `pull_request_target` trigger in any workflow.
- No `${{ github.event.* }}` interpolations in `run:` blocks.
- No self-hosted runners; both workflows use `ubuntu-latest`.
- No `PYPI_API_TOKEN` secret; publishing uses OIDC trusted publishing.
- `publish.yml` publish job correctly scoped to `permissions: { id-token: write }`.
- `workflow_dispatch` on test and publish are both acceptable.

### §13 — PyPI package integrity
- `[tool.hatch.build.targets.wheel] packages = ["src/regstack"]` — only the source
  package ships; no `tests/`, `docs/`, `tasks/`, `examples/`, or `.github/`.
- Version verification step reads `pyproject.toml` via `tomllib`, not by importing
  the package — avoiding the 0.2.0 regression.
- Publishing triggered only on `v*` tag pushes; no branch-push publishing.
- `pyproject.toml` optional extras correctly isolate `pymongo`, `asyncpg`, `aioboto3`,
  `twilio`, and `pyjwt[crypto]` from the base install.
- The base-install smoketest job verifies `import regstack` works from a clean wheel.

### §14 — OAuth subsystem
- PKCE: `code_verifier` stored only on the server-side `oauth_states` row; only
  `code_challenge` (SHA-256 of verifier) goes to the provider.
- State row lifecycle: `consume()` is atomic on both Mongo (`find_one_and_delete`) and
  SQL (SELECT + DELETE in a single transaction); expiry checked using `rs.clock.now()`.
- ID-token verification: signature via JWKS, `iss`, `aud`, `exp`, `nonce` all validated;
  failures raise `OAuthIdTokenError` with generic outer message.
- Linking policy: `email_in_use`, `identity_in_use`, `already_linked` correctly enforced.
- OAuth-only user side effects: login returns same 401; other password flows return 400.
  (See W-6 for `phone/start` exception.)
- Identity uniqueness: `(provider, subject_id)` and `(user_id, provider)` unique
  constraints at both DB and migration level.
- Hooks: `oauth_signin_started`, `oauth_signin_completed`, `oauth_account_linked`,
  `oauth_account_unlinked` present in `KNOWN_EVENTS` and fired at correct points.

### §15 — Multi-backend parity
- `test.yml` CI matrix runs all 3 backends (SQLite, PostgreSQL, MongoDB) on Python
  3.11 and 3.12.
- Migration `0002_oauth.py` has working `upgrade()` and `downgrade()`; uses
  `batch_alter_table` for the `hashed_password` nullable change.
- Mongo indexes match all SQL `UniqueConstraint`s:
  - `users.email` → `email_unique`
  - `oauth_identities (provider, subject_id)` → `provider_subject_unique`
  - `oauth_identities (user_id, provider)` → `user_provider_unique`
- TTL parity: all time-limited Mongo collections have TTL indexes; SQL has `purge_expired()`
  methods with bound-parameter cutoffs.
- `UtcDateTime` TypeDecorator re-attaches UTC on read; Mongo client uses `tz_aware=True`.
