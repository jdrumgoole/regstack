### 🟠 W-12 · pyjwt <2.15.1 · day 9 (SLA expired +1 d)

**Resolved version:** 2.13.0 · **Floor:** `>=2.13.0` · **Target floor:** `>=2.15.1`

SLA expired 2026-10-06 — **1 day past deadline.**

#### Severity correction: CVE-2026-102272 escalated from MEDIUM to HIGH

The 2026-10-06 report described CVE-2026-102272 as "`exp` claim accepted as float-string bypasses integer-only check" (CVSS 5.3 MEDIUM). Web search confirms the correct description is **BOM bypass / GHSA-r6x4-923q-g947** (CVSS 7.4 HIGH): `HMACAlgorithm.prepare_key` does not normalize Unicode byte-order marks before checking whether a key is JSON. A public RSA/EC JWK prefixed with a UTF-8 BOM bypasses asymmetric-key detection and is accepted as an HMAC secret, allowing an attacker who knows the public key to forge tokens via algorithm confusion.

**Impact on regstack:** Direct exploitability is limited. Session JWTs are signed with raw bytes from `derive_secret(jwt_secret, purpose)` — not JWKs — so the BOM-JWK code path is never reached. The OAuth ID-token path uses `PyJWKClient` with `algorithms=["RS256"]`; since regstack constrains decoding to a single algorithm, the mixed-algorithm confusion attack requires also MitM-ing the JWKS endpoint. No change to severity classification of W-12 (already SLA-expired WARNING), but the description was inaccurate.

#### New: CVE-2026-102267 — PyJWT JWKS redirect following

Web search surfaces a previously untracked pyjwt advisory: "PyJWT Vulnerability in JWKS Fetching with Redirects" (CVE-2026-102267). `PyJWKClient.fetch_data()` follows HTTP 301/302 redirects without restriction. An attacker who can MitM or poison DNS for the JWKS endpoint can redirect the JWKS fetch to an attacker-controlled server and serve a crafted key set, bypassing signature verification. Covered by the existing `>=2.15.1` target floor.

**Impact on regstack:** `google.py` passes `jwks_url=GOOGLE_JWKS_URL` to `PyJWKClient`. If the TLS certificate of the redirect target is not pinned (it isn't), and the attacker can inject a 301 at the JWKS server or via DNS, they can supply arbitrary keys. The `JWKS_FETCH_TIMEOUT_SECONDS = 5` bound limits exposure duration but does not block this path. Mitigated by HTTPS (certificate validation is on) in non-MitM scenarios; the practical bar is high.

## New findings today

### CVE-2026-102272 severity corrected to CVSS 7.4 HIGH (BOM bypass)

The 2026-10-06 report described CVE-2026-102272 as "exp claim accepted as float-string bypasses integer-only check" (CVSS 5.3 MEDIUM). Web search (Debian Security Tracker, OpenCVE, Vulert) confirms CVE-2026-102272 maps to GHSA-r6x4-923q-g947: **pyjwt BOM bypass** (CVSS 7.4 HIGH). `HMACAlgorithm.prepare_key` does not strip Unicode byte-order marks before the JSON-object vs raw-key test, allowing a UTF-8 BOM-prefixed RSA public JWK to be accepted as an HMAC secret. Direct exploitability on regstack is low — session JWTs use raw `bytes` keys (not JWKs), and OAuth decoding is constrained to `algorithms=["RS256"]` — but the CVE description and severity in prior reports was wrong. The description is corrected above. The existing W-12 floor bump to `>=2.15.1` covers this.

### CVE-2026-102267 · pyjwt JWKS redirect following (new)

Web search surfaces a previously untracked advisory: **CVE-2026-102267** ("PyJWT Vulnerability in JWKS Fetching with Redirects"). `PyJWKClient.fetch_data()` follows HTTP redirects, allowing a MitM attacker who intercepts the JWKS endpoint connection (or performs DNS poisoning) to redirect the JWKS fetch to an attacker-controlled server with a crafted key set, bypassing Google ID-token signature verification on regstack's OAuth path. Covered by `>=2.15.1` target floor. No separate issue needed — tracked under W-12.
