## 🟠 WARNING (Address within 1 week)

### W-1 — PyJWKClient missing network timeout (`src/regstack/oauth/providers/google.py:83`)

**Status:** Carried forward from 2026-05-22 W-1. Not addressed in the two commits since that review.

```python
self._jwks_client = PyJWKClient(jwks_url, cache_keys=True)
```

`PyJWKClient` is constructed without a `timeout` argument. On a JWKS cache miss the client performs a synchronous `urllib.request.urlopen` call, which PR #80 correctly offloaded to `asyncio.to_thread`. However, the underlying urllib call has no timeout (`timeout=None` → indefinite). Under a sustained Google JWKS outage or network partition, concurrent JWKS-miss requests each hold a thread-pool worker indefinitely. Python's asyncio thread pool is bounded (min(32, cpu_count + 4)); exhausting it blocks all `to_thread` calls application-wide.

**Fix:** One-line change:

```python
self._jwks_client = PyJWKClient(jwks_url, cache_keys=True, timeout=5)
```

`PyJWKClient` has accepted a `timeout` kwarg since pyjwt 2.4; `pyproject.toml` already requires `pyjwt>=2.12.1`.

## 🟡 INFO (Best practice recommendations)

### I-1 — `was_new_account` always `False` in OAuth exchange response (`src/regstack/routers/oauth.py:171,179`)

The `ExchangeResponse.was_new_account` field is hardcoded to `False` in both paths of the `/oauth/exchange` endpoint. The `was_new` boolean is correctly computed inside `_resolve_user` (line 325) and passed to the `oauth_signin_completed` hook (line 386), but it is not stored on the `oauth_states` row, so the exchange endpoint cannot surface it to the SPA.

This is an API accuracy gap, not a security issue. A SPA consuming `was_new_account` to display a "Welcome, new user" prompt will never see `True`. No exploitable condition exists from `False` being returned when the account is actually new.

**Fix:** Add a `result_was_new: bool = False` column to `oauth_states` and populate it in the callback before calling `set_result_token`.

### I-2 — OAuth `/start` and `/link/start` have no per-route IP rate-limit config fields

`RegStackConfig` defines `oauth_exchange_rate_limit` but has no corresponding fields for:

- `GET /oauth/{provider}/start` — creates a state row (DB write) per call
- `POST /oauth/{provider}/link/start` — same (requires auth, so less exposed)
- `GET /oauth/{provider}/callback` — triggers a token-exchange POST to Google

Without configured limits, a single IP can hammer `GET /oauth/google/start` to generate unbounded `oauth_states` rows. The Mongo TTL index and `state_ttl_seconds=300` default bound the blast radius to the number of rows that accumulate in a 5-minute window, but hosts have no knob to throttle this at the IP level without writing their own middleware.

The `oauth_exchange` route is rate-limitable, but that endpoint is the wrong throttle point — it is single-use (state is consumed on first hit) and the DB writes already happened at `/start`.

**Fix:** Add config fields `oauth_start_rate_limit`, `oauth_callback_rate_limit` (and optionally `oauth_link_start_rate_limit`) to `RegStackConfig` and corresponding entries in `ROUTE_LIMIT_MAP` in `auth/rate_limit.py`.

### I-3 — Google token-exchange error response body logged at WARNING (`src/regstack/oauth/providers/google.py:143-145`, `routers/oauth.py:315`)

```python
raise OAuthTokenExchangeError(
    f"google token exchange failed: {response.status_code} {response.text}"
)
```

This exception propagates to the router and is logged at WARNING:

```python
log.warning("oauth token exchange failed: %s", exc)
```

The full Google error body (`response.text`) reaches the production log. Google's token-endpoint error responses are standard JSON (`{"error": "invalid_grant", "error_description": "..."}`); they do not contain the client secret. The user receives only `?error=token_exchange_failed` — no information leaks to the client. However, the `error_description` field can contain user-identifying information (e.g., the user's account state at Google). Under GDPR / data-minimisation principles, logging full third-party error bodies at WARNING (potentially to aggregated log sinks) is a best-practice concern.

**Fix:** Log status code at WARNING and body at DEBUG:

```python
log.warning("google token exchange failed: HTTP %s", response.status_code)
log.debug("google token exchange response body: %s", response.text)
```

### I-4 — Admin `DELETE /admin/users/{user_id}` has no self-deletion guard (`src/regstack/routers/admin.py:120-139`)

An admin can submit `DELETE /admin/users/{their_own_id}` and successfully delete their own account. After deletion their token is still technically valid until expiry (the user row is gone but the blacklist entry is not created — the admin router never calls `rs.blacklist.revoke`). Subsequent requests with the token would return 401 (user not found), so there is no privilege escalation. However, losing the last superuser with a single API call is an operational risk.

**Fix (optional):** Add a guard that prevents self-deletion:

```python
if user.id == _admin.id:
    raise HTTPException(status_code=400, detail="Admins cannot delete their own account.")
```

A stronger guard would also reject demoting or disabling the last superuser, but that requires a `count(is_superuser=True)` check and may be over-engineering for a library that doesn't track "minimum superuser count" as a config invariant.

### §3 — Authentication / Authorization

- Every endpoint that returns or mutates user data uses either `rs.deps.current_user()` or `rs.deps.current_admin()` via `Depends(...)`.
- All responses use `UserPublic.from_user(u)` — `hashed_password` is never serialised in any API response.
- Bulk-revoke discipline confirmed:
  - `update_password` bumps `tokens_invalidated_after` on both backends (`mongo/repositories/user_repo.py:82-93`, `sql/repositories/user_repo.py:73-84`).
  - `update_email` bumps `tokens_invalidated_after` on both backends.
  - Admin `PATCH /admin/users/{id}` with `is_active=False` calls `set_tokens_invalidated_after` (`admin.py:111`).
  - Account deletion cascades `oauth_identities.delete_by_user_id` before `users.delete` on both admin and user-initiated paths.
- OAuth-only users (`hashed_password=None`): `POST /login` returns the same generic 401 as a wrong password. `change-password`, `change-email`, `delete-account`, `phone/start`, `phone/disable` all reject via `require_password_set()` → 400.
- Password comparison uses `rs.password_hasher.verify()` (pwdlib/Argon2id constant-time), not `==`.
- JWT keys derived per-purpose via HMAC-SHA256 (`config/secrets.derive_secret`). Session, password_reset, email_change, phone_setup, and login_mfa purposes each have an isolated derived key.
- `phone/confirm` is unauthenticated by design — it is gated on a short-lived `phone_setup` JWT (purpose-isolated key) that carries `sub=user_id` and `phone=<number>`, equivalent to the email-change confirm flow.

### §14 — OAuth Subsystem

- **PKCE:** `code_verifier = secrets.token_urlsafe(64)` server-side. Only `sha256(verifier)` (base64url, no padding) sent as `code_challenge`. Verifier stored on the state row; never in a URL.
- **State row lifecycle:** Mongo uses `find_one_and_delete` (atomic read+delete, `mongo/repositories/oauth_state_repo.py:43-45`). SQL uses SELECT + DELETE inside one `engine.begin()` transaction (`sql/repositories/oauth_state_repo.py:61-68`). Second exchange call returns 404 on missing row.
- **Expiry check:** State expiry checked against `rs.clock.now()` (`routers/oauth.py:157`), not bare `datetime.now(UTC)`. Clock injection preserved.
- **ID-token verification:** RS256 signature via `PyJWKClient`, `iss = GOOGLE_ISSUER`, `aud = client_id`, `exp > now` (pyjwt enforces by default), `nonce == state_row.nonce` (`google.py:177-188`). All six required claims enforced via `options={"require": [...]}`.
- **Linking policy:** `email_in_use` (no auto-link unless `auto_link_verified_emails=True` AND provider `email_verified=True`); `identity_in_use` (same identity attached to different user in link mode); `already_linked` (linking an already-linked identity). Unlinking last sign-in method with no password → 400.
- **OAuth-only users:** Handled correctly. `POST /login` → same generic 401. `change-password` etc. → 400 via `require_password_set()`.
- **DB uniqueness:** `(provider, subject_id)` UNIQUE and `(user_id, provider)` UNIQUE enforced at DB level on both backends (Mongo unique indexes, SQL `UniqueConstraint`).
- **Hook events:** All four OAuth hooks (`oauth_signin_started`, `oauth_signin_completed`, `oauth_account_linked`, `oauth_account_unlinked`) present in `KNOWN_EVENTS` and fired at the correct points.
