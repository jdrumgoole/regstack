## 🟠 WARNING (Address within 1 week)

### W-1 — Starlette 1.0.0 locked — CVE-2026-48710 (BadHost) unpatched

**Finding:**

`uv.lock` pins `starlette: 1.0.0`. The BadHost vulnerability (CVE-2026-48710, CVSS 8.2 HIGH, disclosed 2026-05-21) was fixed in Starlette **1.0.1**. Any FastAPI application running on Starlette ≤ 1.0.0 is exposed.

**Technical detail:**

Starlette reconstructed `request.url` from the raw `Host` header without validating it first. By injecting characters such as `/`, `?`, or `#` into the `Host` header, an attacker could make `request.url.path` diverge from the actual ASGI-routed path. Middleware or endpoints that make security decisions based on `request.url` (rather than the raw ASGI scope path) could therefore be bypassed.

**Regstack-specific impact assessment:**

regstack's own authentication logic is **not directly vulnerable** via this CVE:

- `AuthDependencies._authenticate()` reads the `Authorization: Bearer <token>` header, not `request.url`; path manipulation cannot bypass it.
- `_validate_redirect()` in `routers/oauth.py` validates the `redirect_to` query parameter against `config.base_url` (from config), not against `request.url`.
- `_callback_url()` builds the OAuth callback URL from `config.base_url` (from config), again not `request.url`.

**However**, the locked version means:
1. Any host that adds path-based middleware (a common pattern for serving mixed content behind regstack) will inherit the vulnerable Starlette. The library is a supply-chain artifact — what regstack locks, hosts run.
2. The uv.lock has not been refreshed since before the 2026-05-21 Starlette 1.0.1 release.

**Fix:**

```bash
# Refresh the lock to pull in Starlette 1.0.1
uv lock --upgrade-package starlette
# Verify
uv run python -c "import starlette; print(starlette.__version__)"
```

Also add a floor comment to `pyproject.toml` to document the CVE reason:

```toml
# fastapi>=0.136.x pulls starlette>=1.0.1, fixing CVE-2026-48710 (BadHost).
"fastapi>=0.120.0",
```

**Reference:** https://badhost.org/, https://ostif.org/disclosing-the-badhost-vulnerability-in-starlette/

## 🟡 INFO (Best practice recommendations)

### I-1 — PyJWT 2.12.1 locked — CVE-2026-48526 algorithm confusion, fix in 2.13.0

**Finding:**

`uv.lock` pins `pyjwt: 2.12.1`. CVE-2026-48526 (algorithm confusion vulnerability) was fixed in PyJWT **2.13.0**. When an application decodes tokens using a raw JWK string while simultaneously supporting mixed algorithm families (symmetric and asymmetric), PyJWT ≤ 2.12.x does not validate that the key matches its intended algorithm context.

**Regstack-specific impact assessment:**

regstack's PyJWT usage is **not vulnerable** to CVE-2026-48526 via either path:

- Session/purpose tokens: decoded with `pyjwt.decode(token, key_bytes, algorithms=["HS256"])` — `key_bytes` is a raw `bytes` from HMAC-SHA256 derivation, not a JWK string; algorithm is pinned to symmetric HS256.
- Google ID tokens (`routers/oauth.py`, `oauth/providers/google.py`): decoded with `pyjwt.decode(id_token, signing_key, algorithms=["RS256"])` — `signing_key` is a key object from `PyJWKClient.get_signing_key_from_jwt()`, not a raw JWK string; algorithm is pinned to RS256.

Neither path uses a raw JWK string or mixes algorithm families in one decode call, so the confusion attack does not apply. Nevertheless, bumping the lock is low-risk and closes the gap for future code paths.

**Fix:**

```bash
uv lock --upgrade-package pyjwt
```

**Reference:** https://cvereports.com/reports/CVE-2026-48526

### I-2 — `jwt_secret` lacks minimum-length enforcement

**Finding (`src/regstack/config/schema.py:187`):**

```python
jwt_secret: SecretStr = Field(default_factory=lambda: SecretStr(""))
```

`JwtCodec.__init__` (`src/regstack/auth/jwt.py:118`) checks the secret is non-empty but does not enforce a minimum length:

```python
if not config.jwt_secret.get_secret_value():
    raise ValueError("...")
```

The documentation (`docs/security.md`, line 31) states the master `jwt_secret` should be "≥32 chars", but nothing in the code enforces this. A host can set `REGSTACK_JWT_SECRET=x` (1-char secret) and regstack will start without complaint. HMAC-SHA256 derived keys from a short secret have negligible keyspace.

**Fix:**

Add a `field_validator` in `RegStackConfig`:

```python
@field_validator("jwt_secret")
@classmethod
def _validate_secret_length(cls, v: SecretStr) -> SecretStr:
    val = v.get_secret_value()
    if val and len(val) < 32:
        raise ValueError(
            "jwt_secret must be at least 32 characters. "
            "Run `regstack init` or set REGSTACK_JWT_SECRET=$(python -c "
            "'import secrets; print(secrets.token_urlsafe(64))')."
        )
    return v
```

Allowing empty at construction time (for test fixtures) while rejecting short non-empty values preserves the existing test UX.

### I-3 — Phone route IP rate limits default to `None`; no-rate-limit configuration not flagged at startup

**Finding (`src/regstack/config/schema.py:239-241`):**

```python
phone_start_rate_limit: str | None = None
phone_confirm_rate_limit: str | None = None
phone_disable_rate_limit: str | None = None
```

Hosts that enable `enable_sms_2fa=True` but do not configure these fields get no IP throttling on the phone setup and code-confirm routes. The per-code attempt counter (`sms_code_max_attempts`, default 5) bounds brute force against a single code, but:

- A fresh `POST /phone/start` re-issues a code, resetting the attempt counter.
- Without an IP rate limit, an attacker can call `POST /phone/start` + `POST /phone/confirm` in a tight loop, each time trying 5 guesses on the new code before requesting another. This costs the target real SMS fees and may produce account enumeration side-channels (SMS delivery success/failure visible in response timing).

The prompt (`scripts/security-review-prompt.md §6`) notes: "Phone routes send paid SMS and brute-force a 6-digit code, so they need IP throttles regardless of the per-code attempt counter."

**Recommendation:**

1. Add a note to `regstack doctor` output when `enable_sms_2fa=True` and any phone rate limit is unconfigured.
2. Document recommended defaults in `docs/configuration.md` (e.g. `phone_start_rate_limit = "3/minute;10/hour"`).
