### W-1 (carry-over, day 37 — SLA MISSED 2026-08-18, 22 days overdue)

**Section:** §1 — Dependency Vulnerability Check
**CVE:** CVE-2026-69247 — `cryptography` Bleichenbacher oracle (`pkcs7_decrypt`)
**Affected range:** `cryptography` ≥ 44.0.0, < 50.0.0
**Resolved in:** `cryptography==50.0.0` (released 2026-07-31 — 47 days ago)
**Current resolved version in `uv.lock`:** 49.0.0 (within affected range)
**Current floor in `pyproject.toml`:** `cryptography>=48.0.1` (does not exclude affected versions)
**Fix required:** Bump floor to `cryptography>=50.0.0` in both the `oauth` and `dev` extras in
`pyproject.toml`; run `uv lock`.
**Tracking:** GitHub issue #181 (`[security] Raise cryptography floor to >=50.0.0`), open since
2026-08-19 — 29 days unacknowledged. No fix PR, no assignee, no comment.

**Technical impact:** `pkcs7_decrypt_der`, `pkcs7_decrypt_pem`, and `pkcs7_decrypt_smime` expose
distinguishable error paths and timing differences during RSA `RecipientInfo.encryptedKey` decryption,
constituting a Bleichenbacher-style oracle. regstack does not call these functions directly, but
`pip install regstack[oauth]` resolves to 49.0.0 by default, shipping a version with an open advisory
to all downstream consumers. The fix (cryptography 50.0.0+) substitutes a random key on RSA
decryption failure per RFC 3218.

**Urgency:** The fix version has been on PyPI for 47 days. The 7-day SLA lapsed 2026-08-18 — now
22 days overdue. Issue #181 has been open 29 days with zero activity. This finding will appear
daily until resolved.

### W-2 (carry-over, day 16 — NEW 2026-09-01) — `POST /confirm-email-change` email-change JWT not revoked after use

**Section:** §3 — Authentication & Authorization Audit
**File:** `src/regstack/routers/account.py`, `confirm_email_change` handler
**Tracking:** GitHub issue #197, open since 2026-09-01 — 16 days unacknowledged.
**Status:** Unresolved. No code change in `account.py` since first flagged.

The `confirm_email_change` endpoint successfully updates the user's email address but does not
call `await rs.blacklist.revoke(token_payload.jti, token_payload.exp)` after doing so. The
password-reset path (`password.py`) correctly performs this revocation after every successful reset.
Within the email-change token's TTL, the same confirmation URL can be submitted repeatedly. Each
subsequent submission attempts `update_email`, which succeeds as a no-op when the address is already
the user's own, and the endpoint returns HTTP 200 — confirming the link is still usable.

The `_decode_email_change_token` helper currently returns only `(user_id, new_email)` and discards
the `jti` and `exp` claims. Any fix must thread these through to the caller so `blacklist.revoke()`
can be called after a successful `update_email`.

### W-3 (carry-over, day 16 — NEW 2026-09-01) — `POST /confirm-email-change` bulk-revoke not applied to email-change tokens

**Section:** §3 — Authentication & Authorization Audit
**File:** `src/regstack/routers/account.py`, `confirm_email_change` handler
**Tracking:** GitHub issue #198, open since 2026-09-01 — 16 days unacknowledged.
**Status:** Unresolved. No code change in `account.py` since first flagged.

If a user changes their password (bumping `tokens_invalidated_after`) after requesting an email
change, the already-issued email-change JWT should be treated as bulk-revoked. The current
`confirm_email_change` handler does not call
`is_payload_bulk_revoked(payload, user.tokens_invalidated_after)` after decoding the token and
fetching the user. The `_decode_email_change_token` helper also discards the `iat` claim, so the
comparison cannot be performed without extending the return signature.

The pattern mirrors the `_authenticate` dependency. Both W-2 and W-3 can be fixed in a single pass
through `confirm_email_change`.

### W-4 (carry-over, day 16 — NEW 2026-09-01) — OAuth `_resolve_user` race raises `UserAlreadyExistsError` → HTTP 500

**Section:** §14 — OAuth Subsystem Audit
**File:** `src/regstack/routers/oauth.py`, `_resolve_user` function
**Tracking:** GitHub issue #199, open since 2026-09-01 — 16 days unacknowledged.
**Status:** Unresolved.

Under concurrent OAuth callbacks for the same new email address (two tabs completing Google sign-in
simultaneously), `_resolve_user` may attempt `users.create()` in both requests after both pass the
`get_by_email` check. The second `create()` raises `UserAlreadyExistsError`, which is not caught
in `_resolve_user`, propagating as HTTP 500. The fix is to catch `UserAlreadyExistsError` after
`create()` and retry with a `get_by_email` lookup — or use an upsert at the DB level. The error
is exploitable only with racing requests and affects only new-user OAuth registrations, but 500
responses leak that an error occurred and may confuse client retry logic.

### W-5 (carry-over, day 10 — NEW 2026-09-07) — `aiosmtplib` floor `>=5.1.1` includes CVE-2026-55558

**Section:** §1 — Dependency Vulnerability Check
**CVE:** CVE-2026-55558 — `aiosmtplib` SMTP command injection via unescaped CR/LF in RCPT addresses
**Affected range:** `aiosmtplib` < 5.1.2
**Resolved in:** `aiosmtplib==5.1.2`
**Current floor in `pyproject.toml`:** `>=5.1.1` (includes the vulnerable version)
**Fix required:** Bump floor to `aiosmtplib>=5.1.2` in `pyproject.toml`; run `uv lock`.
**Tracking:** GitHub issue #206, open since 2026-09-07 — 10 days unacknowledged.

`aiosmtplib.SMTP.mail()`, `.rcpt()`, `.vrfy()`, and `.expn()` in < 5.1.2 do not reject C0 control
characters (CR/LF) in caller-supplied addresses, allowing SMTP command injection if untrusted input
is passed. regstack routes email through its `EmailService` abstraction which constructs `RCPT TO`
from `User.email`, validated by `EmailStr` on intake. Pydantic's `EmailStr` rejects bare CR/LF, so
the risk is mitigated in practice — but a host app that calls `aiosmtplib` directly with the same
floor would be exposed. Closing the floor removes the ambiguity.

### W-6 (carry-over, day 8 — NEW 2026-09-09) — SQL `oauth_states.consume()` SELECT+DELETE not atomic under Postgres

**Section:** §14 — OAuth Subsystem Audit
**File:** `src/regstack/backends/sql/repositories/oauth_state_repo.py`
**Tracking:** GitHub issue #208, open since 2026-09-09 — 8 days unacknowledged.
**Status:** Unresolved.

The SQL `consume()` implementation performs a SELECT then a DELETE in two separate statements.
Under Postgres's default `READ COMMITTED` isolation, two concurrent OAuth callbacks with the same
`state` parameter can both read the row before either deletes it, both succeed, and both issue
access tokens — defeating the one-time-use invariant of the state parameter. The Mongo
implementation uses `find_one_and_delete` (atomic). Fix: replace the SELECT+DELETE with
`DELETE FROM oauth_states WHERE id = :id RETURNING *` under a serialisable transaction, or use
`INSERT ... ON CONFLICT` to mark the row consumed before reading it.

### W-7 (carry-over, day 8 — NEW 2026-09-09) — `admin_resend_verification` creates a dead-end for already-verified users

**Section:** §3 — Authentication & Authorization Audit
**File:** `src/regstack/routers/admin.py`, `admin_resend_verification` handler
**Tracking:** GitHub issue #209, open since 2026-09-09 — 8 days unacknowledged.
**Status:** Unresolved.

When an admin calls `POST /admin/users/{id}/resend-verification` for a user who is already
verified (`is_verified=True`), the handler calls `users.create()` (via the verification flow),
which raises `UserAlreadyExistsError` and returns HTTP 400. The admin receives no indication that
the user is already verified — the error message says "email already registered", which is
confusing and actionable-looking. An admin who misreads this response could unintentionally
trigger repeated verification emails. The fix is to add an early guard: if `user.is_verified`,
return HTTP 422 ("User is already verified") before attempting any database write.

## 🟡 INFO

### I-1 — `mfa_pending_token` JTI not explicitly blacklisted after successful MFA confirm (§7, carry-over)

**File:** `src/regstack/routers/login.py`, MFA confirm handler

After `POST /login/mfa-confirm` succeeds, the `mfa_pending_token`'s JTI is not added to the
blacklist. Single-use is enforced implicitly: the `mfa_codes` row is deleted on first success,
so a second attempt returns code-not-found. The invariant is invisible to future reviewers and
differs from `password_reset` token's explicit blacklisting. Explicit blacklisting would make
the intent visible and prevent any theoretical re-use window if the codes row deletion fails
mid-transaction.

### I-2 — `mfa_pending_token` bulk-revoke check absent in MFA confirm (§7, carry-over)

**File:** `src/regstack/routers/login.py`, MFA confirm handler

The MFA confirm handler decodes `mfa_pending_token` but does not call
`is_payload_bulk_revoked(payload, user.tokens_invalidated_after)`. If the user changes their
password between `/login` (which issues the pending token) and `/login/mfa-confirm`, the pending
token should be treated as revoked. In practice, a password change requires the existing session
— which implies the user is already authenticated — but the defence-in-depth check is missing.

### I-3 — Phone-setup JWT lacks bulk-revoke check (§7, carry-over)

**File:** `src/regstack/routers/sms.py`, phone confirm handler

Same pattern as I-2. The `phone_setup` JWT decoded in `POST /phone/confirm` is not checked
against `user.tokens_invalidated_after`. A password change between `/phone/start` and
`/phone/confirm` would leave the phone-setup token technically valid.

### I-4 — Password-reset token TTL note in CLAUDE.md understates the blacklist invariant (§7, carry-over)

**File:** `CLAUDE.md`, "Three kinds of single-use proof" section

CLAUDE.md correctly notes password-reset tokens are "No DB row", but does not mention that
`password.py` also calls `blacklist.revoke(jti, exp)` after each successful reset. A future
reviewer relying only on CLAUDE.md's description might omit the per-token blacklist revocation
when implementing a new JWT-based single-use flow.

### I-5 — Synthetic OAuth client secret in test fixture looks real (§2, carry-over)

**File:** `tests/unit/test_wizard_oauth_writer.py`

The fixture uses `GOCSPX-secretvalue1234` as a synthetic Google client secret. Automated secret
scanners may flag this pattern. Consider replacing with a clearly synthetic value like
`GOCSPX-FAKE000000000000` to reduce false positives in scanner output.

### I-6 — `regstack doctor` DNS check is opt-in (§11, carry-over)

The DNS resolution check and test-email send are gated behind `--check-dns` and
`--send-test-email` flags. Hosts who run `regstack doctor` after a domain change may not get
DNS feedback unless they know to pass these flags. Consider printing a short note that DNS

### I-7 — `log_bodies = True` logs request/response bodies including auth tokens (§9, carry-over)

**File:** `src/regstack/config/__init__.py`, `log_bodies` field

When `REGSTACK_LOG_BODIES=true` (default `false`), the middleware logs full request/response

The config field has a docstring noting this risk, but the `regstack init` wizard does not warn

### I-12 — SQL `oauth_identities` table lacks database-level FK constraint on `user_id` (§15, carry-over)

**File:** `src/regstack/backends/sql/schema.py`

The `oauth_identities` table has no `FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE
CASCADE`. Application code manually deletes identity rows before the user record in `account.py`
and `admin.py`. Any exception between the two deletes (network error, process crash) leaves
orphan identity rows. No auth bypass is possible from orphans (`get_by_id` returns None for a
deleted user), but orphans accumulate and could confuse future tooling. A FK with `ON DELETE
CASCADE` would provide defence in depth and remove reliance on deletion order in application
code.

### I-13 — PKCE `code_verifier` stored in plaintext in `oauth_states` (§14, carry-over)

**Files:** `src/regstack/backends/sql/schema.py`,
`src/regstack/backends/mongo/repositories/oauth_state_repo.py`

The PKCE `code_verifier` is stored verbatim in `oauth_states`. PKCE was designed assuming the
verifier is known only to the original requester (a native or browser-based client); here it lives
in a server-side table. An attacker who exfiltrates the table during the state TTL window AND
captures the in-flight authorization code could complete the exchange independently. The short
TTL and the need to acquire both artifacts limits practical risk significantly. Storing the
SHA-256 hash of the verifier instead (the `code_challenge` already sent to the provider) would
be defence in depth.
