## 🟡 INFO

### I-1 · `tokens_invalidated_after` exposed in `UserPublic` API responses

**Location:** `src/regstack/models/user.py:105`

`UserPublic` includes `tokens_invalidated_after`, the bulk-revoke cutoff timestamp. The
security-review specification (§9) lists this field alongside `hashed_password` as fields
that should be excluded from public API responses.

The behaviour is **intentional**: `docs/security.md` documents the design decision — SPA
clients can compare this field against their session JWT's `iat` claim to detect session
invalidation (password change, email change, admin disable) without a round-trip. The
trade-off was previously reviewed and accepted as I-2 in the 2026-05-17 review and closed
with documentation.

No code change is required. Noted for ongoing awareness; the field leaks the timestamp of
the most recent credential-changing event, which a high-frequency attacker could use for
correlation. Hosts that wish to hide it can wrap `UserPublic` in their own response model
and exclude the field.

### I-2 · `PyJWKClient` JWKS fetch is synchronous and may block the asyncio event loop

**Location:** `src/regstack/oauth/providers/google.py` — `GoogleProvider.__init__`

```python
self._jwks_client = PyJWKClient(jwks_url, cache_keys=True)
```

pyjwt's `PyJWKClient` fetches the JWKS endpoint using `urllib.request.urlopen`—a
blocking call that runs on the event-loop thread. When the in-process cache is cold (first
call) or a key-rotation triggers an automatic refresh (unknown `kid`), this blocks the
FastAPI event loop for up to 30 seconds (the library's default timeout).

**Mitigations already in place:**

- `cache_keys=True` with a 5-minute TTL means blocking fetches happen at most once every
  five minutes for an active deployment, not on every request.
- The JWKS fetch is only reachable after the OAuth callback has validated a state row
  (requires starting a legitimate OAuth flow) and exchanged a code with Google (requires
  a Google-issued authorization code). Arbitrary external actors cannot trigger the fetch.

**Recommendation:** Pass an explicit `timeout` parameter and consider wrapping the
synchronous fetch in `asyncio.to_thread()` to keep the event loop responsive during the
rare cache-miss case:

```python
# Option A: explicit timeout (no event-loop protection, but bounded)
self._jwks_client = PyJWKClient(jwks_url, cache_keys=True, timeout=10)

# Option B: async-safe (preferred)
import asyncio
signing_key = await asyncio.to_thread(
    self._jwks_client.get_signing_key_from_jwt, id_token
)
```

Risk is **low** given the mitigations but worth addressing before traffic volumes grow.

### I-3 · MongoDB server CVE-2025-14847 (MongoBleed) — operator advisory

**Affected component:** MongoDB server binary (not pymongo driver)  
**CVSS:** 8.7

CVE-2025-14847 ("MongoBleed") allows an unauthenticated attacker on the network to leak
server memory via crafted zlib-compressed messages. It affects MongoDB Server versions
≤ 8.2.2, ≤ 8.0.16, ≤ 7.0.27, ≤ 6.0.26, ≤ 5.0.31, ≤ 4.4.29. The pymongo Python
driver (regstack's `mongo` extra, currently 4.17.0) is **not the vulnerable component**.

regstack itself has no code-level exposure, but host operators running the `mongo` backend
should:

1. Upgrade MongoDB server to ≥ 8.2.3 / 8.0.17 / 7.0.28 / 6.0.27 / 5.0.32 / 4.4.30.
2. If an upgrade is not immediately possible, disable zlib compression in `mongod.conf`:
   `net.compression.compressors: snappy` (removing `zlib`).

**Recommendation for regstack:** Add a `regstack doctor` check that logs a WARNING when
the connected MongoDB server reports a version below the patched minimum. Document the
minimum supported server version in `docs/embedding.md`.

### §14 OAuth Subsystem Audit

**§14a PKCE invariants:** `code_verifier` is generated in `_begin_flow` and stored only
on the `oauth_states` row. Only `code_challenge` (SHA-256 of verifier, base64url-
encoded) goes in the authorization URL. ✓

**§14b State row lifecycle:**

- Missing / wrong-provider state: `bad_state` redirect. ✓
- Expired state: `state_expires_at < rs.clock.now()` — uses the injected clock, not
  `datetime.now()`. ✓
- Exchange row consumed atomically: `find_one_and_delete` (Mongo) and
  `SELECT + DELETE` in one transaction (SQL). A second exchange with the same id returns
  404 / "already consumed". ✓

**§14c ID-token verification:** `GoogleProvider.verify_id_token` verifies:
signature (against Google JWKS), `iss`, `aud`, `exp`, `iat`, `nonce`; all via pyjwt
with `require: [sub, iss, aud, exp, iat, nonce]`. Nonce re-checked explicitly in Python
after decode. Failures raise `OAuthIdTokenError`; the router logs the message and
redirects with a short error code. ✓

**§14d Linking-policy enforcement:**

- Identity already linked to a different account → `identity_in_use`. ✓
- Identity linked to same account → `already_linked`. ✓
- Email exists without `auto_link_verified_emails` → `email_in_use`. ✓
- Auto-link fires only when `auto_link_verified_emails=True` AND `email_verified=True`. ✓

**§14e OAuth-only user side effects:**

- `POST /login` with `hashed_password=None` returns generic 401. ✓
- `change-password`, `change-email`, `delete-account` return 400 via
  `require_password_set()`. ✓
- `DELETE /oauth/{provider}/link` returns 400 when user has no password and only one
  linked identity. ✓

**§14f Identity-row uniqueness:** DB-level unique constraints on both backends:

**§14g Hooks:** `oauth_signin_started`, `oauth_signin_completed`, `oauth_account_linked`,
