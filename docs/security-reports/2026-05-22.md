## 🟠 WARNING (Address within 1 week)

### W-1 — PyJWKClient missing timeout (`src/regstack/oauth/providers/google.py:83`)

**Finding:**

```python
self._jwks_client = PyJWKClient(jwks_url, cache_keys=True)
```

No `timeout` argument is passed to `PyJWKClient`. The client performs a synchronous `urllib.request.urlopen` call when the JWKS key cache is cold or expired. PR #80 (2026-05-20 review) correctly offloaded this call to `asyncio.to_thread` so it no longer blocks the event loop directly:

```python
signing_key_obj = await asyncio.to_thread(
    self._jwks_client.get_signing_key_from_jwt, id_token
)
```

However, the underlying urllib call still has no timeout (`timeout=None` → indefinite). Consequences:

- **Thread-pool exhaustion:** Under sustained OAuth load, if Google's JWKS endpoint becomes slow or unreachable, concurrent JWKS-miss requests each hold a worker thread indefinitely. Python's default asyncio thread pool is bounded (min(32, os.cpu_count() + 4) threads); exhausting it blocks all `to_thread` calls across the entire application.
- **Attack surface:** An attacker cannot force JWKS cache misses (cache hits bypass the network entirely, and the JWT `kid` must belong to a real Google key to pass signature verification). The risk is an operational Google JWKS outage or network partition, not a direct attack. However, the 5-minute default cache TTL (`lifespan` not set, so PyJWT uses its internal default) means regular JWKS refreshes happen, and a sustained outage would cycle through the thread pool.

**Fix:** Add a timeout, e.g.:

```python
self._jwks_client = PyJWKClient(jwks_url, cache_keys=True, timeout=5)
```

PyJWT >= 2.4 accepts a `timeout` keyword argument on `PyJWKClient.__init__`. The project already requires `pyjwt>=2.12.1`, so this parameter is available.

**Note:** This finding was not explicitly addressed in PR #80 — that PR fixed the event-loop-blocking issue (I-2 from the 2026-05-20 review) but did not add a timeout. The thread-pool exhaustion risk is the remaining exposure.

## 🟡 INFO (Best practice recommendations)

### I-1 — `was_new_account` always `False` in OAuth exchange response (`src/regstack/routers/oauth.py:176`)

The `ExchangeResponse.was_new_account` field is hardcoded to `False` in the `/oauth/exchange` endpoint:

```python
return ExchangeResponse(
    access_token=state.result_token,
    redirect_to=state.redirect_to,
    was_new_account=False,   # ← always False
    expires_in=rs.config.jwt_ttl_seconds,
)
```

The `was_new` boolean is correctly computed during `_resolve_user` in the callback, but it is not persisted to the `oauth_states` row, so the exchange endpoint cannot surface it. SPAs using this field to display a "Welcome! Account created." prompt will never see it set to `True`.

This is not a security issue — a SPA seeing `False` when an account was genuinely new does not create an exploitable condition. It is an API accuracy gap that may confuse host implementors. Fix: add a `result_was_new: bool = False` column to `oauth_states` and populate it during the callback.

### I-3 — OAuth token-exchange exception includes full Google response body in server logs

In `google.py:143-145`, `OAuthTokenExchangeError` is constructed with:

```python
raise OAuthTokenExchangeError(
    f"google token exchange failed: {response.status_code} {response.text}"
)
```

This exception is caught in `routers/oauth.py` and logged at `WARNING` level:

```python
log.warning("oauth token exchange failed: %s", exc)
```

The user sees only `?error=token_exchange_failed`; no information leaks to the client. Google's token endpoint error responses are standard JSON (`{"error": "invalid_grant", "error_description": "..."}`) and do not contain the client secret or authorization code. Risk in practice is low.

Suggested improvement: separate the status-code portion (log at WARNING) from the response-body portion (log at DEBUG) to keep production log noise down:

```python
log.warning("google token exchange failed: HTTP %s", response.status_code)
log.debug("google token exchange response body: %s", response.text)
```

### §3 — Authentication & Authorization

- Every authenticated endpoint injects either `rs.deps.current_user()` or `rs.deps.current_admin()`.
- All user-state-mutating endpoints (change-password, change-email, delete-account, admin patch/delete) require authentication.
- All responses use `UserPublic.from_user(u)` — `hashed_password` is never returned. `tokens_invalidated_after` is intentionally included in `UserPublic` (documented trade-off from I-2, 2026-05-17 review, closed in PR #63).
- Bulk-revoke discipline verified: `update_password` bumps `tokens_invalidated_after` on both backends; `update_email` does the same; admin disable (`set_active(id, is_active=False)`) calls `set_tokens_invalidated_after`; account deletion cascades `oauth_identities` before `users.delete`.
- OAuth-only users (`hashed_password=None`): login returns the same generic 401 as a wrong-password attempt; `change-password`, `change-email`, `delete-account` reject via `require_password_set()`.
- Password verification uses `rs.password_hasher.verify()` (pwdlib/Argon2id constant-time comparison), not `==`.
- JWT signing keys use HMAC-SHA256 per-purpose derivation in `config/secrets.derive_secret`. Compromise of one purpose key does not expose the master or other keys.

### §4 — Storage-Layer Injection

**MongoDB:** No `$where`, `$expr`, `$function`, or `$accumulator` operators found in any repository. All query filters use static field names with user-supplied values as bound parameters. `ObjectId.is_valid()` guards every `get_by_id` lookup before `ObjectId(...)` conversion. No user-input regex patterns.

**SQL:** All queries use SQLAlchemy Core parameterized binds. The two `text()` calls are: `text("SELECT 1")` in the `ping()` health check (no user input) and `text("SELECT COUNT(*) FROM users WHERE hashed_password IS NULL")` in the `0002` migration downgrade pre-check (no user input). `UtcDateTime` TypeDecorator consistently re-attaches UTC tzinfo on read, preventing silent tz-naive corruption of bulk-revoke comparisons.

### §6 — Rate Limiting & DoS Prevention

- `LockoutService.check()` fires at the very top of the login handler, before user lookup or password verification. A locked account always returns 429 with `Retry-After`.
- `record_failure` is called for all failure branches (user not found, wrong password, disabled, unverified) before the 401/403 response.
- `login_attempts` Mongo TTL index expires rows after `login_lockout_window_seconds`.
- Admin user listing has `Query(ge=1, le=200)` cap on `limit`.
- OAuth `state` rows have a TTL index on Mongo and `purge_expired()` for SQL backends.
- No file-upload endpoints exist.
- `rate_limit_disabled=True` short-circuits both `record_failure` and `check` — no docs written in test mode.

### §7 — Session & Token Security

- HS256 algorithm (configurable), secret ≥32 chars enforced at `JwtCodec` construction.
- Every JWT includes a `jti` generated with `secrets.token_urlsafe(16)`.
- `iat` emitted as `float` (RFC 7519 NumericDate) — microsecond precision enables correct `iat <= cutoff` bulk-revoke comparisons when a login completes in the same wall-clock second as a password change.
- pyjwt's `exp`/`iat`/`nbf` automatic checks disabled; both validated against injected `Clock`. `FrozenClock` tests and production correctness both rely on this seam.
- `_authenticate` validates: decode → blacklist (jti) → active user → bulk-revoke cutoff, in correct order.
- No token values appear in log messages. Token decode errors return a single static "Invalid or expired token." 401.
- Password-reset tokens blacklisted on first use (PR #17, "Review #17" comment in `password.py:97`), preventing replay.

### §14 — OAuth Subsystem

- **PKCE:** `code_verifier` generated server-side with `secrets.token_urlsafe(64)`, stored on the `oauth_states` row. Only `code_challenge = sha256(verifier)` sent to the provider. Verifier never appears in a redirect URL.
- **State row lifecycle:** Mongo uses `find_one_and_delete` (atomic); SQL uses SELECT + DELETE inside a single `engine.begin()` transaction (atomic). Second exchange call returns 404. Expiry checked against `rs.clock.now()` (not bare `datetime.now(UTC)`) — clock injection preserved for tests.
- **ID-token verification:** Signature via `PyJWKClient` + RS256, `iss` matches `GOOGLE_ISSUER`, `aud` matches `client_id`, `exp > now`, `nonce` matches `state_row.nonce`. Failure raises `OAuthIdTokenError` (generic outer message); internal detail is logged, not echoed to redirect.
- **Linking policy:** Existing-email sign-in → `email_in_use` (no auto-link unless `auto_link_verified_emails=True` AND `email_verified=True`). Already-linked identity to different user → `identity_in_use`. Same identity same user → `already_linked`. Unlink last method with no password → 400.
- **OAuth-only users:** `POST /login` → generic 401; `change-password`, `change-email`, `delete-account` → `require_password_set()` 400.
- **Identity uniqueness:** `(provider, subject_id)` UNIQUE and `(user_id, provider)` UNIQUE enforced at DB level on both backends (Mongo unique indexes, SQL `UniqueConstraint`).
- **Hooks:** `oauth_signin_started`, `oauth_signin_completed`, `oauth_account_linked`, `oauth_account_unlinked` all present in `KNOWN_EVENTS` and fired at correct points in the router.
