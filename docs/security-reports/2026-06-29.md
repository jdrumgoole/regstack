### W-3 — CVE-2026-45447: `cryptography` bundled OpenSSL heap UAF (CVSS 7.5 High) — carry-forward

**Package:** `cryptography` (in `oauth` optional extra: `cryptography>=46.0.7`)
**Resolved:** `47.0.0` · **Safe version:** `>=48.0.1`
**Advisory:** GHSA-537c-gmf6-5ccf · Published: June 9, 2026
**Tracked:** GitHub issue #123

PyPI `cryptography` wheels bundle a statically-linked OpenSSL. All wheels `>=0.5.0,<48.0.1` include
an OpenSSL version with a heap use-after-free in `PKCS7_verify()` (empty `digestAlgorithms` SET in a
PKCS#7/S/MIME message). Consequences: process crash, heap corruption, potential RCE.

Regstack's own `PyJWKClient` path uses RSA/EC key operations and does not call `PKCS7_verify()`
directly. However the `oauth` extra floor `>=46.0.7` allows downstream hosts to resolve `47.0.0`
(vulnerable); hosts that also use `cryptography` for TLS cert handling or S/MIME are directly
exposed.

**Action required:**
1. Bump `oauth` extra: `"cryptography>=48.0.1"` with updated CVE comment in `pyproject.toml`.
2. Bump `dev` extra: `"cryptography>=48.0.1"`.
3. Run `uv lock`.

### W-4 — CVE-2026-53533: `aiosmtplib 5.1.0` SMTP command injection (CVSS 6.5 Moderate) — carry-forward

**Package:** `aiosmtplib` (base dependency: `aiosmtplib>=3.0`)
**Resolved:** `5.1.0` · **Safe version:** `>=5.1.1`
**Advisory:** GHSA-v3q9-hj7j-63hq · Published: June 15, 2026
**Tracked:** GitHub issue #124

The 5.1.1 release notes confirm the fix: control characters (C0 range 0x00–0x1F and DEL 0x7F,
including CR, LF, NUL) are now rejected in SMTP command arguments (`mail()`, `rcpt()`, `vrfy()`,
`expn()`, `sendmail()`). Prior versions accepted these characters, allowing injection into the SMTP
command stream — a crafted email address such as `attacker@evil.com\r\nBcc: victim@example.com`
could silently add blind-copy recipients to verification, password-reset, or MFA emails.

The SMTP backend (`SmtpEmailService`) sends tokens and one-time links. An SMTP injection here is
directly on regstack's security-critical code paths.

**Action required:**
1. Bump `"aiosmtplib>=5.1.1"` in `pyproject.toml` with updated CVE comment.
2. Run `uv lock`.

### W-5 — CVE-2026-32690: `pydantic-settings 2.14.0` symlink path traversal (CVSS 5.9 Medium) — carry-forward

**Package:** `pydantic-settings` (base dependency: `pydantic-settings>=2.2`)
**Resolved:** `2.14.0` · **Safe version:** `>=2.14.2`
**Advisory:** DailyCVE DC-Jun2026-536 · Published: June 2026
**Tracked:** GitHub issue #125

Affects `pydantic-settings 2.12.0–2.14.1`. When a `BaseSettings` subclass reads from a secrets
directory (`secrets_dir`), there is an inconsistency: the size-check step does **not** follow
symlinks but the file-loader **does**. An attacker with write access to the secrets directory can
create a symlink to an arbitrary filesystem path; `pydantic-settings` will read the target file
and expose it as a config value.

`RegStackConfig` extends `BaseSettings` and reads from `secrets_env_path` (typically
`regstack.secrets.env`). The attack requires write access to the secrets directory — CVSS `AC:H`
— but any deployment that stores the `regstack.secrets.env` alongside operator-writable files is
in scope.

**Action required:**
1. Bump `"pydantic-settings>=2.14.2"` in `pyproject.toml`.
2. Run `uv lock`.

## 🟡 INFO (Best practice recommendations)

### I-1 — `UserPublic.tokens_invalidated_after` and `phone_number` exposure (carry-forward)

`UserPublic` exposes `tokens_invalidated_after` (intentional — enables SPA bulk-revoke detection
client-side) and `phone_number` (design decision). Hosts with stricter PII requirements should
subclass `UserPublic` or add a projection step. No code change required in regstack itself.

### I-2 — `admin_promote_pending` path parameter not validated as `EmailStr` (carry-forward)

`POST /admin/pending/{email}/promote` (`src/regstack/routers/admin.py:204`) accepts
`email: str = Path(...)`. A syntactically invalid email address passes the parameter binding and
returns 404. The endpoint is admin-gated so the risk is low, but the fix is a one-liner:
`Annotated[EmailStr, Path(...)]`.

### I-3 — Duplicate tracking issue for python-multipart cluster (carry-forward)

Issues #118 (2026-06-23) and #120 (2026-06-24) both track the python-multipart floor bump. Issue
#120 should be updated to enumerate all four CVEs (CVE-2026-53537/53538/53539/53540); issue #118
should then be closed as a duplicate. This issue management task has not been completed since it
was first raised in the 2026-06-26 review.
