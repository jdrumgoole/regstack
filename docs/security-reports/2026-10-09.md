## Section 3 — Authentication and Authorization

### 🟠 W-2 · Email-change token not jti-blacklisted · day 39 (SLA expired +32 d)

Unchanged. `POST /confirm-email-change` (`src/regstack/routers/account.py:177`) decodes the email-change JWT, extracts `jti` from the claims, but never calls `blacklist.is_revoked(jti)` before processing nor `blacklist.revoke(jti, exp)` after success. A valid email-change link can be replayed until its TTL expires.

**Fix:** return `jti` and `exp` from `_decode_email_change_token`, check `await rs.blacklist.is_revoked(jti)` before proceeding, call `await rs.blacklist.revoke(jti, exp)` on success.

---

### 🟠 W-4 · OAuth new-user concurrent registration race → unhandled 500 · day 39 (SLA expired +32 d)

Unchanged. Concurrent OAuth sign-ins for a new email address can both pass the `find_by_subject` check, both attempt `users.create`, and one raises an unhandled `UserAlreadyExistsError`. The callback redirects to `?error=oauth_error` (generic 500 path) instead of the expected `?error=email_in_use` or a clean session token for the winner.

---

### 🟠 W-8 · Timing oracle on login for OAuth-only accounts · day 21 (SLA expired +14 d)

Unchanged. `hashed_password is None` short-circuits `pwdlib`'s `verify()` call with a direct `return False`, so an attacker can statistically distinguish OAuth-only from password-having accounts by measuring login response time (no hash work = faster 401).

---

### 🟠 W-13 · Admin `promote-pending` echoes unvalidated email path param · day 6 (SLA 2026-10-11 — **2 days remaining**)

Unchanged. `src/regstack/routers/admin.py:210` declares `email: str = Path(...)` in `admin_promote_pending` instead of `email: EmailStr = Path(...)`. A malformed value passes through without validation and is echoed unescaped in both the 404 response body (`f"No pending registration for {email}."`) and the 409 response body (`f"A user with email {email} already exists."`). **SLA expires 2026-10-11 — 2 days remaining.**

**Fix:** change `email: str = Path(...)` → `email: EmailStr = Path(...)` (add `from pydantic import EmailStr` if not already imported on that line's scope) in `src/regstack/routers/admin.py:210`.

## Section 5 — Input Validation

### 🟡 I-5 · TOML injection in `regstack init` wizard · day 6

Carry-forward. Free-form inputs (client ID, client secret) in `src/regstack/wizard/oauth_google/writer.py` are interpolated into TOML via f-string assignment to the `SECRETS_ENV_KEY` variable rather than going through tomlkit's key-value escaping. A value containing `\n` or `=` could break the secrets env file format. Low severity (developer-facing CLI, not a network path), but the pattern is wrong.

### 🟡 I-6 · `current_password` fields lack `max_length` · day 6

Carry-forward. `ChangePasswordRequest.current_password` and `DeleteAccountRequest.current_password` are plain `str` fields with no `max_length` constraint, allowing arbitrarily long payloads to reach Argon2. Recommended: `max_length=1024`.

### 🟡 I-7 · Token fields in confirm-flow models lack `max_length` · day 6

Carry-forward. `ConfirmEmailChangeRequest.token`, `ResetPasswordRequest.token`, and `VerifyRequest.token` are plain `str` with no upper bound. Recommended: `max_length=512`.

### 🟢 CLEAN — other input validation

All API inputs flow through Pydantic models. `EmailStr` on all email-bearing fields. E.164 phone validation via `is_valid_e164()`. Jinja2 autoescape on for all HTML email templates. No `| safe` filters in any SSR template. No `{% autoescape false %}` blocks. `_validate_redirect` in `routers/oauth.py` blocks backslash normalization attacks, protocol-relative URLs, and off-origin targets.

## Section 14 — OAuth Subsystem

### 🟢 CLEAN (flow integrity)

PKCE: `code_verifier` stored on `oauth_states` row only; only `code_challenge` (SHA-256 of verifier) sent to provider. State row lifecycle: missing row → `?error=bad_state`; expired row → `?error=state_expired` using `rs.clock.now()` (not `datetime.now(UTC)`). Mongo consume: `find_one_and_delete` (atomic). Identity uniqueness at DB level (`(provider, subject_id)` and `(user_id, provider)`). Hooks firing correctly. No changes.

### 🟠 W-6 · SQL `OAuthStateRepo.consume` non-atomic under READ COMMITTED · day 31 (SLA expired +24 d)

Unchanged. `src/regstack/backends/sql/repositories/oauth_state_repo.py` wraps SELECT + DELETE in `engine.begin()` (one transaction), but PostgreSQL's default READ COMMITTED isolation means a concurrent request can read the same row between the SELECT and DELETE, allowing two `/oauth/exchange` calls with the same state ID to both return a session token. Requires a `FOR UPDATE` lock on the SELECT or `SELECT … DELETE RETURNING` to be truly atomic.
