**Affected range:** `cryptography` ≥ 44.0.0, < 50.0.0
**Resolved in:** `cryptography==50.0.0` (released 2026-07-31 — 40 days ago)
**Current resolved version in `uv.lock`:** 49.0.0 (within affected range)
**Current floor in `pyproject.toml`:** `cryptography>=48.0.1` (does not exclude affected versions)
**Fix required:** Bump floor to `cryptography>=50.0.0` in both the `oauth` and `dev` extras in

**Tracking:** GitHub issue #181 (`[security] Raise cryptography floor to >=50.0.0`), open since

**Technical impact:** `pkcs7_decrypt_der`, `pkcs7_decrypt_pem`, and `pkcs7_decrypt_smime` expose

**Urgency:** The fix version has been on PyPI for 40 days. The 7-day SLA lapsed 2026-08-18 — now
15 days overdue. This finding will appear daily until resolved.

### W-2 (carry-over, day 9 — NEW 2026-09-01) — `POST /confirm-email-change` email-change JWT not revoked after use

**Section:** §3 — Authentication & Authorization Audit
**File:** `src/regstack/routers/account.py`, `confirm_email_change` handler
**Tracking:** GitHub issue #197, open since 2026-09-01 — 9 days unacknowledged.
**Status:** Unresolved. No code change in `account.py` since first flagged.

The `confirm_email_change` endpoint successfully updates the user's email address but does not
call `await rs.blacklist.revoke(token_payload.jti, token_payload.exp)` after doing so. The
password-reset path (`password.py`) correctly performs this revocation after every successful reset.
Within the email-change token's TTL, the same confirmation URL can be submitted repeatedly. Each
subsequent submission attempts `update_email`, which succeeds as a no-op when the address is already
the user's own, and the endpoint returns HTTP 200 — confirming the link is still usable.

The `_decode_email_change_token` helper currently returns only `(user_id, new_email)` and discards
the `jti` and `exp` claims. Any fix must thread these through to the caller so `blacklist.revoke()`
can be called after a successful `update_email`.

### W-3 (carry-over, day 9 — NEW 2026-09-01) — `POST /confirm-email-change` bulk-revoke not applied to email-change tokens

**Section:** §3 — Authentication & Authorization Audit
**File:** `src/regstack/routers/account.py`, `confirm_email_change` handler
**Tracking:** GitHub issue #198, open since 2026-09-01 — 9 days unacknowledged.
**Status:** Unresolved. No code change in `account.py` since first flagged.

If a user changes their password (bumping `tokens_invalidated_after`) after requesting an email
change, the already-issued email-change JWT should be treated as bulk-revoked. The current
`confirm_email_change` handler does not call
`is_payload_bulk_revoked(payload, user.tokens_invalidated_after)` after decoding the token and
fetching the user. The `_decode_email_change_token` helper also discards the `iat` claim, so the
comparison cannot be performed without extending the return signature.

The pattern mirrors the `_authenticate` dependency. Both W-2 and W-3 can be fixed in a single pass
through `confirm_email_change`.

### W-4 (carry-over, day 9 — NEW 2026-09-01) — OAuth `_resolve_user` unhandled `UserAlreadyExistsError` → HTTP 500

**Section:** §14 — OAuth Subsystem Audit
**File:** `src/regstack/routers/oauth.py`, `_resolve_user` (branch 4 — brand-new account creation)
**Tracking:** GitHub issue #199, open since 2026-09-01 — 9 days unacknowledged.
**Status:** Unresolved. No code change in `oauth.py` since first flagged.

In `_resolve_user`, branch 4 (new account via OAuth) calls `await rs.users.create(new_user)`.
`UserRepo.create` raises `UserAlreadyExistsError` (wrapping a `DuplicateKeyError` or
`IntegrityError`) when a concurrent request inserts the same email between the `get_by_email`
lookup and the `create` call. This exception propagates out of `_resolve_user` unhandled; the outer
`oauth_callback` catches only `_LinkConflictError`, so the race turns into an HTTP 500 — a
database error message may appear in FastAPI's default exception handler depending on host
configuration.

The fix is to catch `UserAlreadyExistsError` in the branch-4 block and raise
`_LinkConflictError("email_in_use")` instead, matching what the non-racy lookup returns.

### W-5 (carry-over, day 3 — NEW 2026-09-07) — `aiosmtplib` floor does not formally exclude CVE-2026-55558


**Section:** §1 — Dependency Vulnerability Check
**CVE:** CVE-2026-55558 — STARTTLS response injection in `aiosmtplib`
**Affected version:** `aiosmtplib==5.1.1`
**Resolved in:** `aiosmtplib==5.1.2`

**Technical impact:** aiosmtplib 5.1.1 does not discard buffered server data before the STARTTLS

within the vulnerable range. One-line fix.

### W-6 (NEW 2026-09-09) — SQL `oauth_states.consume()` is not atomic under Postgres

**Section:** §14 — OAuth Subsystem Audit / §4 — Storage-layer Safety
**File:** `src/regstack/backends/sql/repositories/oauth_state_repo.py`, `consume()` method
**Status:** NEW finding. Verified by code inspection.

The SQL `consume()` implementation reads the row then deletes it inside a single `engine.begin()`
transaction block, with no `SELECT FOR UPDATE`:

```python
async with self._engine.begin() as conn:
    row = (await conn.execute(select(self._t).where(...))).first()
    if row is None:
        return None
    await conn.execute(delete(self._t).where(...))
return _row_to_state(row)
```

Under Postgres's default `READ COMMITTED` isolation, two concurrent `POST /oauth/exchange`
requests with the same `state_id` can both execute the `SELECT` before either transaction
commits its `DELETE`. Both transactions read the row (including `result_token`) and proceed to
delete it — the second delete silently affects 0 rows but the transaction commits successfully.
Both callers return the `OAuthState` to their respective clients, potentially issuing two
independent session JWTs from a single OAuth callback.

By contrast, the MongoDB backend uses `find_one_and_delete` which is a single server-side atomic
operation and cannot exhibit this race. The code comment reads "Read + delete in one transaction
so a second concurrent /oauth/exchange call sees the row as already-gone" — this is correct for
serialized transactions but not for `READ COMMITTED` concurrent readers.

**Practical exploitability:** A legitimate browser makes one `/oauth/exchange` call. Exploitation
requires an attacker to make two simultaneous POST requests with the same `state_id` within the
exchange window (default 30 s after the callback). This could be achieved by a malicious browser
extension, client-side XSS, or a captured POST body. Under SQLite, the database-level write lock
serializes all transactions, so SQLite is unaffected. Only Postgres deployments with `asyncpg`
are at risk.

**Fix:** Replace the SELECT+DELETE pair with a single `DELETE ... RETURNING *` statement, which is
atomic at the database level and supported by both Postgres and SQLite ≥ 3.35 (the minimum SQLite
version under Python 3.11):

```python
stmt = delete(self._t).where(self._t.c.id == state_id).returning(*self._t.c)
async with self._engine.begin() as conn:
    row = (await conn.execute(stmt)).first()
return _row_to_state(row) if row else None
```

### W-7 (NEW 2026-09-09) — `POST /admin/users/{id}/resend-verification` creates a dead-end for unverified users already in the `users` table

**Section:** §3 — Authentication & Authorization Audit
**File:** `src/regstack/routers/admin.py`, `admin_resend_verification`; `src/regstack/routers/verify.py`, `verify`
**Status:** NEW finding. Verified by code inspection.

`admin_resend_verification` is designed to unblock unverified users by sending them a new
verification email. The implementation upserts a `PendingRegistration` row for the existing user
and sends the link. However, `POST /verify` always attempts to create a new user via
`await rs.users.create(user)`. Since the user already exists in the `users` table (that is the
premise — an unverified `users` row), `users.create()` raises `UserAlreadyExistsError`, which
`verify.py` catches and converts to HTTP 400 "This email is already registered. Please sign in."

The user cannot sign in because they remain `is_verified=False`. The admin endpoint sends a
verification email that will always fail, leaving the user permanently stuck unless an admin
calls `POST /admin/pending/{email}/promote` (or a direct `set_verified` call) as a separate
follow-on step — which is not documented in the endpoint's summary or error message.

The `verify.py` comment acknowledges the race with `promote_pending`: "An admin's `promote_pending`
call (or a duplicate `POST /verify` racing with itself) can have created the user between our
find-pending and now." This comment is about a different race; it does not address the case where
the user already existed before the admin called `resend-verification`.

**Fix (option A — preferred):** In `verify.py`, after catching `UserAlreadyExistsError`, check
whether the matching `users` row has `is_verified=False`. If so, call `rs.users.set_verified(user.id)`
to flip the flag and return `UserPublic.from_user(user)` instead of raising 400.

**Fix (option B):** Change `admin_resend_verification` to skip the `pending.upsert` step and
instead issue the verification email with a link to a dedicated admin-confirm endpoint that calls
`rs.users.set_verified()` directly.

### I-12 — `POST /register` returns 409 with explicit "email already registered" detail (§9, new)

`POST /register` returns HTTP 409 Conflict with "An account with that email already exists." for
duplicate emails. This deliberately differs from `POST /forgot-password` and
`POST /resend-verification`, which always return 202. The 409 body acts as an unauthenticated
email-existence oracle. This is a well-known and widely accepted trade-off (the UX value of "that
email is taken" is real), and the inconsistency with the forgot-password path appears intentional.
Documenting it explicitly alongside the anti-enumeration decisions on the other endpoints would
clarify that it is a conscious design choice, not an oversight.

### I-13 — `mfa_pending_token` JTI not explicitly blacklisted after `mfa-confirm` success (§7, new)

**File:** `src/regstack/routers/login.py`, MFA confirm handler

After a successful `POST /login/mfa-confirm`, the `mfa_pending_token`'s JTI is not added to the
blacklist repo. Single-use is enforced implicitly: the `mfa_codes` row is deleted on success, so a
second verification attempt returns the code-not-found error. This works, but the invariant is
invisible to future reviewers and differs from the `password_reset` token's explicit blacklisting
in `password.py`. Explicit blacklisting after first successful use would make the intent visible
and prevent any theoretical re-use window.

### I-14 — SQL `oauth_identities` table lacks a database-level FK constraint on `user_id` (§15, new)

**File:** `src/regstack/backends/sql/schema.py`

The `oauth_identities` table has no `FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE`.
Application code manually deletes identity rows before the user record in `account.py` and
`admin.py`. Any exception between the two deletes (network error, process crash) leaves orphan
identity rows. No auth bypass is possible from orphans (`get_by_id` returns None for a deleted
user), but orphans accumulate and could confuse future tooling. A FK with `ON DELETE CASCADE`
would provide defence in depth and remove reliance on deletion order in application code.

### I-15 — PKCE `code_verifier` stored in plaintext in `oauth_states` (§14, new)

**Files:** `src/regstack/backends/sql/schema.py`, `src/regstack/backends/mongo/repositories/oauth_state_repo.py`

The PKCE `code_verifier` is stored verbatim in `oauth_states`. PKCE was designed assuming the
verifier is known only to the original requester (a native or browser-based client); here it lives
in a server-side table. An attacker who exfiltrates the table during the state TTL window AND
captures the in-flight authorization code could complete the exchange independently. The short TTL
and the need to acquire both artifacts limits practical risk significantly. Storing the SHA-256
hash of the verifier instead (the `code_challenge` already sent to the provider) would be
defence in depth.
