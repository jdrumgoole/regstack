## 🟠 WARNING

### W-1 — CVE-2026-48710 (BadHost): Starlette 1.0.0 in lockfile

**Location:** `uv.lock` (starlette 1.0.0), `pyproject.toml` (fastapi>=0.120.0)

The `uv.lock` resolves to **Starlette 1.0.0**, which is the vulnerable version for
CVE-2026-48710 ("BadHost"). The vulnerability: a Host header containing `/`, `?`, or
`#` causes `request.url.path` to diverge from the ASGI-routed path, enabling
path-based auth middleware to be bypassed without authentication. The fix shipped
as Starlette 1.0.1 on 2026-05-21 — the same day as the most recent security
remediation commit (f5a0493) but evidently before the lockfile was regenerated.

**Impact on regstack itself:** regstack's own auth code does not use `request.url.path`
for any security decision. `_validate_redirect` (in `routers/oauth.py`) compares
against `config.base_url` (config-supplied), not `request.url`. FastAPI's router
reads `request.scope["path"]` internally, which comes directly from the ASGI server
and is not affected. No regstack endpoint uses `request.url` in a security-sensitive
way.

**Impact on host apps:** Any host application that layers auth middleware using
`request.url.path` is at risk if it installs regstack and resolves to Starlette 1.0.0.
Because `pyproject.toml` only pins `fastapi>=0.120.0`, there is no published floor
that guarantees Starlette 1.0.1+ to downstream consumers.

**Recommended actions:**
1. Regenerate the lockfile (`uv lock --upgrade-package starlette`) to pull in Starlette 1.0.1+.
2. Raise the fastapi lower bound in `pyproject.toml` to a version that transitively
   requires Starlette ≥1.0.1 (verify with `uv pip show starlette` after upgrading).
3. Add a note to `docs/security.md` advising host apps against using `request.url.path`
   in security middleware (use `request.scope["path"]` instead).

## 🟡 INFO

### I-1 — CVE-2026-48526: PyJWT 2.12.1 locked; algorithm confusion fixed in 2.13.0

**Location:** `uv.lock` (pyjwt 2.12.1), `pyproject.toml` (`pyjwt>=2.12.1`)

CVE-2026-48526 is an algorithm-confusion vulnerability fixed in PyJWT 2.13.0: when
a raw JWK JSON string is passed as the key AND the `algorithms` list mixes symmetric
and asymmetric families, an attacker can forge tokens signed with the public JWK as
an HMAC secret.

**Regstack is not directly exploitable** by this CVE:
- Internal JWTs (session, password reset, email change, login MFA, phone setup) use
  HMAC with raw `bytes` derived via `derive_secret()` — never a raw JWK string.
- Google ID-token verification specifies `algorithms=["RS256"]` only and uses a key
  object returned by `PyJWKClient`, not a raw JWK string.
- There is no code path in regstack that passes a JWK string with a mixed algorithm
  list.

**Recommended action:** Bump the lower bound to `pyjwt>=2.13.0` as defense-in-depth
and to keep regstack aligned with the latest security patches. Update uv.lock
accordingly.

### I-2 — JWT secret minimum length not enforced at construction

**Location:** `src/regstack/auth/jwt.py:118`, `src/regstack/app.py`

`JwtCodec.__init__` only checks `if not config.jwt_secret.get_secret_value()`,
rejecting empty strings but accepting secrets of any non-zero length. The security
review specification states "≥32 chars enforced at construction." A 1-character
HMAC-SHA256 key still produces valid-looking JWTs but reduces the brute-force
resistance of the signing key far below what HS256 can theoretically provide.

`regstack init` and `generate_secret()` both produce ≥64-character keys, so
production deployments set up via the wizard are safe. The gap is the programmatic
path where a host passes `jwt_secret="short"` directly; the library silently accepts
it.

**Recommended action:** Add a minimum-length guard in `JwtCodec.__init__` (32 chars
is a reasonable floor — it provides the full security of HMAC-SHA256):

```python
secret = config.jwt_secret.get_secret_value()
if not secret:
    raise ValueError("...")
if len(secret) < 32:
    raise ValueError(
        "jwt_secret must be at least 32 characters. "
        "Run `regstack init` to generate one."
    )
```

### I-3 — `tokens_invalidated_after` exposed in `UserPublic` (acknowledged)

**Location:** `src/regstack/models/user.py:105`, `docs/security.md:79`

`UserPublic` includes `tokens_invalidated_after`. This was previously flagged as
I-2 in the 2026-05-17 review and resolved via documentation in `docs/security.md`
(commit 9d3f5f1). The design is intentional: SPAs can compare this value against the
local session JWT's `iat` claim to detect bulk-revocation without polling `/me`. The
trade-off (revealing when the last bulk-revoke occurred) is documented. No further
action required.

### I-4 — PyPI version history cannot be verified from this environment

**Location:** PyPI / `src/regstack/version.py`

The git HEAD version (0.8.2) matches both `pyproject.toml` and `version.py`. Whether
any past regstack releases on PyPI have been yanked, and whether 0.8.2 is the
highest published version, could not be verified from within the CI container (no
outbound PyPI index access). Recommend a manual `pip index versions regstack` check
before each release to confirm no out-of-band publish has occurred.

### §14 — OAuth Subsystem Audit

**14a — PKCE:** `code_verifier` generated server-side (`secrets.token_urlsafe(64)`),
stored on the `OAuthState` row, never included in the redirect URL. Only the
`code_challenge` (SHA-256 of the verifier, base64url-encoded) goes to the provider. ✓

**14b — State row lifecycle:** Missing row → `bad_state`; expired row → `state_expired`
(comparison uses `rs.clock.now()`). Consume is atomic: MongoDB uses `find_one_and_delete`;
SQL uses a `begin` transaction with select + delete. A second `/oauth/exchange` with
the same `id` returns 404. ✓

**14c — ID-token verification:** Signature via `PyJWKClient`, `iss` == Google issuer,
`aud` == `client_id`, `exp` validated by pyjwt, `nonce` compared. Algorithm pinned
to `["RS256"]`. Any failure raises `OAuthIdTokenError` with generic outer message
(full reason logged at WARNING only). ✓

**14d — Linking-policy enforcement:** Email-clash without `auto_link_verified_emails`
→ `email_in_use`. Identity linked to different user → `identity_in_use`. Same user
re-linking same identity → `already_linked`. `auto_link_verified_emails` only fires
when the ID token's `email_verified=true`. ✓

**14e — OAuth-only user side effects:** `DELETE /oauth/{provider}/link` returns 400
when user has no password and this is the only linked identity. ✓

**14f — Identity-row uniqueness:** Both `(provider, subject_id)` and `(user_id, provider)`
have database-level UNIQUE constraints in SQL (SQLAlchemy `UniqueConstraint`) and
Mongo (`provider_subject_unique`, `user_provider_unique` indexes). ✓

**14g — Hooks:** `oauth_signin_started`, `oauth_signin_completed`, `oauth_account_linked`,
`oauth_account_unlinked` all present in `hooks/events.KNOWN_EVENTS` and fired at the
correct points in `routers/oauth.py`. ✓
