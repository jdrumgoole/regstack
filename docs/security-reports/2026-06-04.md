## 🔴 CRITICAL

### C-1 — Starlette 1.0.0 locked; CVE-2026-48710 (BadHost) requires ≥ 1.0.1

**File:** `uv.lock` (locked `starlette = "1.0.0"`)
**CVE:** CVE-2026-48710 · GHSA-86qp-5c8j-p5mr · Disclosed 2026-05-22

Starlette < 1.0.1 does not validate the HTTP `Host` header before using it to
reconstruct `request.url`. Because Starlette's routing algorithm matches routes
against the raw path while `request.url` is rebuilt from the `Host` header, a
crafted `Host` value can cause `request.url.path` to diverge from the path that
was actually routed. Any middleware or endpoint that makes security decisions
based on `request.url.path` rather than `request.scope["path"]` is exposed to an
authentication bypass.

regstack's own auth checks are JWT-based and do not read `request.url.path` for
access control, which limits the direct impact inside the library's own routers.
However:

- Every host application that embeds regstack and uses `request.url.path` in its
  own middleware (e.g. an IP-allowlist, a scoped API guard, a WAF shim) inherits
  the vulnerable Starlette.
- The published PyPI wheel ships with `starlette` as a transitive dependency at
  exactly 1.0.0 today; downstream consumers running `pip install regstack` will
  pull in the vulnerable version until this is resolved.
- Starlette 1.0.1 (the fix) was released 2026-05-21, one day before public
  disclosure. FastAPI 0.136.1 (the locked version) predates the fix but works
  with Starlette 1.0.1.

**Remediation:**

1. Immediately run `uv lock --upgrade-package starlette` to resolve to ≥ 1.0.1.
2. Add `starlette>=1.0.1` as an explicit lower bound in `pyproject.toml`
   `[project.dependencies]` (FastAPI already bundles starlette, but an explicit
   floor ensures future `uv lock` runs cannot silently regress).
3. Release a patch version (0.8.3) that carries the updated lock so downstream
   consumers who pin `regstack` also get the fix.
4. Advise host application authors to audit any middleware that reads
   `request.url.path` and replace with `request.scope["path"]`.

## 🟠 WARNING

### W-1 — OAuth state `consume()` not atomic under PostgreSQL READ COMMITTED

**Files:** `src/regstack/backends/sql/repositories/oauth_state_repo.py`

The SQL `consume()` method reads the state row then deletes it within a single
transaction:

```python
async with self._engine.begin() as conn:
    row = (await conn.execute(select(self._t).where(self._t.c.id == state_id))).first()
    if row is None:
        return None
    await conn.execute(delete(self._t).where(self._t.c.id == state_id))
```

Under PostgreSQL's default `READ COMMITTED` isolation, two concurrent requests
that arrive with the same `state_id` can both execute the `SELECT` before either
`DELETE` commits. Both reads succeed; both functions return the state row (and its
`result_token` session JWT); only the first `DELETE` removes the row — the second
deletes 0 rows but still returns the previously-read data. This breaks the
single-use guarantee of the OAuth exchange endpoint.

Preconditions for exploitation:
- Attacker must know the `state_id` (a 32-byte URL-safe random string visible in
  the `/account/oauth-complete?id=<state_id>` URL during the completion window).
- The race window is bounded by `oauth.completion_ttl_seconds` (default 30 s).

MongoDB's `find_one_and_delete()` in `MongoOAuthStateRepo.consume()` is atomic
and is not affected. SQLite is also safe (file-level serialisation).

**Remediation:** Replace the SELECT + DELETE sequence with a `DELETE … RETURNING
*` statement for PostgreSQL (atomic by definition); for SQLite, the existing
approach is safe. Alternatively, use `SELECT … FOR UPDATE` to lock the row before
deleting it. Example:

```python
from sqlalchemy import delete
from sqlalchemy.dialects.postgresql import insert  # not needed, just use delete+returning

# PostgreSQL-safe atomic consume:
stmt = delete(self._t).where(self._t.c.id == state_id).returning(*self._t.c)
async with self._engine.begin() as conn:
    row = (await conn.execute(stmt)).first()
return _row_to_state(row) if row else None
```

This approach works on both PostgreSQL and SQLite (SQLAlchemy maps `RETURNING` to
the appropriate dialect).

### W-2 — `PyJWKClient` has no HTTP timeout; worker-thread exhaustion risk

**File:** `src/regstack/oauth/providers/google.py:83`

```python
self._jwks_client = PyJWKClient(jwks_url, cache_keys=True)
```

`PyJWKClient` uses synchronous `urllib.request.urlopen` internally. The 2026-05-20
review (I-2) correctly moved the JWKS fetch to `asyncio.to_thread` so it no longer
blocks the event loop. However, no `timeout` argument is passed to `PyJWKClient`,
so each JWKS cache-miss fetch uses `urllib`'s OS-level default (can be several
minutes on some systems).

If Google's JWKS endpoint becomes slow or unreachable, a burst of OAuth sign-ins
during the outage can exhaust the asyncio thread-pool executor, degrading all
concurrent async operations for the process — including non-OAuth endpoints.

PyJWT ≥ 2.8 accepts `PyJWKClient(..., timeout=N)`.

**Remediation:**

```python
self._jwks_client = PyJWKClient(jwks_url, cache_keys=True, timeout=10)
```

A 10-second timeout is consistent with the explicit `httpx.AsyncClient(timeout=10.0)`
already used for the token exchange in the same file.

## 🟡 INFO

### I-1 — `UserPublic` exposes `tokens_invalidated_after`

**File:** `src/regstack/models/user.py:105`

`UserPublic` (the public projection returned by `/me`, admin endpoints, etc.)
includes the `tokens_invalidated_after` field. This is intentional — the model
docstring explains it allows SPAs to detect session invalidation client-side
without a round-trip. The trade-off is documented in `CLAUDE.md` and
`docs/security.md`.

Residual concern: the field leaks the exact UTC timestamp of the most recent
password change, email change, or administrative session revocation. An attacker
with read access to the API response can determine *when* a sensitive account
operation occurred. This is a defence-in-depth gap, not an exploitable
vulnerability.

Recommendation: document in `SECURITY.md` that this field is intentional and
note that host applications that need to hide this information can project it out
of the `UserPublic` response in their own endpoint wrappers.

### I-2 — `aiosmtplib` lower bound in `pyproject.toml` lags the lock by two major versions

**File:** `pyproject.toml:39`

`pyproject.toml` declares `aiosmtplib>=3.0` but the lock resolves to 5.1.0.
Consumers who install regstack without locking will receive 5.x; a minimum bound
of 3.0 still permits older versions that may have API and security differences.
This also makes the lower-bound comment misleading for anyone reading the
dependency declaration.

Recommendation: bump to `aiosmtplib>=5.0` to match the actual tested baseline and
prevent inadvertent resolution to an untested older major.

### I-3 — Jinja2 pinned to CVE-fix floor exactly (3.1.6)

**File:** `pyproject.toml:31`

`jinja2>=3.1.6` was chosen to capture the CVE-2025-27516 fix. 3.1.6 is the
current latest release. No new Jinja2 CVEs were identified in the 90-day search
window for 2026. This finding is advisory: if a post-3.1.6 Jinja2 vulnerability
is disclosed, the minimum bound would not protect consumers who pin at the floor.
`uv.lock` ensures the exact version used in CI and the published wheel, so the
risk is limited to consumers who install the package without locking.

No action required today; monitor Jinja2 release notes.

### I-4 — `cryptography` 47.0.0 installed; latest is 48.0.0 per Snyk

**Files:** `uv.lock` (`cryptography = "47.0.0"`), `pyproject.toml:54` (`>=46.0.7`)

All three 2026-era cryptography CVEs (CVE-2026-26007, CVE-2026-34073,
CVE-2026-39892) were fixed in 46.0.5–46.0.7. The locked 47.0.0 covers all of
them. No open advisory against 47.0.x was found in the search window. The latest
available release is 48.0.0; upgrading keeps the gap to the security-release
frontier smaller.

Recommendation: run `uv lock --upgrade-package cryptography` to move to 48.x
at the next routine dependency update cycle.

### I-5 — `pyjwt` 2.12.1 — pip-audit false-positive risk

**File:** `uv.lock` (`pyjwt = "2.12.1"`)

pip-audit has been observed (github.com/jpadilla/pyjwt/issues/1168) flagging
PyJWT 2.12.1 with PYSEC-2025-183 despite the advisory being fixed in 2.12.0.
This is a false positive in the pip-audit database, not an actual vulnerability.
CVE-2026-32597 (`crit` header bypass) is fixed in 2.12.0 and 2.12.1 ships the
correct fix. If CI adds pip-audit, suppress this finding with a per-package
ignore rule rather than inadvertently downgrading.
