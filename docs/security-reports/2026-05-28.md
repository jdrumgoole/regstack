## 🟠 WARNING (Address within 1 week)

### W-1 — PyJWKClient missing explicit timeout (carried from 2026-05-22; still open)

**Location:** `src/regstack/oauth/providers/google.py:83`

```python
self._jwks_client = PyJWKClient(jwks_url, cache_keys=True)
```

No `timeout` argument is passed to `PyJWKClient`. The JWKS fetch call
(`urllib.request.urlopen`) has no explicit deadline, meaning a slow or
non-responsive Google JWKS endpoint can hold the `asyncio.to_thread`
worker thread indefinitely. Python's asyncio thread pool is bounded
(`min(32, os.cpu_count() + 4)` threads); exhausting it blocks all
`to_thread` calls for the entire application.

The 2026-05-20 review's PR #80 correctly offloaded the blocking call to
`asyncio.to_thread`, but did not add a timeout. This remaining gap has
appeared in the 2026-05-20, 2026-05-21, and 2026-05-22 reviews without
being acted on. Escalating from prior INFO/WARNING to **still-WARNING**.

**Fix** (one line):

```python
self._jwks_client = PyJWKClient(jwks_url, cache_keys=True, timeout=5)
```

`PyJWKClient` has accepted a `timeout` keyword argument since pyjwt 2.4;
the project floor is `pyjwt>=2.12.1`.

## 🟡 INFO (Best practice recommendations)

### I-1 — `was_new_account` always `False` in OAuth exchange response (carried from 2026-05-22)

**Location:** `src/regstack/routers/oauth.py:176`

The `was_new` boolean is correctly computed in `_resolve_user` during the
callback, but is not persisted to the `oauth_states` row, so the
`/oauth/exchange` endpoint hard-codes `was_new_account=False`. SPAs using
this field for a "Welcome! Account created." message will never see `True`.
This is an API accuracy gap, not a security issue. Fix: add a
`result_was_new: bool` column to `oauth_states` and populate it in the
callback.

were identified in the 2026-05-22 review. Public write-ups remain sparse.
The current `fastapi>=0.120.0` floor addresses the prior high-severity

### I-3 — OAuth token-exchange response body logged at WARNING (carried from 2026-05-22)

**Location:** `src/regstack/oauth/providers/google.py:143–145`

```python
raise OAuthTokenExchangeError(
    f"google token exchange failed: {response.status_code} {response.text}"
)
```

This is caught in the router and logged at `WARNING`. No client-visible leak
exists and Google's error bodies don't contain secrets, but `response.text`
(potentially multi-KB JSON) appears in every warning log entry for a failed
token exchange. Suggestion: log status code at `WARNING`, response body at
`DEBUG`.

### I-4 — `jwt_secret` minimum length not enforced at construction

**Location:** `src/regstack/auth/jwt.py:118–122`, `src/regstack/config/schema.py:290–295`

The `JwtCodec` constructor raises `ValueError` on an empty secret but has no
minimum-length check. A 1-character secret (`REGSTACK_JWT_SECRET=x`) is
accepted silently. The `_warn_empty_secret` config validator also does no
length validation (by design — it documents that tests can opt out). The
`generate_secret()` helper and `regstack init` wizard produce 64-byte
URL-safe secrets (~85 chars), so the risk only materialises when someone
manually sets a very short secret. The 2026-05-22 review's §7 CLEAN section
incorrectly stated "≥32 chars enforced at `JwtCodec` construction"; this
review corrects that record.

**Suggested fix:** Add a minimum-length guard in `JwtCodec.__init__`:

```python
secret = config.jwt_secret.get_secret_value()
if not secret:
    raise ValueError(...)
if len(secret) < 32:
    raise ValueError(
        "jwt_secret is shorter than 32 characters. Use `regstack init` or "
        "set REGSTACK_JWT_SECRET to a value of at least 32 random characters."
    )
```

This does not break tests that currently pass an empty secret via
`FrozenClock`-style fixtures (those already bypass `RegStack.__init__`
directly), but would catch accidental short-secret deployments early.

1. `text("SELECT 1")` in `SqlBackend.ping()` — no user input.
2. `sa.text("SELECT COUNT(*) FROM users WHERE hashed_password IS NULL")` in

`UtcDateTime` TypeDecorator in `backends/sql/types.py` consistently

`purge_expired()` on every SQL repo uses parameterized cutoff timestamps;
no string interpolation.

### §6 — Rate Limiting & DoS Prevention

- `LockoutService.check()` fires at the top of the login handler, before
  user lookup or password verification. A locked account always returns 429
  with `Retry-After`.
- `record_failure` is called for all pre-active-user failure branches (not
  found, wrong password, disabled, unverified), so a locked-out attacker
  can't distinguish account states by whether the counter increments.
- `login_attempts` Mongo TTL index sized to
  `login_lockout_window_seconds`; SQL backend `purge_expired()` provides
  equivalent reaping.
- Admin user listing (`GET /admin/users`): `limit` capped with
  `Query(ge=1, le=200)`.
- OAuth `state` rows: 5-minute default TTL (`state_ttl_seconds=300`),
  enforced via Mongo TTL index and SQL `purge_expired()`.
- No file-upload endpoints exist.

### §7 — Session & Token Security

- JWT algorithm: HS256 by default (configurable as HS384, HS512).
- `JwtCodec.__init__` raises `ValueError` on an empty `jwt_secret`.
  (See I-4 for the missing minimum-length enforcement.)
- Every JWT carries a unique `jti` generated with
  `secrets.token_urlsafe(16)`.
- `iat` emitted as a `float` (RFC 7519 NumericDate allows non-integers),
  enabling sub-second precision in the `iat <= cutoff` bulk-revoke
  comparison — a login completing microseconds after a password change
  has a strictly-greater `iat` and is not falsely revoked.
- pyjwt's `exp`/`iat`/`nbf` automatic checks are disabled;
  expiry is validated manually against the injected `Clock` (not
  `time.time()`), preserving `FrozenClock` test determinism.
- `_authenticate` validates in this order: decode → blacklist (`jti`) →
  active user lookup → bulk-revoke cutoff (`iat <= tokens_invalidated_after`).
- Token decode errors → static "Invalid or expired token." 401; no
  pyjwt exception text echoed.
- Password-reset tokens blacklisted on first use (prevents replay of
  captured reset links).

### §14 — OAuth Subsystem Audit

- **PKCE:** `code_verifier` generated with `secrets.token_urlsafe(64)`,
  stored on the state row. Only `code_challenge = base64url(sha256(verifier))`
  sent to the provider. Verifier never appears in any redirect URL.
- **State row lifecycle:** Mongo uses `find_one_and_delete` (atomic); SQL
  uses SELECT + DELETE inside `engine.begin()` (atomic). A second
  `/oauth/exchange` call with the same `id` returns 404. Expiry checked
  against `rs.clock.now()`.
- **ID-token verification:** RS256 via `PyJWKClient`, validates `iss`,
  `aud`, `exp`, `nonce`. Failure raises `OAuthIdTokenError`; detail
  logged, not echoed to the redirect.
- **Linking policy:** Existing-email sign-in → `email_in_use` unless
  `auto_link_verified_emails=True` AND `email_verified=True`. Already-linked
  identity on different user → `identity_in_use`. Same identity same user
  → `already_linked`. Last sign-in method unlink → 400.
- **OAuth-only users:** `POST /login` → generic 401;
  `change-password`/`change-email`/`delete-account` → 400 via
  `require_password_set()`.
- **Identity uniqueness:** `(provider, subject_id)` UNIQUE and `(user_id,
  provider)` UNIQUE enforced at DB level on both backends.
- **Hooks:** `oauth_signin_started`, `oauth_signin_completed`,
  `oauth_account_linked`, `oauth_account_unlinked` all present in
  `KNOWN_EVENTS` and fired at correct points.
