## 🟠 WARNING (Address within 1 week)

### W-1 · CVE-2026-42561 — python-multipart DoS via unlimited part-header parsing

**File:** `pyproject.toml`, line `"python-multipart>=0.0.26"`
**CVE:** [CVE-2026-42561](https://cve.threatint.eu/CVE/CVE-2026-42561)

`MultipartParser` in python-multipart < 0.0.27 imposes no limit on the
number or cumulative size of individual part headers inside a multipart
request. An attacker sends a request with thousands of repeated headers
(or one very large header value) without a terminator, causing the parser
to consume unbounded CPU/memory before rejecting the request. The current
floor `>=0.0.26` covers the earlier CVE-2026-40347 (preamble/epilogue DoS)
but does **not** include the 0.0.27 fix for part-header exhaustion.

The active latest is 0.0.28 (2026-05-10). While regstack's own endpoints
use JSON bodies exclusively, `python-multipart` is a declared core
dependency (required by FastAPI for any form-data processing path in the
host app), so every regstack consumer inherits this floor.

**Remediation:** In `pyproject.toml`, change:

```toml
# python-multipart>=0.0.26 picks up CVE-2026-40347 ...
"python-multipart>=0.0.26",
```

to:

```toml
# python-multipart>=0.0.27 picks up CVE-2026-40347 (DoS via oversized
# multipart preamble/epilogue) and CVE-2026-42561 (DoS via unlimited
# part-header count/size).
"python-multipart>=0.0.27",
```

## 🟡 INFO (Best practice recommendations)

### I-1 · Eight Mongo set_* methods call ObjectId() without is_valid() guard

**File:** `src/regstack/backends/mongo/repositories/user_repo.py`, lines 63–141

`get_by_id()` and `delete()` correctly call `ObjectId.is_valid(user_id)`
before converting, returning `None`/`False` on invalid input. However,
eight mutation methods — `set_last_login`, `set_tokens_invalidated_after`,
`update_password`, `set_active`, `set_superuser`, `set_full_name`,
`set_phone`, `set_mfa_enabled`, `update_email` — call `ObjectId(user_id)`
directly without the guard. There is no current exploit path because all
call sites receive `user.id` which was already validated by `get_by_id`,
but a future call with raw external input would raise an uncaught
`bson.errors.InvalidId` (500, not 404).

**Remediation:** Add `if not ObjectId.is_valid(user_id): return` (or raise
a clear error) at the top of each affected method to match the existing
pattern in `get_by_id` and `delete`.

### I-2 · /login/mfa-confirm and /oauth/exchange absent from per-IP rate-limit map

**File:** `src/regstack/auth/rate_limit.py`, `ROUTE_LIMIT_MAP`

The per-route IP rate-limiting configuration (`rate_limit` extra +
`slowapi`) covers `/login` and the registration/verification endpoints
but does not include `/login/mfa-confirm` or `/oauth/exchange`. The
`mfa_codes` attempt counter (bounded by `sms_code_max_attempts`) provides
per-code protection against brute-force on the 6-digit SMS code, and the
`mfa_pending_token` expiry limits the attack window. These are meaningful
controls. A per-IP throttle on these two endpoints would add defence-in-
depth against distributed guessing campaigns from multiple source IPs.

**Remediation:** Add default rate-limit strings for these paths to
`ROUTE_LIMIT_MAP` (or document that they are intentionally omitted and
rely solely on the per-code attempt counter).

### I-3 · OAuth callback logs provider-controlled error string without sanitization

**File:** `src/regstack/routers/oauth.py`, line 282

```python
log.info("oauth callback error from provider %s: %s", provider_name, error)
```

The `error` query parameter originates from the OAuth provider redirect
and is attacker-controlled. A compromised or malicious provider could
inject newlines or ANSI escape sequences into the server's log stream
(log injection). The redirect correctly uses the hardcoded string
`"oauth_failed"` rather than echoing `error` to users, so there is no
API-level injection. The risk is confined to log integrity.

**Remediation:** Sanitize before logging:
```python
safe_error = (error or "")[:200].replace("\n", " ").replace("\r", " ")
log.info("oauth callback error from provider %s: %s", provider_name, safe_error)
```

### I-4 · Migration 0002 downgrade() comment promises a NULL guard that is not implemented

**File:** `src/regstack/backends/sql/migrations/versions/0002_oauth.py`, lines 79–91

The `downgrade()` docstring says "Refuse to roll back a NULL→NOT NULL column
if any OAuth-only users exist", but the implementation performs the
`ALTER COLUMN … NOT NULL` unconditionally. On PostgreSQL this raises a
constraint violation at runtime if OAuth-only users exist (a noisy but
safe failure). On SQLite, `batch_alter_table` silently succeeds because
SQLite ignores NOT NULL constraints during the CREATE-COPY-DROP-RENAME
sequence — meaning the downgrade would complete without error even with
data that violates the constraint.

**Remediation:** Add a pre-check to the downgrade:
```python
def downgrade() -> None:
    import sqlalchemy as _sa
    conn = op.get_bind()
    count = conn.execute(
        _sa.text("SELECT COUNT(*) FROM users WHERE hashed_password IS NULL")
    ).scalar()
    if count:
        raise RuntimeError(
            f"Cannot downgrade: {count} OAuth-only user(s) with NULL hashed_password exist."
        )
    with op.batch_alter_table("users") as batch_op:
        ...
```

### I-5 · oauth_states.mode validity not enforced at database level in MongoDB

**File:** `src/regstack/backends/sql/schema.py` vs `src/regstack/backends/mongo/indexes.py`

The SQL schema includes `CheckConstraint("mode IN ('signin', 'link')",
name="ck_oauth_states_mode_valid")`. The MongoDB backend has no equivalent
constraint — only `OAuthState.model_validate()` at the application layer
enforces this. This is a minor parity gap; `model_validate()` runs on
every read so no invalid value survives to a router, but it is not
enforced at the storage layer.

**Remediation:** Add a `$jsonSchema` validator on the `oauth_states`
collection in `install_indexes`, or document the app-layer enforcement as
intentional.

### I-6 · tokens_invalidated_after included in UserPublic API response

**File:** `src/regstack/models/user.py`, line 99

`UserPublic` (the API response model) includes `tokens_invalidated_after`.
The docstring explains the intent — SPAs can compare this value to the
local JWT's `iat` to detect invalidation without polling. The tradeoff is
that the exact timestamp of the last password change / email change /
admin-disable is visible to any caller holding a valid session token,
including a stolen one. An attacker holding a victim's token can learn
when the account was last affected by a bulk-revoke event.

This is a documented design choice, not a vulnerability. Document it
explicitly in `docs/security.md` so host integrators understand the
trade-off and can decide whether to expose or suppress this field via a
custom `UserPublic` projection.

### I-7 · transport = "cookie" config option silently accepted but never implemented

**File:** `src/regstack/config/schema.py`, `TokenTransport = Literal["bearer", "cookie"]`

The `cookie` transport value is accepted by the config model and `cookie_domain`
is a valid config field, but `AuthDependencies._authenticate` reads only
`HTTPBearer` tokens — no `Set-Cookie` response headers are ever set. A
host that configures `transport = "cookie"` would receive a silent no-op
rather than cookie-based auth. This risks a security misconfiguration if
a host expects cookie transport.

**Remediation:** Either implement cookie transport, or change the config
type to `Literal["bearer"]` and document cookie support as a future
milestone.

### I-8 · No sigstore attestations on PyPI publish

**File:** `.github/workflows/publish.yml`, line 82 (`pypa/gh-action-pypi-publish`)

The publish workflow uses OIDC trusted publishing (correct — no API token)
but does not set `attestations: true` on the `pypa/gh-action-pypi-publish`
action. Sigstore attestations would cryptographically bind the published
wheel to this specific GitHub Actions run, allowing consumers to verify
that the wheel came from regstack's CI rather than a compromised PyPI
account. PyPI supports PEP 740 attestations natively.

**Remediation:**
```yaml
- uses: pypa/gh-action-pypi-publish@cef221092ed1bacb1cc03d23a2d87d1d172e277b
  with:
    attestations: true
```

### I-10 · publish.yml workflow_dispatch allows build runs without a tag

**File:** `.github/workflows/publish.yml`, line 17

The `on: workflow_dispatch:` trigger lets any repository maintainer run
the build job manually without a `v*` tag push. The `publish` job is
correctly guarded with `if: startsWith(github.ref, 'refs/tags/v')`, so

to enforce the documented "tag triggers publish" intent, or add the same
`if:` guard to the `build` job.

and the version floors are accurate. No additional unaddressed CVEs found

### §2 Hardcoded secrets
No API keys, connection strings with credentials, private key material, or
JWT blobs found in `src/`, `tests/`, or `examples/`. Only
`src/regstack/config/secrets.py` appears in `git ls-files` with

### §3 Authentication and authorization
- Every state-mutating authenticated endpoint injects `current_user` or
  `current_admin`. No unauthenticated mutation endpoints exist that are
  not protected by a purpose-scoped signed JWT (password-reset, email-change,
  phone-setup).
- Bulk-revoke discipline is correct at all five required sites:
  `change-password`, `reset-password`, `confirm-email-change`,
  admin `PATCH {is_active: false}`, and account deletion.
- Account deletion correctly cascades `oauth_identities.delete_by_user_id`
  before `users.delete` in both the user-initiated and admin-initiated flows.
- OAuth-only users (`hashed_password=None`) receive the same generic 401
  as a wrong-password attempt at `/login` — no account enumeration.
- `require_password_set()` raises 400 (not 401) for OAuth-only users on
  change-password, change-email, delete-account, and phone routes — the
  auth context is already established so 400 is appropriate.
- Admin list endpoint caps `limit` at 200 via `Query(ge=1, le=200)`.
- All endpoints return `UserPublic` projection; `hashed_password` is never
  serialised to API responses.

### §4 Storage-layer injection (MongoDB)
No `$where`, `$expr`, `$function`, or `$accumulator` operators used
anywhere. All query filters use literal field equality or `ObjectId`
lookups. No regex patterns built from user input. `get_by_id()` and
`delete()` call `ObjectId.is_valid()` before converting (see I-1 for
the eight set_* methods that are caller-validated). No `$in` arrays
accept user-supplied unbounded input.

### §4 Storage-layer injection (SQL)
All queries use SQLAlchemy Core with parameterised binds. No f-string
or `%`-interpolation into raw SQL detected. `UtcDateTime` TypeDecorator
correctly re-attaches UTC timezone on every read in
`src/regstack/backends/sql/types.py`. `purge_expired()` implementations
use bound parameters for the cutoff timestamp.

### §5 Input validation
- Every API endpoint uses a Pydantic model with `extra="forbid"`.
- `EmailStr` used on all email-bearing request fields.
- `is_valid_e164()` called before phone number storage and SMS dispatch.
- All Jinja2 environments have `select_autoescape(["html"])` — no `| safe`
  filters or `{% autoescape false %}` blocks anywhere in UI or email templates.

### §6 Rate limiting
- `LockoutService.check()` fires before password verification in the
  login route, blocking all probing before any DB user lookup.
- Even with the correct password, disabled/unverified accounts increment
  the lockout counter to prevent credential-stuffing via account-status
  enumeration.
- MongoDB `login_attempts` TTL index is sized to `login_lockout_window_seconds`.
- SQL backends use `purge_expired()` reaper + read-side filter.
- `rate_limit_disabled=True` short-circuits the lockout only in tests.

### §7 Session and token security
- `JwtCodec` disables pyjwt's `exp`/`iat` checks and validates both
  claims against the injected `Clock`. `FrozenClock`-driven tests get
  consistent behaviour without `time.sleep`.
- `iat` is emitted as a float (`self.iat.timestamp()`) — sub-second
  precision allows a login microseconds after a password change to have
  `iat > cutoff` and survive bulk revocation.
- Every JWT includes `jti` (16-byte URL-safe random). Per-token revocation
  via `BlacklistRepo` is therefore always available.
- JWT algorithm restricted to `Literal["HS256", "HS384", "HS512"]`;
  algorithm `none` is not configurable.
- `_authenticate` checks: decode → blacklist `jti` → user active →
  bulk-revoke cutoff, in that order. Any failure returns generic 401 with
  no pyjwt error text echoed.
- `PyJWKClient` (Google JWKS) has a 30-second default timeout in pyjwt 2.12.1.
  No explicit override needed.

### §8 CSP and the SSR layer
- No `<style>` blocks or `style="..."` attributes in any UI template.

- No inline `<script>` tags. `regstack.js` loaded via `<script src defer>`.
- `oauth_complete.html` follows the same discipline.
- SSR pages are stateless — no `{{ user.email }}` or similar auth state
