### W-1 — Four CVEs in `python-multipart <0.0.32` (DoS + smuggling cluster) — **carry-forward, expanded**

**Package:** `python-multipart`
**Floor:** `>=0.0.27` · **Resolved:** `0.0.28` · **Latest safe:** `0.0.32`
**Tracked:** GitHub issues #118 (2026-06-23) and #120 (2026-06-24, duplicate)

Previous reviews cited only CVE-2026-53539. Three additional CVEs share the same `<0.0.30`/`<0.0.31` fix boundary:

| CVE | CVSS | Fixed in | Description |
|---|---|---|---|
| CVE-2026-53539 | **7.5 High** | 0.0.30 | `QuerystringParser` processes `application/x-www-form-urlencoded` bodies with an O(B²) algorithm when `;` is used as the field separator. A crafted body of many semicolons stalls a worker on pure-CPU work, enabling unauthenticated DoS. |
| CVE-2026-53540 | 3.7 Low | **0.0.31** | `parse_form()` does not validate `Content-Length` before bounding its chunked read. A negative `Content-Length` turns the bounded read into a read-until-EOF, loading the entire request body into memory — unbounded memory allocation DoS. |
| CVE-2026-53538 | 3.7 Low | 0.0.30 | `QuerystringParser` treats `;` as a field separator alongside `&`, differing from the WHATWG URL standard. A WAF sees `role=user&x=;role=admin` as two fields; python-multipart sees three — enabling field smuggling. |
| CVE-2026-53537 | 3.1 Low | 0.0.30 | `parse_options_header` used `email.message.Message` which applies RFC 2231/5987 decoding. Components that don't (WAFs, proxies) see a different field name, enabling `Content-Disposition` smuggling. |

CVE-2026-53540 requires `>=0.0.31`; the others require `>=0.0.30`. Current latest is `0.0.32`.

**Action required:**
1. Bump floor to `python-multipart>=0.0.32` in `pyproject.toml`. Update the inline CVE comment to enumerate all four CVEs.
2. Run `uv lock`.
3. Update issue #120 to include all four CVEs; close duplicate #118.

### W-3 — GHSA-537c-gmf6-5ccf / CVE-2026-45447: `cryptography` bundled OpenSSL heap UAF (CVSS 7.5 High) — **new**

**Package:** `cryptography` (in `oauth` optional extra: `cryptography>=46.0.7`)
**Resolved:** `47.0.0` · **Fixed in:** `48.0.1`
**Published:** June 9, 2026 (GitHub Advisory Database: GHSA-537c-gmf6-5ccf)
**Not present in any prior review**

PyPI wheels for `cryptography` bundle a statically-linked OpenSSL. All wheels in the range `>=0.5.0, <48.0.1` bundle an OpenSSL version vulnerable to CVE-2026-45447: a heap use-after-free in `PKCS7_verify()` triggered by a crafted PKCS#7/S/MIME message with an empty `digestAlgorithms` field. This can cause process crashes, heap corruption, and potentially remote code execution.

**Exposure for regstack:** regstack uses `cryptography` (via the `oauth` extra) for Google OAuth ID-token signature verification via `PyJWKClient` — an RSA/EC key path that does not call `PKCS7_verify()` directly. However:
- The `oauth` optional extra declares `cryptography>=46.0.7`, which allows resolution of `47.0.0` (vulnerable).
- Downstream hosts that install `regstack[oauth]` will resolve a vulnerable wheel unless the floor is raised.
- Hosts that also use `cryptography` for other purposes (TLS certificate handling, S/MIME signing/verification) are directly exposed to the RCE vector.

**Action required:**
1. In `pyproject.toml`, bump the `oauth` extra floor:
   ```toml
   # cryptography>=48.0.1 closes CVE-2026-45447 (OpenSSL PKCS7_verify heap UAF,
   # CVSS 7.5, June 9 2026) in addition to CVE-2026-26007/34073/39892.
   oauth = ["pyjwt[crypto]>=2.13.0", "cryptography>=48.0.1"]
   ```
2. Also update the `dev` extra's `cryptography>=46.0.7` to `>=48.0.1` so the development environment uses a patched version.
3. Run `uv lock`.
4. Open a `[security]` GitHub Issue (`[security] CVE-2026-45447: bump cryptography floor to >=48.0.1`).

### W-4 — CVE-2026-53533: `aiosmtplib 5.1.0` SMTP injection (CVSS 6.5 Moderate) — **new**

**Package:** `aiosmtplib` (base dependency: `aiosmtplib>=3.0`)
**Resolved:** `5.1.0` · **Fixed in:** `5.1.1`
**Published:** June 15, 2026 (OPENSUSE-SU-2026:11035-1; CVSS:3.1 AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:L)
**Not present in any prior review**

CVE-2026-53533 affects `aiosmtplib <5.1.1`. The CVSS vector (network-accessible, no authentication required, low confidentiality + integrity impact) is consistent with an SMTP command or header injection — allowing a crafted input to inject additional SMTP commands or email headers into the mail session. The full technical write-up had not been disclosed at the time of this review.

**Exposure for regstack:** regstack's SMTP email backend (`SmtpEmailService`, `src/regstack/email/backends/smtp.py`) uses `aiosmtplib` to send verification, password-reset, MFA, and notification emails. Any unvalidated user-supplied content that flows into email subject or body fields through `MailComposer` could be weaponised against an unpatched `aiosmtplib` to inject SMTP commands or extra email headers (e.g., injecting `Bcc:` to exfiltrate verification emails to an attacker's inbox). The email templates use Jinja2 with HTML autoescaping; however, injection at the SMTP protocol layer is distinct from template-level XSS.

**Action required:**
1. Bump the floor: `"aiosmtplib>=5.1.1"` in `pyproject.toml`.
2. Run `uv lock`.
3. Open a `[security]` GitHub Issue (`[security] CVE-2026-53533: bump aiosmtplib floor to >=5.1.1`).

### W-5 — CVE-2026-32690: `pydantic-settings 2.14.0` path traversal (CVSS 5.9 Medium) — **new**

**Package:** `pydantic-settings` (base dependency: `pydantic-settings>=2.2`)
**Resolved:** `2.14.0` · **Fixed in:** `2.14.2`
**Published:** June 2026 (DailyCVE DC-Jun2026-536)
**Not present in any prior review**

CVE-2026-32690 is a path traversal vulnerability in `pydantic-settings 2.12.0–2.14.1`. When a settings model reads from an `.env` file or secrets directory, insufficient path sanitisation allows a crafted path string to read files outside the intended directory. A CVSS:3.1 score of 5.9 (`AV:N/AC:H/PR:N/UI:N`) indicates a high-complexity network-reachable attack.

**Exposure for regstack:** `RegStackConfig` extends `pydantic-settings.BaseSettings`. The `config/loader.load_config` function accepts `toml_path` and `secrets_env_path` as `Path` arguments. If an attacker can influence these paths (e.g., via a maliciously crafted `REGSTACK_*` environment variable that pydantic-settings resolves to a file path outside the config directory), they could read arbitrary host filesystem files. The attack requires influencing config-loading arguments, which is typically operator-controlled — but the attack complexity depends on how the host app surfaces path selection to callers.

**Action required:**
1. Bump the floor: `"pydantic-settings>=2.14.2"` in `pyproject.toml`.
2. Run `uv lock`.
3. Open a `[security]` GitHub Issue (`[security] CVE-2026-32690: bump pydantic-settings floor to >=2.14.2`).
