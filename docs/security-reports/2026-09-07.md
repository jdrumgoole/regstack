## 🟠 WARNING

### W-1 (carry-over, day 28 — SLA MISSED 2026-08-18)

**Section:** §1 — Dependency Vulnerability Check
**CVE:** CVE-2026-69247 — `cryptography` Bleichenbacher oracle (`pkcs7_decrypt`)
**Affected range:** `cryptography` ≥ 44.0.0, < 50.0.0
**Resolved in:** `cryptography==50.0.0` (released 2026-07-31 — 38 days ago)
**Current resolved version in `uv.lock`:** 49.0.0 (within affected range)
**Current floor in `pyproject.toml`:** `cryptography>=48.0.1` (does not exclude affected versions)
**Fix required:** Bump floor to `cryptography>=50.0.0` in both the `oauth` and `dev` extras in
`pyproject.toml`; run `uv lock`.
**Tracking:** GitHub issue #181 (`[security] Raise cryptography floor to >=50.0.0`), open since
2026-08-19 — no fix PR, no assignee, no comment — **20 days unacknowledged.**

**Technical impact:** `pkcs7_decrypt_der`, `pkcs7_decrypt_pem`, and `pkcs7_decrypt_smime` expose
distinguishable error paths and timing differences during RSA `RecipientInfo.encryptedKey` decryption,
constituting a Bleichenbacher-style oracle. regstack does not call these functions directly, but
`pip install regstack[oauth]` resolves to 49.0.0 by default, shipping a version with an open advisory
to all downstream consumers. The fix (cryptography 50.0.0+) substitutes a random key on RSA
decryption failure per RFC 3218.

**Urgency:** The fix version has been on PyPI for 38 days. The 7-day SLA lapsed 2026-08-18. This
finding will appear daily until resolved.

### W-2 (carry-over, day 7 — NEW 2026-09-01) — `POST /confirm-email-change` email-change JWT not revoked after use

**Section:** §3 — Authentication & Authorization Audit
**File:** `src/regstack/routers/account.py`, `confirm_email_change` handler
**Status:** Unresolved. No change to `account.py` since first flagged.

The `confirm_email_change` endpoint successfully updates the user's email address but does not
call `await rs.blacklist.revoke(token_payload.jti, token_payload.exp)` after doing so. The
password-reset path (`password.py`) correctly performs this revocation after every successful
reset. Within the email-change token's TTL, the same confirmation URL can be submitted repeatedly.
Each subsequent submission attempts `update_email`, which succeeds as a no-op when the address is
already the user's own, and the endpoint returns HTTP 200 — confirming the link is still usable.

The `_decode_email_change_token` helper currently returns only `(user_id, new_email)` and discards
the `jti` and `exp` claims. Any fix must thread these through to the caller so `blacklist.revoke()`
can be called after a successful `update_email`.

### W-3 (carry-over, day 7 — NEW 2026-09-01) — `POST /confirm-email-change` bulk-revoke not applied to email-change tokens

**Section:** §3 — Authentication & Authorization Audit
**File:** `src/regstack/routers/account.py`, `confirm_email_change` handler
**Status:** Unresolved. No change to `account.py` since first flagged.

If a user changes their password (bumping `tokens_invalidated_after`) after requesting an email
change, the already-issued email-change JWT should be treated as bulk-revoked. The current
`confirm_email_change` handler does not call `is_payload_bulk_revoked(payload, user.tokens_invalidated_after)`
after decoding the token and fetching the user. The `_decode_email_change_token` helper also discards
the `iat` claim, so the comparison cannot be performed without extending the return signature.

The pattern mirrors the `_authenticate` dependency. Both W-2 and W-3 can be fixed in a single pass
through `confirm_email_change`.

### W-4 (carry-over, day 7 — NEW 2026-09-01) — OAuth `_resolve_user` unhandled `UserAlreadyExistsError` → HTTP 500

**Section:** §3 / §14 — Authentication & Authorization / OAuth Subsystem
**File:** `src/regstack/routers/oauth.py`, `_resolve_user` (brand-new account path, ~line 716),
`oauth_callback` (~line 325)
**Status:** Unresolved. No change to `oauth.py` since first flagged.

In the brand-new-account path of `_resolve_user`:

```python
new_user = await rs.users.create(new_user)   # <-- unguarded
```

If two concurrent OAuth sign-ins for the same email arrive simultaneously (e.g. two browser tabs),
the second `create()` call raises `UserAlreadyExistsError` (a `DuplicateKeyError` wrapper). This
exception is not caught in `_resolve_user`; it propagates through `oauth_callback`'s bare `except
_LinkConflictError` and surfaces as an unhandled HTTP 500. Under `config.allow_registration=True`
and concurrent OAuth flows, this is a reliable crash path, not a theoretical race.

**Fix:** Wrap `await rs.users.create(new_user)` in `try/except UserAlreadyExistsError:` and re-raise
as `_LinkConflictError("email_in_use")`, matching the existing-user path above it.

### W-5 (NEW) — CVE-2026-55558: aiosmtplib STARTTLS response injection — floor allows vulnerable version

**Section:** §1 — Dependency Vulnerability Check
**CVE:** CVE-2026-55558 — aiosmtplib STARTTLS response injection (HIGH)
**Affected range:** aiosmtplib < 5.1.2
**Resolved in:** aiosmtplib 5.1.2 (released 2026-06-20)
**Current floor in `pyproject.toml`:** `aiosmtplib>=5.1.1` (includes vulnerable 5.1.1)
**Current locked version in `uv.lock`:** 5.1.2 (patched — dev environment is safe)

**Technical impact:** An on-path attacker performing a MITM against the SMTP connection can inject
response lines before the TLS handshake completes. aiosmtplib leaves injected lines buffered and
then parses them as legitimate post-TLS server responses, allowing the attacker to control SMTP
dialogue flow (e.g. accept or redirect mail). The vulnerability is not exploitable when
`use_tls=True` (implicit TLS on port 465), but regstack's SMTP backend defaults to STARTTLS
(`smtp_starttls=True`), making the default configuration affected.

**Why this matters even though `uv.lock` has 5.1.2:** regstack ships a `pyproject.toml` floor of
`>=5.1.1`. Host applications that `pip install regstack` without using regstack's lock file may
resolve to 5.1.1 if their own dependency resolver satisfies that bound from cache or a different
set of constraints. The floor must be raised to `>=5.1.2` to guarantee downstream consumers get
the patched version.

**Fix:** Change `"aiosmtplib>=5.1.1"` to `"aiosmtplib>=5.1.2"` in `pyproject.toml`
`[project.dependencies]`; run `uv lock`. Update the inline comment to reference CVE-2026-55558.

## 🟡 INFO

### I-1 — Issue #181 unacknowledged (day 20)

GitHub issue #181 (`[security] Raise cryptography floor to >=50.0.0`), opened by the 2026-08-19
automated review to track W-1, remains open with no PR, no assignee, and no comment as of today
(20 days unacknowledged). The 7-day response SLA has been missed by 13 days.

### I-2 — CVE-2026-4984 (Twilio webhook signature bypass) — informational for host apps

CVE-2026-4984 discloses that Twilio webhook handlers which fail to validate the `X-Twilio-Signature`
header allow forged payloads to cause the app to fetch attacker-controlled URLs using embedded Twilio
credentials. regstack uses the Twilio SDK for outbound SMS only; it does not expose or register any
Twilio webhook endpoints, so the CVE does not apply to regstack's own code surface. However, host
applications that pair regstack with Twilio-webhook functionality of their own should verify that
every webhook endpoint calls `RequestValidator.validate()` before processing the payload.

### I-3 — CVE-2026-23996 (FastAPI API key timing) — not applicable to regstack's auth model

CVE-2026-23996 documents a measurable response-time side-channel in certain FastAPI API-key
verification patterns that allows statistical key enumeration. regstack uses `HTTPBearer` + JWT
verification, not API-key header comparison, so this CVE does not affect regstack's own
authentication paths. Host applications that layer API-key auth on top of regstack should review
their key comparison for timing safety.

### I-4 — CVE-2026-24486 (python-multipart path traversal) — already covered (carry-over)

`pyproject.toml` floor is `python-multipart>=0.0.32` which covers CVE-2026-24486. The locked
version satisfies this floor. No action needed; noted for completeness.

### I-5 — SecantusDB pre-release in `secantus` and `dev` extras (carry-over)

The `dev` extra pulls SecantusDB from a pre-release index. Pre-release packages bypass the
normal supply-chain audit process. Acceptable for a test-only dependency; note it when evaluating
the test backend matrix.

### I-6 — GitHub Actions SHA pins slightly behind latest minor releases (carry-over)

All third-party actions in `publish.yml` and `test.yml` are SHA-pinned (not tag-based), which is
correct. The pinned SHAs (`actions/checkout@de0fac2e...`, `astral-sh/setup-uv@08807647...`,
`pypa/gh-action-pypi-publish@cef221092...`, `actions/upload-artifact@043fb46d...`,
`actions/download-artifact@3e5f45b2...`) correspond to known-good versions but may not be the
latest patch. Routine SHA refresh is recommended quarterly.

### I-7 — SNS backend uses ambient boto3 credential chain; no explicit credential config (carry-over)

The SNS SMS backend delegates credential resolution to the boto3 default chain (env vars, shared
credential file, instance metadata). There is no `config.sms.sns_access_key_id` field —
intentionally avoided to prevent credential hardcoding. Document in operator docs that IAM role
attachment is the recommended deployment pattern.
