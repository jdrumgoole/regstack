## 🟡 INFO (Best practice recommendations)

### I1 — Per-IP rate limiting default-off *(carry-over; documentation updated)*

**File:** `docs/configuration.md:248–258`, `src/regstack/config/schema.py:224–241`

Commit `f390cc6` added a prominent "Every one of these fields defaults to
unset" callout to the configuration reference, explaining the why: turning
them on fails closed for hosts that haven't installed the `rate_limit`
extra, so enabling them by default would silently break base installs that
don't carry `slowapi`. The default-off behaviour is now documented; the
actual defaults are unchanged and the design decision is sound. Carrying
forward as INFO so operators are reminded on every review.

**Recommendation:** Operators should configure at least `register_rate_limit`,
`forgot_password_rate_limit`, and `resend_verification_rate_limit` to
protect outbound email budget and prevent address-harvesting probes.

### I2 — `UserPublic.tokens_invalidated_after` exposed in API responses *(carry-over)*

**File:** `src/regstack/models/user.py:105`

`tokens_invalidated_after` is included in every `/me`, `/admin/users/{id}`,
and `UserPublic` response. This is a documented design trade-off: SPAs use
the timestamp to detect stale sessions without a separate round-trip. If the
threat model treats internal event timing as sensitive, the field should be
excluded from `UserPublic`. No change since last review.

---

### I3 — Admin error messages echo the `email` path parameter *(carry-over)*

**File:** `src/regstack/routers/admin.py:224,229`

Two admin-only (`is_superuser=True`) error responses include the email
address from the URL path (e.g. `"No pending registration for {email}."`).
There is no current security risk — only superusers reach these endpoints.
If a future refactor accidentally drops the admin guard, these messages
would enumerate whether a given email exists, contradicting the
anti-enumeration discipline applied to `/forgot-password` and
`/resend-verification`. No change since last review.

---

### I4 — `oauth` extra explicitly pins `cryptography>=48.0.1` *(carry-over)*

**File:** `pyproject.toml:98`

The `oauth` extra carries an explicit `cryptography>=48.0.1` floor alongside
`pyjwt[crypto]>=2.13.0`. This is intentional: `pyjwt[crypto]` pulls
`cryptography` transitively but without a floor high enough to close
CVE-2026-26007, CVE-2026-34073, CVE-2026-39892, and CVE-2026-45447. The
explicit pin is correct defence-in-depth. Noted so future reviewers understand
the intent; the pin can be removed once `pyjwt` raises its own
`cryptography` floor past 48.0.1. No change since last review.

---

### I5 — SNS SMS backend uses boto3 default credential chain *(carry-over)*

**File:** `src/regstack/sms/sns.py:29`

`aioboto3.Session()` is constructed with no credential arguments; the SNS
backend relies entirely on boto3's ambient credential chain (instance
profile, env vars, etc.). This is the preferred AWS pattern for EC2/ECS
deployments and is asymmetric with the SES email backend (which exposes
`ses_access_key_id` / `ses_secret_access_key` config fields). Noted for
operator awareness. No change since last review.

---

### I6 — OAuth exchange consumes expired state before returning 400 *(carry-over)*

**File:** `src/regstack/routers/oauth.py:151–161`

`/oauth/exchange` calls `consume()` (atomic delete) and then checks
`state.expires_at < rs.clock.now()`. An expired-but-otherwise-valid state
row is permanently consumed before the 400 error is returned, forcing the
user to restart the full OAuth flow. The ordering is secure (no replay is
possible once the row is gone), but a check-before-consume ordering would
be friendlier. No change since last review.

---

### I7 — `cmd:` log-source kind executes operator-supplied shell commands *(carry-over)*

**File:** `src/regstack/cli/validate/logtail.py:106`

The `cmd:<arbitrary shell command>` log-source kind runs `sh -c <target>`
where `<target>` comes from the operator's config file. This is the declared
contract for this source kind — it is intentional operator-level behaviour,
not user input, and not reachable through the HTTP API. Noted for auditors.
No change since last review.

## 🟢 CLEAN (Passed review)

**W1 RESOLVED — JWT secret minimum length now enforced at construction:**
`JwtCodec.__init__` (`src/regstack/auth/jwt.py:127`) now raises `ValueError`
when `config.jwt_secret` is shorter than `MIN_JWT_SECRET_LENGTH` (32 chars,
defined in `config/secrets.py`). A secret of `REGSTACK_JWT_SECRET=x` now
fails at `RegStack()` construction with a clear error message rather than
silently signing tokens with near-zero entropy. The runtime guard and the
`regstack doctor` check share the same constant. Tests added in
`tests/unit/test_jwt.py`. Previously tracked as issue #153.

**W2 RESOLVED — Single-use token URLs redacted before hook dispatch:**
All five hook callsites that fire `url=<link-containing-raw-token>` now also
pass `url_without_token=redact_token(url, token)`:
- `routers/register.py` (`verification_requested`)
- `routers/verify.py` (`verification_requested`)
- `routers/password.py` (`password_reset_requested`)
- `routers/account.py` (`email_change_requested`)
- `routers/admin.py` (`verification_requested` on admin-resend)

`redact_token()` (`src/regstack/hooks/redaction.py`) replaces both the raw
token and its percent-encoded form with `[REDACTED]`, so it holds for hosts
using path-segment or hash-fragment `*_url_template` layouts. Tests added in
`tests/unit/test_hook_redaction.py` and
`tests/integration/test_hook_token_redaction.py`. Previously tracked as
issue #154.

**Top 3 priorities for the development team:**

1. **[I1] Configure per-IP rate limits in your deployment.** A fresh
   regstack deployment has per-account lockout on `/login` but no IP-level
   rate limiting on `/register`, `/forgot-password`, or
   `/resend-verification`. The documentation now explains why defaults are
   off (fails closed for base-install users without `slowapi`). Operators
   should still set limits appropriate to their traffic profile.

2. **[I2] Review whether `tokens_invalidated_after` belongs in `UserPublic`.**
   The timestamp leaks when each user's sessions were last force-invalidated.
   For most deployments this is a useful SPA optimisation; for
   higher-sensitivity deployments it is internal metadata that should be
   excluded. Decide once and document the reasoning in `UserPublic`.

3. **[I3] Guard against future admin-endpoint auth drift.** The
   `admin_promote_pending` endpoint echoes the email path parameter in 404/409
   responses. Today this is safe (admin-only). Consider using a generic
   "operation failed" message to make the endpoint safe even if the guard
   is accidentally dropped in a future refactor.
