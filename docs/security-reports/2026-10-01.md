## Section 1 — Dependency CVEs

### 🟠 W-1 — `cryptography` floor below 50.0.1 (day 52 — **37 days past SLA**)

`pyproject.toml` declares `cryptography>=48.0.1` in `optional-dependencies.oauth` and `dev`. The minimum safe floor is **50.0.1** (released 2026-08-25). Four CVEs now tracked under this finding:

- **CVE-2026-69247** (Bleichenbacher oracle on PKCS#7 RSA PKCS#1 v1.5 decryption — CVSS HIGH; fixed in 50.0.1). On the live code path for OAuth-enabled deployments.
- **CVE-2026-69248** (wildcard DNS SAN escapes `permittedSubtrees` name constraints; fixed in 49.0.0). Relevant to the JWKS certificate chain during OAuth ID-token validation.
- **CVE-2026-69249** *(new — discovered today)* (CVSS 8.7 HIGH; fixed in 49.0.0): Duplicate self-signed intermediates in a certificate chain cause exponential path-building recursion. Affects versions 42.0.0 through 48.0.0. The current floor 48.0.1 sits above the stated upper bound (48.0.0), but since the fix was introduced only in 49.0.0, 48.0.1 is likely vulnerable too unless the PyCA team backported it; the safest treatment is to assume 48.0.1 is affected until confirmed otherwise. The proposed floor bump (50.0.1) unambiguously resolves this.
- **CVE-2026-39892** (buffer overflow in Hash.update() on non-contiguous buffers; affects 45.0.0–46.0.6, fixed in 46.0.7). The current floor 48.0.1 already exceeds the affected range — this CVE is covered by the existing floor and does **not** need the bump. Listed here for completeness.

**Remediation:** Bump `cryptography>=50.0.1` in `optional-dependencies.oauth` and `dev`; run `uv lock`. The single bump covers all four CVEs.

### 🟠 W-12 — `pyjwt` floor below 2.14.0 — nine-CVE cluster (day 3 of SLA clock — **5 days remaining**)

`pyproject.toml` declares `pyjwt>=2.13.0` in `dependencies` (base install, every consumer) and `pyjwt[crypto]>=2.13.0` in `optional-dependencies.oauth` and `dev`. PyJWT 2.14.0 (released 2026-09-11) fixes a nine-CVE cluster. Most directly impactful:

- **CVE-2026-102268 (CVSS 9.1 — CRITICAL severity class):** `is_pem_format` whitespace/line-ending mutation bypasses the HS/asymmetric confusion guard. regstack uses HS256 with HMAC keys only; however, the deficient floor ships with every `pip install regstack` and exposes any host that combines regstack with asymmetric JWT logic.
- **CVE-2026-102267 (CVSS 7.4 — HIGH):** `PyJWKClient` follows HTTP redirects without validation on the JWKS fetch. Directly on regstack's OAuth ID-token verification code path.
- **CVE-2026-102271 (HIGH):** DER-form public keys accepted as HMAC secrets, bypassing the CVE-2022-29217 guard.
- **CVE-2026-102266 (HIGH):** Empty HMAC keys accepted as symmetric `PyJWK`, bypassing empty-key validation.
- **CVE-2026-102269, CVE-2026-102270 (MODERATE):** Non-Base64URL characters in compact JWS segments; ReDoS in `is_pem_format`.

Because `pyjwt` is in the base `dependencies` (not optional), the deficient floor reaches **every** downstream consumer of regstack, not just OAuth users.

**Remediation:** Bump both `pyjwt>=2.14.0` (base) and `pyjwt[crypto]>=2.14.0` (oauth, dev) in `pyproject.toml`; run `uv lock`.

### 🟡 I-3 — `UserPublic` schema includes internal session-management field (day 52)

### 🟡 I-4 — JWT audience not validated by default *(new)*

`RegStackConfig.jwt_audience: str | None = None` — audience validation is disabled by default. A session token minted by one regstack instance is accepted by any other regstack instance that shares the same `jwt_secret`, regardless of the host application. In practice, purpose-based key derivation (`derive_secret(jwt_secret, "session")`) already ensures session tokens cannot satisfy password-reset or email-change decodes on the same instance. However, two distinct regstack applications configured with the same master secret (e.g., a dev instance and a staging instance sharing a secret) accept each other's session tokens.

**Remediation:** Document in the configuration guide that multi-application deployments sharing infrastructure must set distinct `jwt_secret` values; optionally default `jwt_audience` to a non-null derived value (e.g., `derive_secret(jwt_secret, "audience_tag")`) in a future minor release.

## Section 14 — OAuth Subsystem Audit

### 🟢 CLEAN — PKCE invariants, ID-token verification, linking policy, identity-row uniqueness, hooks

No code changes. `_begin_flow` stores `code_verifier = secrets.token_urlsafe(64)` on the `OAuthState` row only; only `code_challenge = base64url(sha256(code_verifier))` goes to the provider URL. ### 🟠 W-4 — Race condition: new OAuth user creation raises unhandled 500 (day 31 — **24 days past SLA**)

`src/regstack/routers/oauth.py` (`_resolve_user`): `await rs.users.create(new_user)` not wrapped in `try/except UserAlreadyExistsError`. Two concurrent requests with the same Google `sub` can both reach this line; the second raises an unhandled 500. **Still open. No change.**

**Remediation:** Wrap in `try/except UserAlreadyExistsError` and fall back to `rs.users.get_by_email(info.email)`.

### 🟠 W-6 — SQL `OAuthStateRepo.consume` non-atomic under READ COMMITTED (day 23 — **16 days past SLA**)

`src/regstack/backends/sql/repositories/oauth_state_repo.py`: Under PostgreSQL's default READ COMMITTED isolation level, two concurrent connections can both `SELECT` the state row before either commits the `DELETE`; both callers receive the state row and can exchange it for a session token. **Still open. No change.**

**Remediation:** Replace the SELECT + DELETE with a single `DELETE FROM oauth_states WHERE id = ? RETURNING *`, or add `with_for_update()` to the SELECT.

## Carry-forward Findings Not Separately Discussed Above

### 🟠 W-2 — Email-change token `jti` never blacklisted (day 31 — **24 days past SLA**)

`src/regstack/routers/account.py` `confirm_email_change`: after successfully decoding the email-change JWT and calling `users.update_email(...)`, the handler never calls `blacklist.revoke(jti, exp)`. A valid email-change link can be replayed until it expires (default 60-min TTL). **Still open. No change.**

**Remediation:** After `_decode_email_change_token(token)`, extract `jti`/`exp`, check `await rs.blacklist.is_revoked(jti)` → 400 if consumed, then call `await rs.blacklist.revoke(jti, exp)` on success.

### 🟠 W-3 — Email-change handler skips bulk-revocation check (day 31 — **24 days past SLA**)

`src/regstack/routers/account.py` `confirm_email_change`: after `_decode_email_change_token`, the handler fetches the user but never calls `is_payload_bulk_revoked(payload, user.tokens_invalidated_after)`. A token minted before a `change-password` event would still be accepted, allowing a stolen email-change link to change a user's email even after the user has reset their password. **Still open. No change.**

**Remediation:** After `users.get_by_id(user_id)`, add `if is_payload_bulk_revoked(payload, user.tokens_invalidated_after): raise HTTPException(400, "Expired token.")`.

### 🟠 W-8 — Timing oracle distinguishes OAuth-only accounts on login (day 13 — **6 days past SLA**)

`src/regstack/routers/login.py`: `if user.hashed_password is None or not rs.password_hasher.verify(...)` — Python short-circuit evaluation means the Argon2 `verify()` call is skipped entirely when `hashed_password is None`. Login returns measurably faster for OAuth-only accounts than for accounts with an incorrect password, enabling timing-based enumeration of which accounts use OAuth-only sign-in. **Still open. No change.**

**Remediation:** Always call `rs.password_hasher.dummy_verify()` when `hashed_password is None` before raising the 401.
