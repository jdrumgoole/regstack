### W-2 — confirm_email_change: email-change JWT not blacklisted after use (day 18, SLA overdue 11 days)

**Tracking:** Issue #197  
**File:** `src/regstack/routers/account.py` — `confirm_email_change`

`_decode_email_change_token` returns a payload but discards the `jti`. After `users.update_email(...)` succeeds the token is never inserted into `BlacklistRepo`. A replay attack within the token's TTL window can re-run `update_email` a second time, repeatedly cycling the victim's email address and bumping `tokens_invalidated_after` to force session expiry.

**Remediation:** Extract `jti` from the payload and call `blacklist.revoke(jti, exp)` after `update_email` succeeds, mirroring the logout pattern.

### W-3 — confirm_email_change: bulk-revoke cutoff not applied to the token itself (day 18, SLA overdue 11 days)

**Tracking:** Issue #198  
**File:** `src/regstack/routers/account.py` — `confirm_email_change`

`_decode_email_change_token` does not call `is_payload_bulk_revoked` before acting. If a user's `tokens_invalidated_after` has been bumped (e.g., by a concurrent `change-password`), a pre-bump email-change token can still be consumed. The window is narrow but the invariant is violated.

**Remediation:** After decoding the email-change token, fetch the user and call `is_payload_bulk_revoked(payload, user.tokens_invalidated_after)`. If revoked, return 401.

### W-4 — OAuth _resolve_user: UserAlreadyExistsError not caught on concurrent new-user branch (day 18, SLA overdue 11 days)

**Tracking:** Issue #199  
**File:** `src/regstack/routers/oauth.py` — `_resolve_user`

In the new-user branch, `users.create()` can raise `UserAlreadyExistsError` if two OAuth callbacks arrive simultaneously for the same email address. This exception propagates unhandled → HTTP 500 instead of a safe recovery path.

**Remediation:** Wrap `users.create()` in a `try/except UserAlreadyExistsError` block; on conflict, fall through to `users.get_by_email()` and continue with the link step.

### W-6 — SQL oauth_states.consume() SELECT+DELETE not atomic (day 10, SLA overdue 3 days)

**Tracking:** Issue #208  
**File:** `src/regstack/backends/sql/repositories/oauth_state_repo.py`

The SQL backend's `consume()` wraps a `SELECT` and `DELETE` in a `BEGIN` transaction. On PostgreSQL at `READ COMMITTED` isolation, two concurrent `POST /oauth/exchange` calls can both read the row before either commits the delete, yielding two "successful" consumes of the same state row. This breaks the one-shot PKCE guarantee.

**Remediation:** Use `DELETE ... RETURNING *` (Postgres/SQLite 3.35+) or `SELECT ... FOR UPDATE` inside the transaction so only one concurrent caller can consume the row.

### W-8 — Timing oracle: OAuth-only account type disclosed via response latency (NEW TODAY)

**Tracking:** Issue #217  
**File:** `src/regstack/routers/login.py` line 99

```python
if user.hashed_password is None or not rs.password_hasher.verify(
    payload.password, user.hashed_password
):
```

Python short-circuit `or` evaluation means that when `user.hashed_password is None` (OAuth-only account), `rs.password_hasher.verify()` is never called. Argon2id verification takes ~100 ms by design; skipping it causes OAuth-only accounts to respond in ~1 ms. An attacker with a list of email addresses can distinguish OAuth-only accounts from password accounts (and non-existent accounts) purely by measuring response latency — despite the code comment explicitly stating that account type must not be disclosed.

This also allows probing whether a known password is correct for any account type once the timing oracle reveals it has a password — one class of account (OAuth-only) is effectively enumerable by timing alone.

**Remediation:** Always run a dummy Argon2 verify before returning the 401, even when `hashed_password is None`. Store `is_oauth_only = user.hashed_password is None` before verification; then call `rs.password_hasher.verify(payload.password, user.hashed_password or DUMMY_HASH)`, discard the result if `is_oauth_only`, and return the same generic 401. Most password-hasher libraries expose a `dummy_verify()` or equivalent for exactly this use case.

### W-9 — SNS SMS backend: no config fields for explicit AWS credentials (NEW TODAY)

**Tracking:** Issue #218  
**File:** `src/regstack/sms/sns.py` line 29; `src/regstack/config/schema.py` `SmsConfig`

The SES email backend exposes `ses_access_key_id`, `ses_secret_access_key`, and `ses_profile` in `EmailConfig` so credentials can be supplied explicitly when no ambient IAM role is available. The SNS SMS backend calls `aioboto3.Session()` with no credential arguments and has no equivalent fields in `SmsConfig`. In environments without ambient IAM (a bare EC2 instance, a non-AWS VPC host, or any non-AWS cloud) the SNS backend will silently fail with an `AuthorizationError` from aioboto3 rather than a configuration validation error at startup. The asymmetry is undocumented.

**Remediation:** Add `sns_access_key_id: SecretStr | None`, `sns_secret_access_key: SecretStr | None`, and `sns_profile: str | None` to `SmsConfig` (matching the SES pattern). Pass them to `aioboto3.Session(...)` in `sns.py` when set, with the same mutual-exclusivity validator. Document the fallback to ambient IAM in `regstack init`.

### W-10 — GoogleProvider stores client_secret as plain str (NEW TODAY)

**Tracking:** Issue #219  
**File:** `src/regstack/oauth/providers/google.py` lines 79, 90

`GoogleProvider.__init__` accepts `client_secret: str` (a plain Python `str`) and stores it as `self._client_secret`. All other credential fields in the codebase (`smtp_password`, `ses_secret_access_key`, `twilio_auth_token`, `google_client_secret` on `OAuthConfig`) use Pydantic `SecretStr`, which overrides `__repr__` to emit `'**********'` in place of the value. A plain `str` attribute will appear verbatim in:

- Exception tracebacks that capture `self` in local-variable frames (Sentry, Datadog APM, and most error-aggregation SDKs serialize all local variables in a traceback frame)
- Python heap dumps and core dumps
- Any introspection tool that enumerates the instance's `__dict__`

The caller in `app.py` correctly unwraps `SecretStr.get_secret_value()` before passing the value in, so the secret is already a naked string by the time it enters `GoogleProvider`. The fix therefore requires threading the `SecretStr` through rather than unwrapping at the call site.

**Remediation:** Change `GoogleProvider.__init__` to accept `client_secret: SecretStr` (not `str`); update the call site in `app.py` to pass the `SecretStr` directly rather than unwrapping it; call `.get_secret_value()` only at the use site inside `exchange_code`. Add `__repr__` returning `<GoogleProvider client_id=...>` (no secret).

## 🟡 INFO

### I-1 — SQL purge_expired() not automatically scheduled

**Files:** All SQL repos with `expires_at` columns; `src/regstack/backends/protocols.py`

MongoDB TTL indexes expire documents automatically. On SQL backends, expired rows accumulate indefinitely unless the host application calls `purge_expired()` on each repo. The protocol interface documents this requirement, but there is no built-in background task, startup hook, or documentation in the user-facing README or `regstack init` output to inform hosts. The accumulation is a storage leak, not a security bypass (expiry checks are done in-query), but a host that never calls `purge_expired()` will have unbounded table growth for `login_attempts`, `pending_registrations`, `mfa_codes`, `token_blacklist`, and `oauth_states`.

**Recommendation:** Add a note to the `docs/` user guide and/or the `regstack init` output instructing SQL-backend users to schedule `purge_expired()` calls. Optionally provide a `RegStack.purge_expired_all()` convenience method.

### I-2 — pyproject.toml CVE comment misattributes CVE-2026-2978/2979

**File:** `pyproject.toml` (comment near `fastapi>=0.120.0`)

The comment attributes CVE-2026-2978 and CVE-2026-2979 to `fastapi`. Those CVEs affect the unrelated third-party package "FastApiAdmin", not the `fastapi` package itself. The floor version for `fastapi` is correct but the comment creates confusion about the actual threat. No security impact; update the comment for accuracy.

### I-3 — tokens_invalidated_after included in UserPublic

**File:** `src/regstack/models/user.py` line 105

`tokens_invalidated_after` is exposed in `UserPublic`. This is documented as intentional (allows SPAs to detect token invalidation without a round-trip). No attack vector identified; authenticated users can only read their own value; admins can read all users'. Noted for awareness.

## 🟢 CLEAN

All 15 review sections were covered. The following areas passed without findings:

- **Hardcoded secrets**: No API keys, private keys, or credentials in source, tests, or examples. `.gitignore` complete. No credential commits in git history.
- **Storage injection**: MongoDB repos use typed Python values as filters — no user-input operator injection possible. SQL repos use SQLAlchemy Core parameterized queries throughout — no `text()` with interpolation, no f-string SQL.
- **Input validation**: All API inputs go through Pydantic v2 models with `extra="forbid"`. `EmailStr` on all email fields. E.164 validation on all phone fields. Jinja2 `autoescape` on for both email and SSR templates. No `| safe` or `{% autoescape false %}` in any bundled template. OAuth `redirect_to` validated same-origin before use.
- **JWT mechanics**: `jti` present on every token. `iat` emitted as float. pyjwt `exp`/`iat` checks disabled, validated manually against injected `Clock`. Token revocation order correct (decode → blacklist → bulk-revoke → is_active).
- **CSP / SSR layer**: Zero `<style>` blocks, `style="..."` attributes, or inline `<script>` tags across all 11 SSR templates. Pages are stateless (no auth state rendered into HTML).
- **Data exposure**: `UserPublic` used on all response paths; `BaseUser` (including `hashed_password`) never returned directly. No `detail=str(exc)` patterns — all error messages are hardcoded strings. OAuth callback failures redirect with opaque short codes.
- **GitHub Actions**: All action `uses:` entries pinned to full commit SHA. No `${{ github.event.* }}` in `run:` blocks. Least-privilege `permissions:` declared on all jobs. No `pull_request_target`. No self-hosted runners. OIDC trusted publishing; no `PYPI_API_TOKEN`.
- **PyPI wheel**: Only `src/regstack/` ships. Tests, docs, examples, CI config, and developer tooling excluded. Optional extras correctly scoped. Sigstore PEP 740 attestations generated at publish time.
- **OAuth subsystem**: PKCE `code_verifier` is server-side only; `code_challenge` sent to provider. State row lifecycle correct (missing → `bad_state`; expired → `state_expired`; atomic consume on both backends). Full ID-token verification (JWKS signature, `iss`, `aud`, `exp`, nonce). Linking-policy enforcement present for all conflict cases. Identity-row uniqueness enforced at DB level on both backends.
- **Multi-backend parity**: CI matrix covers all four backends (SQLite, Postgres, Mongo, Secantus). All SQL migrations have `upgrade()` and `downgrade()`. Autogenerate-drift test confirms schema ↔ migration consistency. All unique constraints have matching Mongo unique indexes. `tz_aware=True` on Mongo client; `UtcDateTime` TypeDecorator on SQL.
- **SMTP / SES / Twilio integrations**: All credentials use `SecretStr`. None echoed in logs or error messages. aioboto3 and Twilio SDK lazy-imported.
