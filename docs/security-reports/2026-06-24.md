## 🟠 WARNING (Address within 1 week)

### W-1 — CVE-2026-53539: python-multipart Quadratic-Complexity DoS (CVSS High) — **carry-forward, unfixed**

**Package:** `python-multipart`
**Current floor:** `>=0.0.27` · **Resolved in `uv.lock`:** `0.0.28`
**Fixed in:** `0.0.30`

First flagged as W-1 in the 2026-06-23 review; the floor and lock have not been updated.

The `QuerystringParser` in `python_multipart/multipart.py` processes `application/x-www-form-urlencoded` bodies with an O(B²) algorithm when `;` is used as the field separator. A crafted body of many semicolons stalls the worker on pure-Python CPU work, enabling unauthenticated Denial of Service. Every regstack auth endpoint is reachable before authentication occurs.

**Action required:**
1. Bump the floor to `python-multipart>=0.0.30` in `pyproject.toml` (update the inline CVE comment to add CVE-2026-53539).
2. Run `uv lock` to update `uv.lock`.
3. Open (or update) a `[security]` GitHub Issue tracking this change.

### W-2 — CVE-2026-54283: Starlette/FastAPI DoS via Form Limits Bypass (CVSS High) — **new**

**Package:** `starlette`
**Current floor:** `>=1.0.1` · **Resolved in `uv.lock`:** `1.3.1` (patched)
**Vulnerable range:** ≤1.3.0 · **Fixed in:** `1.3.1` (released 2026-06-12)

Starlette's `request.form()` accepts `max_fields` and `max_part_size` parameters to cap resource consumption when parsing form data. These limits are correctly enforced for `multipart/form-data` but are **completely ignored** for `application/x-www-form-urlencoded`. An attacker can submit a body with ~1,000,000 fields (sub-10 MB) or a single field with a 50 MB value; either stalls the worker event loop for seconds and blocks all other requests.

regstack's own endpoints use JSON bodies parsed through Pydantic, so regstack's own `request.form()` calls are not the primary exposure. The concern is as a library: `pyproject.toml` declares `starlette>=1.0.1`, which allows downstream consumers who `pip install regstack` to resolve any Starlette version from 1.0.1 through 1.3.0 — all of which are vulnerable. The current `uv.lock` already pins 1.3.1 (safe), but the declared floor must be raised so hosts inherit protection automatically.

**Action required:**
1. Bump the floor to `starlette>=1.3.1` in `pyproject.toml` and add an inline comment citing CVE-2026-54283.
2. Run `uv lock`.
3. Open a `[security]` GitHub Issue.

### I-2 — `admin_promote_pending` path parameter not validated as `EmailStr` (carry-forward)

Unchanged from the 2026-06-23 review. `POST /admin/pending/{email}/promote` (`src/regstack/routers/admin.py:204`) accepts `email: str = Path(...)`. ### §3 — Authentication & authorization

- Every authenticated endpoint depends on `rs.deps.current_user()` or `rs.deps.current_admin()`. No route serialises a user object without going through `UserPublic.from_user()`, which excludes `hashed_password`.
- **Bulk-revoke discipline verified:** password reset (`routers/password.py`) calls `update_password` (bumps `tokens_invalidated_after`) and `lockout.clear`; `change-password` bumps hash and cutoff via `update_password`; `confirm-email-change` bumps cutoff via `update_email`; admin `PATCH /admin/users/{id} {is_active: false}` calls `set_tokens_invalidated_after` (`routers/admin.py:111`); account deletion cascades `oauth_identities.delete_by_user_id` before `users.delete` in both user-initiated and admin delete paths.
- **OAuth-only users:** `login` checks `user.hashed_password is None` and returns the same generic 401 as a wrong-password attempt (no enumeration). `change-password`, `change-email`, `delete-account` return 400 via `require_password_set`. `DELETE /oauth/{provider}/link` returns 400 when no other auth method remains.
- Password comparison uses `pwdlib.PasswordHasher.verify` (Argon2id constant-time), never `==`.
- JWT signing keys are purpose-derived via HMAC-SHA256 (`config/secrets.derive_secret`); a captured session token cannot satisfy the password-reset, email-change, phone-setup, or MFA endpoints.

### §4 — Storage-layer injection safety

**MongoDB:** All query filters in `backends/mongo/repositories/` use Python dict literals with user-supplied values as document values, never as operators. No `$where`, `$expr`, `$function`, or `$accumulator` usage found. No regex patterns built from user input. `ObjectId.is_valid()` guards every method accepting a `user_id` string before `ObjectId(user_id)` is called (`user_repo.py:54`). Both safe. `UtcDateTime` TypeDecorator re-attaches UTC on every read. `purge_expired()` implementations use bound timestamp parameters.

### §14 — OAuth subsystem

**14a — PKCE invariants:** `_begin_flow` (`routers/oauth.py:598`) generates `code_verifier` via `secrets.token_urlsafe(64)` and stores it on the `OAuthState` row. Only the SHA-256 `code_challenge` goes to the provider's authorization URL — the verifier never appears in the redirect.

**14b — State row lifecycle:** `state_id` is `secrets.token_urlsafe(32)`. Callback rejects missing/wrong-provider rows (`?error=bad_state`) and expired rows via `rs.clock.now()` (injected clock, not `datetime.now()`). `consume()` is atomic: `find_one_and_delete` on Mongo; SQL repos delete the row after reading — a second exchange call returns `None → 404`.

**14c — ID-token verification:** `GoogleProvider.verify_id_token` verifies signature against Google's JWKS (5 s timeout), checks `iss`, `aud`, `exp`, `iat`, `nonce`. All failures raise `OAuthIdTokenError` — reason logged at WARNING only, never echoed in the redirect.

**14d — Linking policy:** Auto-link fires only when `oauth.auto_link_verified_emails=True` AND `id_token.email_verified=True`. An identity linked to a different user raises `identity_in_use`; re-linking the same identity to the same user raises `already_linked`.

**14e — OAuth-only user side effects:** Login returns same generic 401 as wrong password for `hashed_password=None` users. `change-password`, `change-email`, `delete-account` return 400 via `require_password_set`. `DELETE /oauth/{provider}/link` returns 400 when no other sign-in method remains.

**14f — Identity-row uniqueness:** Mongo unique indexes on `(provider, subject_id)` and `(user_id, provider)` in `backends/mongo/indexes.py:73-86`. SQL `UniqueConstraint` on the same pairs in `schema.py:143-144`. Parity confirmed.

**14g — Hooks:** `oauth_signin_started`, `oauth_signin_completed`, `oauth_account_linked`, `oauth_account_unlinked` all present in `KNOWN_EVENTS` (`hooks/events.py:32-35`). Router fires them at the correct points in `routers/oauth.py`.

### §15 — Multi-backend parity & schema migration safety

**15a — CI matrix:** `test.yml` runs `pytest -n auto --tb=short` against MongoDB and PostgreSQL as service containers and SQLite inline, across Python 3.11 and 3.12. All three backends exercised on every push and PR.

**15b — Schema migration safety:** Three migrations: `0001_initial_schema.py`, `0002_oauth.py`, `0003_oauth_state_result_was_new.py`. All have `upgrade()` and `downgrade()`. `0002_oauth.py` uses `batch_alter_table` for SQLite-safe column nullability changes.

**15c — Mongo index parity:** Every SQL `UniqueConstraint` has a matching Mongo unique index: `users.email` → `email_unique`; `oauth_identities (provider, subject_id)` → `provider_subject_unique`; `oauth_identities (user_id, provider)` → `user_provider_unique`. All `expires_at`-bearing tables have Mongo TTL indexes; SQL repos expose `purge_expired()` with bound parameters.

**15d — Datetime tz-awareness:** `make_client(tz_aware=True)` for Mongo. `UtcDateTime` TypeDecorator re-attaches UTC in `process_result_value` on every read. No naive datetime regression found.
