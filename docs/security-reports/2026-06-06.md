## 🟠 WARNING (Address within 1 week)

### W-1 — CVE-2026-48710 (Starlette "BadHost") — uv.lock pins vulnerable 1.0.0; no consumer-facing floor

**CVE:** CVE-2026-48710  
**Affected:** Starlette < 1.0.1  
**Lock file version:** `1.0.0` (`uv.lock` line: `name = "starlette" / version = "1.0.0"`)  
**Fixed in:** Starlette 1.0.1  

**What the vulnerability does:**

Starlette < 1.0.1 derives `request.url` from the `Host` header without sanitisation. A `Host` value containing `/`, `?`, or `#` shifts the path/query/fragment boundaries during re-parse, so `request.url.path` no longer matches the path the ASGI server actually received and routed against. Any middleware or guard that uses `request.url.path` (or `request.url.hostname`) for an authorisation decision can be bypassed with a single malformed character in the `Host` header.

**Impact on regstack specifically:**

regstack's own auth model does **not** use path-based middleware. Every authenticated endpoint uses `Depends(rs.deps.current_user())` or `Depends(rs.deps.current_admin())`, which validates an `Authorization: Bearer <token>` header entirely independently of the URL path. A BadHost-crafted request cannot bypass regstack's JWT validation; it could not obtain a `BaseUser` it's not entitled to.

However, the vulnerability still matters for this project at two levels:

1. **Development and CI environment:** `uv.lock` pins Starlette to 1.0.0. All CI runs and local development use the vulnerable version. If a future regstack middleware or SSR route is added that inspects `request.url.path` before authentication, the vulnerable env silently runs tests against incorrect behaviour.

2. **Downstream consumers:** `pyproject.toml` expresses `fastapi>=0.120.0` without an explicit `starlette` lower bound. FastAPI's own metadata allows Starlette ≥ 0.46.0. A host that runs `pip install regstack` today could resolve to Starlette 1.0.0. Hosts that add their own path-based auth middleware (very common) would inherit the vulnerability.

**Recommended fix:**

```toml
# pyproject.toml — add an explicit Starlette floor to protect consumers
dependencies = [
    "fastapi>=0.120.0",
    "starlette>=1.0.1",      # CVE-2026-48710 (BadHost host-header auth bypass)
    ...
]
```

Then regenerate the lock file:

```bash
uv lock --upgrade-package starlette
```

Adding `starlette>=1.0.1` directly to `dependencies` is the only reliable way to floor the transitive dep for every consumer of the wheel. Bumping only `fastapi` does not help unless FastAPI itself also floors Starlette >= 1.0.1 in its own metadata (it does not as of 0.136.1 — it allows ≥ 0.46.0).

**References:** [BadHost advisory](https://badhost.org/), [OSTIF disclosure](https://ostif.org/disclosing-the-badhost-vulnerability-in-starlette/), [CVE-2026-48710 NVD](https://cvefeed.io/vuln/detail/CVE-2026-48710)

## 🟡 INFO (Best practice recommendations)

### I-1 — `tokens_invalidated_after` exposed in `UserPublic` responses

`UserPublic.tokens_invalidated_after` (type `datetime | None`) appears in the response body of `GET /me`, `GET /admin/users/{id}`, and `POST /confirm-email-change`. The field discloses the precise timestamp of the most recent security-affecting event (password change, email change, admin disable) to any session-token holder.

This is a **documented intentional trade-off** — see `docs/security.md` §"Data-exposure trade-off". The rationale is that SPA clients can compare this against the local JWT's `iat` to detect a server-side revocation without a separate round-trip. The field cannot be used to forge tokens; the disclosure risk is operational (a stolen session token reveals when account security last changed).

No action required. Flagged here for completeness and to confirm the trade-off is still accepted. Hosts for whom this is unacceptable can strip the field at their own API layer.
