## Section 1 — Dependency CVEs

### 🟠 W-1 — `cryptography` floor below patched release (day 48 — **33 days past SLA**)

`pyproject.toml` declares `cryptography>=48.0.1` in both the `oauth` extra and the `dev` extra. The minimum safe floor is **50.0.1**, covering these confirmed CVEs:

- **CVE-2026-69247** (PKCS#7 `EnvelopedData` Bleichenbacher oracle — CVSS HIGH; fixed in 50.0.1). Distinguishable error paths and timing differences during RSA PKCS#1 v1.5 decryption expose a Bleichenbacher oracle on the PKCS#7 decryption code path. The `pyjwt[crypto]` OAuth path loads RSA primitives at import time; this CVE is on the live code path for OAuth-enabled deployments.
- **CVE-2026-69248** (wildcard DNS name allows escape from `permittedSubtrees` name constraints; fixed in 49.0.0). Certificate verifier accepts wildcard SAN entries that should be rejected by `permittedSubtrees` constraints — directly relevant to the JWKS certificate chain verified during OAuth ID-token validation.
- **CVE-2026-69249** (exponential path-building DoS via duplicate self-signed intermediates; fixed in 48.0.1). **Already covered** by the existing floor.

**CVE ID correction:** Previous reports cited CVE-2026-0001 and CVE-2026-0002 as additional findings against `cryptography`. These IDs could not be independently verified in NVD, GHSA, OpenCVE, Snyk, or SentinelOne as of this review. They are removed from the finding; CVE-2026-69247 and CVE-2026-69248 remain valid and are sufficient to require the bump.

**Remediation:** Bump floor to `cryptography>=50.0.1` in both the `oauth` and `dev` entries in `pyproject.toml`; run `uv lock` and push.

### 🟠 W-5 — `aiosmtplib` floor below patched release (day 21 — **14 days past SLA**)

`pyproject.toml` declares `aiosmtplib>=5.1.1`. **CVE-2026-55558** (GHSA-vxj7-4xrp-5vr4, CVSS MEDIUM; fixed in 5.1.2): STARTTLS response injection — the library does not clear the receive buffer after the plaintext `220` upgrade response before the TLS handshake begins; an active network attacker on the plaintext leg can inject SMTP response lines that survive into the TLS session, desynchronising all subsequent command/response pairs. Any deployment using `email_backend=smtp` with STARTTLS is exposed.

**CVE ID correction:** Previous reports cited this as CVE-2026-0010. The confirmed assigned ID is **CVE-2026-55558** (GHSA-vxj7-4xrp-5vr4). The finding is otherwise unchanged.

**Remediation:** Bump floor to `aiosmtplib>=5.1.2` in `pyproject.toml`; run `uv lock`.

### 🟠 W-11 — `pymongo` floor exposes two CVEs (NEW — day 1 of SLA clock)

`pyproject.toml` declares `pymongo>=4.9` (present in the `mongo` and `secantus` optional extras and in `dev`). Two CVEs published **2026-09-10** are not covered:

- **CVE-2026-88029** (CVSS 8.3 — HIGH): High-integrity/availability impact via a network-based attack requiring no user interaction; fix released as pymongo **4.18.1** on 2026-09-10. The specific attack vector is not fully disclosed pending coordinated disclosure window, but the HIGH CVSS without authentication prerequisites places this in the same urgency tier as W-1.
- **CVE-2026-96748** (CVSS 6.5 — MEDIUM): Connection string parsing decodes percent-encoded characters in the host portion before splitting on delimiters, allowing an attacker-controlled connection string to inject additional servers. Relevant if any host app passes user-controlled data into the MongoDB URL.

These CVEs were published 17 days ago and appear to have been missed by previous automated reviews, which reported pymongo as CLEAN. The `mongo` backend is used in production-grade regstack deployments; hosts inheriting this floor are exposed.

**Remediation:** Bump floor to `pymongo>=4.18.1` in `optional-dependencies.mongo`, `optional-dependencies.secantus`, and `dev` entries in `pyproject.toml`; run `uv lock`.

## Section 3 — Authentication & Authorisation Audit

### 🟢 CLEAN — Endpoint authentication coverage

All mutating endpoints inject `rs.deps.current_user()` or `rs.deps.current_admin()`. Admin endpoints (`/admin/stats`, `/admin/users`, `/admin/users/{id}`, `PATCH /admin/users/{id}`, `DELETE /admin/users/{id}`, `/admin/users/{id}/resend-verification`, `/admin/pending/{email}/promote`) all depend on `rs.deps.current_admin()`. All data responses use `UserPublic.from_user()`.

### 🟢 CLEAN — Bulk-revoke discipline

Password reset calls `users.update_password()` (which atomically bumps `tokens_invalidated_after`) and `lockout.clear()`. Password change calls `users.update_password()` and `lockout.clear()`. Admin disable calls `users.set_tokens_invalidated_after()` before returning 200. Account deletion cascades OAuth identities before deleting the user row. Email-change confirm calls `users.update_email()` which atomically bumps `tokens_invalidated_after`. All pass the discipline check (modulo W-2 and W-3, which concern the token lifecycle around email-change, not the revocation bump itself).

### 🟠 W-8 — Timing oracle on login for OAuth-only accounts (day 9 — **2 days past SLA**)

`src/regstack/routers/login.py:99`: the login handler contains:

```python
if user.hashed_password is None or not rs.password_hasher.verify(
    payload.password, user.hashed_password
):
```

Python short-circuits on `hashed_password is None`: if the account is OAuth-only, the ~100 ms Argon2 verify is skipped and the response returns in ~1 ms. An attacker can probe whether a given email is OAuth-only vs password-enabled with ~200 requests and a simple latency histogram.

**Remediation:** Always run a dummy Argon2 verify when `hashed_password is None` to preserve constant time (e.g., `rs.password_hasher.dummy_verify()` or equivalent constant-time guard), then raise the same generic 401.

### 🟢 CLEAN — `hashed_password is None` side effects

`change-password`, `change-email`, `delete-account` all call `require_password_set(user)` before proceeding. OAuth unlink refuses if it would remove the only sign-in method. Login returns the same generic 401 for missing password as for a wrong password (modulo the timing gap above, W-8).

### 🟢 CLEAN — Constant-time password comparison

`pwdlib` (argon2) is used for all password hashing and verification. No `==` comparison is used on raw password strings.

### 🟢 CLEAN — Per-purpose JWT key derivation

`derive_secret(jwt_secret, purpose)` in `src/regstack/config/secrets.py` uses `hmac.new(master, purpose.encode(), hashlib.sha256).digest()`. Each purpose (`session`, `password_reset`, `email_change`, `phone_setup`, `login_mfa`) gets a distinct derived key. Compromise of one derived key does not compromise the master.

## Section 4 — Storage-layer Injection Safety

### 🟢 CLEAN — MongoDB backend

All MongoDB queries use typed BSON document constructors with literal operator names. No user input is interpolated into query operators. No `$where`, `$expr`, `$function`, or `$accumulator` operators are used. No regex patterns are built from user input. `get_by_id` guards with `ObjectId.is_valid(user_id)` before casting throughout all Mongo repos. No `$in` queries accept unbounded user-supplied arrays.

### 🟢 CLEAN — SQL backend

All SQL queries in `src/regstack/backends/sql/repositories/` use SQLAlchemy Core with parameterised binds. No f-string or `%`-interpolation into raw SQL. Two `text(...)` usages exist: `text("SELECT 1")` for a health-ping (no user input); `text("SELECT COUNT(*) FROM users WHERE hashed_password IS NULL")` in migration `0002_oauth.py` (no user input). `purge_expired()` implementations across all five SQL repos use bound `now` parameters throughout.

### 🟢 CLEAN — `UtcDateTime` TypeDecorator

`src/regstack/backends/sql/types.py` consistently re-attaches UTC tzinfo on result values via `process_result_value`. Type error on non-datetime values is raised rather than silently passed.

### 🟠 W-6 — SQL `OAuthStateRepo.consume` non-atomic read-delete (day 19 — **12 days past SLA**)

`src/regstack/backends/sql/repositories/oauth_state_repo.py`: `consume` performs a `SELECT` followed by a `DELETE` in a single transaction. Under both PostgreSQL (READ COMMITTED) and SQLite, two concurrent connections can each execute the SELECT and observe the row before either commits the DELETE, allowing both to receive the same state row and exchange the OAuth token twice.

The MongoDB backend uses `find_one_and_delete`, which is atomic at the server level. The SQL path must match this guarantee.

**Remediation:** Rewrite `consume` to use `DELETE … RETURNING *` (PostgreSQL) or an equivalent serialised exclusive transaction pattern (SQLite) so the SELECT and DELETE are one atomic server-side operation.

## Section 7 — Session & Token Security

### 🟢 CLEAN — JWT configuration, `jti`, `iat` float, clock injection, revocation discipline

`JwtCodec.__init__` enforces `len(jwt_secret) >= MIN_JWT_SECRET_LENGTH (32)`. Every token minted by `JwtCodec.encode()` receives `jti=secrets.token_urlsafe(16)`. `iat` is emitted as a float (`payload.iat.timestamp()`). pyjwt's built-in `exp`/`iat` validation is disabled via `options={"verify_exp": False, "verify_iat": False}`; both are validated against the injected `Clock`. `_authenticate` enforces decode → blacklist check → bulk-revoke check → `is_active` in the correct order.

### 🟢 CLEAN — No token leakage in logs

`_authenticate` catches `TokenError` and raises a static 401 without echoing the pyjwt exception text. OAuth callback errors log only generic short codes — never the raw token, id_token, or JWT secret content.

### 🟠 W-2 — Email-change token `jti` never blacklisted (day 27 — **20 days past SLA**)

`src/regstack/routers/account.py` → `confirm_email_change`: after successfully decoding the email-change JWT and calling `users.update_email(...)`, the handler never extracts the token's `jti` or calls `blacklist.revoke(jti, exp)`. A valid email-change link can therefore be replayed until it expires (default 60 min TTL), allowing an attacker who obtains a copy of the link to repeatedly swap the email address.

**Remediation:** After `_decode_email_change_token(token)`, extract `payload.jti` and `payload.exp`. Check `await rs.blacklist.is_revoked(jti)` first (→ 400 if already consumed). On success, call `await rs.blacklist.revoke(jti, exp)` before returning.

### 🟠 W-3 — Email-change handler skips bulk-revocation check (day 27 — **20 days past SLA**)

`src/regstack/routers/account.py` → `confirm_email_change`: after `_decode_email_change_token`, the handler fetches the user by `sub` but never calls `is_payload_bulk_revoked(payload, user.tokens_invalidated_after)`. A token minted before a `change-password` event (which bumps `tokens_invalidated_after`) would still be accepted to change the email.

**Remediation:** After `users.get_by_id(user_id)`, add:
```python
if is_payload_bulk_revoked(payload, user.tokens_invalidated_after):
    raise HTTPException(status_code=400, detail="Email-change link has been invalidated.")
```

## Section 11 — Third-Party Integration Security

### 🟢 CLEAN — SMTP backend

`SmtpEmailService` reads `smtp_password` only via `self._config.smtp_password.get_secret_value()` at send time. Password never appears in logs or error messages.

### 🟢 CLEAN — SES backend

`EmailConfig` declares `ses_access_key_id: SecretStr | None` and `ses_secret_access_key: SecretStr | None`. Credentials are loaded from config or ambient credential chain; never hardcoded. `aioboto3` import is lazy.

### 🟠 W-9 — `SmsConfig` SNS credential fields not `SecretStr` (day 9 — **2 days past SLA**)

`src/regstack/config/schema.py`: `SmsConfig` declares `twilio_auth_token: SecretStr | None` correctly for the Twilio path, but the SNS path exposes no explicit credential fields (only `sns_region: str`) — relying entirely on boto3's ambient credential chain with no `SecretStr` protection in the pydantic model.

**Remediation:** Add `aws_access_key_id: str | None = None` and `aws_secret_access_key: SecretStr | None = None` to `SmsConfig`; pass them to the SNS client when provided, falling back to ambient credentials otherwise. Mirror the pattern `EmailConfig` uses for `ses_access_key_id`/`ses_secret_access_key`.

### 🟠 W-10 — `GoogleOAuthProvider` holds `client_secret` as plain `str` (day 9 — **2 days past SLA**)

`src/regstack/oauth/providers/google.py:79,90`: `__init__` accepts `client_secret: str` and stores it as `self._client_secret = client_secret`. The pydantic config layer correctly stores the value as `SecretStr`, but it is unwrapped before being passed to the provider constructor. If the provider object is ever serialised or printed for debugging, the secret appears in plaintext.

**Remediation:** Change the parameter type to `SecretStr`, store as-is, and call `.get_secret_value()` only at the token-exchange POST.

### 🟢 CLEAN — Google JWKS verification

`GoogleProvider.verify_id_token` validates signature via `PyJWKClient` against Google's JWKS URL, validates `iss`, `aud`, `exp`, `iat`, `nonce`, and `sub`. JWKS fetch is offloaded to `asyncio.to_thread` with `timeout=JWKS_FETCH_TIMEOUT_SECONDS (5)`. Algorithm pinned to `RS256`. On any failure, `OAuthIdTokenError` is raised with a generic outer message; the specific failure is logged at WARNING only, never echoed to the redirect.

## Section 14 — OAuth Subsystem Audit

### 🟢 CLEAN — PKCE invariants

`_begin_flow` in `src/regstack/routers/oauth.py` generates `code_verifier = secrets.token_urlsafe(64)` server-side and stores it only on the `OAuthState` row. Only the SHA-256 challenge (`code_challenge`) is passed to the provider as a query parameter.

### 🟢 CLEAN — State row lifecycle (modulo W-6)

State row existence, provider match, and `expires_at` are validated against `rs.clock.now()` (not `datetime.now(UTC)`) before the code exchange proceeds. After the callback succeeds, `exchange` calls `oauth_states.consume` which reads and deletes the row. Mongo uses `find_one_and_delete` (atomic). SQL non-atomicity is tracked as W-6.

### 🟢 CLEAN — ID-token verification

`GoogleProvider.verify_id_token` validates: signature via `PyJWKClient` (JWKS fetched with 5-second timeout); `iss` matches configured issuer; `aud` matches configured `client_id`; `exp > now` (enforced by pyjwt); `iat` present; `nonce` claim explicitly checked against `expected_nonce` after decode. Any failure raises `OAuthIdTokenError` with a generic outer message.

### 🟠 W-4 — Race condition: new OAuth user creation unhandled 500 (day 27 — **20 days past SLA**)

`src/regstack/routers/oauth.py:716`: in `_resolve_user`, the branch for brand-new accounts calls `await rs.users.create(new_user)` without catching `UserAlreadyExistsError`. Two concurrent requests with the same Google `sub` arriving within milliseconds can both reach this line; the second raises an unhandled exception that propagates as a 500.

**Remediation:** Wrap `rs.users.create(new_user)` in a `try/except UserAlreadyExistsError` and fall back to `rs.users.get_by_email(info.email)` to retrieve the just-created user.

### 🟢 CLEAN — Linking-policy enforcement, OAuth-only user side effects, identity-row uniqueness, hooks

`_resolve_user` raises `_LinkConflictError("email_in_use")` for existing email-registered users (when auto-link is off), `_LinkConflictError("identity_in_use")` for cross-user identity conflicts, and `_LinkConflictError("already_linked")` for same-user duplicate links. `change-password`, `change-email`, `delete-account` all call `require_password_set(user)`. OAuth unlink refuses when the user has no password and only one linked provider. `(provider, subject_id)` and `(user_id, provider)` uniqueness enforced at the DB level. All four OAuth hook events are in `KNOWN_EVENTS` and fired at the correct points.
