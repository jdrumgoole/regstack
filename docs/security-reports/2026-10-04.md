## Section 3 — Authentication and Authorization

### 🟠 W-2 · Email-change token not jti-blacklisted · day 34 (SLA expired +27 d)

**File:** `src/regstack/routers/account.py`

`POST /confirm-email-change` consumes the email-change JWT but never calls `blacklist.is_revoked(jti)` before use, nor `blacklist.revoke(jti, exp)` after success. A second click on the same confirmation link re-enters the handler, calls `update_email(user.id, same_email)` (idempotent for the email value), but also bumps `tokens_invalidated_after` again — logging the user out of their freshly established post-change session. Inconsistent with the password-reset flow, which correctly blacklists the token's jti.

**Fix:** (a) update `_decode_email_change_token` to return `jti` alongside `(user_id, new_email)`; (b) check `blacklist.is_revoked(jti)` at the top of `confirm_email_change`; (c) call `blacklist.revoke(jti, exp)` on success.

**CORRECTION re W-3:** Yesterday's report W-3 ("confirm-email-change doesn't check `is_active`") was a false positive. Code inspection at `account.py:186–191` confirms `users.get_by_id` is called and `user.is_active` is checked before any mutation. W-3 is **closed** as of this report.

### 🟠 W-4 · OAuth new-user concurrent registration race → unhandled 500 · day 34 (SLA expired +27 d)

**File:** `src/regstack/routers/oauth.py` — `_resolve_user`

When two OAuth callbacks for the same new identity arrive within milliseconds (edge case but possible under retry storms), both pass the "identity not found" check and both attempt `users.create`. The second attempt raises `UserAlreadyExistsError` which propagates as an unhandled 500.

**Fix:** wrap the `users.create` call in `try/except UserAlreadyExistsError`; on conflict, re-fetch the winner and return them.

### 🟠 W-8 · Timing oracle on login for OAuth-only accounts · day 16 (SLA expired +9 d)

**File:** `src/regstack/routers/login.py` lines 99–103

When `user.hashed_password is None`, `rs.password_hasher.verify` is short-circuited entirely. An attacker can distinguish OAuth-only accounts from non-existent accounts by response latency (non-existent fast; OAuth-only skips Argon2 — also fast but differently so).

**Fix:** run a dummy `rs.password_hasher.verify(payload.password, dummy_hash)` even when `hashed_password is None`.

### 🟠 W-13 · Admin `promote-pending` endpoint echoes unvalidated email path param · day 1 (new)

**File:** `src/regstack/routers/admin.py:209–230`

```python
async def admin_promote_pending(
    email: str = Path(..., description="Email of the pending registration"),
    ...
```

The `email` path parameter is typed `str`, not `EmailStr`. The value is echoed verbatim in two HTTP 404/409 error detail strings:

```python
detail=f"No pending registration for {email}."
detail=f"A user with email {email} already exists."
```

This is an admin-only endpoint (requires `is_superuser`), so the direct attack surface is narrow. However, it is the only endpoint in the router layer that accepts an email as a path parameter without `EmailStr` validation, creating an inconsistency, and a malformed or excessively long value reaches the repo query layer unfiltered.

**Fix:** change `email: str = Path(...)` to `email: EmailStr = Path(...)` (or add `Annotated[str, Path(...), StringConstraints(max_length=254)]`).

## Section 5 — Input Validation

### 🟡 I-5 · TOML injection in `regstack init` via unescaped user inputs · day 1 (new)

**File:** `src/regstack/cli/init.py:240–280` (`_render_toml`)

Free-form inputs (`app_name`, `base_url`, `from_address`, `from_name`, `smtp_host`, `mongodb_database`) are interpolated into TOML double-quoted strings via f-strings without escaping TOML metacharacters. A value containing `"` or `\n` produces structurally broken or injected TOML (e.g. `app_name = 'Acme" \nmalicious_key = "injected'`). No remote attack surface — the CLI runs as the operator. However, a malformed interactive input silently corrupts the generated config file.

**Recommendation:** use `tomlkit` (already a `wizard` extra dependency) for writing TOML values.

### 🟡 I-6 · `current_password` fields lack `max_length` on authenticated routes · day 1 (new)

**Files:** `src/regstack/routers/account.py:29,36,46`; `src/regstack/routers/phone.py:27,43`

`ChangePasswordRequest.current_password`, `ChangeEmailRequest.current_password`, `DeleteAccountRequest.current_password`, `PhoneStartRequest.current_password`, and `PhoneDisableRequest.current_password` are all typed `str` with no `max_length`. An authenticated user submitting several MB forces a full Argon2 hash computation against the oversized value. `LoginRequest.password` correctly uses `PasswordStr` with `max_length=128`. These endpoints are auth-gated and covered by `rate_limit` optionals, substantially reducing risk.

**Recommendation:** add `max_length=128` (or match `PasswordStr`) to all `current_password` fields.

### 🟡 I-7 · Token fields in confirm-flow models lack `max_length` · day 1 (new)

**Files:** `src/regstack/routers/login.py:54` (`MfaConfirmRequest.mfa_pending_token`), `src/regstack/routers/phone.py:32` (`PhoneConfirmRequest.pending_token`), `src/regstack/routers/account.py:41` (`ConfirmEmailChangeRequest.token`), `src/regstack/routers/password.py:25` (`ResetPasswordRequest.token`), `src/regstack/routers/verify.py:21` (`VerifyRequest.token`)

### 🟠 W-10 · `GoogleProvider` holds `client_secret` as plain `str` · day 16 (SLA expired +9 d)

**File:** `src/regstack/oauth/providers/google.py:79,90`

## Section 14 — OAuth Subsystem

### 🟢 CLEAN (flow integrity)

- **PKCE:** `code_verifier` generated server-side, stored in the `oauth_states` row only; `code_challenge` (SHA-256) goes to the provider. Never in any URL the browser sees.
- **State lifecycle:** `oauth_states.consume` uses `find_one_and_delete` (atomic) on Mongo. SQL `OAuthStateRepo.consume` is under an open advisory (W-6 below).
- **ID-token verification:** RS256; `aud=client_id`; `iss=GOOGLE_ISSUER`; `exp > now`; required claims `[sub, iss, aud, exp, iat, nonce]`; manual nonce double-check. PyJWT exception collapsed to `OAuthIdTokenError` — no raw pyjwt reason echoed.
- **Linking policy:** `?error=email_in_use` when auto-link disabled; `?error=identity_in_use` / `?error=already_linked` guard re-link scenarios.
- **OAuth-only users:** `POST /login` (hashed_password=None) returns same generic 401 as wrong-password path. `change-password`, `change-email`, `delete-account` return 400 with forgot-password pointer. `DELETE /oauth/{provider}/link` returns 400 (`last sign-in method`) if no password and only one provider.
- **Identity uniqueness:** `(provider, subject_id)` and `(user_id, provider)` enforced at DB level in both SQL and Mongo.
- **OAuth hooks:** `oauth_signin_started`, `oauth_signin_completed`, `oauth_account_linked`, `oauth_account_unlinked` in `KNOWN_EVENTS` and fired at correct router points.

### 🟠 W-6 · SQL `OAuthStateRepo.consume` non-atomic under READ COMMITTED · day 26 (SLA expired +19 d)

**File:** `src/regstack/backends/sql/repositories/oauth_state_repo.py`

SQL `consume()` executes SELECT then DELETE in a single `engine.begin()` transaction. Under READ COMMITTED (PostgreSQL default, SQLite WAL), a second concurrent request with the same `state` can read the row before the first transaction's DELETE commits, defeating the one-shot guarantee. Mongo's `find_one_and_delete` is inherently atomic.

**Fix:** use `DELETE … RETURNING *` (Postgres) or `SELECT … FOR UPDATE` + `DELETE` under SERIALIZABLE isolation.
