## 🔴 CRITICAL (Immediate action required)

### C-1 — `cryptography` CVE-2026-26007: ECC private key recovery (CVSS 8.2)

**Affected path:** `oauth` extra → `pyjwt[crypto]` → `cryptography` (transitive)

The `cryptography` library's public-key loading functions (`EllipticCurvePublicNumbers.public_key()`, `load_pem_public_key()`) fail to verify that the supplied point belongs to the prime-order subgroup. An attacker who can supply a crafted ECC public key can recover the server's private key via an invalid-curve attack, enabling ECDH key recovery or ECDSA signature forgery.

**Why this matters for regstack:** The OAuth flow in `src/regstack/oauth/providers/google.py` calls `PyJWKClient.get_signing_key_from_jwt()` which processes keys fetched from Google's JWKS endpoint. A MITM or a compromised JWKS response could supply a malicious ECC key triggering the vulnerability.

**Fixed in:** `cryptography>=46.0.5` (full fix for all three 2026 CVEs at `>=46.0.7`)

**Action:** Add `cryptography>=46.0.7` explicitly to `pyproject.toml` `[project.optional-dependencies] oauth` (currently this dep is only pulled transitively via `pyjwt[crypto]` with no floor).

Related CVEs fixed by the same pin:
- **CVE-2026-34073** (medium) — DNS name-constraint validation gap in X.509 cert chains.
- **CVE-2026-39892** (moderate) — Buffer overflow on non-contiguous buffer input to `Hash.update()`.

### C-2 — MongoDB CVE-2025-14847 "MongoBleed" (CVSS 8.7, CISA KEV, actively exploited)

**Affected path:** Any deployment using the `mongo` backend

MongoDB server 3.6–8.2.2 leaks uninitialized heap memory in zlib-compressed network responses when message length fields are mismatched. The attack is unauthenticated and requires no credentials. CISA added this to the Known Exploited Vulnerabilities catalogue in December 2025; a working public exploit exists.

regstack's `pymongo` driver itself has no CVE, but it connects to vulnerable server instances. **Every regstack deployment using MongoDB inherits this vulnerability from the server tier.**

**Fixed server versions:** 8.2.3, 8.0.17, 7.0.28, 6.0.27, 5.0.32, 4.4.30.  
**Workaround:** Disable zlib compression (`--networkMessageCompressors snappy,zstd` or `disabled`).

**Action:** Add a note to `docs/architecture.md` and `regstack doctor` health check output that the MongoDB backend requires a patched server (≥ the version for your branch). Consider adding a `doctor` check that reads `db.command("buildInfo")["version"]` and warns if it is below the patched floor.

## 🟠 WARNING (Address within 1 week)

### W-1 — PyJWT CVE-2026-32597: `crit` header bypass (CVSS 7.5)

**File:** `pyproject.toml` — `pyjwt>=2.8` in main dependencies  

PyJWT does not validate the `crit` (Critical) header extension (RFC 7515 §4.1.11). A token listing an unrecognised extension in `crit` must be rejected; PyJWT 2.8–2.11.x accepts it instead. An attacker who can craft or modify JWTs (e.g. token forgery after key leak) could exploit this to bypass claim checks in edge-case configurations.

**Fixed in:** `pyjwt>=2.12.0`

**Action:** Bump the lower bound to `pyjwt>=2.12.0` in both `[project.dependencies]` (main, which carries `pyjwt>=2.8`) and `[project.optional-dependencies] oauth` (which carries `pyjwt[crypto]>=2.8`).

### W-3 — JWT decode error detail leaks PyJWT exception message

**File:** `src/regstack/auth/dependencies.py:120`

```python
raise HTTPException(
    status_code=status.HTTP_401_UNAUTHORIZED,
    detail=f"Invalid token: {exc}",   # leaks PyJWT reason
    ...
)
```

The exception string from PyJWT (e.g. `"Signature verification failed"`, `"Not enough segments"`, `"Invalid header string: must start with a valid JSON object"`) is returned verbatim to the client. The security review prompt is explicit: "JWT decode errors → 401 generic, never the specific reason." This aids attackers in understanding the failure mode (malformed vs. wrong-key vs. expired).

**Action:** Replace with a static `detail="Invalid or expired token."`. The detailed reason is already available via Python's exception chaining in server logs.

### W-4 — Phone MFA endpoints crash (500) for OAuth-only users

**File:** `src/regstack/routers/phone.py` lines 65, 149

`POST /phone/start` (line 65) and `DELETE /phone` (line 149) call:

```python
if not rs.password_hasher.verify(payload.current_password, user.hashed_password):
```

without first checking `user.hashed_password is not None`. For OAuth-only users, `hashed_password` is `None`. Passing `None` as the hash argument to `pwdlib` raises `TypeError`, which FastAPI surfaces as an unhandled 500. This also creates a secondary information-disclosure path: an attacker who knows a target email can probe whether the account is OAuth-only by checking whether they receive a 400 (password mismatch) or 500 (OAuth-only).

`account.py` already has `_require_password_set(user)` for exactly this pattern. `phone.py` is missing the guard.

**Action:** Call `_require_password_set(user)` (imported from `account.py` or moved to a shared location) at the top of both `start` and `disable` handlers in `phone.py`, before the password verification.

### W-5 — Admin `DELETE /admin/users/{id}` does not cascade `oauth_identities`

**File:** `src/regstack/routers/admin.py:131`

```python
await rs.users.delete(user.id)           # no oauth_identities cleanup
await rs.pending.delete_by_email(user.email)
```

The user-facing `DELETE /account` endpoint (account.py:233) correctly calls `await rs.oauth_identities.delete_by_user_id(user.id)` before deleting the user. The admin endpoint does not. This leaves orphaned `oauth_identity` rows in both backends (neither SQLite, Postgres, nor Mongo has a foreign-key cascade between users and oauth_identities).

While the orphaned rows cannot be used to log in (the callback path validates `user.is_active` after resolving the identity), they accumulate indefinitely and could confuse future joins or analytics queries. If a new user registers with the same email as a deleted account and the old identity's `subject_id` is re-linked, the `(provider, subject_id)` unique constraint will raise `OAuthIdentityAlreadyLinkedError` — preventing that OAuth identity from ever being linked again.

**Action:** Add `await rs.oauth_identities.delete_by_user_id(user.id)` before `await rs.users.delete(user.id)` in `admin.py:delete_user`.

### W-6 — GitHub Actions `uses:` directives are tag-pinned, not SHA-pinned

**Files:** `.github/workflows/publish.yml`, `.github/workflows/test.yml`

All `uses:` directives reference mutable tags that can be silently repointed by the upstream maintainer:

| Workflow | Action | Tag used |
|----------|--------|----------|
| both | `actions/checkout` | `@v4` |
| both | `astral-sh/setup-uv` | `@v3` |
| both | `actions/upload-artifact` | `@v4` |
| publish.yml | `actions/download-artifact` | `@v4` |
| publish.yml | `pypa/gh-action-pypi-publish` | `@release/v1` |

`pypa/gh-action-pypi-publish@release/v1` is the highest-risk case: it runs with `id-token: write` permission and publishes directly to PyPI. A supply-chain compromise of this action's tag would allow arbitrary code injection into every published regstack wheel.

**Action:** Pin all `uses:` to their full commit SHA. GitHub's Dependabot (`dependabot.yml` with `package-ecosystem: github-actions`) will keep the SHAs up to date automatically.

Example:
```yaml
- uses: pypa/gh-action-pypi-publish@76f52bc884231ac62f66f0bb069e0be7c85e8ac2  # release/v1
```

### W-7 — SQL OAuth state exchange: TOCTOU race condition on Postgres

**File:** `src/regstack/backends/sql/repositories/oauth_state_repo.py:52–60`

```python
async def consume(self, state_id: str) -> OAuthState | None:
    async with self._engine.begin() as conn:
        row = (await conn.execute(select(self._t).where(...))).first()  # read
        if row is None:
            return None
        await conn.execute(delete(self._t).where(...))                   # delete
    return _row_to_state(row)
```

Under Postgres's default `READ COMMITTED` isolation, two concurrent `POST /oauth/exchange` requests for the same `state_id` can both read the state row in their respective transactions before either commits the delete. Both would proceed to return a valid session JWT for the same OAuth state, effectively issuing two tokens from a single login.

The MongoDB implementation correctly uses `find_one_and_delete` (server-side atomic operation) and is not affected.

**Action:** Replace the SELECT + DELETE with a single `DELETE ... RETURNING *` statement on Postgres/SQLite, or add `SELECT ... FOR UPDATE` before the delete to serialize access. A cross-database approach:

```python
stmt = delete(self._t).where(self._t.c.id == state_id).returning(*self._t.c)
row = (await conn.execute(stmt)).first()
```

SQLAlchemy 2.x and both asyncpg + aiosqlite support `RETURNING`.

### W-8 — `pywebview` and `uvicorn` shipped as base dependencies

**File:** `pyproject.toml` lines 37–39

```toml
"pywebview>=5.0",
"tomlkit>=0.13",
"uvicorn[standard]>=0.29",
```

`pywebview>=5.0` is a native GUI framework that embeds a platform WebView (macOS WebKit, Windows WebView2, Linux WebKitGTK). On Linux it pulls in `PyGObject` and the GLib/WebKitGTK system libraries. Making this a base dependency of a library means **every** `pip install regstack` consumer — including CI pipelines, Docker containers, and production deployments — transitively installs a desktop GUI stack they will never use.

Risks:
- The native WebView engine carries its own CVE history (e.g. Chrome WebView CVE-2026-0628 surfaced during this review period).
- It significantly expands the package's attack surface and install size for consumers who don't use the wizard.
- `uvicorn[standard]>=0.29` in the base dependencies forces an ASGI server on consumers who may be running behind a different server (Gunicorn, Hypercorn, etc.).

**Action:** Move `pywebview`, `tomlkit`, and `uvicorn[standard]` (the wizard's runtime dependencies) to a `wizard` optional extra. The `dev` extra already pins `uvicorn[standard]` independently; a small deduplication opportunity.

### I-3 — `workflow_dispatch` on `publish.yml`; `build` job has no `permissions:` block

**File:** `.github/workflows/publish.yml`

1. **`workflow_dispatch`** as an additional trigger allows a repository admin to manually run the publish workflow. The publish job is correctly gated by `if: startsWith(github.ref, 'refs/tags/v')`, so a manual trigger without a tag cannot actually push to PyPI — but the `build` step (which calls `uv build`) will still run. This is low risk but can confuse auditors.

2. **Missing `permissions:` on the `build` job.** The `publish` job correctly limits to `id-token: write`. The `build` job has no `permissions:` block, defaulting to the repository's default (typically `contents: read` for public repos, but can be `write` if the repo default is changed). Add `permissions: contents: read` explicitly.

3. **No workflow-level `permissions:` in `test.yml`.** Same rationale — explicit is better than inherited.

**Action:** Add `permissions: contents: read` to the `build` job in `publish.yml`, and add `permissions: contents: read` at the workflow level of `test.yml`.

### I-4 — `_encode_email_change_token` emits integer `iat` (inconsistent with float design)

**File:** `src/regstack/routers/account.py:259`

```python
"iat": int(now.timestamp()),   # should be float per CLAUDE.md design
```

The documented invariant (CLAUDE.md "Bulk revocation: float `iat` and `<=` cutoff") states that `iat` must be a float so a session token issued microseconds after a password/email change isn't falsely revoked. `JwtCodec.encode` correctly emits `self.iat.timestamp()` (float). The hand-rolled email-change token encoder uses `int(now.timestamp())` instead.

Email-change tokens are used only to confirm the new address — they don't carry session access — so the practical security impact on bulk revocation is nil. However, the inconsistency is a maintenance hazard for future contributors who read the code.

**Action:** Change `"iat": int(now.timestamp())` to `"iat": now.timestamp()` in `account.py:259`. Apply the same fix to the `_encode_mfa_token` helper in `login.py:174` where the same pattern appears.

### I-5 — `mfa_login_started` hook fires raw SMS code to subscribers

**File:** `src/regstack/routers/login.py:158`

```python
await rs.hooks.fire("mfa_login_started", user=user, code=raw_code)
```

The raw 6-digit SMS code is passed to hook handlers as `code=raw_code`. A host that logs hook arguments (a common debug pattern) would write live, valid MFA codes to its log files. The codes expire in 5 minutes, so the window is short, but centralised log shipping to third-party SIEMs (Splunk, Datadog, etc.) would extend exposure.

**Action:** Remove `code=raw_code` from the hook payload, or document explicitly in `hooks/events.py` / API docs that `mfa_login_started.code` is a live secret and must not be logged.

## 🟢 CLEAN (Passed review)

The following areas were reviewed and found to be secure or appropriately designed:

**§3 Authentication & Authorization**
- All authenticated endpoints correctly inject `rs.deps.current_user()` or `rs.deps.current_admin()`.
- Admin operations correctly require `is_superuser=True` via `current_admin()`.
- Login lockout: `LockoutService.check` fires before password verification, `record_failure` on both "user not found" and "wrong password" branches.
- Constant-time password comparison via `pwdlib` (Argon2id) — no `==` comparisons.
- `reset-password` calls `update_password` (which bumps `tokens_invalidated_after`) AND `lockout.clear`.
- `change-password` bumps `tokens_invalidated_after` via `update_password`. ✓
- `confirm-email-change` bumps `tokens_invalidated_after` via `update_email`. ✓
- Admin `PATCH /users/{id}` (disable) bumps `tokens_invalidated_after` (`admin.py:111`). ✓
- Self-service `DELETE /account` cascades `oauth_identities` before user deletion. ✓
- OAuth-only users (`hashed_password=None`) receive the same generic 401 on login as wrong-password attempts — no account-type enumeration. ✓
- Anti-enumeration on `forgot-password` and `resend-verification`: identical 202 response regardless of email existence. ✓

**§4 Injection Safety**
- No `$where`, `$expr`, `$function`, or `$accumulator` operators in any MongoDB query.
- `ObjectId.is_valid(user_id)` guards all user-facing MongoDB lookups before `ObjectId()` is called.
- All SQL queries use SQLAlchemy Core parameterised expressions. No f-string or `%` interpolation into raw SQL.
- `UtcDateTime` TypeDecorator correctly re-attaches UTC on read for SQLite (and is a no-op for Postgres which preserves timezone natively).
- `purge_expired()` in all SQL repos uses bound parameters for the cutoff timestamp.

**§5 Input Validation**
- All API endpoints accept typed Pydantic models with `extra="forbid"`. No raw `dict` or untyped JSON bodies.
- `EmailStr` validation on all email-bearing fields.
- `is_valid_e164()` called on phone-number input before storage.
- Zero `| safe` filters or `{% autoescape false %}` blocks in any template (email or SSR).

**§7 Session & Token Security**
- HS256 algorithm; per-purpose HMAC-SHA256 derived keys via `derive_secret`. Compromise of one purpose key does not compromise others.
- Every JWT includes `jti` (required in decode options; `secrets.token_urlsafe(16)` at encode time).
- `iat` emitted as float (`self.iat.timestamp()`) in `JwtCodec` — microsecond precision for bulk-revoke correctness.
- PyJWT `verify_exp`/`verify_iat` disabled; expiry re-validated against injected `Clock` — tests are deterministic, production is correct.
- Revocation order in `_authenticate`: decode → `blacklist.is_revoked(jti)` → `get_by_id + is_active` → `is_payload_bulk_revoked`. Correct.
- No JWT secret, SMTP password, or OAuth `client_secret` value appears in any log call.

**§8 CSP / SSR Templates**
- Zero `style="..."` attributes and zero `<style>` blocks in any SSR template.
- Only one `<script>` tag: `base.html:44` (`<script src="..." defer>`). No inline scripts.
- No `{{ user.* }}` or session state rendered server-side — all auth state managed client-side by `regstack.js`.
- `oauth_complete.html` renders only static strings and `{{ ui_prefix }}` (operator-configured, not user input).

**§9 Data Exposure**
- `UserPublic` correctly excludes `hashed_password`, `tokens_invalidated_after`, and `updated_at`. All router endpoints return `UserPublic.from_user()`, never raw `BaseUser`.
- No `f"...{exc}"` patterns in HTTP error response `detail` fields (except W-3 above).

**§10 Git History**
- 30 recent commits reviewed; no credential commits, no accidental secret files.
- `git log --all --diff-filter=A -- '*.env' '*.key' '*.pem' '*secret*' '*credential*'` returns only the initial commit adding `config/secrets.py` (the HMAC utility module, not a credential file).

**§11 Third-Party Integration Security**
- SMTP password loaded via `SecretStr.get_secret_value()` only at send time. Never stored as plain string or logged.
- AWS credentials for SES/SNS come from the standard boto3 credential chain — no hardcoded keys.
- Twilio `auth_token` is `SecretStr` in config; unwrapped only in `send()`.
- Google `client_secret` is `SecretStr` in `OAuthConfig`; unwrapped once in `app.py` before being passed to `GoogleProvider`. Not logged.
- `PyJWKClient` uses `cache_keys=True` and a 30-second default timeout. JWKS URL defaults to Google's HTTPS endpoint.
- `verify_id_token` validates: signature (RS256), `iss`, `aud`, `exp`, `iat`, `nonce`, and `sub` presence. Complete ID-token verification.

**§12 GitHub Actions**
- No `pull_request_target` trigger in either workflow.
- No self-hosted runners (`runs-on: ubuntu-latest` throughout).
- No `${{ github.event.* }}` interpolated into `run:` shell blocks. The only variable expansion in `run:` is `${GITHUB_REF##*/}` (standard shell expansion, not expression context injection).
- No `PYPI_API_TOKEN` secret. OIDC trusted publishing correctly used.
- `publish` job scope: `permissions: id-token: write` only. No `contents: write` or `pull-requests: write`.
- `workflow_dispatch` cannot publish to PyPI without a matching `v*` tag (gated by the `if:` condition on the publish job).
- `actions/cache` keyed on `uv.lock` (file hash), not on user-controlled input.

**§13 PyPI Package Integrity**
- `[tool.hatch.build.targets.wheel]` packages only `["src/regstack"]` — tests, docs, examples, tasks, `.github/` cannot end up in the wheel.
- No developer-machine paths (`/Users/`, `/home/`) in source; `localhost` / `127.0.0.1` appear only in wizard CLI server code (never shipped in production code paths).
- Version verified via `tomllib` in the publish workflow (not by importing the package).
- CLI entry point (`regstack = "regstack.cli.__main__:main"`) does not default to a production database.
- Optional-extra hygiene: `pymongo`, `asyncpg`, `pyjwt[crypto]`, `aioboto3`, and `twilio` are all in `[project.optional-dependencies]`, not in main `[project.dependencies]`.

**§14 OAuth Subsystem**
- PKCE: `code_verifier` stored on the state row only; never in redirect URLs. `code_challenge = base64url(sha256(verifier))` with S256.
- State row lifecycle: `find()` in callback validates provider/expiry; `consume()` atomically deletes the row (Mongo: `find_one_and_delete`; SQL: SELECT+DELETE in one transaction). Second exchange gets 404.
- Expiry checks use `rs.clock.now()` (not `datetime.now(UTC)`) — deterministic under `FrozenClock`.
- Auto-link only fires when `auto_link_verified_emails=True` AND `info.email_verified=True`.
- `identity_in_use`, `already_linked`, `email_in_use`, `user_inactive` error codes are redirected as short strings — no exception internals leaked.
- `DELETE /oauth/{provider}/link` refuses to remove the last sign-in method when no password is set.
- `(provider, subject_id)` and `(user_id, provider)` unique constraints enforced at the DB layer in both backends.
- OAuth hooks `oauth_signin_started`, `oauth_signin_completed`, `oauth_account_linked`, `oauth_account_unlinked` all present in `KNOWN_EVENTS` and fired at correct points.

**§15 Multi-backend Parity**
- CI matrix covers Python 3.11 and 3.12 × SQLite + Postgres + MongoDB on every push and PR.
- Migration `0002_oauth` uses `batch_alter_table` for SQLite compat and has a working `downgrade()`.
- `make_client()` sets `tz_aware=True`; `UtcDateTime` TypeDecorator normalises to UTC on read.

### Top 3 priorities for the development team

1. **Pin `cryptography>=46.0.7` explicitly and bump `pyjwt>=2.12.0`** (C-1, W-1) — the cryptography CVEs are CVSS 8.2 and directly relevant to the OAuth path (ECC key validation during JWKS-backed ID-token verification). These are one-line `pyproject.toml` changes with immediate security impact.

2. **Fix phone endpoint 500 for OAuth-only users** (W-4) — a two-line fix (`_require_password_set` guard) that closes an unhandled-exception information-disclosure path. Without it, OAuth-only users attempting to set up MFA hit a confusing 500 and reveal their account type to an attacker.

3. **Pin GitHub Actions to commit SHAs, especially `pypa/gh-action-pypi-publish`** (W-6) — a compromised publish action running with `id-token: write` could inject arbitrary code into every future regstack wheel. SHA-pinning + Dependabot automation eliminates this risk with minimal ongoing overhead.
