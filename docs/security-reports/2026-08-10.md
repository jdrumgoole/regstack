## 🟡 INFO (Best practice recommendations)

### I-1 · `UserPublic` exposes `tokens_invalidated_after` — acknowledged intentional design

**Section:** §9 — Data Exposure  
**File:** `src/regstack/models/user.py`  
**Carry-over from:** 2026-08-09 (and prior reviews)

`UserPublic.tokens_invalidated_after` is included in API responses. The code carries an inline docstring explaining this is intentional: SPAs can compare this field to their session JWT's `iat` to detect server-side revocation without an extra round-trip. The field reveals when a password or email change occurred, which is low-sensitivity metadata. No action recommended unless future privacy requirements tighten.

### I-2 · CLI `cmd:` log-source variant passes operator input to shell

**Section:** §5 — Input Validation & Injection  
**File:** `src/regstack/cli/validate/logtail.py`  
**Carry-over from:** 2026-08-09

The `regstack validate --log-source cmd:<command>` path passes the user-supplied value via `["sh", "-c", target]`. This is an operator-facing tool explicitly documented as accepting arbitrary shell commands, running only on operator workstations under the operator's own credentials. No HTTP endpoint can reach this code path. Noting for awareness; the design is intentional. If ever exposed to untrusted input, the `cmd:` variant must be removed or sandboxed.

### I-3 · PyJWT floor sits exactly at minimum CVE-fixed version

**Section:** §1 — Dependency Vulnerability Check  
**File:** `pyproject.toml` line 55  
**New observation**

The floor `pyjwt >= 2.13.0` is the exact version that fixes CVE-2026-48524 (JWKS cache DoS) and CVE-2026-48526 (algorithm confusion via public JWK as HMAC secret). While there is no known lower-pinned transitive dependency in the current lock file, there is zero safety margin: any new transitive that requires `pyjwt >= 2.x` could resolve to `2.13.0` or a future patch with its own advisory. Recommend confirming `uv.lock` pins PyJWT at the resolved version during the next release cycle and consider raising the floor to `>= 2.14.0` (if/when released) to create headroom.

### §3 — Authentication & Authorization Audit

- All authenticated endpoints inject `rs.deps.current_user()` or `rs.deps.current_admin()` via FastAPI `Depends`. No authenticated endpoint accepts unauthenticated requests.
- All mutating endpoints require authentication. Public endpoints (`/forgot-password`, `/resend-verification`, `/reset-password`, `/verify`, OAuth callback) are correctly unauthenticated and anti-enumeration-safe.
- `UserPublic.from_user()` is the only serialization path used in all API responses; `hashed_password` and raw `BaseUser` internals never appear in response bodies.
- **Bulk-revoke discipline verified:**
  - **Password reset** (`reset-password`): calls `users.update_password` (bumps `tokens_invalidated_after`) + `lockout.clear` + blacklists the reset `jti`. ✅
  - **Password change** (`change-password`): calls `users.update_password`. ✅
  - **Email-change confirm** (`confirm-email-change`): `users.update_email` bumps `tokens_invalidated_after`. ✅
  - **Admin disable** (`PATCH /admin/users/{id}` with `is_active=False`): calls `users.set_tokens_invalidated_after`. ✅
  - **Account deletion**: cascades `oauth_identities.delete_by_user_id` before `users.delete`. ✅
- OAuth-only users (`hashed_password=None`) handled correctly: `login.py` returns same generic 401 as wrong-password; `change-password`, `change-email`, `delete-account` return 400 with forgot-password pointer.
- Password comparison via `pwdlib.PasswordHasher.verify()` (constant-time Argon2id). No `==` comparison.
- JWT signing keys derived per-purpose via `derive_secret(jwt_secret, purpose)` using HMAC-SHA256. Purposes: `session`, `password_reset`, `email_change`, `phone_setup`, `login_mfa`. Compromise of one derived key does not compromise the master or any other purpose.
