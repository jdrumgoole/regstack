## Section 1 — Dependency CVEs

### 🟠 W-1 — `cryptography` floor below patched release (day 49 — **34 days past SLA**)

`pyproject.toml` declares `cryptography>=48.0.1` in both the `oauth` extra and the `dev` extra. The minimum safe floor is **50.0.1**, covering these confirmed CVEs:

- **CVE-2026-69247** (PKCS#7 `EnvelopedData` Bleichenbacher oracle — CVSS HIGH; fixed in 50.0.1). Distinguishable error paths and timing differences during RSA PKCS#1 v1.5 decryption expose a Bleichenbacher oracle on the PKCS#7 decryption code path. The `pyjwt[crypto]` OAuth path loads RSA primitives at import time; this CVE is on the live code path for OAuth-enabled deployments.
- **CVE-2026-69248** (wildcard DNS name allows escape from `permittedSubtrees` name constraints; fixed in 49.0.0). Certificate verifier accepts wildcard SAN entries that should be rejected by `permittedSubtrees` constraints — directly relevant to the JWKS certificate chain verified during OAuth ID-token validation.
- **CVE-2026-69249** (exponential path-building DoS via duplicate self-signed intermediates; fixed in 48.0.1). Already covered by the existing floor.

**Remediation:** Bump floor to `cryptography>=50.0.1` in both the `oauth` and `dev` entries in `pyproject.toml`; run `uv lock` and push.

### 🟠 W-5 — `aiosmtplib` floor below patched release (day 22 — **15 days past SLA**) ← EXTENDED TODAY

`pyproject.toml` declares `aiosmtplib>=5.1.1`. **Two CVEs** now require a floor of **5.1.3**:

- **CVE-2026-55558** (GHSA-vxj7-4xrp-5vr4, CVSS 5.9 Medium; fixed in 5.1.2): STARTTLS response injection — the library does not clear the receive buffer after the plaintext `220` upgrade response before the TLS handshake begins; an active network attacker on the plaintext leg can inject SMTP response lines that survive into the TLS session. Any deployment using `email_backend=smtp` with STARTTLS is exposed.
- **CVE-2026-90467** (CVSS 4.0 Medium; fixed in 5.1.3 — **NEW, disclosed 2026-09-12**): ESMTP parameter injection — aiosmtplib before 5.1.3 fails to validate email addresses supplied by callers. Addresses containing spaces and angle brackets can be used to append ESMTP parameters (AUTH, NOTIFY, ORCPT) to `MAIL FROM` and `RCPT TO` command lines, forging authenticated sender identities or forcing delivery notifications to attacker-controlled third parties. All `smtp` backend deployments that send user-supplied or user-influenced email addresses are affected.

**Process note:** CVE-2026-90467 was publicly disclosed 2026-09-12 — it was missed by 16 consecutive daily automated reviews. The previous reviews were checking only for the STARTTLS vulnerability (CVE-2026-55558); the newer injection CVE was not caught until today. The same process gap is also present in W-11.

**Remediation:** Bump floor to `aiosmtplib>=5.1.3` in `pyproject.toml`; run `uv lock`. The `>=5.1.2` floor specified by previous reports is itself vulnerable to CVE-2026-90467.

### 🟠 W-11 — `pymongo` floor below patched release (day 2 of SLA clock) ← EXTENDED TODAY

`pyproject.toml` declares `pymongo>=4.9` (in `optional-dependencies.mongo`, `optional-dependencies.secantus`, and `dev`). Yesterday's W-11 found CVE-2026-88029 (HIGH, CVSS 8.3) and CVE-2026-96748 (Medium, CVSS 6.5) fixed in 4.18.1. ## Section 3 — Authentication & Authorization Audit

### 🟢 CLEAN — Endpoint authentication coverage

All mutating endpoints inject `rs.deps.current_user()` or `rs.deps.current_admin()`. Admin endpoints (stats, user listings, user mutation, resend-verification, pending-promote) all require `rs.deps.current_admin()`. All data responses use `UserPublic.from_user()`.

### 🟢 CLEAN — Bulk-revoke discipline

Password reset calls `users.update_password()` + `lockout.clear()`. Password change calls `users.update_password()` + `lockout.clear()`. Admin disable calls `users.set_tokens_invalidated_after()`. Account deletion cascades OAuth identities before deleting the user. Email-change confirm calls `users.update_email()` which bumps `tokens_invalidated_after` — modulo W-2 and W-3, which concern `jti` blacklisting and bulk-revoke check within the confirm handler itself.

### 🟠 W-8 — Timing oracle on login for OAuth-only accounts (day 10 — **3 days past SLA**)

`src/regstack/routers/login.py:99` short-circuits on `hashed_password is None` before the ~100 ms Argon2 verify:

```python
if user.hashed_password is None or not rs.password_hasher.verify(
    payload.password, user.hashed_password
):
```

An attacker can distinguish OAuth-only from password-enabled accounts with ~200 requests and a latency histogram. **Still open. No change.**

**Remediation:** Run a constant-time dummy Argon2 verify when `hashed_password is None`, then raise the same generic 401.

### 🟢 CLEAN — `hashed_password is None` side effects

`change-password`, `change-email`, `delete-account` all call `require_password_set(user)`. OAuth unlink refuses if it would remove the only sign-in method. Login returns the same generic 401 for missing password as for a wrong password (modulo W-8 timing).

### 🟢 CLEAN — Constant-time password comparison, per-purpose JWT key derivation

`pwdlib` (argon2) used throughout; no `==` on raw passwords. `derive_secret(jwt_secret, purpose)` using HMAC-SHA256 in `config/secrets.py` gives each purpose a distinct key.

## Section 4 — Storage-layer Injection Safety

### 🟢 CLEAN — MongoDB backend

All MongoDB queries use typed BSON document constructors with literal operator names. No `$where`, `$expr`, `$function`, or `$accumulator` operators. No user-input regex patterns. `ObjectId.is_valid()` guards all `get_by_id` calls. No unbounded `$in` from user-supplied arrays.

### 🟢 CLEAN — SQL backend

All SQL queries use SQLAlchemy Core with parameterised binds. Two `text(...)` usages (`SELECT 1` health ping; migration 0002 count query) have no user input. `purge_expired()` across all five SQL repos uses bound `now` parameters. `UtcDateTime` TypeDecorator consistently re-attaches UTC on result values.

### 🟠 W-6 — SQL `OAuthStateRepo.consume` non-atomic (day 20 — **13 days past SLA**)

`src/regstack/backends/sql/repositories/oauth_state_repo.py:63`: `consume` wraps `SELECT` + `DELETE` in a single `begin()` transaction with a misleading comment claiming it prevents double-consumption. Under PostgreSQL `READ COMMITTED` (the default), two concurrent connections can both read the row before either commits the `DELETE`, allowing both to receive the same `OAuthState` and exchange the OAuth token twice. The MongoDB backend uses `find_one_and_delete` which is atomic. **Still open. No change.**

**Remediation:** Replace with `DELETE … RETURNING *` (PostgreSQL) or a `SELECT FOR UPDATE … DELETE` serialised pattern (SQLite) so the read and delete are one atomic server-side operation.

## Section 7 — Session & Token Security

### 🟢 CLEAN — JWT configuration, `jti`, `iat` float, clock injection, revocation discipline

`JwtCodec.__init__` enforces `len(jwt_secret) >= 32`. Every token minted by `JwtCodec.encode()` includes `jti=secrets.token_urlsafe(16)`. `iat` emitted as float (RFC 7519 NumericDate) via `payload.iat.timestamp()`. pyjwt's built-in `exp`/`iat` validation disabled; both checked against injected `Clock`. `_authenticate` enforces: decode → blacklist check → `is_active` check → bulk-revoke check — all in the correct order.

### 🟢 CLEAN — No token leakage in logs

`_authenticate` catches `TokenError` and raises a static 401 without echoing the pyjwt exception text. OAuth callback errors log only generic short codes; no raw token, id_token, or JWT secret content in logs.

### 🟠 W-2 — Email-change token `jti` never blacklisted (day 28 — **21 days past SLA**)

`src/regstack/routers/account.py:177` (`confirm_email_change`): after successfully decoding the email-change JWT and calling `users.update_email(...)`, the handler never extracts `payload.jti` or calls `blacklist.revoke(jti, exp)`. A valid email-change link can be replayed until it expires (default 60 min TTL). **Still open. No change.**

**Remediation:** After `_decode_email_change_token(token)`, extract `payload.jti` and `payload.exp`. Check `await rs.blacklist.is_revoked(jti)` first (→ 400 if already consumed). On success, call `await rs.blacklist.revoke(jti, exp)` before returning.

### 🟠 W-3 — Email-change handler skips bulk-revocation check (day 28 — **21 days past SLA**)

`src/regstack/routers/account.py:177` (`confirm_email_change`): after `_decode_email_change_token`, the handler fetches the user by `sub` but never calls `is_payload_bulk_revoked(payload, user.tokens_invalidated_after)`. A token minted before a `change-password` event would still be accepted to change the email. **Still open. No change.**

**Remediation:** After `users.get_by_id(user_id)`, add:
```python
if is_payload_bulk_revoked(payload, user.tokens_invalidated_after):
    raise HTTPException(status_code=400, detail="Email-change link has been invalidated.")
```

## Section 11 — Third-Party Integration Security

### 🟢 CLEAN — SMTP backend

### 🟢 CLEAN — SES backend

### 🟠 W-9 — `SmsConfig` SNS credential fields not `SecretStr` (day 10 — **3 days past SLA**)

`src/regstack/config/schema.py`: `SmsConfig` relies entirely on boto3's ambient credential chain for SNS with no `SecretStr` protection in the pydantic model for explicit AWS credentials. **Still open. No change.**

**Remediation:** Add `aws_access_key_id: str | None = None` and `aws_secret_access_key: SecretStr | None = None` to `SmsConfig`; pass them to the SNS client when provided, mirroring the `EmailConfig` pattern.

### 🟠 W-10 — `GoogleOAuthProvider` holds `client_secret` as plain `str` (day 10 — **3 days past SLA**)

`src/regstack/oauth/providers/google.py:79,90`: `__init__` accepts `client_secret: str` and stores it as `self._client_secret = client_secret`. The pydantic config layer correctly stores it as `SecretStr`, but it is unwrapped before being passed to the provider constructor. If the provider object is ever serialised or printed, the secret appears in plaintext. **Still open. No change.**

**Remediation:** Change parameter type to `SecretStr`; call `.get_secret_value()` only at the token-exchange POST.

### 🟢 CLEAN — Google JWKS verification

`GoogleProvider.verify_id_token` validates signature via `PyJWKClient` against Google's JWKS URL with a 5-second timeout, validates `iss`, `aud`, `exp`, `iat`, `nonce`, and `sub`. Algorithm pinned to `RS256`. Failures raise `OAuthIdTokenError` with a generic outer message; specific failure logged at WARNING only.

## Section 14 — OAuth Subsystem Audit

### 🟢 CLEAN — PKCE invariants

`_begin_flow` generates `code_verifier = secrets.token_urlsafe(64)` server-side and stores it only on the `OAuthState` row. Only the SHA-256 challenge is passed to the provider as a query parameter.

### 🟢 CLEAN — State row lifecycle (modulo W-6)

State row existence, provider match, and `expires_at` validated against `rs.clock.now()`. After callback, `exchange` calls `oauth_states.consume` which reads and deletes atomically on Mongo (`find_one_and_delete`). SQL non-atomicity tracked as W-6.

### 🟢 CLEAN — ID-token verification

`GoogleProvider.verify_id_token` validates: signature via `PyJWKClient` (5-second timeout), `iss` matches configured issuer, `aud` matches `client_id`, `exp > now`, `iat` present, `nonce` claim explicitly checked. Any failure raises `OAuthIdTokenError` with a generic outer message.

### 🟠 W-4 — Race condition: new OAuth user creation unhandled 500 (day 28 — **21 days past SLA**)

`src/regstack/routers/oauth.py:716`: `_resolve_user` calls `await rs.users.create(new_user)` without catching `UserAlreadyExistsError`. Two concurrent requests with the same Google `sub` arriving within milliseconds can both reach this line; the second raises an unhandled exception that propagates as a 500. **Still open. No change.**

**Remediation:** Wrap in `try/except UserAlreadyExistsError` and fall back to `rs.users.get_by_email(info.email)`.

### 🟢 CLEAN — Linking-policy, OAuth-only side effects, identity-row uniqueness, hooks

`_resolve_user` raises appropriate `_LinkConflictError` for all conflict scenarios. `change-password`, `change-email`, `delete-account` call `require_password_set(user)`. OAuth unlink refuses when the user has no password and only one linked provider. `(provider, subject_id)` and `(user_id, provider)` uniqueness enforced at the DB level. All four OAuth hook events in `KNOWN_EVENTS` and fired at the correct points.
