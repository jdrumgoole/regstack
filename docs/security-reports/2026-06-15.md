## 🟠 WARNING (Address within 1 week)

### W-1 — CVE-2026-48710 (BadHost): Starlette 1.0.0 in lockfile — fix requires ≥ 1.0.1

**CVE:** CVE-2026-48710  
**GHSA:** GHSA-86qp-5c8j-p5mr  
**Affected:** Starlette 0.8.3 – 1.0.0 (inclusive)  
**Fix:** Starlette ≥ 1.0.1 (released 2026-05-21)  
**Pinned in uv.lock:** `starlette==1.0.0`  
**pyproject.toml floor:** `fastapi>=0.120.0` (transitively pulls starlette, but does not constrain to ≥1.0.1)

**Root cause:**

Prior to Starlette 1.0.1, `request.url` was reconstructed by concatenating the HTTP `Host` header with the raw request path and re-parsing the result. The `Host` value was never validated against RFC 9112 §3.2 / RFC 3986 §3.2.2 before concatenation. A single injected `/`, `?`, or `#` character in the `Host` header could make `request.url.path` report a different path than the one the router actually dispatched on (which uses `scope["path"]`).

**Impact on regstack:**

regstack's own auth is Depends()-injection on each route (`Depends(rs.deps.current_user())`), reading the `Authorization: Bearer` header — not path-based middleware reading `request.url.path`. FastAPI's router dispatches on `scope["path"]` (unaffected by the malformed Host), not `request.url.path`. A direct JWT-bypass against regstack's own endpoints via this CVE is therefore not demonstrable from first principles.

However, as a **library shipped in the PyPI wheel**:

1. `uv.lock` resolves to a version with an open CVE. A consumer who pins to regstack's lockfile inherits the vulnerability.
2. Host apps that layer path-based auth middleware (common pattern for e.g. blocking `/admin` at the middleware level) above regstack endpoints are directly exploitable.
3. The `pyproject.toml` declared floor on `fastapi` does not guarantee downstream consumers pull `starlette>=1.0.1`.

**Fix:**

```toml
# pyproject.toml — base dependencies
"starlette>=1.0.1",
```

Then regenerate the lockfile:

```bash
uv lock --upgrade-package starlette
```

This is a one-line change; Starlette 1.0.1 is backwards-compatible with Starlette 1.0.0.

## 🟡 INFO (Best practice recommendations)

### I-1 — CVE-2026-48526: PyJWT 2.12.1 in lockfile — algorithm-confusion fix in ≥ 2.13.0

**CVE:** CVE-2026-48526  
**Affected:** PyJWT < 2.13.0  
**Fix:** PyJWT 2.13.0  
**Pinned in uv.lock:** `pyjwt==2.12.1`

**Vulnerability description:**

When an application decodes JWTs supporting **both** symmetric and asymmetric algorithms in a single `pyjwt.decode()` call while passing a JWK JSON document as the HMAC key, PyJWT < 2.13.0 does not validate that the key matches the intended algorithm family. An attacker can sign a forged token with the issuer's public key material (treated as an HMAC secret), bypassing signature verification.

**Impact on regstack:**

Two entirely separate code paths consume PyJWT:

1. **Session tokens** (`auth/jwt.py:JwtCodec.decode`): key is `bytes` from `derive_secret(jwt_secret, purpose)` (raw HMAC-SHA256 output); algorithms is `[config.jwt_algorithm]` (default `"HS256"`). Not a JWK JSON. Not mixed-family.

2. **Google ID-token verification** (`oauth/providers/google.py:GoogleProvider.verify_id_token`): key is an RSA key object from `PyJWKClient`; algorithms is `["RS256"]`. Not HMAC, not mixed.

Neither code path mixes symmetric and asymmetric algorithms in a single `decode()` call, which is the precondition the CVE requires. **No practical attack path exists against regstack's architecture at this time.**

**Action (defense-in-depth):**

Bump the floor in `pyproject.toml`:

```toml
# base dependencies
"pyjwt>=2.13.0",

# oauth extra
"pyjwt[crypto]>=2.13.0",
```

And in the `dev` extra:

```toml
"pyjwt[crypto]>=2.13.0",
```

This closes the gap for any future code change that might inadvertently mix algorithm families.

### §7 — Session & Token Security

- JWT algorithm: HS256 (configurable); secret read from `config.jwt_secret` (a `SecretStr`); minimum length enforced at construction.
- Every JWT includes `jti` (random `secrets.token_urlsafe(16)`). Per-token revocation via `BlacklistRepo` is functional.
- `iat` emitted as float (RFC 7519 NumericDate, `to_claims` line: `"iat": self.iat.timestamp()`). `exp` is int. This ensures a login completing microseconds after a password change has `iat > cutoff` and is not falsely revoked.
- `JwtCodec.decode` disables pyjwt's `verify_exp`/`verify_iat`/`verify_nbf` and validates both against the injected `Clock`. Tests using `FrozenClock` get deterministic expiry behaviour.
- `_authenticate` order verified:
  1. Decode token → 401 on `TokenError` (static message, no pyjwt reason echoed).
  2. `blacklist.is_revoked(jti)` → 401 if revoked.
  3. `users.get_by_id(sub)` → 401 if not found or `is_active=False`.
  4. `is_payload_bulk_revoked(payload, user.tokens_invalidated_after)` → 401 if `iat <= cutoff`.
- Token leakage scan of `src/regstack/routers/`: no `access_token`, `id_token`, or JWT string found in `log.info`/`log.warning`/`log.error` calls. Google token-exchange body is at `DEBUG` (resolved from I-3, 2026-05-22).
- JWT signing keys per-purpose; `_key(purpose)` returns `derive_secret(jwt_secret, purpose)`. Session key compromise does not expose password-reset, email-change, phone-setup, or login-MFA keys.
