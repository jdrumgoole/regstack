## Section 1 — Dependency CVEs

### 🟠 W-12 — `pyjwt` floor below 2.14.0 — nine-CVE cluster (day 1 of SLA clock) ← **NEW TODAY**

`pyproject.toml` declares `pyjwt>=2.13.0` in `dependencies` and `pyjwt[crypto]>=2.13.0` in `optional-dependencies.oauth` and `dev`. PyJWT 2.14.0 was released on 2026-09-11 and fixes a nine-CVE cluster. Two CVEs are directly on regstack's live code paths:

- **CVE-2026-102268 (CVSS 9.1 — CRITICAL severity class):** `is_pem_format` in `jwt/utils.py` does not recognise every PEM representation accepted by the `cryptography` loader. When an application mixes HMAC and asymmetric algorithms and supplies a mutated public-key PEM as raw bytes, `HMACAlgorithm.prepare_key` treats the unrecognised asymmetric key as an HMAC secret; an attacker who knows the public key can then forge authenticated HMAC tokens. **Applicability to regstack's own tokens:** regstack's `JwtCodec` uses HS256 with HMAC keys derived via `derive_secret()` — no PEM is involved, and the algorithm is never mixed with an asymmetric one. The specific forgery path does not apply to regstack's own session or purpose tokens. **Applicability to the OAuth path:** `GoogleProvider.verify_id_token` pins `algorithms=["RS256"]`, which closes the HMAC-confusion exploit on the ID-token verification step. **Residual risk:** Any downstream host application that combines regstack with their own asymmetric-key JWT logic over the same pyjwt installation — a common pattern — inherits the vulnerable version floor. The base `dependencies` list is installed on every `pip install regstack`; a vulnerable pyjwt is thus part of regstack's supply-chain footprint. The floor must be raised regardless of regstack's internal mitigations.

- **CVE-2026-102267 (CVSS 7.4 — HIGH):** `PyJWKClient` follows HTTP redirects when fetching the JWKS endpoint without validation. A DNS/BGP hijack or a compromised CDN edge node for `www.googleapis.com` could redirect the JWKS fetch to a server returning attacker-controlled signing keys. This is a direct code-path vulnerability for `GoogleProvider.verify_id_token`, which calls `self._jwks_client.get_signing_key_from_jwt(id_token)` inside `asyncio.to_thread`. The 5-second fetch timeout (`JWKS_FETCH_TIMEOUT_SECONDS = 5`) bounds the DoS window but does not block a redirect-injected malicious key. This CVE is directly on regstack's OAuth ID-token verification path for every deployment with `enable_oauth=True`.

- **CVE-2026-102266 (CVSS 7.4):** `HMACAlgorithm.from_jwk` does not reject JWK objects whose `kty` is inconsistent with the algorithm string, allowing HMAC/asymmetric confusion through the JWK import path. Not directly on regstack's own JWT codec path but affects downstream consumers of the installed pyjwt version.

- **CVE-2026-102265, CVE-2026-102269, CVE-2026-102270, CVE-2026-102273, CVE-2026-102274, CVE-2026-102275 (CVSS 4.4–6.5):** Additional medium-severity fixes in 2.14.0. Full details in the pyjwt 2.14.0 release notes.

**Remediation:** Bump both floor entries to `pyjwt>=2.14.0` and `pyjwt[crypto]>=2.14.0` in `pyproject.toml`; run `uv lock`. Two-line edit; no API-surface change.

## Section 3 — Authentication & Authorization Audit

### 🟢 CLEAN — Endpoint authentication coverage

All mutating endpoints inject `rs.deps.current_user()` or `rs.deps.current_admin()`. Admin endpoints (stats, user listings, user mutation, resend-verification, pending-promote) all require `rs.deps.current_admin()`. `UserPublic.from_user()` is the only projection used in API responses.

### 🟢 CLEAN — Bulk-revoke discipline

Password reset: `users.update_password()` + `lockout.clear()`. Password change: `users.update_password()` + `lockout.clear()`. Admin disable: `users.set_tokens_invalidated_after()`. Account deletion: cascades `oauth_identities.delete_by_user_id()` before `users.delete()`. Email-change confirm: `users.update_email()` bumps `tokens_invalidated_after` — modulo W-2 and W-3 (jti blacklisting and bulk-revoke check absent from the confirm handler).

### 🟢 CLEAN — OAuth-only user handling

`POST /login` checks `user.hashed_password is None` before `verify()`, returning the same generic 401 as a wrong-password attempt. `change-password`, `change-email`, `delete-account` call `require_password_set(user)` → 400. OAuth unlink refuses when `hashed_password is None` and no other provider is linked. Constant-time `pwdlib` comparison used via `password_hasher.verify()`.

### 🟢 CLEAN — JWT purpose derivation

`JwtCodec._key(purpose)` calls `derive_secret(master, purpose)` (HMAC-SHA256). Every purpose (`session`, `password_reset`, `email_change`, `phone_setup`, `login_mfa`) uses a distinct derived key. `JwtCodec` disables pyjwt's `exp`/`iat` checks, validates both against the injected `Clock`, and requires `jti`. `iat` is emitted as a float. Bulk-revoke comparison is `payload.iat <= cutoff`.

## Carry-forward Findings Not Separately Discussed Above

### 🟠 W-2 — Email-change token `jti` never blacklisted (day 29 — **22 days past SLA**)

`src/regstack/routers/account.py` `confirm_email_change`: after successfully decoding the email-change JWT and calling `users.update_email(...)`, the handler never extracts `payload.jti` or calls `blacklist.revoke(jti, exp)`. A valid email-change link can be replayed until it expires (default 60-min TTL). **Still open. No change.**

**Remediation:** After `_decode_email_change_token(token)`, extract `jti`/`exp`, check `await rs.blacklist.is_revoked(jti)` → 400 if consumed, then call `await rs.blacklist.revoke(jti, exp)` on success.

### 🟠 W-3 — Email-change handler skips bulk-revocation check (day 29 — **22 days past SLA**)

`src/regstack/routers/account.py` `confirm_email_change`: after `_decode_email_change_token`, the handler fetches the user but never calls `is_payload_bulk_revoked(payload, user.tokens_invalidated_after)`. A token minted before a `change-password` event would still be accepted. **Still open. No change.**

**Remediation:** After `users.get_by_id(user_id)`, add a bulk-revoke check.

### 🟠 W-6 — SQL `OAuthStateRepo.consume` non-atomic under READ COMMITTED (day 21 — **14 days past SLA**)

`src/regstack/backends/sql/repositories/oauth_state_repo.py`: `consume` wraps both the `SELECT` and `DELETE` in a single `engine.begin()` transaction, which serialises operations from a single connection. However, under PostgreSQL's default READ COMMITTED isolation level, two concurrent connections can both `SELECT` the row before either commits the `DELETE`. The second connection's `DELETE` affects 0 rows, but it has already returned the state data — both callers receive the state row and can exchange it for a session token. The fix requires either `SELECT ... FOR UPDATE` row-level locking or a single `DELETE ... RETURNING *` statement. SQLite uses database-level locking so the race is not reachable there. **Still open. No change.**

**Remediation:** Replace the SELECT + DELETE with a single `DELETE FROM oauth_states WHERE id = ? RETURNING *` bound to the `asyncpg` / `aiosqlite` backend, or add `with_for_update()` to the SELECT.

### 🟠 W-8 — Timing oracle distinguishes OAuth-only accounts on login (day 11 — **4 days past SLA**)

`src/regstack/routers/login.py:99–103`: when `user.hashed_password is None`, the short-circuit `or` prevents the Argon2 `verify()` call. This means login returns measurably faster for OAuth-only accounts than for accounts with an incorrect password, allowing timing-based enumeration of which accounts use OAuth-only sign-in. **Still open. No change.**

**Remediation:** Always call `rs.password_hasher.dummy_verify()` (a no-op Argon2 verification that takes the same time as a real one) when `hashed_password is None`, before raising the 401.
