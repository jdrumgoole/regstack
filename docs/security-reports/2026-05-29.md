## 🟠 WARNING (Address within 1 week)

### W-1 · Starlette 1.0.0 in lockfile — BadHost CVE-2026-48710

**Section:** §1 Dependency Vulnerability Check  
**File:** `uv.lock` (resolved `starlette = 1.0.0`)

CVE-2026-48710 ("BadHost") was disclosed and fixed in Starlette 1.0.1
(released 2026-05-21, eight days ago). The current `uv.lock` was generated
before that release and still pins starlette to 1.0.0.

**Technical detail:** Starlette < 1.0.1 constructs `request.url` (including
`request.url.path`) by consuming the raw `Host` header without sanitising it
first. An attacker who sends a single malformed character in `Host` can cause
`request.url.path` to appear to be a different path than what the ASGI router
actually dispatched, bypassing any middleware that gates access using
`request.url.path` comparisons.

**Impact on regstack specifically:**  
regstack's own auth enforcement is in FastAPI `Depends(...)` closures and
reads the `Authorization: Bearer` header through `HTTPBearer` — it does not
use `request.url.path` for access control decisions. So regstack's own
endpoints are not directly bypassed. However:

1. Host apps that add their own path-based security middleware (a very common
   pattern: "block `/admin/*` in middleware") inherit the vulnerability.
2. Publishing a wheel whose transitive closure ships a starlette with an
   active CVE is a supply-chain concern for any downstream consumer.

**Recommended fix:**

```bash
# Refresh lockfile so uv resolves the patched starlette 1.0.1
uv lock --upgrade-package starlette
uv sync --extra dev
```

Additionally, add an explicit floor in `pyproject.toml` so the constraint
is documented and survives future `uv lock` runs:

```toml
# fastapi>=0.120.0 picks up CVE-2025-62727; starlette>=1.0.1 picks up
# CVE-2026-48710 (BadHost host-header auth-bypass).
"fastapi>=0.120.0",
"starlette>=1.0.1",   # transitive, but floor this explicitly
```

### W-2 · PyJWKClient JWKS fetch has no timeout — thread-pool exhaustion risk

**Section:** §11 Third-Party Integration Security / §14c ID-token verification  
**File:** `src/regstack/oauth/providers/google.py:83`

```python
self._jwks_client = PyJWKClient(jwks_url, cache_keys=True)
```

`PyJWKClient` supports a `timeout` parameter (added in pyjwt 2.4.0). Without
it, the `urllib.request.urlopen` call inside `PyJWKClient.get_signing_key_from_jwt`
has no deadline.

Commit `81005cf` correctly moved the JWKS fetch to `asyncio.to_thread` so the
event loop is not blocked on a cache miss. However, threads from the asyncio
default thread pool (typically 5–32 workers) can still be occupied
indefinitely if Google's JWKS endpoint is slow or unreachable. Under sustained
OAuth sign-in traffic during a transient Google outage, all thread-pool workers
could be waiting on JWKS fetches simultaneously, stalling every other operation
offloaded to threads.

**Recommended fix:**

```python
self._jwks_client = PyJWKClient(jwks_url, cache_keys=True, timeout=10)
```

10 seconds is a reasonable outer bound for a JWKS round-trip. The error
raised on timeout will be caught by the outer `except Exception` block in
`verify_id_token` and surfaced as `OAuthIdTokenError("jwks lookup failed: …")`,
which the router redirects to `?error=id_token_failed` — no change to the
caller interface required.

## 🟡 INFO (Best-practice recommendations)

### I-1 · Per-IP rate limiting is opt-in only — no default configuration

**Section:** §6 Rate Limiting & DoS Prevention  
**File:** `src/regstack/config/schema.py:224-242`

All `*_rate_limit` config fields default to `None`. Account-level lockout
(`LockoutService`) is always active, but per-source-IP throttling requires
the host to install the `rate_limit` extra and configure at least
`login_rate_limit`, `register_rate_limit`, and `forgot_password_rate_limit`.

A distributed botnet (many distinct IPs, each below the per-IP threshold)
can still hammer `/register` or `/forgot-password` at scale with no built-in
defence beyond the account-level lockout.

**Recommendation:** Add a prominent "Rate limiting" section to the README /
docs with recommended values and explicit instructions, so operators are less
likely to ship without them:

```toml
login_rate_limit = "10/minute"
register_rate_limit = "5/minute"
forgot_password_rate_limit = "5/minute"
reset_password_rate_limit = "5/minute"
resend_verification_rate_limit = "3/minute"
```

This is a documentation and configuration guidance gap, not a code bug.

### I-2 · Login failure count disclosed in 401 response body

**Section:** §3 Authentication & Authorization / §9 Data Exposure  
**File:** `src/regstack/routers/login.py:40-43`

```python
detail = f"Invalid email or password. {remaining} attempt(s) remaining."
```

The remaining-attempts count leaks to an unauthenticated caller, telling an
attacker exactly how many guesses they have before lockout fires. This was
flagged in Review #15 and accepted as a deliberate usability trade-off (the
MFA confirm response also surfaces `attempts_remaining`). Recording here for
the project to consciously confirm that trade-off in each review cycle.

**Recommendation:** If usability allows, replace with a generic
"Invalid email or password." response (no count) to avoid giving credential-
stuffers a countdown. Alternatively, document the deliberate trade-off in
`docs/security.md` so future reviewers know it is intentional.

### I-3 · OAuthTokenExchangeError logs Google's raw response body

**Section:** §9 Data Exposure / §11 Third-Party Integration  
**File:** `src/regstack/oauth/providers/google.py:143-146`

```python
raise OAuthTokenExchangeError(
    f"google token exchange failed: {response.status_code} {response.text}"
)
```

This exception is caught in `routers/oauth.py:315` and logged via
`log.warning("oauth token exchange failed: %s", exc)`. Google's error
responses are safe in practice, but the raw `response.text` is logged
verbatim: if Google ever includes partially-redacted credential material,
a `client_id` excerpt, or a full redirect URI containing a `code` fragment
in an error body, it would land in the server's log stream.

**Recommendation:** Log only the status code at WARNING level; log the
full body at DEBUG so it is available in local dev but not in production
log aggregators:

```python
# providers/google.py
raise OAuthTokenExchangeError(
    f"google token exchange failed: {response.status_code}"
)
```

### I-4 · Password-reset and email-change JWTs are reusable within their TTL

**Section:** §7 Session & Token Security / §3 Authentication & Authorization  
**Files:** `src/regstack/routers/password.py`, `src/regstack/routers/account.py`

Both the password-reset endpoint (`POST /reset-password`) and the email-change
confirm endpoint (`POST /confirm-email-change`) authenticate callers via a JWT
with no backing DB row. Because the JWT is not consumed on first use, a valid
token can be resubmitted multiple times within its TTL.

**Concrete scenario (password reset):**

1. Alice requests a password reset; the reset JWT is valid for 30 minutes.
2. Alice uses the link, sets her new password.
3. An attacker who separately obtained a copy of the JWT (e.g. from Alice's
   email inbox, clipboard, or a intercepted HTTP request) submits the same
   JWT with a _different_ `new_password` within the remaining TTL window.
4. `update_password` succeeds: Alice is now locked out of her own account.

The 30-minute TTL (`password_reset_token_ttl_seconds = 1800`) limits the
exposure window. This design is documented in `CLAUDE.md` and `docs/security.md`
as intentional ("no DB row because the token is self-contained and
short-lived"). Recording here for completeness and because the threat model
assumes the token remains confidential once used.

**Recommendation (low priority):** Consider adding a `PendingPasswordReset`
collection (similar to `pending_registrations`) that tombstones a `jti` on
first use, or — lower cost — note this explicitly in `docs/security.md` so
operators who need single-use reset links know to implement their own
invalidation hook.

### §3 Authentication & Authorization Audit

- All authenticated endpoints inject `rs.deps.current_user()` or
  `rs.deps.current_admin()`.
- `_authenticate` enforces all three revocation tiers in order: decode →
  `blacklist.is_revoked(jti)` → `is_payload_bulk_revoked(iat, cutoff)` →
  `is_active` check.
- Bulk-revoke triggered correctly on: password reset (`update_password` bumps
  `tokens_invalidated_after`), password change (`update_password`), email change
  confirm (`update_email` bumps), admin disable (`set_tokens_invalidated_after`).
- OAuth-only users (`hashed_password=None`) receive the same generic 401 as
  a wrong-password attempt — no enumeration of OAuth-only accounts.

  `change-email`, `delete-account`, `phone-start`, `phone-disable`.

  (Argon2id, not `==`).
- JWT signing keys are per-purpose via `derive_secret(jwt_secret, purpose)`;

### §4 Storage-layer Injection Safety

**MongoDB:** All queries use pymongo's dict-literal syntax with Python values

`get_by_id` / `update_*` / `delete` calls. No regex patterns built from user
input.

**SQL:** All repositories use SQLAlchemy Core (`select`, `update`, `delete`,
`insert`) with parameterised binds. The only `text()` call is
`text("SELECT 1")` in `SqlBackend.ping()` — no user input involved.
`UtcDateTime.process_result_value` correctly re-attaches UTC tzinfo on read.
`purge_expired()` implementations use bound parameters.
