### 🟠 W-2 · Email-change JWT not jti-blacklisted after confirm · day 62 (SLA expired +48 d)

**Source:** `src/regstack/routers/account.py` `confirm_email_change` — re-verified today.

`POST /confirm-email-change` decodes the email-change JWT, calls `rs.users.update_email`, then returns — it never writes `jti` to the blacklist. Within the token's TTL window the same link can be replayed. If the address was already changed a second replay returns `UserAlreadyExistsError` (409), which an attacker capturing the original link can use to confirm whether the address swap succeeded, contradicting anti-enumeration intent.

**Fix:** after `rs.users.update_email` succeeds, call `rs.blacklist.revoke(token_payload.jti, token_payload.exp)`. Pattern mirrors the password-reset flow at `password.py:123`.

### 🟠 W-4 · OAuth new-user concurrent registration → unhandled 500 · day 62 (SLA expired +48 d)

**Source:** `src/regstack/routers/oauth.py` `_resolve_user` — re-verified today.

In the brand-new-account path (`# 4. Brand-new account.`), `rs.users.create(new_user)` is not wrapped in a `try/except UserAlreadyExistsError`. Under concurrent OAuth callbacks for the same new email address (provider retry or two simultaneous requests), the second call hits the `users.email` UNIQUE constraint and raises an unhandled exception, producing a 500 instead of a graceful `?error=email_in_use` redirect.

**Fix:** wrap `rs.users.create(new_user)` in `try/except UserAlreadyExistsError` and raise `_LinkConflictError("email_in_use")`.

### 🟠 W-6 · SQL OAuthStateRepo.consume non-atomic under READ COMMITTED · day 54 (SLA expired +40 d)

**Source:** `src/regstack/backends/sql/repositories/oauth_state_repo.py` `consume` — re-verified today.

Under PostgreSQL's default READ COMMITTED isolation, the SELECT then DELETE in `consume` allows two concurrent `/oauth/exchange` calls to each read the row before either deletes it. Both obtain a valid result and both get session JWTs, enabling a state_id to be exchanged twice. The Mongo backend uses `find_one_and_delete` (atomic), creating an inconsistency between backends.

**Fix:** replace the SELECT + DELETE pair with a `SELECT ... FOR UPDATE` (`with_for_update()` on the SQLAlchemy select) or a single `DELETE ... RETURNING` inside the `engine.begin()` transaction.

### 🟠 W-8 · Timing oracle on login for OAuth-only accounts · day 44 (SLA expired +30 d)

**Source:** `src/regstack/routers/login.py:99` — re-verified today.

```python
if user.hashed_password is None or not rs.password_hasher.verify(
    payload.password, user.hashed_password
):
```

Python's short-circuit `or` skips the ~100 ms Argon2 `verify()` call when `hashed_password is None`. An attacker timing responses can distinguish OAuth-only accounts (fast 401, ~microseconds) from password-bearing accounts (slow 401, ~100–300 ms Argon2 work), enabling enumeration of which accounts use Google-only sign-in and facilitating targeted phishing.

**Fix:** call `rs.password_hasher.dummy_verify()` (constant-time placeholder) when `hashed_password is None`, before raising the generic 401.

### 🟠 W-10 · GoogleProvider client_secret stored as plain str · day 44 (SLA expired +30 d)

**Source:** `src/regstack/oauth/providers/google.py:90` — re-verified today.

Storing the client_secret as a plain `str` means it is visible in heap dumps, `repr()` output, `pprint(vars(provider))` debug output, and any logging that captures object state. `EmailConfig.smtp_password` is correctly typed as `SecretStr`; `GoogleProvider` should match that discipline.
