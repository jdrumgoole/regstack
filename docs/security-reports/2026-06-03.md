## 🔴 CRITICAL (Immediate action required)

### C-1 — CVE-2026-48710 "BadHost": Starlette 1.0.0 in dependency tree

**Finding:**

`uv.lock` pins `starlette 1.0.0`. Starlette < 1.0.1 is vulnerable to
[CVE-2026-48710](https://cvefeed.io/vuln/detail/CVE-2026-48710) ("BadHost"),
published 21 May 2026. A malformed HTTP `Host` header value containing `/`,
`?`, or `#` causes Starlette to reconstruct `request.url.path` with shifted
path/query/fragment boundaries. Any code that makes security decisions based on
`request.url.path` — typically path-based auth middleware — can be bypassed
while the underlying route still executes.

**Scope within regstack:**

regstack itself does **not** use `request.url.path` for authentication or
authorization decisions (verified by codebase grep — no matches in
`src/regstack/`). The `AuthDependencies._authenticate` path reads only the
`Authorization: Bearer` header; routing decisions are handled by FastAPI's ASGI
router which uses `scope["path"]` directly and is unaffected.

However, regstack is a library published to PyPI. Any host application that
embeds regstack and adds path-based auth middleware (a common FastAPI pattern)
alongside it is directly exploitable via a single crafted request. Regstack's
`pyproject.toml` pins `fastapi>=0.120.0` but does **not** constrain
`starlette` directly; the installed FastAPI 0.136.1 resolves to starlette 1.0.0
transitively without guaranteeing the patched version.

**Fix:**

Add a direct starlette floor to `pyproject.toml` `dependencies`:

```toml
# starlette>=1.0.1 picks up CVE-2026-48710 (BadHost: Host-header path
# poisoning that can bypass path-based auth middleware).
"starlette>=1.0.1",
```

Then run `uv sync --upgrade-package starlette` and commit the updated
`uv.lock`. This is a one-line change to `pyproject.toml`; Starlette 1.1.0
is the current release and is a safe upgrade target.

Starlette 1.0.1 validates the `Host` header against RFC 9112 §3.2 /
RFC 3986 §3.2.2 before constructing `request.url` and falls back to
`scope["server"]` for malformed values, neutralising the attack path.

## 🟠 WARNING (Address within 1 week)

### W-1 — PyJWKClient missing `timeout=` argument (CARRY-OVER from 2026-05-22)

`src/regstack/oauth/providers/google.py:83`:

```python
self._jwks_client = PyJWKClient(jwks_url, cache_keys=True)
```

No `timeout` argument is passed. The underlying `urllib.request.urlopen` call
has no deadline. PR #80 (2026-05-20 review) correctly offloaded the call to
`asyncio.to_thread` so it no longer blocks the event loop, but threads in the
default asyncio pool can still be exhausted under sustained JWKS-miss load if
Google's JWKS endpoint is slow or unreachable.

**Fix** (one line, `google.py:83`):

```python
self._jwks_client = PyJWKClient(jwks_url, cache_keys=True, timeout=5)
```

PyJWT ≥ 2.4 supports the `timeout` keyword on `PyJWKClient.__init__`; the
project already requires `pyjwt>=2.12.1`.

This finding was first raised as W-1 in the 2026-05-22 review and is not yet
resolved.

## 🟡 INFO (Best practice recommendations)

### I-1 — `was_new_account` always `False` in `/oauth/exchange` response (CARRY-OVER)

`src/regstack/routers/oauth.py:176`:

```python
return ExchangeResponse(
    access_token=state.result_token,
    redirect_to=state.redirect_to,
    was_new_account=False,   # ← always False regardless of actual outcome
    expires_in=rs.config.jwt_ttl_seconds,
)
```

The `was_new` boolean computed during `_resolve_user` is never persisted to
the `oauth_states` row, so the exchange endpoint cannot surface it. SPAs that
display a "Welcome! Account created." prompt will never see it set. This is not
a security issue but is an API accuracy gap. Carry-over from 2026-05-22
review (I-1).

### I-2 — OAuth token-exchange exception includes full Google response body in server logs (CARRY-OVER)

`src/regstack/oauth/providers/google.py:143-145`:

```python
raise OAuthTokenExchangeError(
    f"google token exchange failed: {response.status_code} {response.text}"
)
```

Caught in `routers/oauth.py` and logged at WARNING. Google's token endpoint
error responses are standard JSON and do not contain the client secret; the
`response.text` risks verbose noise at production log levels. No client-side
leakage. Suggested improvement: log status code at WARNING, response body at
DEBUG. Carry-over from 2026-05-22 review (I-3).

### §14 — OAuth Subsystem

- **PKCE:** `code_verifier` generated server-side with
  `secrets.token_urlsafe(64)`, stored on the `oauth_states` row. Only
  `code_challenge = sha256(verifier)` sent to the provider. Verifier never
  appears in a redirect URL.
- **State row lifecycle:** `oauth_states.consume` on Mongo uses
  `find_one_and_delete` (atomic); SQL uses SELECT + DELETE inside
  `engine.begin()` (atomic). Second exchange returns 404. Expiry compared
  against `rs.clock.now()` (not bare `datetime.now(UTC)`), preserving
  `FrozenClock` injection.
- **ID-token verification:** RS256 + PyJWKClient against GOOGLE_JWKS_URL;
  validates `iss`, `aud`, `exp`, `nonce`. Failure raises `OAuthIdTokenError`
  with a generic outer message; detail logged but never echoed to redirect.
- **Linking policy:** Same-email sign-in → `email_in_use` (no auto-link
  unless `auto_link_verified_emails=True` AND `email_verified=True`).
  Already-linked identity to different user → `identity_in_use`.
  Same identity same user → `already_linked`. Unlink last method without
  password → 400.
- **OAuth-only users:** `POST /login` → generic 401 (same as wrong password);
  `change-password`, `change-email`, `delete-account` → 400 via
  `require_password_set()`.
- **Identity uniqueness:** `(provider, subject_id)` UNIQUE and

- **Hooks:** `oauth_signin_started`, `oauth_signin_completed`,
