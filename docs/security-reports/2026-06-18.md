### W-1 — CVE-2026-48710 (BadHost): Starlette 1.0.0 in lock file is vulnerable to Host-header auth bypass

**CVE:** CVE-2026-48710  
**CVSS:** Critical (authentication bypass)  
**Affected:** `starlette` < 1.0.1  
**Lock file pin:** `starlette==1.0.0`  
**Fix:** `starlette>=1.0.1`

**Finding:**

The `uv.lock` file pins `starlette` at **1.0.0**, which contains the "BadHost" authentication bypass
(CVE-2026-48710, disclosed 2026-05-22, fixed in Starlette 1.0.1 released 2026-05-21). The
`pyproject.toml` does not list `starlette` as a direct dependency, so the resolved version is
constrained only by `fastapi>=0.120.0`, which does not guarantee a patched Starlette.

**Mechanism:** Starlette < 1.0.1 does not validate the HTTP `Host` header before using it to
reconstruct `request.url`. A single `/`, `?`, or `#` character injected into the Host header causes
`request.url.path` to return a completely different path from what the ASGI server actually routed.
Middleware or application code that enforces security based on `request.url.path` (rather than the
raw ASGI `scope["path"]`) can therefore be bypassed.

**Impact on regstack specifically:** regstack's own authentication (`AuthDependencies._authenticate`)
reads the `Authorization: Bearer` header and does not use `request.url` for any security decision.
The `current_user` and `current_admin` FastAPI `Depends` decorators are endpoint-level, so they
are evaluated after routing — the vulnerability does not bypass them. However:

1. **Host apps are exposed.** Any host application that adds path-based middleware on top of
   regstack (e.g. a global middleware that exempts `/api/auth/login` but protects all other paths)
   will run with a vulnerable Starlette dependency as long as the lock file is not regenerated.

2. **Developer environments.** Running `uv sync` on this repository installs Starlette 1.0.0.
   Any internal tooling (e.g. `regstack validate` command) that runs a FastAPI server is affected.

**Fix:**

Add `starlette>=1.0.1` as a direct dependency constraint in `pyproject.toml`:

```toml
dependencies = [
    ...
    "starlette>=1.0.1",  # CVE-2026-48710 BadHost — floor enforces the patched version
    ...
]
```

Then regenerate the lock file:

```bash
uv lock
```

Verify with: `uv run python -c "import starlette; print(starlette.__version__)"` — must show ≥1.0.1.

### W-2 — CVE-2026-53539: python-multipart 0.0.28 vulnerable to quadratic DoS

**CVE:** CVE-2026-53539  
**CVSS:** High  
**Affected:** `python-multipart` < 0.0.30  
**Lock file pin:** `python-multipart==0.0.28`  
**Floor pin:** `python-multipart>=0.0.27`  
**Fix:** `python-multipart>=0.0.30`

**Finding:**

The lock file pins `python-multipart` at **0.0.28**, which contains a quadratic-complexity CPU DoS
vulnerability (CVE-2026-53539) in `QuerystringParser`. The parser processes
`application/x-www-form-urlencoded` POST bodies by scanning the entire remaining buffer for `&`,
then re-scanning for `;` when `&` is not found — O(B²) comparisons where B is the body size. An
attacker sends a POST with a body of repeated `a;` sequences to force sustained high CPU usage.

The existing floor comment in `pyproject.toml` documents CVE-2026-40347 and CVE-2026-42561 but not
CVE-2026-53539, which was published in June 2026, after the most recent floor bump.

**Impact:** Network-exploitable DoS against any regstack endpoint that accepts
`application/x-www-form-urlencoded` bodies — including the SSR form submission endpoints. A
sustained attack with crafted bodies could saturate the host's CPU.

**Fix:**

Bump the floor in `pyproject.toml`:

```toml
# python-multipart>=0.0.30 picks up CVE-2026-53539 (quadratic DoS via semicolon separators
# in application/x-www-form-urlencoded parser).
"python-multipart>=0.0.30",
```

Then regenerate the lock file: `uv lock`.

## 🟡 INFO (Best practice recommendations)

### I-1 — CVE-2026-48526: pyjwt 2.12.1 vulnerable to algorithm-confusion (HMAC-only use not exploitable)

**CVE:** CVE-2026-48526  
**Affected:** `pyjwt` < 2.13.0  
**Lock file pin:** `pyjwt==2.12.1`  
**Floor pin:** `pyjwt>=2.12.1`

**Finding:**

CVE-2026-48526 (algorithm confusion, published 2026-05-29) affects PyJWT < 2.13.0. When an
application decodes tokens with a raw JWK string and simultaneously supports both HMAC and
asymmetric algorithm families, PyJWT does not verify that the key matches its intended algorithm
context — an attacker can sign a forged token using the provider's public JWK as an HMAC secret.

**regstack is not exploitable as configured.** `JwtCodec.decode` always passes
`algorithms=[self._config.jwt_algorithm]`, where `jwt_algorithm` is constrained to the `HS256 |
HS384 | HS512` literal — pure HMAC. No asymmetric algorithm is ever accepted. The algorithm-
confusion path requires mixed family support that regstack deliberately does not expose.

**Recommendation:** Bump the floor to `>=2.13.0` as defense-in-depth:

```toml
"pyjwt>=2.13.0",
```

Update the floor comment in `pyproject.toml` to document CVE-2026-48526. Then run `uv lock`.

### I-2 — JWT secret minimum-length check absent from `JwtCodec`

**Location:** `src/regstack/auth/jwt.py:118`

**Finding:**

`JwtCodec.__init__` rejects only an **empty** `jwt_secret`; it does not enforce a minimum length:

```python
if not config.jwt_secret.get_secret_value():
    raise ValueError("RegStackConfig.jwt_secret is empty. ...")
```

A host that sets a very short secret (e.g. `REGSTACK_JWT_SECRET=x`) passes this check. The
security review spec says `≥32 chars` should be enforced at construction. HMAC-SHA256 with a key
shorter than 32 bytes (the digest size) provides less security margin than its nominal strength.
The `generate_secret()` helper produces 64-byte secrets (~86 URL-safe chars), but nothing stops a
host from supplying a shorter value.

**Recommendation:** Add a length check at construction time:

```python
secret = config.jwt_secret.get_secret_value()
if not secret:
    raise ValueError(...)
if len(secret) < 32:
    raise ValueError(
        f"RegStackConfig.jwt_secret is too short ({len(secret)} chars); "
        "32+ characters are required. Use `regstack init` to generate one."
    )
```

### I-3 — `UserPublic` exposes `tokens_invalidated_after` (spec divergence)

**Location:** `src/regstack/models/user.py:105`

**Finding:**

`UserPublic` currently includes a `tokens_invalidated_after` field:

```python
tokens_invalidated_after: datetime | None = None
"""Bulk-revoke cutoff. SPAs comparing this to their session JWT's
`iat` can tell when the token they hold has been invalidated ..."""
```

The security review specification (§9) lists `tokens_invalidated_after` as a field that `UserPublic`
should **exclude**. The field was added intentionally in v0.5.9 (commit #43) to let SPAs detect
session invalidation client-side, but this diverges from the spec.

Practical data-exposure implications:
- The field reveals **when** the user last triggered a bulk-revoke event (password change, email
  change, admin disable). An authenticated attacker who can read `GET /me` could observe when a
  user reset their password.
- The `GET /admin/users` listing returns `tokens_invalidated_after` for every user to every admin,
  giving superusers visibility into other users' security event history.

**Options:**
1. Remove the field from `UserPublic` and document that SPAs should call `GET /me` after a
   successful `POST /change-password` / `POST /change-email` to get a fresh token if needed.
2. Keep the field and update the security-review spec to document the deliberate trade-off.

This is flagged as INFO because the inclusion appears intentional and is documented in the code; the
spec divergence should be resolved explicitly.

### §14 — OAuth Subsystem Audit

**14a — PKCE invariants:** `_begin_flow` (`routers/oauth.py:598`) generates `code_verifier`
server-side, stores it on the `OAuthState` row, and passes only `code_challenge`
(SHA-256 of verifier) to the provider. Verifier never appears in the authorization URL. ✓

**14b — State row lifecycle:** Callback checks `state_row is None` → `?error=bad_state`; checks
`state_row.expires_at < rs.clock.now()` → `?error=state_expired` (uses injected clock, not
`datetime.now(UTC)`). `/oauth/exchange` calls `oauth_states.consume()` which reads + deletes in
one transaction (SQL) or atomic `find_one_and_delete` (Mongo) — second exchange returns 404. ✓

**14c — ID-token verification:** `GoogleProvider.verify_id_token` validates signature via JWKS,
`iss == GOOGLE_ISSUER`, `aud == client_id`, `exp`, `iat`, `nonce` (required claim list enforced).

logged at WARNING only. ✓

**14d — Linking-policy enforcement:** Default behaviour: existing email-registered user →
`?error=email_in_use`. Auto-link only when `auto_link_verified_emails=True` AND
`email_verified=True`. Identity already linked to different user → `?error=identity_in_use`.
Re-linking same identity to same user → `?error=already_linked`. ✓

**14e — OAuth-only user side effects:** `POST /login` returns same generic 401 for
`hashed_password=None` users. `change-password`, `change-email`, `delete-account` call
`require_password_set`. `DELETE /oauth/{provider}/link` returns 400 when it would remove the last
sign-in method (`not has_password and other_identities == 0`). ✓

**14f — Identity-row uniqueness:** SQL: `UniqueConstraint("provider", "subject_id")` and
`UniqueConstraint("user_id", "provider")` in `schema.py`. Mongo: `provider_subject_unique` and
`user_provider_unique` indexes in `indexes.py`. ✓

**14g — Hooks:** All four OAuth events (`oauth_signin_started`, `oauth_signin_completed`,
